In a library's own folder, `keel check` imports the library's own `./tools` and holds the library and the `@keel/*` packages its `package.json` names in scope, as an app listing it does: its formats, rules and config hold over its own files, and a declared `./tools` that does not import is E1159 at `package.json` (k.library-pack Own folder). A library's `contract()` belongs in the file its `exports["./contract"]` names, a `*.contract.ts` file under `src/`; any other file of the library is E1513 naming that file, and a `./contract` naming another file holds no contract (k.contract). In a library's route component file, one its own `manifest(` binds to one route, that no other import, re-export, `import()`, `require` or `new URL` of the project reaches (resolved as the bundler resolves it), that no `public.exports` line or `exports` entry (a pattern's included) reaches, in a library with no computed `import()`, `require` or `import.meta.glob`, an element may take the literal id `<manifest id>.<rest>` (k.library Ids, E1161). A registered rule's project holds a library's `module.ts` at `modules/<id>/module.ts`, so a rule finding a file's module by path (std-i18n, std-messages) reaches the library's `src/` (k.library In an app). A `module.ts` that is no manifest (deeper than `modules/<id>/module.ts`, or under a library's `src/` or `unsafe/`) is E1171 and no rule's project holds it (k.module). An app's folder whose `package.json` says `"keel": "library"` is E1170 and is checked as an app; `keel pack` stops with it (k.module). A rule code two packages' `./tools` register is E1753 naming both, not E1159. A library after an id's first holder reads no file under `modules/<id>/`, so E1166 stands alone (k.library).

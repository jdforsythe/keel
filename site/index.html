Full-stack web frameworkpre-0.1, nothing is stable

A web framework written for the agent that writes your app.

Most new application code is written by coding agents, in frameworks designed for people. Keel is designed for the agent: one way to do each thing, a spec small enough to load, a checker that returns each error with its fix, and a ledger that states what has been proven, tested, or only run.

01

What you write

A Keel app is four kinds of source. Everything else is a declaration or a derivation that the compiler, the checker and the build produce from those four.

*.schema.ts Schemas

What the data is. One declaration gives you the type, the validator, codecs, generators for property tests, and docs.

s.object({ title: s.string() })
store + transaction Transactions

What can happen to the data. A named, pure (state, payload) => state. It is the only way a store changes, and every one lands in the log.

transaction(board, "api.addTodo", …)
Name.tsx Components

How it looks. TSX with typed props, compiled to direct DOM operations. Style props take token names, never CSS.

<Box gap="3" bg="card">
routes.ts A route manifest

How it is organized. Each route id maps to a path, typed params and search, a loader, a component, a layout and a guard.

manifest({ "todos.list": … })

From those, Keel derives element ids, the accessibility expectations, the reactive dependency graph, the stylesheet, the HTTP surface, the server entry, the Dockerfile and the CI files. Every derived file is read-only, and a hand edit fails keel check with E1005.

02

Principles

Every change to Keel is reviewed against these twelve, and reviews cite them by number. Each one names the consequence it buys.

  1. One wayEvery alternative is a place for a model to hallucinate. No dual APIs. A deprecation is a removal at the next major.
  2. No action at a distanceNothing outside a file changes what that file does. No global cascade, no context providers, no ordering invariants, no auto-imports.
  3. Locality and addressabilityOne export per file, and the file name is the export. Every component, element, state path and route has a stable string id.
  4. Everything is a schemaDeclared once with types; validation, codecs, generators, docs, mocks and tests derive from it. Closed vocabularies wherever a string would do.
  5. The checker says how to fix itEvery diagnostic has a stable code, a location, one line of message, and a fix diff when one exists.
  6. The runtime is queryableState, the dependency graph, the render tree, the accessibility tree and the transaction log are tool endpoints.
  7. Structure is an operationScaffold and codemod are first-class. A change that spans several files is never a hand edit.
  8. Small, frozen, spec'd surfaceOnce frozen, the kernel spec never changes meaning. No task needs more than 4k tokens of spec in context.
  9. In-distribution where freeTypeScript, JSX, familiar names. Novelty is spent only where it buys predictability, and the checker teaches it.
  10. Pure core, effects at the edgesState is serializable and every effect comes through ctx. Every test reads "given state, do events, expect".
  11. Claims lag machineryThe ledger reports only rungs that exist. This page follows the ledger.
  12. Tokens are a budgetDocs, spec and every tool's output are measured in tokens and gated in CI.
03

Promises and rules

Keel makes a small number of promises to you, and asks you to follow a small number of rules in return. The rules are what make the promises checkable: the checker enforces each one with a code you can look up.

What Keel promises

  • A frozen kernel.Every kernel change now goes through an RFC. When the frozen status lands, a frozen section never changes meaning.
  • Every error has a code and, where possible, a fix.The diff in the diagnostic is the edit you apply.
  • Output fits a budget.keel check on golden-1 with 10 injected errors prints at most 600 tokens; keel explain at most 300.
  • Claims match evidence.Each spec clause sits on one rung in the ledger, and keel ledger --diff fails the build when a covered section gains an untested clause (E1707).
  • Structural edits stay clean.If keel check was clean before a scaffold or codemod, it is clean after; otherwise nothing is written (E1353).
  • Escape hatches are counted.unsafe is the only path around a guarantee, it needs a justification string, and the ledger counts it.

What Keel asks of you

  • One export per file, named like the file.Todo.schema.ts exports Todo (E1752).
  • No throw, no try.Return err(...) and use attempt (E1451, E1452).
  • No ambient effects.No Date.now, Math.random, fetch, localStorage or DOM access in app code. Use ctx.clock, ctx.random, ctx.net, ctx.storage (E1601).
  • No any, casts, ! or @ts-ignore.Outside unsafe/ directories, the type is the contract.
  • Ids carry their module.Routes, stores, transactions and error codes start with the module id: todos.view, api.addTodo (E1155).
  • Control flow is a component.<If when>, <For each key>, <Match on>; never && in JSX, never destructured props.

Bets we have not proven

These are commitments made without evidence. We list them so you can weigh them, and we never cite them as findings.

  1. Distribution follows usageA public corpus, skills and examples shrink the novelty cost of Keel across model generations.
  2. One way survives pressureOne way per thing holds up under product pressure if escape hatches are named, justified and counted.
  3. The ledger is the evidenceCompanies will adopt a new framework when the code is agent-written and the ledger shows what it proves.
  4. Frozen kernel, evolving stdlibThat split is a stable enough contract for a learner that reads everything in context.
  5. Sessions become testsTurning a recorded production session into a test closes the maintenance loop well enough to compete with incumbents.
04

How to think in Keel

Picture the app as a set of stores, each holding state of one schema. State changes only through named transactions, and each transaction is recorded in a log. Components read stores and call transactions; loaders and actions read and write on behalf of a route. Effects such as time, randomness, network and storage arrive through ctx, so the same code runs against the real world, a native shell, or a seeded simulation.

Because state is serializable and every change is named, a test is always the same three steps. You give a state, you apply events, you compare the result. Undo, replay, audit and recorded sessions all read the same log.

Habits that make Keel code read well

  • Name the file before the code.The file name tells Keel the role: Name.schema.ts, name.server.ts, name.guard.ts, Name.tsx. Pick the role, and the rules for it follow.
  • Write the schema first.Params, search, loader output, action input and component props are all schemas. Types come from s.infer.
  • Return results.A loader that cannot find a list returns err({ code: "keel.notFound", ... }), and the route's errorElement renders it.
  • Give elements ids.Ids such as todos.addTodo are how tests fire events, how the inspector finds nodes, and how a diagnostic names the element it means.
  • Keep structure in operations.Rename a module or add a field with keel codemod, so every file that names it changes together.
  • Read the error code.keel explain E1505 answers in at most 120 tokens; keel spec --for E1505 returns the section that defines it.

Modules and deployables

All app code lives in modules/<id>/. A module is a vertical slice: its schemas, stores, routes, components and handlers, with a manifest that names what it depends on, which ctx capabilities it uses, and which files and routes other modules may reach. A deployable is a set of modules that builds to one artifact, declared in topology.ts. No other file names a deployable, so moving a module to its own server is an edit to that one file.

apps/golden-1/topology.ts
import { topology } from "@keel/server";

export default topology({
  web: { modules: ["todos"], adapter: "client", host: "api" },
  api: { modules: ["api", "digest", "sessions"], adapter: "node", storage: "sqlite" },
});

How a page reaches the screen

  1. Vite serves index.html, which loads /@keel/entry.ts. The plugin generates that entry from topology.ts and each module's routes.ts.
  2. The entry creates a real ctx, builds a router from the merged manifest, and mounts it into #app.
  3. The router matches the URL, parses params with their schema (a failure is a 404 rendered by errorElement), and drops search keys that fail.
  4. Guards run outermost first, then loaders. A loader returns a Result.
  5. The chain renders outermost first: the layout, then the page as its children, given { params, search, data }.

On a node deployable the same route renders to HTML on the server, with store state in a JSON script tag. Components with handlers or effects become islands, and the resume entry attaches to the server's DOM without rendering again.

06

Kernel API

Each kernel package has one spec section, retrievable with pnpm spec <id> under a 1,500-token budget. The cards below list the exports you use most, with a line from a real app.

@keel/schemak.schema

Runtime schemas with inference, Result helpers, personal-data tags and secrets.

s.string · int · enum · id · object · array · union · secret · .optional() · .pii() · ok · err · attempt · Infer

export const TodoParams = s.object({
  listId: s.id("TodoList"), todoId: s.id("Todo"),
});
export type TodoParams = s.infer<typeof TodoParams>;

@keel/storek.store

Schema-typed stores whose changes go through pure, logged transactions.

store · transaction · invariant · tx · snapshot · restore · { concurrent: "rebase" | "reject" }

export const shoppingList = store(ShoppingList,
  { recipes: [] }, { id: "recipes.list" });
invariant(shoppingList, (s) =>
  new Set(s.recipes.map((r) => r.id)).size === s.recipes.length);

@keel/reactivek.reactive

Signals, computed values, effects with declared writes, scopes, and resources with a closed state union.

signal · computed · effect({ writes }) · resource · batch · scope

const status = computed(() =>
  statusOf(editorChart.store.get("state")));

@keel/runtime-domk.component

Mounts components and supplies the control-flow intrinsics. A component is (props, slots, ctx?).

mount · If · For · Match · Case · Boundary

<For each={shown()} key="id">
  {(todo) => <TodoRow todo={todo} />}
</For>

@keel/routerk.router

The route manifest, loaders, actions, guards, Form, typed hrefs and history.

manifest · .href · .actions · loader · action · guard · Form · navigate

routes.href("todos.list", { listId }, { filter: "done" })

@keel/formsk.forms

Form state from an object schema, with typed field bindings that controls take through field.

form · f.field(path) · toFormData

const f = form(TodoDraft, { id: "todos.addForm",
  initial: { priority: "normal" } });
<Input field={f.field("title")} label="Title" />

@keel/uik.ui

Typed elements whose style props take token names only. No class, no CSS in components.

Box · Text · Heading · Button · Link · Image · Input · TextArea · Select · Checkbox · defineTokens · brandTokens

<Box direction="row" gap="3" px="3" py="2" bg="card">

@keel/ctxk.ctx

The effect context, in real, shell or seeded sim mode. A sim ctx can route network requests in tests.

createCtx · clock · random.id · net · storage.get / set / read / commit

const ctx = createCtx({ mode: "sim", seed: 1 });
ctx.net.route("http://api.keel.invalid/api/*",
  (req) => api.fetch(req));

@keel/serverk.server

The topology, and a Hono app per deployable that serves routes, JSON, streams and runners.

topology · createApp · commitStores

const app = await createApp({ topology, routes, ctx });
const res = await app.fetch(new Request(url));

@keel/servicesk.services

An HTTP API declared as schemas, and a typed client whose calls return Result and never throw.

endpoints · service({ module | base, schema })

export const todos = endpoints({
  lists: { method: "GET", path: "/api/lists", output: BoardView },
});

@keel/testingk.testing

The harness and the correctness tools that put claims on rungs.

render · renderRoute · fire · settle · find · properties · explore · simulate · prove · ledger

const t = render(Keys, { props: {}, ctx });
await t.fire("lb", { type: "keydown", key: "ArrowDown" });

@keel/compiler · check · scaffold · clitools

The compiler emits artifacts, check runs the rule registry, scaffold computes edit sets, and cli serves all of them as keel, over MCP and over LSP.

module · compile · defineRule · explain · scaffold · run · formatter

export default module({ id: "todos", deps: ["api"],
  capabilities: ["net", "storage"],
  public: { exports: [], routes: [] } });

Standard library

The stdlib is 25 packages named @keel/std-<x>, each built on the kernel's extension points, versioned separately and frozen one at a time. A module lists the ones it uses in deps.

Valuesschema types over Intl and ISO text

std-moneycovered

Integer minor-unit Money and Currency, with addition and locale formatting.

formatMoney({ amount: 1250, currency: "EUR" }, "de-DE") // "12,50 €"

std-temporalcovered

Instant, PlainDate, TimeZone and Duration types, with conversions and formatting.

formatDate("2026-11-10", "en-US", "long") // "November 10, 2026"

std-textcovered

Grapheme-aware line and para, Email, Slug, truncation and comparison.

graphemes("👨‍👩‍👧") // 1

std-i18ncovered

The Locale type, formatNumber, plural and localeName.

plural(1, "en-US", { one: "# recipe", other: "# recipes" })

std-messagescovered

Typed message sets, one file per locale, loaded on demand.

messages(AppLocale, { title: {}, count: { n: s.int({ min: 0 }) } },
  (locale) => import(`./RecipesText/${locale}.ts`))

std-brandscovered

Check rule E2101: ids passed to s.id and random.id are PascalCase, with an autofix.

s.id("Todo")   // ok
s.id("todo")   // E2101, fix: "Todo"
Interfacewidgets and tables on Part

std-headlesscovered

Listbox, Combobox, Menu, Tabs, Dialog, Disclosure, Toaster. Keyboard, focus and ARIA follow the WAI-ARIA Authoring Practices, one tested state chart per widget.

std-tablescovered

Columns, search, sort and paging, with the query in the route's search. One applyQuery serves the loader and the client.

columns(CatalogRow, { key: "id", rowHeader: "title",
  sort: ["title", "price"], search: ["title"] })
Serverjobs, schedules, credentials

std-jobscovered

Durable background jobs per module: enqueue with a key, retry with backoff, lease and restart.

await jobs.enqueue(ctx, "orders.sendReceipt", { orderId }, { key: orderId })

std-schedulescovered

Five-field cron in a time zone that enqueues jobs, with catch-up after downtime.

{ cron: "0 3 * * *", zone: "UTC", job: "orders.digest", input: {} }

std-credentialscovered

Password hashing and verification of a Secret, and token minting and checking, in node deployables.

const h = await credentials(ctx).hash(input.password)

std-healthcovered

A stdlib module that adds GET /health when you place it in a deployable.

Realtime and offlinechannels, live views, outbox, races

std-channelscovered

Named channels over a server event stream, carrying schema-typed messages.

channel("todos.board", { path: "/api/board/events",
  params: s.object({}), message: BoardMessage })

std-livecovered

Keeps a client store current by re-reading through its loader after each channel push.

std-offlinecovered

An outbox for writes made offline. Each write keeps its key and base, goes out in order on reconnect, and waits for the user when refused.

send(ctx, boardOutbox, origin, "editTodo", call, { base: view.get("head") })

std-conflictscovered

Finds races: rebased writes whose result depends on their order against writes they did not see (E2701).

Correctness and operationscharts, sessions, timings

std-statechartscovered

A flat state chart compiled to a store with one transaction per event, so explore and the checker read it like any store.

chart("todos.editor", { initial: "viewing",
  states: { viewing: { on: { edit: "editing" } }, … } })

std-sessionscovered

Records a redacted session in the browser; ingest, replay, minimize and turn it into a test. Includes a GitHub Action and a production monitor.

std-timingscovered

Per-name timing stats on a ctx, shown as an inspector section.

std-reportcovered

A report.tally record, rendered by the CLI in compact, pretty and JSON form.

std-geocovered

A geo capability on ctx; the sim form returns a seeded position.

Reachdurable storage, workflows, native shells

std-dbproposed

SQLite and Postgres storage drivers. The generated server entry opens the one topology.ts names; app code never imports it (E2151).

std-workflowsproposed

Durable multi-step workflows: a state chart per instance in one server store, each step run as a job, resumable after a restart.

std-capacitorproposed

Storage and net drivers for Android and iOS builds. Native builds have not run yet.

std-tauriproposed

Storage and net drivers for Linux, macOS and Windows builds. Native builds have not run yet.

Your first app, by hand

This section builds Tally, a one-page counter, with every file typed by you. It has one module, one store, two transactions and one route. It runs in the browser only. Packages are not published yet, so the folder lives inside the Keel repo under apps/, where pnpm links the @keel/* workspace packages.

The shapes below follow the kernel spec and the golden apps. Treat this as a preview: docs/guide/build-golden-1.md is the full, tested walkthrough of a larger app.

  1. Project files

    Copy package.json, tsconfig.json, vite.config.ts and index.html from apps/golden-1, give the package a new name, then run pnpm install at the repo root. Or let the scaffold write them: keel scaffold project tally --workspace. The two files that are pure Keel are the tokens and the topology.

    apps/tally/tokens.ts

/** The Keel brand: palette, Source Serif 4 and JetBrains Mono, radius 0, hairline dividers. */
export const tokens = brandTokens;
    apps/tally/topology.ts
    import { topology } from "@keel/server";

export default topology({
  web: { modules: ["tally"], adapter: "client" },
});
    apps/tally/vite.config.ts
    import keel from "@keel/compiler/vite";
import { defineConfig } from "vite";

export default defineConfig({ plugins: [keel()] });

  2. The module manifest

    The folder name is the module id, and the id prefixes every store, transaction and route inside it. Tally needs no other modules and no ctx capabilities.

    modules/tally/module.ts
    import { module } from "@keel/compiler";

export default module({
  id: "tally",
  deps: [],
  capabilities: [],
  public: { exports: [], routes: [] },
});

  3. A schema and a store

    The schema says what a count is. The store holds one value of it, starts at zero, and carries an invariant that every transaction must keep.

    modules/tally/Count.schema.ts
    import { s } from "@keel/schema";

/** The tally: a whole number, never below zero. */
export const Count = s.object({ n: s.int({ min: 0 }) });
export type Count = s.infer<typeof Count>;
    modules/tally/count.ts
    import { invariant, store } from "@keel/store";
import { Count } from "./Count.schema.ts";

/** The count in this browser tab. Changes only through tally.add and tally.reset. */
export const count = store(Count, { n: 0 }, { id: "tally.count" });

invariant(count, (state) => state.n >= 0);

  4. Transactions

    Each transaction is a pure function from the old state and a typed payload to the new state. Neither of these takes a payload, so both use an empty object schema.

    modules/tally/Nothing.schema.ts
    import { s } from "@keel/schema";

/** The payload of a transaction that takes no fields. */
export const Nothing = s.object({});
export type Nothing = s.infer<typeof Nothing>;
    modules/tally/add.ts
    import { transaction } from "@keel/store";
import { Nothing } from "./Nothing.schema.ts";
import { count } from "./count.ts";

/** Adds one to the tally. */
export const add = transaction(count, "tally.add", Nothing, (state) => ({ n: state.n + 1 }));
    modules/tally/reset.ts
    import { transaction } from "@keel/store";
import { Nothing } from "./Nothing.schema.ts";
import { count } from "./count.ts";

/** Sets the tally back to zero. */
export const reset = transaction(count, "tally.reset", Nothing, () => ({ n: 0 }));

  5. A component

    The component reads the store and calls the transactions with tx. It lists them in uses so the compiler knows which writes it makes. Every element that a test or the inspector needs has an id, and every style prop names a token from tokens.ts.

    modules/tally/TallyPage.tsx
    import { type Infer, s } from "@keel/schema";
import { tx } from "@keel/store";
import { Box, Button, Heading, Text } from "@keel/ui";
import { add } from "./add.ts";
import { count } from "./count.ts";
import { reset } from "./reset.ts";

export const Props = s.object({});

export const uses = [add, reset];

/** Route tally.home: the count, Add one and Reset. */
export default function TallyPage(_props: Infer<typeof Props>) {
  const addOne = (): void => {
    const r = tx(add, {});
    if (!r.ok) return;
  };
  const clear = (): void => {
    const r = tx(reset, {});
    if (!r.ok) return;
  };
  return (
    <Box as="main" id="tally.page" direction="column" gap="4" p="5" bg="surface" fg="text" font="serif">
      <Heading id="tally.title" level={1} fontSize="2xl" m="0">
        Tally
      </Heading>
      <Text id="tally.value" font="mono" fontSize="xl">
        {count.get("n")}
      </Text>
      <Box direction="row" gap="3">
        <Button id="tally.add" onClick={addOne} px="4" py="2" bg="text" fg="card" border="rule" radius="none">
          Add one
        </Button>
        <Button id="tally.reset" onClick={clear} px="4" py="2" bg="card" fg="text" border="rule" radius="none">
          Reset
        </Button>
      </Box>
    </Box>
  );
}

  6. The route manifest

    One route, id tally.home, at /. Links to it anywhere in the module come from routes.href("tally.home"), never a string path.

    modules/tally/routes.ts

  "tally.home": { path: "/", component: TallyPage, title: () => "Tally" },
});

  7. A test

    properties runs a transaction against payloads generated from its schema and checks the store's invariant after each. render mounts the component on a seeded sim ctx, and fire sends an event to an element by id.

    test/tally.test.ts
    import { createCtx } from "@keel/ctx";
import { properties, render } from "@keel/testing";
import { expect, it } from "vitest";
import TallyPage from "../modules/tally/TallyPage.tsx";
import { add } from "../modules/tally/add.ts";
import { reset } from "../modules/tally/reset.ts";

it("add and reset keep the invariant for every generated state", async () => {
  await properties(add);
  await properties(reset);
});

it("Add one shows 1", async () => {
  const t = render(TallyPage, { props: {}, ctx: createCtx({ mode: "sim", seed: 1 }) });
  await t.fire("tally.add", { type: "click" });
  expect(t.find("tally.value").text).toBe("1");
  t.dispose();
});

  8. Check, test, run

    shell, from apps/tally
    pnpm keel check     # silent when clean, one trailer line
pnpm keel test      # ok 2 tests, 0 failed, 0 skipped
pnpm keel dev       # hot reload on http://localhost:5173
pnpm keel build     # dist/web/, static files

    If you get something wrong, the checker answers with a code and, where it can, the diff that fixes it. Destructure props and you get E1401; call Date.now() and you get E1601; put two exports in add.ts and you get E1752.

loadList.server.ts

export const loadList = loader(
  { output: TodoList, params: ListParams },
  async ({ params }, ctx) => {
    const board = await refreshView(ctx);
    if (!board.ok) return board;
    const list = board.value.lists
      .find((l) => l.id === params.listId);
    return list === undefined
      ? err({ code: "keel.notFound",
          message: `No list ${params.listId}`,
          data: { listId: params.listId } })
      : ok(list);
  });

editable.guard.ts

export const editable = guard(
  { redirect: "todos.index" },
  async (_req, ctx) =>
    (await ctx.storage.get("todos.readOnly")) === "1"
      ? err({ code: "keel.denied",
          message: "todos are read-only",
          data: null })
      : ok(null),
);

Server state with an invariant

On a node deployable each request gets its own instance of a server store, restored from ctx.storage and saved in one commit when an action succeeds. Two processes that read the same board and both write get a 409 keel.conflict for the second write, unless the transaction declares concurrent: "rebase".

modules/api/addTodo.ts
export const addTodo = (board: Store<Board>) =>
  transaction(
    board,
    "api.addTodo",
    s.object({
      id: s.id("Todo"),
      listId: s.id("TodoList"),
      title: s.string({ min: 1, max: 120 }),
      priority: s.enum(["low", "normal", "high"]),
    }),
    (state, p) =>
      state.todos.some((t) => t.id === p.id) || !state.lists.some((l) => l.id === p.listId)
        ? state
        : { ...state, todos: [...state.todos, { ...p, done: false }] },
    { concurrent: "rebase" },
  );

Climbing a rung in golden-1

The todo app's board carries one invariant: ids are unique and every todo belongs to a known list. The same six transactions sit on three rungs at once. properties runs each against generated payloads. explore visits all 112 states three writes deep. prove shows by induction with Z3 that no state and no payload can break it.

apps/golden-1/test/board.prove.test.ts
it("the six board transactions keep the invariant from every state it allows", async () => {
  const b = sc.run(board);
  const r = await prove([addList(b), addTodo(b), toggleTodo(b), editTodo(b), hideList(b), showList(b)]);
  expect([...r.proven].sort()).toEqual(
    ["api.addList", "api.addTodo", "api.editTodo", "api.hideList", "api.showList", "api.toggleTodo"].sort(),
  );
}, 60_000);

Kernel packages also carry a mutation score with a threshold of 70%, run by Stryker and recorded in the ledger, so a test suite that passes without testing anything shows up as a number.

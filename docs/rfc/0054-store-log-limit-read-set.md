# RFC 0054: store log limit, hashed caller, and serializable server saves

Status: implemented (ADR-0044)

## Problem
- **Red team M7 (backlog 0131).** A saved store snapshot kept the whole transaction log forever. Each entry carried `meta.caller`, the `keel-caller` cookie value itself, so anyone who reads `ctx.storage` (a backup, a log line) could send that cookie and undo as that caller. Every request re-parsed the stored JSON and restored, validated and bound every entry, so cost grew with the store's age. In memory, `undo` replayed the whole log.
- **Red team (backlog 0148), write skew.** The 409 check covered only changed stores (`changed.find` in `saveStores.ts`). Action A reads `app.lists` and writes `app.todos`; an overlapping B deletes the list in `app.lists`; both commit, and a todo points at a deleted list.
- **Read skew.** `open` loaded a factory's keys one `await` at a time. A save of K1 and K2 that started between two loads gave the request the old K1 and the new K2. A GET then rendered a state that never existed.

## Proposal
1. **Log limit (k.store).** `store(schema, initial, { logLimit })`: a store keeps at most `logLimit` entries (default 256). A value that is not a non-negative integer throws at `store`. A commit past the limit folds the oldest entry into the base `undo` replays from, which `snapshot()` returns as `initial`. `restore` folds a longer log the same way. Every snapshot, and so every save, holds at most `logLimit` entries. State never changes. `log()`, `snapshot().log` and `undo` cover the kept window exactly as before.
2. **Undo past the window.** A folded entry is part of the base. `undo()` and `undoWhere(pred)` reach only kept entries. With none left they return `false` and change nothing, as with an empty log today. No new code: both already answer with a boolean, and a refused undo is not an error.
3. **Why 256 entries, not bytes.** A count is the same on every runtime and for every schema, so undo depth is predictable. A byte budget would make undo depth depend on payload sizes and on the encoding. 256 covers any interactive undo depth. It bounds per-request restore work at 256 validated, bound entries per store and storage at 256 entries per store, whatever the traffic. A store that needs more history passes a larger `logLimit`. An audit trail belongs in a stdlib log, not in undo state.
4. **Caller id, not caller token (k.server).** Loaders and actions get `caller` as the base64url SHA-256 of the `keel-caller` token (no padding; `""` stays `""`). The cookie is unchanged, and so is the in-memory ownership check: `undoWhere((e) => e.meta?.caller === caller)` compares ids. Stored `meta.caller` is an id that cannot be sent back as a cookie. Recovering a token from it means inverting SHA-256 over at least 16 random characters. No key is needed: the token is random, not guessable, so a plain hash suffices and survives restarts. Raising this in the store would be action at a distance: the store never knows which meta value is a secret. The hash is Node's synchronous `crypto.createHash`, imported once at `createApp` like `fs`. The asynchronous Web Crypto digest resolves off the event loop, which the `@keel/testing` settle rounds do not wait for; golden-2's in-process api tests failed with "fire did not settle".
5. **Read set (k.server, backlog 0148).** A commit checks every key the request opened, changed or only read, against the copy it restored from. Any drift is 409 `keel.conflict` and nothing is saved. A factory opens all its stores, so the factory is the unit of conflict. The check and the writes run in one `inOrder` section over the opened keys, so no save of a read key lands between them. An action that changed nothing saves nothing and needs no check, because its reads were one cut.
6. **One cut per factory.** `openStores` reads all of a factory's keys inside one `inOrder` section on `Served.saving`. The section starts after every save queued on any of the keys settles, and no later save of them lands before it ends. A request therefore sees each factory's stores as of the same saves. Loads and saves share the per-key chains from backlog 0125.
7. **Parse once (backlog 0131).** `Saved` gains `json`, the parsed snapshot. It is parsed when the key is read from storage or saved, once per stored version. Each request restores its own instance from it; `restore` copies and never mutates its input. Per request, a store costs one restore of at most `logLimit` entries.

**Consistency model.** Actions are serializable per factory, by optimistic concurrency control over the factory's whole key set. Successful commits are equivalent to running them one at a time, in commit order. A GET sees each factory as of the same saves. Two factories opened by one request may be cut at different points; each factory is read once. A multi-key save is still not atomic across keys when a storage `set` rejects: the copy and storage agree per key (backlog 0125, unchanged).

## Alternatives
- **Compact only in `snapshot()` (log unbounded in memory).** Rejected: in-memory `undo` and `snapshot()` stay O(log). The in-memory log and the persisted one would also disagree, so `undo` before a save could reach entries that are gone after it.
- **Byte budget.** Rejected (proposal 3).
- **An `E13xx` for undo past the window.** Rejected: an empty log already answers `false`. A code would split one outcome into two.
- **Strip `meta.caller` on save, or keep the token and hash at save.** Rejected: a server that rewrites app meta is action at a distance. The live store and the saved one would also disagree about who wrote an entry.
- **HMAC with a server secret.** Rejected for now: it needs key management and rotation, which would invalidate every recorded owner. SHA-256 of a random token already resists inversion.
- **Track the stores an action actually read (`get`/`select` dependencies).** Rejected: reads come through `get`, `select`, computeds and log scans. One untracked path is silent write skew. Conflicting on the factory's key set is coarse but cannot miss a read. Split a factory when unrelated stores contend.
- **Lock keys for the whole action (pessimistic).** Rejected: an action that awaits I/O would block every other request on its stores.

## Conformance diff
- **k.store, added.** "After more than `logLimit` commits, `log()` holds the latest `logLimit` entries, replaying them from `snapshot().initial` reproduces state, and `undo()` returns `true` exactly `logLimit` times." and "`restore` of a snapshot whose log exceeds `logLimit` keeps its state and its latest `logLimit` entries." Tests: `packages/store/conformance/log-limit.test.ts` and `log-limit-restore.test.ts`, seed 1337.
- **k.server, changed.** "`caller` is the hash of the sent cookie's token, else of a fresh one set as a cookie on a write, else `\"\"`." Test: `packages/server/conformance/caller-token.test.ts`.
- **k.server, added.** "A save is 409 `keel.conflict` if a store the action only read was saved since; no request sees one store before a save and another after it." Test: `packages/server/conformance/read-set-conflict.test.ts` (write skew, and a held storage read for read skew).
- **Unit and property tests.** `store/test/logLimit.property.test.ts` checks the store against a capped-history model and `trim`. `server/test/serializable.property.test.ts` uses fast-check, seed 1337, with `fc.scheduler` ordering storage reads, writes and request starts. Over interleaved requests reading and writing random subsets of three stores, it requires an acyclic multiversion serialization graph of the committed actions and every GET (no write or read skew), and that both 200 and 409 occur. `server/test/snapshotCompaction.test.ts` covers parse once per version and a 300-entry pre-0054 snapshot. `server/test/serverState.test.ts` checks that a stored entry carries the caller id, never the token. All failed before the change; the property's first counterexample was write skew among three overlapping actions.

## Migration
- **Old snapshots load.** The format is unchanged (`{ state, log, initial }`). A snapshot with more than 256 entries restores with its oldest entries folded into `initial`. Storage is rewritten only at the next save of that store, then with at most 256 entries.
- **Old caller entries.** Entries saved before this change carry the raw token in `meta.caller`. They no longer match any `caller`, so `undoWhere` by caller refuses them, which fails closed. They leave storage once 256 newer entries fold them into the base.
- **App code.** None. Apps compare `meta.caller` with `caller` and keep working. A test that passes `caller` by hand is unaffected. A test asserting the raw cookie in `caller` asserts its hash.
- **Throughput.** Two actions on one factory now conflict even when they wrote different stores, if either read the other's (and every opened store counts as read). A client that sees 409 refetches and retries, as before.

## Token impact
- k.store: 1,166 to 1,359 tokens.
- k.server: 1,500 to 1,499 tokens (additions offset by editorial cuts).
- Runtime: one SHA-256 per request; one parse per stored version instead of per request; restore bounded by `logLimit`.
- Size: `@keel/store` 2,090 to 2,225 bytes gzip (budget 3 kB). `@keel/server` 11,254 to 11,393 bytes gzip; its budget goes from 11 kB to 11.5 kB (`tooling/budgets.json`). It was 10 bytes under before; caller hashing, the read-set check and one-cut loads cost 139 bytes.

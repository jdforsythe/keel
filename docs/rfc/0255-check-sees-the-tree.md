# RFC 0255: k.derived: check sees the project as it is

Status: accepted (ADR-0293) by the orchestrator on 2026-11-26, to be confirmed by the operator. Implemented on lane-r-fresh: slices 1 to 4 (one evaluation, the cache, surface version 3) and slice 5 (section 10): every build-time evaluation runs in the evaluator, a child process, and the in-process views are withdrawn. Adds k.evaluator (E1048) and k.derived (derived files, their readers, refresh, frozen runs, the derivation cache; W1018). Amends k.compiler (Artifacts, Build-time evaluation, E1005, W1005 reserved), k.compat (Surface version 3 without `sources`; the Sources paragraph removed; Base compares the derived surface), k.check (step 3, the sort note), k.a11y (Artifacts, Claims), k.ledger (the `a11y` order, W1731, two clauses), k.deploy, k.shell and std.tauri (deploy files are views), k.library-pack (`--check` becomes `--frozen`), k.contract (Static reading reports E1111 alone), the glossary (`derived file`) and the tools area. From `tasks/p1/TODO.md` W17 ("`keel check` refreshes its derived `.keel/` files before judging").

Personas: A2 and its agent form (edit, check, done), A7 (`keel test` after an edit), A3 (CI and committed files), A8 (the build is a function of the tree), F1 (the cost of changing this later); A6 through the ledger.

## Decisions
- D1: no command judges, tests or serves from a derived file's bytes on disk. Each reader takes the derivation of the tree it runs over. The files in `.keel/` and `deploy/` become views of the derivation, written for people, reviewers and tools.
- D2: every command that runs over a tree and is not frozen writes each view whose bytes differ (`keel check`, `keel build`, `keel test`, `keel dev`, an applied scaffold operation). The editor's language server writes none. One trailer count, `2 refreshed`.
- D3: frozen is pnpm's `--frozen-lockfile` idea: `--frozen`, on by default under `CI`. Frozen writes nothing, and a view that differs from its derivation is E1005.
- D4: the evaluated derivations (`routes.json`, `surface.json`) come from one evaluation and are cached in `node_modules/.cache/keel/derived/` under the type cache's rule: an entry keyed by everything the evaluation read, used only when each read gets the same answer. No digest is written into a committed file, so none can be forged there.
- D5: `surface.json` holds the surface only (version 3): its `sources` and k.compat's normal form go, because freshness is the derivation's job, not the record's.
- D6: the compiled views are not committed; `surface.json` and the deploy files are. A scaffolded `.gitignore` says so.
- D7: W1005 is reserved: `keel check` evaluates `routes.json` instead of reading literals beside it, so no part of it is unverified.
- D8: what the evaluation reads, it reads through views, and what no view can record it refuses (E1050), so a cached derivation stays the one a fresh evaluation gives. The views live in the evaluator's own realm and answer by asking the command (D10). Every symbolic link on the path to a file it loaded or read is a real-path probe. A refused built-in may be imported, and only a call into it is refused: a handler that uses it runs at request time, never in the evaluation.
- D9: a lookup that found nothing is a probe whose answer is absent, so creating that path is a miss. The recorded set is finite: the questions the evaluation's own resolver and its views asked (k.check-cache Evaluation probes lists them), nothing guessed beside them. Every route to the host's module loader (`node:module` but `createRequire`, `isBuiltin` and `builtinModules`, `process.mainModule`, `import.meta.resolve`, a code file named at run time, `Function` and `eval`) is refused.

- D10: a build-time evaluation never runs in a command's process. It runs in the evaluator: one Node child per bundle, under Node's permission model with no file right but its own bundle, code from strings off, an environment built from nothing. Its realm, timers and module instances end with it. Every fact of the machine it learns is an answer the command gave and recorded, so what can change the result and what is keyed are one set by construction, not by a list of members. It is the evaluator RFC 0251 specifies, built here once; RFC 0251 adds its `prerender` kind and its grants to it. An evaluation that gives no result is E1048.

## Problem
`keel check` compares each `.keel/` file with what the compiler derives and reports E1005 when they differ; it reads `surface.json` from disk for `--base`; `keel test` reads `.keel/a11y.json` from disk; `keel ledger` finds projects by `.keel/routes.json`; `keel dev`'s inspect document reads the files from disk. Only `keel build` and the Vite plugin write them. So after an edit an author, or an agent, either runs `keel build` before `keel check` or reads an error about a file they never touched. The guide says it outright (`docs/guide/build-golden-1.md`): "Run `keel build` before `keel check` after edits." The `keel` skill carries it as a rule an agent must remember: "`keel check` (E1005 on `.keel/` files after an edit until `keel build` runs)".

## Proposal

### 1. Readers take the derivation
`keel check` gives its rules, E1511 and the current side of `--base` the derivation of the tree. `keel test` derives `a11y.json` in its own process before vitest starts and hands it to each test process; the setup reads no `.keel/` file. `keel ledger` derives each project's `routes.json`. Dev's inspect document serves the derivation the Vite plugin holds. A file Keel cannot derive is read as before: the `--base` surface (another tree's), `ledger.json`, `monitored.json`, a library's shipped `.keel/ledger.json`.

With this alone cases 1 to 7 and 12 give the right answer, and E1005 for a stale view can no longer appear by surprise: nothing reads it.

### 2. Views are refreshed by every run that is not frozen
After judging, `keel check` writes each view whose bytes differ from the derivation; `keel build`, `keel test`, `keel dev` and an applied scaffold operation do the same at their own moment. The trailer says so in one count, per `docs/OUTPUT.md`: `ok check 217 files, 2 refreshed, 0 errors, 2 warnings`; at 0 the count is left out, so a clean check of a fresh tree prints exactly today's line.

**Is writing acceptable for a checker?** People expect `keel check` to judge, not edit. It writes only files Keel owns and nothing else: never a source file, nothing in `dist/`, nothing outside the project. TypeScript's `.tsbuildinfo`, ESLint's cache and Keel's own type cache already make a checker a writer of derived state. `.keel/` views are pure functions of the tree, so a refresh changes no meaning. The one tracked file it can change is `surface.json`, and only when the surface changed. That is the same contract as `pnpm install` updating the lockfile, which CI then runs frozen.

**A view that cannot be written** (a read-only checkout, a container layer, no permission) is W1018 with the path and the reason; the run goes on with its derivation. Case 11 becomes a passing run with one warning per differing view.

**The language server writes nothing.** It checks unsaved buffers, so a view written from them would describe a tree that is not on disk. An MCP `check` given file texts writes nothing for the same reason; one over the disk writes as the CLI does.

### 3. Frozen
`--frozen`, or `CI` set to a value other than empty, `0` or `false`, or `KEEL_FROZEN=1` makes a run frozen. A frozen command sets `KEEL_FROZEN=1` for its children, and the Vite plugin reads it, so a frozen `keel test` or `keel build` writes no view through the plugin either. Frozen, no view is written, and a view present that differs from its derivation is E1005; an absent view is no diagnostic (the compiled views are not committed, so CI has none). E1005 for `surface.json` names the store, contract or entry that differs first.

`CI` turns frozen on because the pipelines people write by hand are the ones that would otherwise let a stale record onto the main line (A3). pnpm does the same with `--frozen-lockfile`, so the behaviour is the one a newcomer expects (principle 9).

There is no `keel check --check`. `keel pack --check` (k.library-pack) is the one other command with a write-nothing mode; renaming it `--frozen` would give the idea one name (For the operator, 3).

### 4. What is committed
| file | committed | why |
| --- | --- | --- |
| `.keel/surface.json` | yes | the base the generated CI compares against (`git show origin/<base>:.keel/surface.json`), and a reviewer reads an API or stored-state change in its diff |
| `deploy/**`, the CI workflow | yes | they are what runs in deployment and CI; a reviewer reads them |
| `.keel/a11y.json`, `ids.json`, `deps.json`, `styles.json`, `std.json`, `schemes.json`, `routes.json` | no | caches of the compile and the route evaluation; nothing reads them; committing them adds a churn line to most pull requests and a merge conflict between any two that touch components |
| `.keel/ledger.json`, `.keel/monitored.json` | as k.ledger says | not derived from the tree |

`keel scaffold project` writes the six view names into `.gitignore`. The repository's apps stop tracking them (Build plan, slice 2).

**`surface.json` holds the surface, not its freshness.** Its `sources` map and k.compat's normal form exist so `keel check` could tell, without evaluating, whether the file was stale. Check now evaluates (from cache when nothing changed), so `sources` goes and the file is `version: 3`. A reviewer's diff then shows only surface changes. Today it also shows one hash line per page, schema or helper file touched (case 1 made `surface.json` stale through `StartPage.tsx`), and two pull requests that touch different pages conflict on it. `--base` reads version 2 and 3; a version 2 file's `sources` is ignored.

**A committed digest was rejected.** An `inputs` digest written into each view would let readers skip re-derivation, but the digest is a public function of the tree: anyone can write a stale or forged `surface.json` with the digest of the new tree, and a frozen CI that trusts it merges a wrong base for every later `--base`. So frozen CI always derives and compares bytes, and the digest lives only in the local cache (section 5), where it is as trusted as `node_modules`.

### 5. The derivation cache
The compiled views take 50 to 125 ms and are derived on every run. The route evaluation is the cost: one evaluation of contracts, route tables and store factories now gives both `routes.json` and `surface.json`, the way `buildRoutes` evaluates today (an esbuild bundle imported once), so `surfaceRun`'s Vite SSR server goes. Its result is cached in `<root>/node_modules/.cache/keel/derived/` under k.check-cache's rule:

- **Key and probes.** The entry is named by the SHA-256 of the Keel version, the project's code file paths and the evaluation's inputs. The inputs are each file it loaded, the `package.json` of each package holding one, and each file its code reads through `node:fs` or `node:fs/promises`, each with the SHA-256 of its bytes. The probes are every other question that code asks the file system (existence, real path, folder listing, an absent file) and each `process.env` name it reads, with the value. An input is recorded by its path through the project and resolved again at every read, each symbolic link on the path a real-path probe, so a `node_modules` link pointed at another folder (a pnpm upgrade, a re-link, a second version in the store) is a miss even while the old folder still holds its old bytes. An entry is used only when every input and probe, asked again, gets the same answer. Modification times are never read: a file rewritten with its old time is a miss (k.derived clause 16).
- **What can change the result and what is keyed are one set.** This is the lesson RFC 0251 records for approvals, and it is why the inputs are what the evaluation asked, not a list Keel guesses: `surface.json`'s `sources` guessed "project files" and missed every package (cases 6 and 7). E1759 (k.host Node globals) refuses `node:fs` and `process` in a browser file, so a schema or contract of a module a page renders cannot read by path; a server-only file, the `routes.ts` of a node-only module and any package can, at import time or in a store factory. Those reads and environment values are keyed rather than refused, so a package reading its own data file stays usable and the guarantee "a cached derivation is the one a fresh evaluation gives" holds as written. The rest cannot differ between two evaluations of one tree: app code reads no clock, randomness or network (E1601), and store factories run on a sim ctx. Running the evaluation in RFC 0251's `data` child later narrows what it may read; it changes no key.
- **What the evaluation sees** (as built in slice 3; section 10 moves the views into the evaluator's own realm, withdraws the proxy over the command's global object, and restates what is not keyed). Every host view denies by default. One allowlist, `HOST_VIEWS` in `@keel/compiler` (`packages/compiler/src/internal/HOST_VIEWS.ts`), names each member of the global object, `process`, `navigator`, `WebAssembly`, a `node:fs` stat result and file handle, and each Node built-in, in one of three categories. Observed: its reads are recorded as inputs or probes (k.check-cache Evaluation probes): file reads and opens for reading, existence tests, stats and each stat field the code reads, real paths, listings, resolver and `require` lookups, `process.env` names, and stable facts of `process`, `os`, `tty` and `navigator`; the working folder, Node's version and the default locale and time zone are probes of every evaluation. Pure: no host state, given as it is (`path`, `url`, `Buffer`, `util` formatting, `crypto` over given bytes, timers, the clock, random values); `console`, `process.stdout`, `process.stderr`, `process` listeners and `util` warnings write nowhere. Refused (E1050): everything else, a function at its call or construction and any other value at its read, so a member Node adds is refused until it is listed; among them facts that move on their own (`os.cpus`, `process.pid`, `hrtime`), a stat's `atime` (a read moves it, so it cannot be recorded stably), `node:fs` writes and opens for writing, every route to the host's loader (D9), a `.node` addon at its import, and `WebAssembly` instantiation with imports. The global object is a proxy with every trap over a layer of its own, so reflection on it (a property descriptor's getter) reaches only views, and the bundle's writes to it and to `process.env` stay in the evaluation. An E1050 is placed at the refused call's first frame in a project file, or names `<package>/<path>:<line>` in its message when that frame is in a package. Not keyed, stated in k.derived: the clock and random values (app code reads neither, E1601), a file another process changes while the evaluation runs, Node's own warnings, and code that sets out to reach the host by a route no view sees, a function's `constructor` compiling a string being the known one: the evaluation is not a security boundary, and only an evaluation in its own process under Node's permission model (RFC 0251's `data` child, slice 3) closes that route.
- **Who writes.** The evaluator writes nothing; it returns the route tables' data and the surface as JSON. Keel's own process, with the user's rights, writes the cache entry and the views through the one writer (`writeArtifact`: a `<name>.<pid>.tmp` file, mode 0444, renamed into place).

### 6. Concurrency
An editor's language server, a terminal `keel check`, `keel dev` and an agent's MCP calls can run together. No lock is taken: a stale lock left by a killed process would stop every later run, and two runs over one tree derive the same bytes. Each view is one atomic rename, so a reader sees a whole file. A run re-reads its inputs' hashes before it renames, and skips the write when one changed during the run, so a slow run cannot put an older tree's view over a newer one's. Nothing Keel judges reads a view, so a brief window where the views on disk describe different moments of the tree never changes a verdict. Two processes writing one cache entry: the last rename stands, as for the type cache.

### 7. Work, not milliseconds
The claim a test asserts is the work done, counted, because a wall-clock bound flakes on a shared machine (`docs/TESTING.md` bounds a test's time only through the watchdog, never as an assertion):
- **No input changed:** no evaluation runs and one cache entry is read per project; the compile runs as it does today.
- **An edit to a file the evaluation did not load** (a test file): no evaluation.
- **An edit to a file it loaded:** exactly one evaluation of that project, and the entry it writes records exactly the files the evaluation loaded.
- **The seam:** the json summary's `counts` (`refreshed`, `evaluated`, `cached`, on every run, 0 included) and the cache entry's `inputs` (k.derived Derivation cache). k.derived clauses 22 to 25 assert them.

What the counts cost, measured as documentation and not as a clause: on `apps/household` at a 1-minute load of 18, a warm compile of every source 31 ms and one route evaluation 257 ms (`buildRoutes`'s bundle; the surface rides the same evaluation once slice 3 lands), against 2.3 s for a warm `keel check`. Measured by a script that imported `artifactHashes`, `buildRoutes` and `surfaceRun` from this branch and timed each twice in one process with `performance.now()`, beside `/usr/bin/time` for the whole commands. A re-indent re-evaluates once and writes nothing (clause 17).

### 8. keel test, keel dev, keel ledger, scaffold
- `keel test` derives the compiled views in its own process before vitest starts, hands `a11y.json` to each test process (vitest's `provide` and `inject`), and refreshes the views unless frozen. A render with no `artifacts` then always runs E1702 against the tree under test, in a project never built too (clause 12), which today runs no E1702 when `.keel/a11y.json` is absent.
- `keel dev` refreshes after each change to any file a derivation read, or to the project's code file paths, whatever the file's name: a `*.contract.ts` edit alone refreshes `routes.json` and the inspect document as a `routes.ts` edit does (case 12). Each refresh writes every view that differs, `surface.json` and the deploy files included, so an author who runs only dev never commits a stale surface, and `keel check` beside a running dev server agrees with it by construction.
- No run rewrites the file its `--base` names, `.keel/surface.json` included: a base that a run refreshed would compare the tree with itself on the next run and hide the E1563 it reported. The `--base` text and the `keel-data` skill say what to pass: the base branch's file, `git show origin/main:.keel/surface.json > /tmp/base.json` then `keel check --base /tmp/base.json`. Every other view is still refreshed beside an error.
- `keel ledger` derives each project's `routes.json` (the cache makes a ledger after a check cost no evaluation) and finds projects as `keel check` does.
- A scaffold operation's refresh (k.scaffold Refresh) is this refresh; nothing changes in k.scaffold.

### 9. What an agent needs to know afterwards
Nothing. Edit, `keel check`, done: the result is about the tree. The lines to delete are in Docs and skills.

### 10. The evaluator: the evaluation leaves the command's process
**Why the in-process design is withdrawn.** Three review rounds each broke "a cached derivation is the one a fresh evaluation gives" by a new route, and each fix was a longer list: observed reads (round 1), a default-deny allowlist (round 2). Round 3 reproduced five more, and none is a forgotten member:

| # | fault | cause |
|-|-|-|
| F1 | under `keel dev`, after one request to a `node` deployable, every later evaluation is refused: `installServerDom` put `document` on the dev process's global object and `globalDefines()` reads the host's globals at each bundle | the evaluation shares a global object with its host |
| F2 | `fs.createReadStream(x).constructor` is Node's `fs.ReadStream`; `new RS(path)` reads unrecorded, and with `{ flags: 'w' }` truncates | a view hands out the host's own objects |
| F3 | `Math.__n++`, `Error.stackTraceLimit = 0`, `util.inspect.defaultOptions`, `events.defaultMaxListeners` persist into the next evaluation and into the command | pure members are the host's objects |
| F4 | a `setInterval` keeps `keel check` alive after its summary; an unsettled top-level await exits 13 with Node's message, and `keel dev` never listens | the evaluation shares an event loop with its host |
| F5 | a `data:` module is placed as a project file; a minified package gets no column | positions travel as marks in message text |

Also flagged: `Buffer.allocUnsafe` returns old host memory; `crypto.getHashes` follows `OPENSSL_CONF`. Every one comes from one fact: the evaluation shares a realm, an event loop and object identities with the process that hosts it. A list inside a shared realm names what the writer thought of. The design is restated at that fact.

**Where it runs.** Weighed against F1 to F4 and the flagged items:

| | own globals and intrinsics (F1, F3) | own loop, killable (F4) | unrecorded read fails below JavaScript (F2) | start, measured here |
|-|-|-|-|-|
| `node:vm` context in the command's process | globals yes; Node's built-in modules stay the host's objects | no: one loop; a synchronous loop needs `timeout` per call and timers are the host's | no | under 1 ms |
| worker thread | yes | yes (`terminate`) | no: the permission model is per process, so a worker reads as the command does | 11 to 14 ms |
| child process | yes | yes (a signal) | yes: `--permission` with no file right | 33 to 37 ms |

Only the child closes all four, and it is the one RFC 0251 already specifies. A worker inside the child was weighed as the way to wait for an answer (`Atomics.wait`) and dropped: it needs `--allow-worker`, a right the evaluation should not hold, and the pipe below needs none.

**The design.**
- *One process per bundle.* `evaluate({ kind: 'data', entry, deadlineMs })` of `@keel/compiler` starts Node on the bundle with `--permission`, `--allow-fs-read` for the bundle's folder alone, `--disallow-code-generation-from-strings` and `--zero-fill-buffers`, in a new empty working folder, with an environment built from nothing but the zone and locale names (`TZ`, `LANG`, `LC_*`), which the cache already probes. No evaluator is reused: sharing between evaluations is the fault, so nothing is amortised by keeping one alive. The cache is the amortisation: a run whose inputs are unchanged starts none for the tree.
- *A prepared realm, not a proxy.* The child's global object is its own, so the bundle's banner replaces members in place from the one allowlist (`HOST_VIEWS`): pure stays, observed becomes a view, everything else refuses. No esbuild `define` rewrites a global name, `globalThis` is the real global object of the child, and `globalDefines()` and the `__keelGlobal` proxy go. What the host's global object holds no longer matters (F1). A write to `Math` or `Error` dies with the process (F3).
- *The command answers.* The child holds no file right, so a view cannot read: it asks the command over a pipe the child inherited, waits (a blocking `readSync`), and the command reads the disk or its own environment, answers, and records the question as the input or probe it already is. Measured here (Node 24.22, macOS, load 17): 200 questions in 4 to 6 ms. The fs view is Keel's own code over those answers and holds no object of Node's `node:fs`: a stat result, a handle, a stream are the view's classes, and `createReadStream(x).constructor` is a class that asks (F2). If code does reach Node's own `fs`, Node refuses the read and the write whatever the route, so the outcome is an error in a cached run and a fresh run alike, never a stale hit.
- *The end.* The entry's result ends the evaluation; the command then kills the child. A timer or handle left behind dies with it and is no diagnostic: a pool's reaper interval at import is ordinary package code, runs nothing in an evaluation, and refusing it at creation would fail `pg`-like packages for no gain (F4, first half). No result within the deadline (30 s by the command's monotonic clock, from the child's start) is E1048; Node ending the child on an unsettled top-level await is E1048 at once; any other early exit is E1049 with a fixed message. The deadline is 100 times household's evaluation here (257 ms), so load does not reach it; a test passes its own `deadlineMs`.
- *Records, not marks.* A refusal's code, message and bundle positions cross the pipe as fields, and the command maps them through the source map it holds. Nothing is encoded in message text, so no path can print a mark (F1's unplaced, uncoded line), a frame with no file on disk is skipped (F5), and a package frame carries its column (F5).

**What each finding becomes.**
| finding | under the evaluator |
|-|-|
| F1 | impossible: the child's globals are a fresh Node's; `keel dev` refreshes after any number of requests (k.evaluator, last clause) |

**What remains of the lists.** `HOST_VIEWS` stays as data, with its three categories, and every E1050 clause of k.compiler stands as written. What changes is what the list is trusted for. For the file system it is the observation, and Node's permission model is the guarantee beneath it. For facts no file holds (the child's process id, timings, memory, the host name, the network on Node 22 and 24) the list is still the only gate; reaching them needs Node's own `process` or loader past the prepared realm, for which no route is known, since no code from a string runs and every loader route is a view. k.evaluator Not held says exactly that, and the sentence "a function's `constructor` compiling a string" leaves the not-keyed list: V8 refuses it.

**One evaluator.** RFC 0251 (k.machine Evaluator, on `lane-r-boundary`) specifies the same child: `evaluate` of `@keel/compiler`, `--permission`, code from strings off, an empty working folder, an environment from nothing, the result as JSON. Its conformance is written there (`machine-evaluator.test.ts`, `machine-seams.test.ts`); its build step 7 is not started (the lane's head is still conformance for its earlier steps). Three ways to meet it:
1. *Build the evaluator's isolation here, and RFC 0251 uses it.* Chosen. Nothing is thrown away: this lane builds the function, the flags, the question pipe, the lifecycle, E1048 and the placing; RFC 0251's step 7 adds the `prerender` kind, narrows the answers to its grants (`read` folders, `env` names) and adds its loader hook.
2. *Build a smaller thing here that RFC 0251 replaces* (a worker thread). Fixes F1, F3 and F4, leaves F2 to lists, and the worker host, its `Atomics` channel and its termination code are deleted when the child lands. A second evaluator for a few weeks, and a fourth round on F2. Rejected.
3. *Merge what is sound and leave the cache behind a stated limit until RFC 0251 lands.* F1 and F4 are functional faults, not evasions, so they need a fix now whatever else waits, and the smallest fix for both is a process of its own, which is most of option 1. Rejected.

The merge order loosens. This lane no longer waits for `lane-r-boundary`, which itself waits for RFC 0242 and RFC 0245: `lane-r-fresh` merges when slice 5 is built and reviewed, and `lane-r-boundary` builds its step 7 on the `evaluate` it then finds on the main line. Four points meet at that merge and are RFC 0251's to settle (For the operator, 8).

**The dev process.** `keel dev` calls `evaluate` like every command, so a refresh depends on the tree and never on what the server has served. It kills an evaluator whose bundle a newer change made stale. The other fault of the review, the SSR reload of `virtual:keel/dev` failing with "store shopping.outbox: id already in use by a live store", is not the evaluation's: the build-time bundle carries its own copy of `@keel/store`. Its cause: `apps/household/modules/shopping/listOutbox.ts` creates the outbox at module top level under a scope that is never disposed; `reloadDev` in `packages/compiler/src/vite.ts` closes the apps and invalidates the dev entry and the edited file's importers, so `listOutbox.ts` runs again while `@keel/store`'s `registries.shared` (`packages/store/src/internal/registries.ts`) still holds the id, and `store()` throws (`packages/store/src/store.ts`). The fix belongs to the dev reload: the dev entry marks the module registry's store ids as carried over (`storesReload` in `@keel/store/internal`, beside `inspectorsReload`), so a module evaluated again creates its store in place of the earlier load's and two stores of one id within one load still throw. A root scope disposed by `reloadDev` was built first and withdrawn: disposing it needs the whole server graph evaluated again on every reload, and that work in the dev process held up the evaluator's answers past k.evaluator's 2 s. No spec change.

**Cost.** Basis: the experiment above (a `--permission` child, start to exit, 33 to 37 ms; RFC 0251 measured 30 ms), and this RFC's table (one route evaluation 257 ms, a warm check 2.2 to 2.9 s).
- A warm `keel check` with the tree's derivation cached starts one evaluator, for `tokens.ts` (k.a11y-static: evaluated on every run): about 35 ms of process start, 1 to 2 percent, and it can run beside the type pass since it no longer holds the command's thread.
- A check after an edit to an input starts two: about 70 ms over today's 257 ms evaluation, and the same overlap applies.
- A `keel dev` refresh: one evaluator, about 35 ms over the bundle and evaluation it runs today.
- If the measured warm cost passes 5 percent, the tokens evaluation joins the tree's bundle and its cache entry (`entrySource` already takes both); that changes what `counts.evaluated` counts and is left out until measured.

**Platforms.** CI runs Linux and macOS. The mechanism uses `spawn` with extra `stdio` pipes and `readSync` on an inherited descriptor, which Node documents for Windows too; it is not verified there, and no Windows runner exists. `--permission` is stable from Node 22.13, so `engines` moves from `>=22` to `>=22.13` (RFC 0251 moves it to 22.15 for its loader hook).

### Personas
- **A2, human and agent: how many commands from an edit to a verdict?** One, `keel check`. Today two, in an order an agent must remember, and E1005's message ("run keel build") names a cause the author did not touch. An agent following the diagnostics word for word spent a build per edit; now it spends nothing.
- **A7: does `keel test` after an edit test the edit?** Yes: E1702 runs against the derivation of the tree under test, a read-only checkout runs its tests (case 11), and a red test names its cause, never a file left from an earlier build.
- **A3: do two teams break each other, and does CI hold?** The committed record is the surface alone, so two pull requests touching different pages no longer conflict on it. CI derives the current surface whatever is committed, so a dependency bump that breaks stored states fails on E1563 (case 6), and a stale committed surface fails E1005 under the default frozen run. A merge of two fresh branches that is stale together is caught by the push run on the main line, which is frozen too.
- **A8: is the build a function of the tree?** Yes, more than before: `keel build` evaluates from the same cached derivation `keel check` used, and no input outside the evaluation's loaded set can change a view (slice 3 on RFC 0251's wall). Nothing environment-specific enters a committed file: no digest, no absolute path, no Node version.
- **F1: what does this cost to change later?** Little, by design. No new committed format: the views keep their bytes, `surface.json` loses a field. The cache is private to `node_modules/.cache` and can change shape in any release, since deleting it is always safe. The public surface added is one flag, one environment value, one trailer count and one warning code.
- **A6** reads `keel evidence` built from a ledger whose `a11y:` items now follow the routes the tree has, not the last build's.

## Alternatives
- **A watcher daemon** that rebuilds `.keel/` on every save. It needs a process that someone or something must start, keep alive and stop. An agent in a fresh shell has none running, so its check is as stale as today. Two daemons on one tree race, and a killed one leaves state that looks fresh. The project is checked by a command; the command should see the tree it is given. Rejected.
- **"Always build first", documented.** It is today's state, in the guide and in the `keel` skill. It costs a full build (7.6 to 11.8 s here) per edit, and it is exactly what the owner's question rules out: a rule an agent has to remember, which fails silently for the one that does not (cases 5 to 7 are green without it). Rejected.
- **A warning only** (W instead of E1005 for a stale view). Removes the wrong red and keeps every wrong green: the stale surface still feeds `--base`, and the stale `a11y.json` still feeds E1702. Rejected.
- **(a) alone: re-derive everything on every run, never cache.** Correct, and the fallback when `node_modules` is absent. As the default it adds 0.3 to 0.7 s of evaluation to every check, which breaks k.check's 1 s warm bound. Kept as the uncached path, rejected as the only path.
- **(b) a digest in every view, readers verify.** Faster than (a), but the digest is public (section 4), it pins machine-independent hashing into committed files forever (F1), and every dependency bump changes a committed file whose content did not change, which fails a bot's pull request under frozen CI. Rejected for committed files; adopted inside the private cache.
- **(c) no views on disk at all.** The compiled views have readers outside Keel: people opening `ids.json`, tools that read the dependency graph, the inspector when it is not running (principle 6 makes these tool endpoints). Keeping them as gitignored views costs one rename each when they change. Rejected; the committed set shrinks to the record.
- **Refresh in `keel check` only when `.keel/` already exists**, as k.scaffold Refresh does. A never-built project then has no views until a build, so tools that read them see nothing. Rejected for check; scaffold keeps its rule because a generator's refresh is part of an edit set, and the next check writes the views anyway.
- **Keep `surface.json`'s `sources` and the normal form.** They were the cheap staleness test that let check avoid evaluation. Check now evaluates from a cache whose key is exact, so they would only keep two pull requests conflicting and a formatter rule set to maintain. Rejected.

- **A `node:vm` context or a worker thread for the evaluation** (section 10): each leaves the permission model shared with the command, so an unrecorded read still succeeds. Rejected for the child process.
- **One long-lived evaluator per run, a fresh realm per evaluation.** A realm inside a kept process is a `vm` context or a worker again, with the same gap, and saves about 35 ms on the one run in many that evaluates twice. Rejected.
- **Refuse a timer at its creation.** Fails ordinary packages at import for something that changes no result. Rejected: it ends with the evaluator.
- **A full membrane** (every object a view returns wrapped, recursively). It is the list approach one level down, in the realm it is meant to guard. Rejected for views that hold none of Node's objects, over a runtime that refuses.

# RFC 0133: a served document resumes: the server writes regions, a layout island's `children` holds the child level, and every island resumes

Status: implemented (ADR-0155)

## Problem
Two independent faults, each read in the code on 2026-11-18.

1. **No regions are written.** k.runtime Resume markup says the server wraps each structural op's content in `<!--[-->` … `<!--]-->` right before its anchor. Nothing writes them. The server renders a level through the client `mount` on a detached host (`packages/server/src/internal/renderUnit.ts`); outside a resume claim, `prepare` (`packages/runtime-dom/src/internal/prepare.ts`) puts an op's content straight before an empty anchor, and at resume `regionOf` throws `no server region` for the first `If`, `For`, `Match` or `Boundary` in an island. The consumer is built to the spec; the producer is not. The runtime's resume tests hand-write server HTML; the one server test that feeds `createApp` output into `resume` (`packages/server/test/island-ui-root.resume.test.ts`) covers single-level pages of base elements with no structural op, so the two halves were never checked against each other where they differ. The spec has no clause tying them together.
2. **A layout island's slot is undefined at resume.** `renderChain` renders a layout with a `children` thunk returning the child level's HTML as a fragment, and marks each level whose element has a bound node `data-k-island`; the props it stores in `#k-state` have no `children`. The compiler lowers `{props.children()}` to a `slot` at an anonymous anchor `<!---->`. At resume `resume` (`packages/runtime-dom/src/ops/resume.ts`) takes only outermost islands and calls the layout with props lacking `children`: the slot renders nothing, the server's child element is unclaimed, the template's shape does not match, and the layout falls back to a client re-render (E1253), throwing away the page island's server nodes with it. The spec (k.runtime Islands and resume, k.router's layout `children` slot, k.server's route levels) does not say what a layout island's `children` is at resume, nor that an island inside an island resumes.

Together: any served page with a layout island, or with a structural op inside an island, re-renders on the client. golden-1's board is such a page.

## Proposal
A new kernel section, `k.resume` (`spec/kernel/k.resume.md`), status proposed. k.runtime is at 1,499 tokens and keeps every bullet; the new clauses are the contract between the server (producer) and `resume` (consumer), so they sit in one place both builders read.

### 1. Regions, from a server mode of the runtime
The server renders each level with the runtime in a server mode in which every structural op writes its content in a region before its anchor, an empty region when it renders nothing. So does every template slot other than a component slot `<!--+-->`: a slot call such as `children()` or a JSX expression of elements. A `For` region holds its rows, or its `empty` content. The root Boundary of a level's render writes no region, since an island root is the element itself. At resume a slot claims its region's nodes in order, as an op does.

Slot calls get regions because the child-level content and any slot call's content may be a fragment, text or nothing; one element cannot delimit them. The region is the delimiter k.runtime already uses for ops, and `regionOf`, `shapeOf` and `alignTexts` already read it, so the consumer gains no new marker.

The spec names the behaviour, not the switch: how `renderUnit` tells the runtime it is producing a document is the builder's call (an internal option of the runtime's internal entry, not app surface).

### 2. A layout island's `children` at resume
At resume an island level's `children` is a thunk that renders no child level: it returns the nodes of its slot's region, which stay in place and which the layout does not claim. Nested islands inside them resume on their own (3). A later call (an `If` branch or a `Boundary` rendering anew) returns the same nodes and moves them to its place; a removed place detaches them and disposes nothing in them, so a page island hidden and shown keeps its state and handlers. When the server placed no content, a call returns nothing.

**Misuse.** A second call while the layout builds, or a later call while the content is in the document, throws E1255, on the server and in a resumed island; the level fails as a throw does (errorElement, else the 500 document; on the client the island's root Boundary). Two copies of a child level would put the same island roots, element ids and `#k-state` props in the document twice, and there is one set of server nodes to hand out. Zero calls need no rule: the server places nothing and the client claims nothing. A conditional call is specified, not refused: shown at the request, it toggles over the held nodes; hidden at the request, it stays empty on the client (a Limits sentence), since a static level ships no JS and a page island's component alone cannot rebuild its static ancestors' HTML.

E1255 is in E125x (k.runtime's block, now shared with k.resume): the fault is a resume contract. E1254 was deleted in rfc:0040 and is not reused. It is an explain-only code raised by the server render and the resumed island, asserted by conformance (ADR-0029 (c)); its `explain` entry is added with the build.

### 3. Every island resumes, in document order, independently
Every `[data-k-island]` root resumes in document order (an ancestor before its descendants), each with its own props from `#k-state` by route id, root Boundary and delegated listeners; an island's claim stops at a nested island root. A mismatch (E1253) re-renders that island in place of its server element, and only it. A re-rendered layout's `children` returns the held content, so its descendants keep their nodes and resume after it; a descendant that re-renders replaces its element in the held content. This keeps k.runtime's fallback rule (the failing island re-renders, dropping its own queued events) and makes it local.

### 4. Producer meets consumer
The first Conformance bullet: for every route of a test app, the body of the document `createApp` serves, resumed with the app's compiled components and stores, returns no warning, keeps every server node, and a fired handler runs and updates its bindings. Every other bullet is phrased over served documents too, so the blind writer cannot hand-write the HTML.

## Alternatives
- **Delimit the child level as exactly one element** (a `<!--+-->` slot for `children()`). Simpler claim, but a page may return a fragment, text, a string or nothing, and a layout around a non-island page would gain a wrapper constraint. Rejected: it adds a constraint on app code.
- **Ship `children` in `#k-state`** (the child HTML, or a marker the client re-renders from). Re-rendering the child level on the client needs every static level's component in the client bundle, which k.runtime's "static HTML ships no JS" forbids; HTML in `#k-state` doubles the document.
- **Resume the layout and its nested islands as one island.** One scope would own the page island's nodes, so a mismatch in either re-renders both, and the page's props would need to flow through the layout's. Rejected for coupling (principle 2).
- **Refuse a conditional `children` (a check rule).** A layout guarding its page behind a signed-in `If` is ordinary, and works when the condition holds at the request. A check rule for "condition false at the request" cannot see request state. The limit is stated; a rule can follow if the evals show the trap.
- **Write regions by post-processing the HTML.** The server would have to know each op's anchor in the serialized output; only the op knows its content's extent.
- **Treat a second `children` call as a move.** The server's two slots and the client's would hold the content at different times, so the claim order would not match the document. Rejected for E1255.

## Choices
Each is the author's call for the orchestrator to confirm or reverse.
- R1: slot calls, `children()` included, are regions, not single elements.
- R2: a layout island's `children` at resume returns the held server nodes; later calls move them.

- R4: every island resumes in document order, independently; a mismatch re-renders only that island.
- R5: a new section, k.resume, rather than trimming k.runtime.

## Amendment (review and browser smoke after the build)
A review of the build and a real-browser smoke of a served golden-1 list page found four faults, each read in the code.

**A. Replay order and reach.** `eventQueue` keys each queued event by its innermost island and `resumeIsland` replays an island's events when that island resumes, through its own delegation root only (`dispatch(root, …)` with `root` the island element). So a click on the page island and then one on the layout replay layout first, and a page event never reaches a layout handler on an element enclosing the target, which a live event reaches by bubbling to the layout's listener. k.runtime asks for replay "in order". Rule: events queued before resume replay once every island has resumed, in the order they fired, each dispatched as a live event: from the target through each enclosing resumed island, innermost handler first, until `stopPropagation`. The `input` k.runtime fires for a control typed before load stays per island, at that island's resume, so every such `input` comes before the first replayed event; that is the order k.runtime's observer bullet already states ("an `input` for a field typed before load, then each queued event"). This reads k.runtime's "per island it then fires `input` …, then replays queued events in order" with "per island" scoping the `input`; it refines the sentence and contradicts no bullet. An event whose target is in a re-rendered island's own nodes is dropped, as k.runtime says; one whose target is in a held island that kept its nodes replays, and reaches a re-rendered layout's handlers as a live one would, since the held content sits in the new layout.

**B. Fallback holds the layout's wrapper.** `salvage` keeps the outermost region between a mismatching layout island and its first nested island root. With `<If><div class="wrap">{children()}</div></If>` that is the `If` region, wrapper included, and the client re-render wraps it again. Innermost is wrong too: under a static middle level the innermost region around the page's root is the static level's slot. No count of regions tells the child level's region apart, so the server marks it: it writes a comment `<!--k-->` as the first node of a child level's content (the fragment `renderChain`'s `children` returns), and a layout island that mismatches before its `children` call holds exactly the region whose first node is the first `<!--k-->` in its element, in document order. That is the child level's server content and nothing of the layout's own output; a static child level with no island below it is held too, which removes ADR-0155's last consequence. Comments are not compared in a claim, so the marker costs nothing on the success path, where it moves with the held content.

**C. Module stores written on the server.** k.server says "server code never writes module stores", and `snapshotStores` puts only the request's registry in `#k-state`, but nothing enforces it. golden-1's `loadIndex`, `loadList` and `loadTodo` call `refreshView`, whose `tx(hydrate, …)` writes the module store `todos.view`, and the page reads its rows from that store. Served by a node process, one request's board reaches the next, and the browser, whose `todos.view` is at its initial state, renders different rows than the server sent. In-process tests pass because server and client share one module instance.

Rule: while a request `createApp` serves runs, a `tx` on a store in the module registry (k.store Registries) throws an `Error` whose message starts with `E1256` and names the store, and changes nothing. "While a request runs" is the request's guards, loaders (live ones included), action and the render of its levels, through every `await` in them: the builder carries the request through async continuations (as `requestSecrets` does with `AsyncLocalStorage`), not the synchronous `owner()` chain, which `refreshView`'s `await` would escape. Reads are allowed. Stores created during the request are in the request's registry and are written freely; `stores` factory stores are untouched. Code outside a request (runners, start-up, a test's setup before `fetch`) is not checked, and neither is `renderRoute` (`@keel/testing`), which runs page loaders as the client router does over `serverState`, not `createApp`. It surfaces as a throw does: a guard, loader or render fails its level (`errorElement`, else the 500 document), an action answers 500 `keel.unexpected`, and the log gets the `diag` with the code; dev and production alike, since the leak is worse in production. A throw rather than an `err`: a `tx` result is often ignored (`void tx(…)`), and the fault is a programming error, as E1255 is.

Code: E1256, in E125x. k.server owns E155x but sits at 1,500 tokens, so the rule's text lives in k.resume, which shares E125x with k.runtime (the map's row already says so; the map is unchanged at 1,198). E1569 is the lowest free code in E155x, kept unused. `explain E1256` (with the build, at most 120 tokens): summary "a tx on a module store while createApp serves a request"; why: module stores are process-wide, so a write reaches every later request and never the browser, which resumes with the store at its initial state; fix: "return the rows as loader data, or name the store in the loader's `stores` factory"; see k.resume.

No static rule: the write in golden-1 is two files away from the `*.server.ts` loader (`refreshView.ts`, `hydrate.ts`) and a check would have to resolve that a `tx`'s transaction is bound to a module-level store across imports. Left as future work for `tasks/FUTURE.md`.

What "its stores" means in k.resume's first bullet: the stores `#k-state` carries, the request's, restored in a client module graph separate from the server's. A store a component creates while its level renders is one of them, and the client has no such store when `resume` restores (`resume` warns E1253 "snapshot for unknown store" today). So: a snapshot restores the store of its id in `resume`'s `stores`, else the store an island creates with that id while it resumes, which starts from the snapshot instead of its initial state; a snapshot no store has taken when every island has resumed is E1253.

**D. Test isolation.** Every in-process served-document test shares one module instance between server and client, which hid C. The served-document cases resume in a client module graph of their own, and `@keel/testing` offers it: `resumeDocument(html, { routes: () => import(path) })` evaluates every module the import reaches anew, `@keel/store` (so its module registry) and `@keel/runtime-dom` included, and resumes with that graph's `resume`, components and `stores()`. The test's own module stores are neither read nor written. Passing the manifest object stays allowed. How the graph is made is the builder's call (`vi.resetModules()` then the import, as `packages/runtime-dom/test/trustedHtml.test.ts` does, or the runner's module API).

**Accepted mechanism (ADR-0155 D5).** While an island claims, a server element with regions gets a temporary own `childNodes` without the region comments and their content, deleted on every path when the claim ends (`resumeIsland`'s `finally`). The review rated it low and it stays, with its limits stated in the ADR: the own `childNodes` is a snapshot taken at the claim, and only `childNodes[i]` reads are covered (`firstChild`, `nextSibling`, `children` and iteration see the real nodes). A guard test pins that compiled output reads a claimed element's children only through `childNodes[i]`.

**golden-1.** golden-1's `web` is `adapter: 'client'` (`topology.ts`), and its `todos` module is built for the browser: loaders run in the client router and hydrate `todos.view`, writes queue in `todos.outbox` in the browser's storage, and `todos.editor` follows the outbox (README, evals/tasks/golden-1 "client-only"). No supported configuration serves its documents through `createApp`: only `test/ssrNode.test.ts` and `test/resumeDocument.test.ts` (a test topology placing `todos` on `node`) and `tooling/smoke/resume.mjs` (a copy rewritten to `node`) do. So golden-1 is client-only by design: its served-document tests go, and the served-resume test and smoke target golden-2, whose `recipes` loaders return their rows as loader data and write no module store, and whose `test/ssrNode.test.ts` already serves it on a test `node` topology.

Choices the operator can reverse:
- A1: replay waits for every island and keeps fired order; the `input` sync stays per island.
- A2: the child level's content begins with `<!--k-->`, rather than an ordinal in `#k-state` or a distinct region opener (which every region reader would have to learn).
- A3: E1256 throws, in dev and production; only `createApp` requests are checked, not `renderRoute` or runners.
- A4: E1256 in E125x, with the text in k.resume; no static rule yet.
- A5: a `#k-state` snapshot with no store in `stores` waits for an island to create one while it resumes.
- A6: `resumeDocument` takes `routes` as an import function for a fresh graph.
- A7: golden-1 is client-only; its served-document tests and the smoke move to golden-2.

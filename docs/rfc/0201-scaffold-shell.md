# RFC 0201: k.scaffold-shell: `keel scaffold shell <tauri|capacitor>` adds a native shell

Status: implemented (ADR-0223), accepted by the orchestrator on 2026-11-24, for the operator to confirm. New section k.scaffold-shell; amends k.scaffold (Operations, Generators, Guarantee, Refresh, Rules), std.tauri and std.capacitor (new **App packages**, Tools, Conformance), the map. Under D103. From examples finding 18.

## Decisions
- D1: `keel scaffold shell <tauri|capacitor> --id <reverse-dns> [--name <title>] [--to <deployable>]` is a generator. It changes `topology.ts` and `package.json`, and no other file.
- D2: `--id` has no default; `--name` defaults to the title-cased `package.json` `name`; `--to` defaults to the one `client` deployable.
- D3: every version it writes is one the shell's std package declares in its own `package.json`: plugins and `@capacitor/core` in `dependencies` (as E1572 already reads them), the CLI and platform packages in new optional `peerDependencies`. `@keel/scaffold` carries them as a file `pnpm generate` writes from those `package.json` files, drift-checked by `pnpm check`.
- D4: Capacitor gets both platform packages; there is no `--platform`.
- D5: the operation refreshes nothing. The install, then `keel build`, follow it; the k.scaffold Guarantee holds after those two.
- D6: one new code, E1359: no one `client` deployable to take the shell. The rest reuse E1052, E1351 and E1353.

## Problem
A native shell is added wholly by hand (examples finding 18). `keel scaffold project` writes one `client` deployable; for `examples/native-tauri` and `examples/native-capacitor` the author then wrote, from `pnpm spec k.shell`, `apps/golden-1/package.json` and the build's failures:

| Hand edit | `native-tauri` | `native-capacitor` |
| --- | --- | --- |
| `topology.ts` | `shells: { tauri: { id: "dev.keel.nativetauri", name: "Native Tauri" } }`, the deployable reflowed one property per line | the same with `capacitor` |
| `dependencies` | `@keel/std-tauri` | `@keel/std-capacitor`, `@capacitor/app` 8.1.2, `@capacitor/core` 8.6.0, `@capacitor/preferences` 8.0.1 |
| `devDependencies` | `@tauri-apps/cli` 2.12.4 | `@capacitor/android`, `@capacitor/cli`, `@capacitor/ios` 8.6.2 |

Everything else in each example's `topology.ts` and `package.json` is byte for byte what `keel scaffold project <name> --workspace` writes. `deploy/web/<shell>/` is generated by `keel build` (k.shell Files).

What knows those versions today:
- **Plugins.** std.capacitor's target gives `plugins(app)` at the versions `@keel/std-capacitor`'s `dependencies` pin (`capacitorPlugins.ts`, `pinned`); E1572 names a missing one with its `package.json` line. std.tauri gives `[]`.
- **`@capacitor/core`.** In `@keel/std-capacitor`'s `dependencies` (8.6.0). Not a plugin, so no E1572; the Capacitor CLI stops without it (`requireCapacitorPackage(config, 'core')` in `@capacitor/cli` 8.6.2 `dist/common.js`).
- **The CLI and platform packages.** Nowhere in Keel. `tauriTools` and `capacitorTools` test for `node_modules/.bin/tauri` and `.bin/cap` (E1575 `@tauri-apps/cli in the app's devDependencies`) and name no version; `cap add <platform>` stops without `@capacitor/<platform>`. The only copies are the golden apps' and the examples'.
- **The std package itself.** E1572 (`topologyNeeds`) names it when `shells` declares the shell.

So `keel check` points at the std package and at the Capacitor plugins, one failure at a time; the CLI and platform versions come from another app.

What constrains a generator here:
- `@keel/scaffold` cannot import the std packages: they depend on `@keel/cli`, which depends on `@keel/scaffold`. And at scaffold time the std package is not installed in the project, so neither its `./tools` nor its `package.json` can be read from there.
- The shell's generated files and CI jobs come from the target's `files` and `ci` (k.shell Shell target), the std package's code. `keel check` reports each missing one as E1005 (tried: moving `deploy/web/tauri/tauri.conf.json` away in `examples/native-tauri` gives one E1005, fix the file). A changed `shells` stales no `.keel/` artifact (tried: renaming the shell gives E1005 on `tauri.conf.json` alone).
- k.scaffold Refresh runs `keel build`'s steps after an applied operation in a built project; with the std package not yet installed its first step, loading the declared shells' targets, is E1159.

## Proposal
### The command
```sh
keel scaffold shell tauri --id com.acme.shop
keel scaffold shell capacitor --id com.acme.shop --name 'Acme Shop' --to web
```
Input `{ shell, id, name?, to? }`, `shell` the first argument. `--id` and `--name` are new structural flags read by `shell` alone; `--to` is the one `move` and `place` take.
- **`id`** has no default. It is the app's store identifier and its return links' scheme (k.return); a default (`com.example.<pkg>`) is an identifier nobody chose that is costly to change after a release.
- **`name`** defaults to the `package.json` `name`, `@scope/` dropped, split at `-`, `_` and `.`, each word's first letter upper-cased, joined by spaces: `native-tauri` gives `Native Tauri`, as the example chose by hand.
- **`to`** defaults to the topology's one `client` deployable.
- **Platforms.** None to choose: Capacitor gets `@capacitor/android` and `@capacitor/ios` both, because its generated CI has an `android` and an `ios` job (std.capacitor CI) and `--platform` picks at build time. Two packages an Android-only app does not run cost nothing at run time.

### The edits, in order
1. `topology.ts`: the deployable gains `shells: { <shell>: { id, name } }` as its last property, or an existing `shells` object gains the entry as its last. The edit is `connectOrigin`'s: the file's quote style, other properties' text kept, a one-line deployable past 120 columns written one property per line. The default project's deployable is one line, and the shell takes it to about 127 columns, so the result is the example's layout:
```ts
import { topology } from "@keel/server";

export default topology({
  web: {
    modules: ["app"],
    adapter: "client",
    styles: ["@keel/ui/fonts"],
    shells: { tauri: { id: "dev.keel.nativetauri", name: "Native Tauri" } },
  },
});
```
2. `package.json`, keys of each object sorted, as `service` writes it:
   - `dependencies`: `@keel/std-<shell>` at the version text of `@keel/server` (`workspace:*` in a workspace app, `^0.0.0` standalone).
   - The shell's app packages (std.tauri, std.capacitor App packages), with `identity` true when `identity.ts` exists: Tauri `devDependencies` `@tauri-apps/cli`; Capacitor `dependencies` `@capacitor/core`, `@capacitor/preferences`, `@capacitor/app` (and `@capacitor/browser` with `identity`), `devDependencies` `@capacitor/cli`, `@capacitor/android`, `@capacitor/ios`.
   - A package already in either field is kept as written, so a person's own `@tauri-apps/cli` range stays. A `plugins` entry at another version text is set, as E1572's fix sets it, because `keel check` requires the exact text.

No other file is created, changed or removed, in any project: no deploy file (the target is not loadable yet), no `.keel/` artifact, nothing under `dist/`.

### Where the versions come from
Each std package declares every version an app lists for it, in its own `package.json`:
```json
{
  "name": "@keel/std-capacitor",
  "dependencies": { "@capacitor/app": "8.1.2", "@capacitor/browser": "8.0.5", "@capacitor/core": "8.6.0", "@capacitor/preferences": "8.0.1" },
  "peerDependencies": { "@capacitor/android": "8.6.2", "@capacitor/cli": "8.6.2", "@capacitor/ios": "8.6.2" },
  "peerDependenciesMeta": { "@capacitor/android": { "optional": true }, "@capacitor/cli": { "optional": true }, "@capacitor/ios": { "optional": true } }
}
```
`@keel/std-tauri` gains `"peerDependencies": { "@tauri-apps/cli": "2.12.4" }`, optional the same way. A peer is what it says: the std package's build runs the app's own `tauri` and `cap` (`toolCommand(dir, "@tauri-apps/cli", "tauri", ...)`), so the app provides them. Optional means an app that lacks one gets no install error; pnpm still warns when an app lists another version.

`tooling/generate.mjs` writes `packages/scaffold/src/internal/SHELL_PACKAGES.ts` from those two files, calling each target's `plugins` with `identity` false and true, so the plugin rule has one home:
```ts
// _generated: from packages/std-tauri/package.json and packages/std-capacitor/package.json; run pnpm generate.
export const SHELL_PACKAGES = {
  capacitor: {
    dependencies: { "@capacitor/app": "8.1.2", "@capacitor/core": "8.6.0", "@capacitor/preferences": "8.0.1" },
    identity: { "@capacitor/browser": "8.0.5" },
    devDependencies: { "@capacitor/android": "8.6.2", "@capacitor/cli": "8.6.2", "@capacitor/ios": "8.6.2" },
  },
  tauri: { dependencies: {}, identity: {}, devDependencies: { "@tauri-apps/cli": "2.12.4" } },
} as const;
```
`pnpm check` runs `generate.mjs --check`, so a std package version bump without the regenerated file is S0007, as `PII_SINKS.ts` in `@keel/cli` is today. The Keel packages release together, so the table in `@keel/scaffold` at a release is the std packages' at that release.

### After the edits
```
change package.json
change topology.ts
ok scaffold shell 0 created, 2 changed, 0 removed
```
1. The package manager installs. Until then `keel check` reports `E1159 shell package @keel/std-tauri/tools cannot be imported (not found)`.
2. `keel build`, or `keel build --target tauri` directly, writes the shell's files and CI jobs (k.shell Files, CI), as it writes every deploy file. Until then `keel check` reports each missing one as E1005 (six for Tauri, one for Capacitor, and the CI workflow outside a workspace), each fixed by that build. In a workspace app with no `deploy/` files yet, the check reads the CI workflow alone, so it is clean straight after the install.
3. `keel check` is clean: no E1572 (every package is listed at its declared version), no E1573 (the `id` was checked), no E1005. `keel build --target <shell>` needs only the native toolchain (E1575: Rust 1.95, WebKitGTK 4.1 on Linux, JDK 21 with the Android SDK, Xcode 26) and, with a `node` deployable, `KEEL_ORIGIN` (k.shell Build 2). An app with no server needs no environment.

The operation refreshes nothing even in a built project: the refresh would load the new shell's target and stop at E1159. The Guarantee is amended to say so.

### What it refuses
Each writes nothing, judged in this order:

| Case | Diagnostic |
| --- | --- |
| `shell` not `tauri` or `capacitor`; no `id`; no `name` and no `package.json` `name`; `to` naming no deployable; no `topology.ts`; `package.json` not a JSON object; the deployable or its `shells` not an object literal | E1052 |
| `id` not reverse-DNS | E1353 naming E1573 |
| no `client` deployable; several and no `to`; `to` naming a `node` or `static` one | E1359 (new) |
| the deployable already declares that shell | E1351 |

```
E1359 topology.ts:4:3 web and admin are client deployables; pass --to with one
  see: keel docs k.scaffold-shell
fail scaffold shell 1 errors
```
The other E1359 messages: `topology.ts has no client deployable for a tauri shell`, `api is a node deployable; a tauri shell needs a client one`. E1052 lines: `shell takes tauri or capacitor`, `shell needs --id, a reverse-DNS app id such as com.acme.shop`, `package.json has no name to title the shell; pass --name`, `--to names no deployable of topology.ts`. Each message is under 90 characters.

E1359 is new, the next free code in k.scaffold's block (E1351 to E1358 are taken; no E1359 anywhere in the tree). E1052 would name an input; this refusal has its cause in the project and two ways out. `keel explain E1359`:
```
E1359 scaffold shell has no one client deployable to take the shell
A native shell packages a client deployable (k.shell). The topology has none, several and --to names none, or --to names a node or static one. Nothing is written.
pass --to <client deployable>, or keel codemod place <module> --to <name> --adapter client
```
A second shell kind on the same deployable is not refused: `shells` then holds both, as k.shell allows. The same kind on another `client` deployable is not refused either.

### Determinism and idempotence
As every generator: the edit set is a function of the tree and the input (and the `@keel/scaffold` release, which fixes the versions). A second run is E1351. `--dry-run` prints the two diffs and writes nothing. The MCP tool takes the same input.

### The examples, replayed
`keel scaffold project native-tauri --workspace`, then `keel scaffold shell tauri --id dev.keel.nativetauri`: `topology.ts` and `package.json` are byte-identical to `examples/native-tauri`'s (the name default gives `Native Tauri`; the reflow gives the hand layout; `workspace:*` for the std package; `2.12.4` from the peer). The same for `native-capacitor` with `--id dev.keel.nativecapacitor`. Every hand edit in the table above is written by the command; what is left is the app's pages.

## Alternatives
- **A `--shell` flag on `scaffold project`** (the finding's wording). Rejected as the only form: a shell is added to existing apps too, and a project flag would be a second way. `scaffold project` then `scaffold shell` is two commands for a new app.
- **Versions as literals in `@keel/scaffold`**, as its project template holds `vite` and `vitest`. Rejected: a second hand-kept copy of what the std package pins, drifting silently; the generated file has one source.
- **`@keel/cli` depending on the std packages to read them.** A package cycle (`std-* -> cli -> std-*`).
- **Read the std package after it is installed: a second run, or `keel check --fix` applying E1572.** Two commands and an install between them, and E1572 covers plugins only.
- **Write the shell's generated files when the std package already resolves from the project.** The same input would give different edit sets by `node_modules`; and in the usual case it does not resolve. `keel build` writes them anyway before any native build.
- **Make the CLI and platform packages plugins (E1572).** `keel check` would then refuse an app whose `@tauri-apps/cli` range differs from Keel's pin, which builds fine. Not proposed; RFC 0198's E1575 entries for `@capacitor/core` and the platform packages remain a separate line.
- **A `keel` field in the std `package.json` instead of `peerDependencies`.** A Keel-only vocabulary for what npm already has a word for, which no package manager would check.
- **`--platform android|ios` for Capacitor.** Not proposed: the generated CI builds both, so an app with one platform package fails its other CI job.
- **A default `id`.** Rejected above; it is the one input a person must choose.

## For the operator
1. **`keel check` is not clean straight after the scaffold: E1159 until the install, then E1005 per shell file until `keel build`.** Recommended: accept; the std package cannot be read before it is installed, `keel build` writes every generated file anyway, and E1005 says `keel build rewrites it`. The other course writes the files when the package already resolves, so the edit set would depend on `node_modules`.
2. **The CLI and platform versions as optional `peerDependencies` of the std packages, copied into `@keel/scaffold` by `pnpm generate`.** Recommended: yes; one source per version, checked for drift, in npm's own vocabulary.
3. **`--id` required, no default.** Recommended: keep; it is the store identifier and the link scheme.
4. **Capacitor always gets both platform packages; no `--platform`.** Recommended: keep while the generated CI builds both.
5. **`@capacitor/core` written by the scaffold but still not checked by E1572 or E1575.** Recommended: an E1575 entry in a later line, as RFC 0198 proposed.

# RFC 0239: a library's own `./tools` in its own folder, its `./contract` file, its route components' ids, library capability names

Status: accepted (ADR-0261), accepted by the orchestrator on 2026-11-25, to be confirmed by the operator. Amends RFC 0163 (k.library: a library's files are read as the app's, D4) for three rules a library's own folder or files met that no author could satisfy, and renames two stdlib capabilities to the form E1607 already asks. Amends k.library-pack (Own folder, Conformance #6), k.contract (Contract, Rules E1513, Conformance #12), k.library (Ids, Conformance #19), std.tokens (Extension points, Conformance #11) and std.geo (Extension point, sim, Conformance #1). No new code; no glossary term.

## For the operator
1. **The own folder imports the library's own `./tools`.** Recommended: "read as an app holds the library installed" already says it; an app that installs a library lists it, so its formats, rules and config are in scope there. Reverse by keeping the own folder blind to its own registrations; then a library cannot use `formatLiteral` with its own format, and its own rules never run over its own files before an app does.
2. **A library's contract lives in the file its `./contract` entry names.** Recommended: a library has no `modules/<id>/` folder to put `<id>.contract.ts` in; its `exports` map is where it already names that file. Reverse by making libraries keep `src/<id>.contract.ts` by name; the `./contract` entry then has to agree with a second convention.
3. **A route component may write a literal id under the library's manifest id.** Recommended: a page has no caller to pass an `id`, and the manifest id is the one prefix no app module or other library holds (E1166). Reverse by giving route components an `id` prop the router fills; that is a router change for one library's sake.
4. **`geo` is `geo.position` and `tokens` is `tokens.opaque`.** Decided before this RFC (D178): E1607 holds for a library. The names say what each grants: the device's position, and minting and checking opaque tokens.

## Decisions
- D1: in a library's own folder (k.library-pack Own folder), `keel check` imports the library's own `./tools`, when it declares one, as an app listing the library imports it, and holds the library and the `@keel/*` packages its `package.json` names (`dependencies`, `peerDependencies`) in scope for formats and registered rules. A declared `./tools` that does not import is E1159 `<name> ./tools <target> does not import; build it` at `package.json`'s `"./tools"` key.
- D2: a library's module contract is the one `contract()` call in the file its `package.json` `exports["./contract"]` names (at `keel`, else the target Node imports), when that file is a `src/` `*.contract.ts` file; a target naming any other file (`dist/` alone, `src/index.ts`, an `unsafe/` file) holds no contract, each call in the library E1513 `contract() belongs in a src/*.contract.ts file, not <target>`. A `contract()` call in any other file of the library, a second `*.contract.ts` among them, is E1513 `contract() belongs in <path>`, `<path>` that file package-relative (`src/health.contract.ts`), or `the file a ./contract export names` when the library declares none. In that file a second call, an id other than the manifest `id` and an export not named `<id>` are E1513 as in an app module, their messages naming `<path>`.
- D3: a library's route component file is one a `manifest(` call of `@keel/router` in a file of the same library binds as an entry's `component`, that name a relative default import of the binding file, whose stem `public.exports` does not list and which no `exports` entry names; the binding file uses that name nowhere else, and no other file of the library imports, re-exports or `import()`s the page, so neither an app nor the library renders it twice. An element there may take a literal `id` (a string, or a template with no substitution, no spread after it) `<id>.<rest>`, `<id>` the library's manifest `id` and `<rest>` not empty; any other id there is judged by k.library Ids as before.
- D4: `@keel/std-geo` registers `geo.position`, `@keel/std-tokens` `tokens.opaque`; the accessors `geo(ctx)` and `tokens(ctx)` are unchanged.
- D5: the project a registered rule sees holds a library's root `module.ts` at `modules/<id>/module.ts`, beside its files at `modules/<id>/<f>`, so a rule finding a file's module by the `module.ts` whose folder prefixes its path (std-i18n's E2301, std-messages' four) reaches the library's `src/`.
- D6 (D184): no stdlib exemption from E2301: `@keel/std-i18n` is where `Intl` lives. It exports `collate`, `numberParts`, `formatUnit`, `formatList`, `formatDateTime` (its `timeZone` required) and `pluralCategories`, each the `Intl` call its std.i18n line names; std-money (`formatMoney`, its parsing marks), std-text (`compareText`), std-tables (its text sort), std-temporal (`formatDate`, `formatInstant`, `formatDuration`, `plainDateOf`) and std-messages (E2407) call them, with the same output. std-money's exact decimal formatting moves with it: `unsafe/decimalParts.ts` in std-i18n.
- D7 (D190): a rule a package registers through its `./tools` judges the modules and libraries that list the package, not the package's own folder: there `keel check` runs the rules of the `@keel/*` packages its `package.json` names and every kernel rule, and none its own `./tools` registers, whether a file imports the library by its name or by `../src`. The own `./tools` is still imported, so its formats hold there and a `./tools` that does not import is still E1159. A package testing its own primitive with generated or run-time inputs (arbitrary charts for `chart`'s throws, database names made per run) is not a consumer of itself. Not a stdlib exemption: it holds for every library.

## Problem
Lane 5 of `tasks/p1/std-on-the-format.md` left four packages waiting on the format:
1. **std-temporal, E1108 at `src/UTC.ts:5`.** `formatLiteral(TimeZone, "UTC")` names the library's own format. An app listing the package reports nothing there, as `keel check` imports the library's `./tools` and consults the registry for a package in scope. The own folder did neither: its manifest does not list the library itself, so `judgeFormat` never consulted the registry and `importDeps` never imported `./tools`. `keel pack` refused, and the package's `check` script ran no `keel check`. The same gap left the scope empty for every own-folder reading, so a dependency's rules (std-i18n's E2301 over std-temporal) never ran there either.
2. **std-health, E1513 at `src/health.contract.ts:4`.** k.contract allows a package's `./contract`, but `contractPlacement` accepted only `modules/<id>/<id>.contract.ts`, and a library file reads as `modules/<id>/src/health.contract.ts`. No library `./contract` could pass.
3. **std-health, E1161 at `src/HealthView.ts:6`.** k.library Ids asks every element's id to be built from the component's `id` prop, so a library widget rendered twice gets two ids. A route component has no caller: the router renders it, with `data`, once per page. std.health fixes its page's id `health.status`.
4. **std-tokens and std-geo, E1607.** `register("tokens")` and `register("geo")` are not `<id>.<lowerCamel>`.

## Proposal
- k.library-pack Own folder: "An app listing it would import its own `./tools`; so does the folder, and its rules, formats and config hold over its files, the `@keel/*` packages its `package.json` names in scope; one that does not import is E1159 (Package) at `package.json`'s `"./tools"` key." (D1)
- k.contract Contract: "(a library's: the one file its `package.json` `exports["./contract"]` names, at `keel`, else the target Node imports)". Rules E1513: "a `contract()` call outside `modules/<id>/<id>.contract.ts`, or in a library's file outside its `./contract` file (`<path>` package-relative, `the file a ./contract export names` when it declares none), a second one, …" (D2)
- k.library Ids: "An element of a route component file (one the library's `manifest(` of `@keel/router` binds as a `component`, a relative default import, its stem in no `public.exports` or `exports` target) may instead take a literal `id` `<id>.<rest>` (no spread after it), `<id>` the manifest `id`, `<rest>` not empty." (D3; "literal" is a string or a template with no substitution, as k.formats reads one.)
- std.geo Extension point: "registers capability `geo.position` (k.data E1607: `<id>.<name>`) with real, shell and sim implementations and exports its accessor `geo`. Modules that use it list `geo.position` in `capabilities` (k.module)."; sim: "(k.ctx derives it from the ctx seed and `geo.position`)". std.tokens Extension points: "Capability registry (k.ctx): `tokens.opaque` (k.data E1607: `<id>.<name>`), reached through `tokens(ctx)`." (D4)
- std.health: "`@keel/std-health` is a library (k.library): its manifest sits at the package root, `module.ts`, and its entries are `.`, `./Health`, `./routes`, `./contract` and `./module`."; "`HealthView`, the route's component, renders `data` as a `main` with the literal id `health.status` (k.library Ids)". Its `./*` pattern entry is removed (no import uses it, and `keel pack` reads every `keel` target as a file), and its `./module` entry has no `keel` condition (its target is no file under `src/` or `unsafe/`; the conformance suite imports it).

## Alternatives
- **A: register the own library by a synthetic app manifest listing it.** The reading would find the library under `node_modules/<name>` on disk, where an own folder has nothing; it needs a special path either way. Rejected for an explicit `own` option through `importDeps` and `check()`.
- **A: leave E1108 and move `UTC` into `unsafe/`.** E1108 is no lifted code, and the hole is the reading's: the same literal passes in every app. Rejected.
- **B: accept `src/<id>.contract.ts` by name.** A library's `exports` already says which file is `./contract`; a name convention beside it lets the two disagree, and a library could keep a contract file the entry does not ship. Rejected.
- **B: skip E1513 in library files.** A library could then declare contracts in any file, and k.contract's "declared once" would not hold. Rejected.
- **C: a literal id in any library file under `<id>.`.** One prefix per library keeps libraries apart, but a widget rendered twice on one page would repeat its ids, which k.library Ids exists to stop. Rejected for route components only.
- **C: the router passes the route id as `props.id`.** The page could then build `${props.id}`; a router API change for one rule, and a page's id would change with its route id. Rejected.
- **D: an exception for stdlib capability names.** Decided against (D178): a library gains no naming the app lacks.

## What a library can now do, and what bounds it
- **Own folder.** It now sees its own formats and its dependencies' rules, so more rules run there, not fewer: std-i18n's E2301 now reports a locale-taking `Intl` call in std-temporal's tests. Its own rules do not run there (D7): std-statecharts' E2755 and std-postgres' E2458 judge the libraries and apps that list them, not those packages' own tests. A format the library's `./tools` registers is consulted only for a `@keel/std-*` owner, as in an app (k.formats). A literal its format refuses is still E1108 (`does not parse`), and a library with no `./tools` registers nothing (`not one registered format`). Tested in `packages/cli/test/own-folder-tools.test.ts`, with an own rule that reports nothing in the folder and reports in an app listing the library.
- **Contract.** Exactly one file of a library can hold `contract()`, the one its `./contract` entry names; any other file is E1513, and one file holds one call with the manifest's id and export name. An app module keeps `modules/<id>/<id>.contract.ts`; a library view folder is keyed by the library's `package.json`, so no app module gains the library reading. Tested in `packages/check/test/library-contract.test.ts`.
- **Route ids.** Only a page the library's own route table binds, through a relative default import, can write a literal id, and only under its manifest id with a non-empty rest: `status`, `status.`, `statusx.page` and `shop.page` stay E1161. A page `public.exports` lists or an `exports` entry names stays E1161, so an app cannot import the page and render it twice under one id; an element in a helper file the page imports stays E1161; a spread after the literal stays E1161. E1166 keeps the prefix this library's: no app module and no other library holds its `id`. Tested in `packages/check/test/library-route-ids.test.ts`.

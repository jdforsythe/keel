# Testing and the ledger

**Rungs.** `proven` (type-level tests; closed-form `explore` over a store's whole space) · `exhaustive` (`explore` from a chosen state, payloads or depth) · `probabilistic` (schema-generated properties and `simulate`, with seed counts) · `example` (hand cases, golden flows) · `monitored` (std.monitor tallies from production, `.keel/monitored.json`). The ledger lists every public function and spec clause with its highest rung (`none` when no evidence exists) and evidence path.

**Kernel requirements.** Conformance green · property tests for every exported pure function · mutation score >= 80% for `schema`, `reactive`, `store`, `router`; >= 70% elsewhere · a11y assertions in `ui`, `runtime-dom` · output budgets in `cli`, `check`.

**Mutation.** `pnpm mutate [--filter=@keel/<pkg>]` (turbo; nightly in CI) or `pnpm --filter @keel/<pkg> mutate` runs Stryker (vitest runner, incremental) through the one runner `tooling/mutate.mjs` with the shared factory `tooling/stryker.mjs`; each package has a short `stryker.config.mjs`. Prints one trailer `ok|fail mutate <pkg> score 84.2% (threshold 80%)`; `KEEL_FORMAT=json` prints the NDJSON summary. The report is `packages/<pkg>/reports/mutation/mutation.json`; `pnpm ledger` (`keel ledger --write tooling/ledger/ledger.json`) turns it into one claim per mutated file, keyed by the sha256 of the source the report holds, and records the package score over them; a claim is fresh while the file on disk has that hash, and a changed file's claim is stale (W1714) and left out of the score. `keel ledger --diff` fails E1713 when a package's score over fresh claims is below its threshold. One mutation run holds a machine-wide lock (`os.tmpdir()/keel-mutate.lock`); a second `pnpm mutate` fails E0010, and `pnpm test` beside a live run prints W0012 and runs anyway. A run with no mutant finished for ten minutes ends E0011 with its results saved; run again to resume. `KEEL_MUTATE_CONCURRENCY=<n>` caps the test runner processes of a run on a shared machine. Thresholds are never lowered; a temporary floor needs a `TODO` and a backlog line.

**Root runs.** `pnpm test`, `pnpm check`, `pnpm build` and `pnpm coverage` run turbo through `tooling/turbo.mjs` with `--continue=dependencies-successful`: a failed task cancels no other, so every task reaches its own verdict. The run passes only when turbo exits 0 and its summary counts every task successful (`tooling/turbo-verdict.mjs`); a failing run prints, per failed task, its `fail ...` line and each failed test's line with its path from the repository (`T0001 packages/cli/test/a.test.ts:12:5 a > saves: Test timed out in 120000ms.`), or, for a task that named no test, its exit status and the last lines it wrote; it ends `E0005 turbo test failed: @keel/cli#test packages/cli/test/a.test.ts:12; @keel/std-postgres#test exit 137, no test named` and counts `failed` and `unfinished` tasks in its trailer, so a task that never finished is a failure, never a silent pass. A vitest fork worker that dies mid-run is a T0001 at each file it was running, naming the test, the signal or exit code and the worker's last fatal line (`T0001 test/a.test.ts:1:1 a > saves: worker killed by SIGABRT: FATAL ERROR: Reached heap limit`); a worker the watchdog killed has said so in its own line.

**Test concurrency.** `pnpm test` and `pnpm coverage` size themselves to the cores the machine's load leaves free when they start (`tooling/test-slots.mjs`): free cores are the cores less the one-minute load average, never under a quarter of the machine. Four tasks run at once while at least three quarters are free, three while half are, two below that, and each task's vitest uses at most one and a half times the free cores divided by the tasks, at least two workers (`KEEL_TEST_WORKERS`, read by `keelConfig`): on 16 cores, four tasks of six workers when quiet and two of three at load 16 or more. A starved worker runs its tests past their timeouts, and the other load on a shared machine is not the run's to lower, so a busy machine gets fewer workers that each keep a fair share of a core. A machine of four cores or fewer runs one task at vitest's own worker count. `--concurrency` or `KEEL_TEST_TASKS` sets the tasks and `KEEL_TEST_WORKERS` the workers of each, over the reckoning; a package config's own `maxWorkers` or `fileParallelism: false` wins over both.

**Wall-clock bounds.** Every package, app and scaffolded project builds its vitest config with `keelConfig` (`@keel/tooling/vitest-config`), which loads the watchdog setup file first in every worker. A watchdog thread beside the test's thread kills the worker process when a test (with its hooks) runs past `allowed × 2 + 30 s`, where `allowed` is its timeout plus two hook timeouts, so vitest's own timeout always fires first when the thread can yield; collection and the hooks between tests are bounded the same way with `allowed` at least 60 s, and a worker whose parent process is gone is killed at once. It prints one line, `T0001 conformance/x.test.ts:1:1 watchdog killed "<test>" after 81.2s (bound 80.0s)`, kills the worker's own child processes with it, and the run fails (a fork worker: vitest reports the worker error, exit 1; a thread pool: the whole vitest process dies, exit 137). A worker also kills its child processes, and theirs, on every other way it ends (exit, SIGTERM, SIGINT, SIGHUP, or vitest's death closing its channel), so a process a test started never outlives the worker; only a SIGKILL of the worker itself skips this. A mutation run is bounded by its budget below, and its whole Stryker process group by the stop and kill path. Under a mutation run the grace is ten minutes in place of 30 s (`tooling/mutate.mjs`): Stryker's own timeout ends a mutant whose test never finishes and counts it as detected, where a runner the watchdog killed first is a crash that Stryker runs again and reports as a runtime error. A property or simulation case declares no time of its own: `keelConfig` gives a test (`it` or `test`, `.only` and `.concurrent` too) that declares no options and whose callback calls `properties` or `simulate` from `@keel/testing` a timeout of 300 ms per run its calls name (a literal `runs`, else 100), never under the configured test timeout (`tooling/property-times.ts`), so a 100-run page property has 30 s and the watchdog bounds it from there. A call reached through a helper is not counted; such a test, and any other long one, passes its own timeout.

**Mutation run time.** No run is longer than its budget: `tooling/budgets.json` `mutate`, in minutes (`default` 30; a package may have its own entry). Stryker runs in its own process group (the core and its test runners). At the budget the runner sends that group one SIGINT, Stryker saves what it tested, and the run ends `fail mutate <pkg> time budget 30m reached at 5,120 of 8,634 mutants; run again to resume (1800.4s)`. The next run starts from the saved results, so a cold package is several bounded runs.
- Cache: `<git common dir>/keel-mutation/<pkg>.json` (`<app>.json` for an app: a unit with a `stryker.config.mjs` passing `{ mutate: APP_MUTATE }` from `tooling/stryker.mjs` mutates `modules/`), shared by every worktree of a clone, so one run of a package at a time per clone (`<pkg>.run.json` holds the claim); CI restores that directory and always saves it under a key of its own run. `<pkg>.times.json` beside it holds the dry run's time per test file. Stryker's incremental diff keys a result on the tests that cover the mutant (name, file and location; an added test reruns the survivors it covers, a changed or removed test reruns what it killed), so test changes need no cache care; a support file a test imports is not a test, and after changing one delete `<pkg>.json`.
- Order: test files run shortest first (`@keel/tooling/quick-first`), so a mutant a quick test kills never pays for a slow one. A package with its own vitest config for mutation runs names the sequencer there.
- Watch and stop: `pnpm mutate:status` prints one line per live run (`check 5,120 of 8,634 mutants, 3,100 reused, 41 a minute, about 14m left`); `pnpm mutate:stop` sends the one SIGINT to every live run's group and waits for it: `ok mutate-stop 1 stopped, 0 killed, no process left (14.2s)`. Stryker exits without saving on a second signal, so the budget, `mutate:stop` and Ctrl-C all claim the run file first and only the first one signals; never signal Stryker by hand. A clean stop saves the cache. A group still alive 120 s after its SIGINT is killed with SIGKILL (nothing saved), by `mutate:stop` or by the runner, whichever is waiting; every ending checks the group by PID and the summary line says `no process left` or names the pids left. `pnpm mutate:changed` ends its whole sequence on a stop: the live package's run stops and no further package starts.
- Per task: `pnpm mutate:changed [--base <ref>]` runs only packages and apps (`apps/<name>`) changed since `<ref>` (default `origin/master`), and only a unit's changed mutated files (`src` of a package, `modules` of an app) when nothing but prose changed beside them; the report keeps every other file's results. The whole run is the nightly one.
- Light run: `pnpm mutate:stale [--list] [--only <pkg>] [--chunk <n>] [--concurrency <n>] [--minutes <n>] [--missing]` runs the mutated files (`src`, or `modules` of an app) whose ledger claim is stale (the file on disk no longer hashes to the claim's `sha`); with `--missing` also the files that have no claim. Packages go one at a time, in chunks of `--chunk` files (default 4) through `tooling/mutate.mjs`, with `KEEL_MUTATE_CONCURRENCY` set to `--concurrency` (default 3) unless it is already set, so it can share a machine. `--minutes` (default 20) bounds the whole call: no chunk starts after it, and the live chunk is stopped as `pnpm mutate:stop` stops it, saving its results. One line per finished chunk, then `ok mutate-stale 12 files left in 3 packages; run again to resume`. `--list` prints the packages, files and chunks and starts nothing. It holds the same machine-wide lock.

**Coverage.** `pnpm coverage [--filter @keel/<pkg>]` (turbo, four packages at a time, one on a machine with four cores or fewer) runs each package's or app's tests once with v8 coverage through its `coverage` script (`tooling/coverage.mjs`, which sets `KEEL_COVERAGE=1` for `keelConfig`). It measures `src/` and `unsafe/` (`modules/` of an app), leaving out tests, `types/`, `*.d.ts` and the files `tooling/generate.mjs` writes, and writes `coverage/coverage-summary.json` and `coverage/meta.json` (commit, whether the package's files differed from it, time), git-ignored. One line per package: `ok coverage @keel/std-text 100% lines, 98% branches, 100% functions, 98.48% statements (5.1s)`. It sets no floor. Without `KEEL_COVERAGE` the test config has no coverage settings, so `pnpm test` is unchanged. A covered line or branch is one the tests executed, not behaviour they proved: an executed line can still be wrong, and mutation scores are the check on that.

**Ledger gate.** `pnpm ledger --diff` reports only what fell: a lowered rung, a higher unsafe count, a missed mutation threshold. `node tooling/ledger-fresh.mjs` (the last step of `pnpm check`) runs `keel ledger` over the tree and fails S0011 per difference from the committed `tooling/ledger/ledger.json`: an export or clause the file lists and the tree lacks (its source is gone), one the tree has and the file lacks, a different rung in either direction, a different unsafe count. `--a11y` (the CI `check` job, after `keel test` has written the apps' `reports/a11y.json`) also compares the WCAG items and the count of items per rung. The mutation section is not compared: its claims come from `reports/mutation/mutation.json`, which only mutation runs write; `pnpm ledger --diff` still checks its scores and thresholds, and `--diff` also catches a claim whose file changed. `--check` of the evidence report derives from the committed ledger file, so the two gates together hold the ledger file to the tree and the evidence file to the ledger file.

**Evidence report.** `pnpm evidence:report` writes `tooling/ledger/evidence.json`, committed, the one source a website or `tasks/COVERAGE.md` reads; its `schema` field is the shape's version. It holds the committed ledger's totals and clauses per spec section by rung, exports and route and WCAG items by rung; per package and app, test files and cases by kind (conformance, unit, other), property calls, files calling `simulate`, `explore` or `prove`, expected failures and skipped cases; mutation score, threshold, report date and stale claims; and coverage from `pnpm coverage`. A package with no run has `null` values and a `reason` (`no mutation run`, `not measured`); one with no local measurement keeps the committed entry, which names its commit. Keys are sorted, so a re-run on the same tree changes only `generatedAt`. A writing run exits 2 with S0010 per path when a spec section, a unit's `package.json` or a test file (tracked, or untracked and not ignored) differs from HEAD, so the data always describes a commit; `tooling/ledger/ledger.json` and the report's own outputs are not among them. `--allow-dirty` writes anyway and records those paths under `dirty` (absent otherwise), for local inspection; a committed file with `dirty` never passes `--check`. `--check` exits 2 with S0007 when the ledger and test parts differ from a fresh count (mutation and coverage need runs and are not compared); `--markdown` also rewrites `tasks/COVERAGE.md` from it. The counting rules are in the header of `tooling/evidence.mjs`. A test count is static, read from the files, not a run: a case may be skipped or failing. A rung of `example` means one passing test names the item, not a proof.

**CI.** `.github/workflows/ci.yml` is generated from `tooling/ci.source.json` and runs on pushes to `master` and on every pull request; a newer push cancels the run it supersedes. Every workflow installs pnpm with `pnpm/action-setup`, which reads the `packageManager` pin of the root `package.json` (`pnpm@11.17.0` and its sha512), and the `minimatch` and `qs` overrides live in `pnpm-workspace.yaml`, where that pnpm reads them. Each workflow declares `permissions: { contents: read }` at its top and every third-party action is pinned to a full commit SHA with its tag in a trailing comment; the one job that needs more, `sessions` in `sessions-nightly.yml`, adds `issues: write` itself. `TURBO_TOKEN` and `TURBO_TEAM` are set on the steps that run turbo (`pnpm check`, `pnpm build`, a test shard), not on the workflow. The `check` job runs `pnpm check`, then `keel test` in golden-2 (it writes the `reports/a11y.json` the ledger reads), `pnpm ledger --diff`, `node tooling/ledger-fresh.mjs --a11y` and `node tooling/ci-shards.mjs --verify`, which fails E0013 when a test task is in no shard or in two; it saves turbo's cache (`.turbo/cache`) for the jobs after it. `test-shard` is a matrix of jobs: `tooling/ci-shards.mjs <n>` deals every workspace package with a test task to one shard, heaviest first by the task's recorded seconds on the 2-core runner (a package without a record weighs its count of test files), and runs that shard's tasks through turbo one at a time, every task even after one fails, streaming their output. A package the script lists in `SPLIT` (`@keel/cli`) runs as several parts with vitest's `--shard=i/k`, each part in a different job, so every test file runs once; a package it lists in `WORKERS` (`@keel/cli`, two) runs its test files on at most that many vitest workers, so the builds its tests spawn do not wait on each other. It names each task as it starts, prints `file <path> <s>s` as each test file ends, ends with one line per task (result, seconds, peak memory of its processes, least free memory, its five slowest files) and prints each failed task's whole log; a cancelled step prints the task it cut and for how long. `node tooling/ci-shards.mjs --plan` prints the shards and their expected seconds; `--verify` also fails E0013 when a part of a split package is in no shard or in two, or two parts share one. `test` passes only when every shard passed. `built-smokes` follows `check` and runs `node tooling/smoke/restart.mjs` (a SIGKILLed golden-1 api restarts on its SQLite file with the stored board row byte-equal) `node tooling/smoke/workflow.mjs` (the removal workflow resumes after a SIGKILL inside a step and ends once) `node tooling/smoke/dev-signin.mjs` (`keel dev` on golden-2: a sign-up and a sign-in through the identity mount, then the account seen as signed in, a recipe posted and read back from the app's database in a PGlite folder, and the browser's request for each server-only file of the accounts routes answered with its stub) and, after installing Chromium, `node tooling/smoke/resume.mjs 3` (golden-2's seeded recipes still there after its `api` deployable restarts on the same PGlite folder; its recipe index, show, new-recipe and catalog pages and its `api` deployable's sign-in page, each resumed three times with no console warning or error, no element removed or added under an island root, focus, typed value and caret kept on the form pages and scroll on the others, and one interaction working) and `node tooling/smoke/household.mjs` (the built `apps/household` served on a free port and driven in Chromium and over HTTP: the guard redirect, the setup action, the list through the API and the loader, a cross-site write refused with 403, the document's stylesheet and a styled element's computed style, and a receipt the server rejects keeping its typed values with `aria-invalid` and the error text, with scripts on and off). `postgres` runs the std-db files that take `KEEL_TEST_POSTGRES_URL` against a Postgres 17 service, then builds and runs `node evals/tasks/golden-1-api/restartProof.ts` (the golden-1 `restartBuilt` proof on SQLite and on that service, without the eval's agent phase); `shell-tauri` and `shell-android` follow `check`, beside the shards, on `ubuntu-24.04` with `KEEL_ORIGIN=http://localhost:4182`: `shell-tauri` installs Tauri 2's Linux packages (WebKitGTK 4.1), WebKitWebDriver (`webkit2gtk-driver`), Rust stable and `tauri-driver` 2.1.0 (cached), runs `keel build --target tauri` in golden-1 (a debug binary; Cargo's registry and its target, kept in `.cargo-target` because each `keel build` empties `dist/<name>/`, are cached), then the shell replay, `node tooling/smoke/shell.mjs --shell tauri` under `xvfb-run`, and the same with `--session outbox`; `shell-android` sets up JDK 21 and runs `keel build --target capacitor --platform android` (Gradle `assembleDebug`, its caches kept) on the runner's Android SDK. `shell-tauri-macos` and `shell-ios` run beside them on `macos-26` under the same change filter, and only while the repository is public (`github.event.repository.private == false`), so a private repository uses no macOS minutes: `shell-tauri-macos` installs Rust stable, runs `keel build --target tauri` (Cargo's registry and `.cargo-target` cached) and `node tooling/smoke/shell-launch.mjs --shell tauri`; `shell-ios` runs `keel build --target capacitor --platform ios` (the runner's Xcode 26, an unsigned Simulator build; SwiftPM's cache kept, Xcode's derived data not, since it is under `dist/web/`, which each build empties) and `node tooling/smoke/shell-launch.mjs --shell ios --reboot`. Neither replays a session or drains an outbox: those run in `shell-tauri` on Linux only. Each shell job uploads its artifact for seven days. `build`, `budgets` and `golden-1-images` follow `test`. Every job on a push or pull request has a time limit. On a pull request that carries the `mutate` label `mutate-pr` mutates the changed packages; weekly `eval` runs the evals. The ordinary test suite also runs on macOS in its own workflow, `.github/workflows/test-macos.yml` (generated from `tooling/test-macos.source.json`), weekly on Mondays at 06:00 UTC and on `workflow_dispatch`, only while the repository is public: a `test-macos` matrix job on `macos-26` (`fail-fast` off, 60-minute limit, `contents: read`) runs `node tooling/ci-shards.mjs <n>` for each shard of the `test-shard` matrix, with no turbo cache from `check`; tests that take `KEEL_TEST_POSTGRES_URL` stay skipped. Mutation also has its own workflow, `.github/workflows/mutate-nightly.yml` (generated from `tooling/mutate-nightly.source.json`), at 03:00 UTC and on `workflow_dispatch`, on `master` only and in no pull-request run: a matrix job per package with a Stryker config, kernel and std (`fail-fast` off, 60-minute limit; the run's own budget is 30 minutes, `tooling/budgets.json`) restores `.git/keel-mutation` from the newest cache entry named `stryker-<pkg>-`, runs `pnpm --filter ./packages/<pkg> mutate`, saves the directory under `stryker-<pkg>-<run id>-<attempt>` even when the run was stopped at its budget, and uploads the package's `mutation.json`; a package that stops at its budget continues from its saved state the next night. A last `ledger` job (after every package job, whatever their results) puts the reports where the ledger reads them and runs `pnpm ledger` and `pnpm ledger --diff`.

**Shell replay.** `node tooling/smoke/shell.mjs --shell tauri [--binary <path>]` checks that a recorded session replayed inside golden-1's Tauri shell gives the server state its sim replay gives. It records a one-user session group under simulation (`apps/golden-1/test/shellSession.ts`: `openGroup` at seed 11 from the stored board Home with Milk and Bread, then open Home, mark Milk done, rename it Oat milk on its edit page, add Eggs) and replays it with `replayGroup`; it stores the same board in a fresh SQLite file, serves the built `api` over it on a free port behind a recording proxy at the build's `KEEL_ORIGIN`, starts the binary through `tauri-driver`, and applies the group file's inputs in the webview over WebDriver by element id: a link is followed by clicking it, a click or a checkbox change is an element click, an `input` clears the field and types the value, and the `submit` and route change a click makes are left to that click. After each input the proxy must go quiet; then the stored `api.board` and `replayGroup`'s, each with its log times left out and its minted ids, write keys and callers numbered by first appearance, must be equal. It prints one `ok` line; E0014 is a shell that could not be started or driven (the step, the requests and the last output lines follow on stderr), E0015 one line per difference. With `--session outbox` it records `apps/golden-1/test/shellOutboxSession.ts` instead: open Home, go offline, mark Bread done, add Butter, come back online. In the shell, going offline stops the api and closes the proxy, so `KEEL_ORIGIN` refuses connections and both writes wait in the `todos.outbox` outbox; coming back online waits until the app's store files (`keel.json`, `keel.b.json`) hold them, kills the app with SIGKILL, starts the api and the proxy again over the same SQLite file and starts the app in a new WebDriver session, whose layout drains the persisted outbox. The board must then equal `replayGroup`'s and the stored outbox be empty; `--drop-store` deletes the store files before the restart, a planted failure that must end in E0015. It needs Linux (`tauri-driver` has no macOS driver; macOS and iOS get the shell drive below), `webkit2gtk-driver`, `tauri-driver` and a display (`xvfb-run -a`), and stops the binary, the driver, the proxy and the api on every path.

**Shell launch.** `node tooling/smoke/shell-launch.mjs --shell tauri|ios` is the check for the shells whose webview no WebDriver reaches (WKWebView): golden-1's Tauri binary on macOS and its Capacitor app on the iOS Simulator. It makes no input in the page, so it checks no write, no outbox and no replay; the shell drive below does. It serves the built `api` over a fresh SQLite file behind a recording proxy at the build's `KEEL_ORIGIN`; the proxy adds one cookie, `keel-smoke=<random>; Max-Age=86400`, to each answer to a request that came without it. It starts the app (the binary with `HOME` in a temporary folder; on iOS it boots the newest available iPhone simulator when none is booted, installs the app fresh and runs `xcrun simctl launch`) and waits for `GET /api/lists` and then the layout's `GET /api/board/events` from the shell's native HTTP client (a `tauri-plugin-http` or `CFNetwork` agent), which shows that the webview loaded the entry and that `net` reached the server through the native client, and for a later request carrying the cookie. Then it kills the app (SIGKILL for Tauri; `simctl terminate`, a force-stop, on iOS; at once, or `--hold <s>` after the cookie was first sent) and starts it again: every request up to the event stream must carry the cookie. `--shell ios --reboot` then shuts the simulator down, boots it and starts the app a third time under the same rule. On iOS `HTTPCookieStorage` writes to disk a moment after it takes a cookie, so `KeelHttp` flushes the session's cookie store before a response that sets a cookie resolves, and the kill waits for nothing. `--drop-data` deletes the app's data before the second launch, a planted failure that must end in E0015. One `ok` line (`ok shell-launch 3 launches, 2 killed, 1 reboots`); E0014 is an app that could not be started or made no request, E0015 a request after a relaunch without the cookie. It runs on macOS only, takes about 2 s for Tauri and 60 s for iOS with a reboot, and leaves no app, proxy, api or simulator it booted running.

**Shell drive.** `node tooling/smoke/shell-drive.mjs --shell tauri|ios [--session replay|outbox]` is the shell replay for those two shells: the sessions, the served api and proxy, the comparison and the diagnostics of `shell.mjs`, with the inputs made through the accessibility tree. For Tauri on macOS it compiles `tooling/smoke/shell-drive/ax.swift` and makes each input with the accessibility API: an element is found by its DOM id (`AXDOMIdentifier`), a link by its URL, a click is `AXPress` and typed text a field's value set. The process that runs it needs the Accessibility permission, which it reads and never asks for; GitHub's macOS runners grant it to the shell of a workflow step. For iOS it builds the UI test in `tooling/smoke/shell-drive/ShellDrive.xcodeproj` (one UI test target, no app), runs it on the simulator against the installed app's bundle id, and hands it one command at a time over a loopback port: a tap, or a field tapped, cleared and typed into. WebKit on iOS gives the accessibility tree a role and a label and no DOM id, so each id of the session is named by role and label from the starting board (`labelled`, `linkTo` in `shellReplay.mjs`). `--session outbox` waits until the shell's store holds both queued writes (the store files under the temporary `HOME`; on iOS the app's preferences file), kills the app (SIGKILL, or `simctl terminate`), brings the server back and starts the app again; the board must equal `replayGroup`'s and the stored outbox be empty, and `--drop-store` is the planted failure that must end in E0015. One `ok` line (`ok shell-drive 6 actions, 2 queued, 1 killed, 1 restarts, 4 head`). It runs on macOS only, takes about 10 s per session for Tauri and about 60 s for iOS, shows the app window or the simulator while it runs, and leaves no app, driver, proxy, api or simulator it booted running.

**Conformance rules.** Written by `conformance-writer` from the spec section before implementation · imports public API only · lives in `packages/<pkg>/conformance/` · a claim that a call does not compile is a type case in `packages/<pkg>/unsafe/conformanceNegativeTypes.ts` (checked by `tsc`, never run), with its run-time half in the named conformance file · changes only via `rfc:NNNN` PRs (hook + CI).

**Evals.** `evals/` holds agent tasks with pass criteria. Metrics: converged ledger-green rate, iterations to green, tokens to green, unsafe count. Run weekly across >= 2 models; results committed to `evals/results/`.

**Harness.** `@keel/testing` addresses elements by id. A component is called `(props, ctx)`; the handle `render` returns exposes the `ctx` it ran on (the sim ctx made for it, or the one given as `ctx`), so a test drives `ctx.clock` and `ctx.net`. `find(id).state` and `a11y()` report `active` (the option `aria-activedescendant` names), `sort` and `checked` (`'mixed'` included). `fire` takes `keydown` with `key`, `shift`, `alt` and `mod`. `renderRoute(id, { url, user? })` opens a page from a path and query, signed in as `user` for the page's own requests; a harness keeps one cookie jar, so a cookie a response sets goes on the next request; under `keel test` the fetch classes are Node's; `location()` returns the history's length and `scrollY`. A widget's a11y claim holds only when every WCAG-mapped rule ran: an axe "needs review" result counts as not run, and the claim stays `none`.

**Determinism.** All kernel tests run under a seeded clock and PRNG via `ctx`. A test reading wall time fails lint.

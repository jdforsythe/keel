# Testing and the ledger

**Rungs.** `proven` (type-level tests that run, `expectTypeOf` or `assertType`; closed-form `explore` over a store's whole space) · `exhaustive` (`explore` from a chosen state, payloads or depth) · `probabilistic` (schema-generated properties and `simulate`, with seed counts) · `example` (hand cases, golden flows) · `monitored` (std.monitor tallies from production, `.keel/monitored.json`). The ledger lists every public function and spec clause with its highest rung (`none` when no evidence exists) and evidence path.

**Kernel requirements.** Conformance green · property tests for every exported pure function · mutation score >= 80% for `schema`, `reactive`, `store`, `router`; >= 70% elsewhere · a11y assertions in `ui`, `runtime-dom` · output budgets in `cli`, `check`.

**Mutation.** `pnpm mutate [--filter=@keel/<pkg>]` (turbo; nightly in CI) or `pnpm --filter @keel/<pkg> mutate` runs Stryker (vitest runner, incremental) through the one runner `tooling/mutate.mjs` with the shared factory `tooling/stryker.mjs`; each package has a short `stryker.config.mjs`. Prints one trailer `ok|fail mutate <pkg> score 84.2% (threshold 80%)`; `KEEL_FORMAT=json` prints the NDJSON summary. The report is `packages/<pkg>/reports/mutation/mutation.json`; `pnpm ledger` (`keel ledger --write tooling/ledger/ledger.json`) turns it into one claim per mutated file, keyed by the sha256 of the source the report holds, and records the package score over them; a claim is fresh while the file on disk has that hash, and a changed file's claim is stale (W1714) and left out of the score. `keel ledger --diff` fails E1713 when a package's score over fresh claims is below its threshold. One mutation run holds a machine-wide lock (`os.tmpdir()/keel-mutate.lock`); a second `pnpm mutate` fails E0010, and `pnpm test` beside a live run prints W0012 and runs anyway. A run with no mutant finished for ten minutes ends E0011 with its results saved; run again to resume. `KEEL_MUTATE_CONCURRENCY=<n>` caps the test runner processes of a run on a shared machine. Thresholds are never lowered; a temporary floor needs a `TODO` and a backlog line.

**Root runs.** `pnpm test`, `pnpm check`, `pnpm build` and `pnpm coverage` run turbo through `tooling/turbo.mjs` with `--continue=dependencies-successful`: a failed task cancels no other, so every task reaches its own verdict. The run passes only when turbo exits 0 and its summary counts every task successful (`tooling/turbo-verdict.mjs`); a failing run prints, per failed task, its `fail ...` line and each failed test's line with its path from the repository (`T0001 packages/cli/test/a.test.ts:12:5 a > saves: Test timed out in 120000ms.`), or, for a task that named no test, its exit status and the last lines it wrote; it ends `E0005 turbo test failed: @keel/cli#test packages/cli/test/a.test.ts:12; @keel/std-postgres#test exit 137: Error: listen EADDRINUSE 127.0.0.1:5432` (a task's last error line, else its last line, else `no test named`) and counts `failed` and `unfinished` tasks in its trailer, so a task that never finished is a failure, never a silent pass. A vitest fork worker that dies mid-run is a T0001 at each file it was running, naming the test, the signal or exit code and the worker's last fatal line (`T0001 test/a.test.ts:1:1 a > saves: worker killed by SIGABRT: FATAL ERROR: Reached heap limit`); a worker the watchdog killed has said so in its own line. A run vitest itself ends as failed or interrupted with no failed test (a filter that matches no file) is a T0001 too (`T0001 no test ran: vitest ended the run as failed`), and an interrupted run names each file it left unfinished.

**Test concurrency.** `pnpm test` and `pnpm coverage` size themselves to the cores the machine's load leaves free when they start (`tooling/test-slots.mjs`): free cores are the cores less the one-minute load average, never under a quarter of the machine. Four tasks run at once while at least three quarters are free, three while half are, two below that, and each task's vitest uses at most one and a half times the free cores divided by the tasks, at least two workers (`KEEL_TEST_WORKERS`, read by `keelConfig`): on 16 cores, four tasks of six workers when quiet and two of three at load 16 or more. A starved worker runs its tests past their timeouts, and the other load on a shared machine is not the run's to lower, so a busy machine gets fewer workers that each keep a fair share of a core. A machine of four cores or fewer runs one task at vitest's own worker count. `--concurrency` or `KEEL_TEST_TASKS` sets the tasks and `KEEL_TEST_WORKERS` the workers of each, over the reckoning; a package config's own `maxWorkers` or `fileParallelism: false` wins over both. A package's own run (`pnpm test` inside `packages/<pkg>`, no `KEEL_TEST_WORKERS`) sizes its vitest the same way, as one task from the load when it starts, at most one fewer worker than the cores (`tooling/vitest-config.ts`).

**Wall-clock bounds.** Every package, app and scaffolded project builds its vitest config with `keelConfig` (`@keel/tooling/vitest-config`), which loads the watchdog setup file first in every worker. A watchdog thread beside the test's thread kills the worker process when a test (with its hooks) runs past `allowed × 2 + 30 s`, where `allowed` is its timeout plus two hook timeouts, so vitest's own timeout always fires first when the thread can yield; collection and the hooks between tests are bounded the same way with `allowed` at least 60 s, and a worker whose parent process is gone is killed at once. It prints one line, `T0001 conformance/x.test.ts:1:1 watchdog killed "<test>" after 81.2s (bound 80.0s)`, kills the worker's own child processes with it, and the run fails (a fork worker: vitest reports the worker error, exit 1; a thread pool: the whole vitest process dies, exit 137). A worker also kills its child processes, and theirs, on every other way it ends (exit, SIGTERM, SIGINT, SIGHUP, or vitest's death closing its channel), so a process a test started never outlives the worker; only a SIGKILL of the worker itself skips this. A mutation run is bounded by its budget below, and its whole Stryker process group by the stop and kill path. Under a mutation run the grace is ten minutes in place of 30 s (`tooling/mutate.mjs`): Stryker's own timeout ends a mutant whose test never finishes and counts it as detected, where a runner the watchdog killed first is a crash that Stryker runs again and reports as a runtime error. A property or simulation case declares no time of its own: `keelConfig` gives a test (`it` or `test`, `.only` and `.concurrent` too) that declares no options and whose callback calls `properties` or `simulate` from `@keel/testing`, or fast-check's `assert`, a timeout of 300 ms per run its calls name (a literal `runs`, or `numRuns` for `assert`, in the call's options or in a top-level `const` object it names, else 100), never under the configured test timeout (`tooling/property-times.ts`), so a 100-run page property has 30 s and the watchdog bounds it from there. A call reached through a helper is not counted; such a test, and any other long one, passes its own timeout. A conformance case or hook that runs `check` from `@keel/check` in process, or a `keel` command (`run` from `@keel/cli`, or the binary as a child process), runs under a timeout of at least 30 s, and at least 60 s when the command runs app code under `keel test` (`keel test`, `keel session replay`, `minimize`, `to-test`): the timeout the case or hook passes when it passes one, else its package's `testTimeout` in `vitest.config.ts`, never vitest's 5 s default. A timeout a case adds takes that floor.

**Mutation run time.** No run is longer than its budget: `tooling/budgets.json` `mutate`, in minutes (`default` 30; a package may have its own entry). Stryker runs in its own process group (the core and its test runners). At the budget the runner sends that group one SIGINT, Stryker saves what it tested (a file it was cut in keeps a partial entry, which `pnpm mutate:stale` lists), and the run ends `fail mutate <pkg> time budget 30m reached at 5,120 of 8,634 mutants; run again to resume (1800.4s)`. The next run starts from the saved results, so a cold package is several bounded runs.
- Cache: `<git common dir>/keel-mutation/<pkg>.json` (`<app>.json` for an app: a unit with a `stryker.config.mjs` passing `{ mutate: APP_MUTATE }` from `tooling/stryker.mjs` mutates `modules/`), shared by every worktree of a clone, so one run of a package at a time per clone (`<pkg>.run.json` holds the claim); CI restores that directory and always saves it under a key of its own run. `<pkg>.times.json` beside it holds the dry run's time per test file. Stryker's incremental diff keys a result on the tests that cover the mutant (name, file and location; an added test reruns the survivors it covers, a changed or removed test reruns what it killed), so test changes need no cache care; a support file a test imports is not a test, and after changing one delete `<pkg>.json`.
- Shards: `pnpm --filter @keel/<pkg> mutate --shard i/N` (or `KEEL_MUTATE_SHARD=i/N`) runs shard `i` of `N` of the package's mutated files, the files of its Stryker `mutate` globs whose sha256 of the package-relative path, modulo `N`, is `i - 1`, so the split is the same on every machine and run. `node tooling/mutate-shard.mjs list i/N packages/<pkg>` prints a shard's files. A shard uses the package's cache file, so running every shard of a package in turn on one machine gives the whole report; `--shard` and `--mutate` are not given together (E0016). The trailer names the shard: `ok mutate check shard 3/8 score 74.1% (threshold 70%)`.
- Justified survivors: `packages/<pkg>/mutation-justified.json` (`apps/<name>/...` for an app) lists the Survived or NoCoverage mutants no test can or should kill, `{ justified: [{ file, mutator, original, replacement, reason, note }] }`: the file relative to the package, Stryker's mutator name, the source text the mutant replaces and its replacement (no line numbers; runs of white space count as one space), a `reason` of `equivalent`, `unreachable` or `performance`, and a one-sentence `note`. `keel ledger` reads a package's file: each claim carries `justified`, the survivors of its file an entry covers, and each package `killed`, `survived`, `noCoverage`, `justified` and `scoreJustified`, the score with the justified survivors left out of the count; E1725 is a malformed entry, or an entry that justifies no mutant of the report on disk (remove it). `pnpm evidence:report` lists `justified` and `scoreJustified` per unit, and `tasks/COVERAGE.md` shows them beside the score. Thresholds are judged on the plain score (k.ledger). `node tooling/mutate-justified.mjs [--only <pkg>]` checks one unit's file without a ledger run, an app's too, on the ledger's own reading of shape and mutant text: M0003 a malformed entry, M0002 an entry that matches no survivor of the report, W0016 no report to check against; the nightly `ledger` job runs it.
- Order: test files run shortest first (`@keel/tooling/quick-first`), so a mutant a quick test kills never pays for a slow one. A package with its own vitest config for mutation runs names the sequencer there.
- Load-time code: `ignoreStatic` leaves out a mutant reached only while a module loads, and a mutant a test reaches is run against that test alone. `@keel/std-sessions` loads its modules a second time inside its command tests (`keel session` imports the package's tools through its own loader), so a schema, a table or a pattern declared at the top of a module would be held against one command test that asserts nothing about it. Its mutation vitest config names a setup file (`packages/std-sessions/vitest.stryker.setup.mjs`) that, for a file under `test/unit/`, credits what the file reaches at import and in its hooks to every test of that file, and in a mutant run turns the mutant on before the file's imports run (Stryker turns it on after them): a unit file answers for the load-time code of the modules it imports. Code only a worker thread or a child process runs is NoCoverage until a test runs it in its own thread.
- Watch and stop: `pnpm mutate:status` prints one line per live run (`check 5,120 of 8,634 mutants, 3,100 reused, 41 a minute, about 14m left`); `pnpm mutate:stop` sends the one SIGINT to every live run's group and waits for it: `ok mutate-stop 1 stopped, 0 killed, no process left (14.2s)`. Stryker exits without saving on a second signal, so the budget, `mutate:stop` and Ctrl-C all claim the run file first and only the first one signals; never signal Stryker by hand. A clean stop saves the cache. A group still alive 120 s after its SIGINT is killed with SIGKILL (nothing saved), by `mutate:stop` or by the runner, whichever is waiting; every ending checks the group by PID and the summary line says `no process left` or names the pids left. `pnpm mutate:changed` ends its whole sequence on a stop: the live package's run stops and no further package starts.
- Per task: `pnpm mutate:changed [--base <ref>]` runs only packages and apps (`apps/<name>`) changed since `<ref>` (default `origin/master`), and only a unit's changed mutated files (`src` of a package, `modules` of an app) when nothing but prose changed beside them; the report keeps every other file's results. The whole run is the nightly one.
- Light run: `pnpm mutate:stale [--list] [--only <pkg>] [--chunk <n>] [--concurrency <n>] [--minutes <n>] [--missing]` runs the mutated files (`src`, or `modules` of an app) whose claim is stale (the file on disk no longer hashes to the claim's `sha`); a claim is the ledger's, or the one a report on disk holds (a report is newer than a ledger written before the run). A file whose report entry is partial is stale too: a run stopped at its bound saves a file's NoCoverage and Ignored mutants at once and drops the mutants still waiting, so the entry holds part of the file and a score over it is a score over that part. Each run reads the mutants of every reported file whose source is unchanged from Stryker's instrumenter (ignored ones included, a few seconds for the whole repo) and lists a file whose entry does not hold exactly those, by mutator, place and replacement: fewer, more or others. A partial entry stays in the report and the cache, so the next run reuses what it holds and tests the rest; a package's score is whole once `--list` names none of its files. A file with only a ledger claim and no report on disk is judged by its sha alone. With `--missing` also the files that have no claim and a mutant to run: a file Stryker's instrumenter finds no mutant in (types, re-exports, constants), or one whose report entry has only ignored mutants, is not listed. Packages go one at a time, in chunks of `--chunk` files (default 4) through `tooling/mutate.mjs`, with `KEEL_MUTATE_CONCURRENCY` set to `--concurrency` (default 3) unless it is already set, so it can share a machine. `--minutes` (default 20) bounds the whole call: no chunk starts after it, and the live chunk is stopped as `pnpm mutate:stop` stops it, saving its results. One line per finished chunk, then `ok mutate-stale 12 files left in 3 packages; run again to resume`. `--list` prints the packages, files and chunks and starts nothing. It holds the same machine-wide lock.

**Coverage.** `pnpm coverage [--filter @keel/<pkg>]` (turbo, four packages at a time, one on a machine with four cores or fewer) runs each package's or app's tests once with v8 coverage through its `coverage` script (`tooling/coverage.mjs`, which sets `KEEL_COVERAGE=1` for `keelConfig`). It measures `src/` and `unsafe/` (`modules/` of an app), leaving out tests (negative type tests, `*.test-d.*`, among them), `types/`, `*.d.ts` and the files `tooling/generate.mjs` writes, and writes `coverage/coverage-summary.json` and `coverage/meta.json` (commit, whether the package's files differed from it, time), git-ignored. One line per package: `ok coverage @keel/std-text 100% lines, 98% branches, 100% functions, 98.48% statements (5.1s)`. It sets no floor. Without `KEEL_COVERAGE` the test config has no coverage settings, so `pnpm test` is unchanged. A covered line or branch is one the tests executed, not behaviour they proved: an executed line can still be wrong, and mutation scores are the check on that.

**Run reports.** Every vitest run, `pnpm test`'s per package through the repository's reporter and `keel test`'s, writes the project's report to `reports/tests/run.json`, or `<i>-of-<k>.json` for a `--shard=<i>/<k>` part (k.test-run Run report): per test file the SHA-256 of its source, per test its location line and state. Reports are never committed; turbo's `test` task keeps them as outputs, so a cache hit restores the report of the run that made it.

**Ledger gate.** `pnpm ledger --diff` reports only what fell: a lowered rung, a higher unsafe count, a missed mutation threshold. `node tooling/ledger-fresh.mjs` (the last step of `pnpm check`) runs `keel ledger` over the tree and fails S0011 per difference from the committed `tooling/ledger/ledger.json` that the tree alone decides: an export or clause the file lists and the tree lacks (its source is gone), one the tree has and the file lacks, a different unsafe or negative type count. Clauses compare by item, `<section>#<key>` (k.ledger-items Clause key), and a message names a clause the tree holds by its position as well. Each E1732 (a `// Spec:` line that cites no clause) and E1733 (two bullets of one section with one normal form) that `keel ledger` reports fails it too. `--runs` (the CI `ledger` job, over every project's `reports/tests/*.json` and the apps' `reports/a11y.json`) also compares each item's rung in either direction, the WCAG items and the count of items per rung. A rung rests on a run: a test gives evidence only while its project's run report records it `passed` at the test file's current `sha` (k.ledger-items Run evidence), so locally `pnpm test` (each package's report) and `keel test` in each app and example come before `pnpm ledger`, `pnpm ledger --diff` and `--runs`; a project whose test files no report holds fresh is W1733. The mutation section is not compared: its claims come from `reports/mutation/mutation.json`, which only mutation runs write; `pnpm ledger --diff` still checks its scores and thresholds, and `--diff` also catches a claim whose file changed. `--check` of the evidence report derives from the committed ledger file, so the two gates together hold the ledger file to the tree and the evidence file to the ledger file.

**Evidence report.** `pnpm evidence:report` writes `tooling/ledger/evidence.json`, committed, the one source a website or `tasks/COVERAGE.md` reads; its `schema` field is the shape's version. It holds the committed ledger's totals and clauses per spec section by rung, exports, and page route and WCAG items by rung and per project; per package and app, test files and cases by kind (conformance, unit, other), property calls, files calling `simulate`, `explore` or `prove`, expected failures and skipped cases; mutation score, threshold, report date and stale claims; and coverage from `pnpm coverage`. A package with no run has `null` values and a `reason` (`no mutation run`, `not measured`); one with no local measurement keeps the committed entry, which names its commit. Keys are sorted, so a re-run on the same tree changes only `generatedAt`. A writing run exits 2 with S0010 per path when a spec section, a unit's `package.json` or a test file (tracked, or untracked and not ignored) differs from HEAD, so the data always describes a commit; `tooling/ledger/ledger.json` and the report's own outputs are not among them. `--allow-dirty` writes anyway and records those paths under `dirty` (absent otherwise), for local inspection; a committed file with `dirty` never passes `--check`. `--check` exits 2 with S0007 when the ledger and test parts differ from a fresh count (mutation and coverage need runs and are not compared); `--markdown` also rewrites `tasks/COVERAGE.md` from it. The counting rules are in the header of `tooling/evidence.mjs`. A test count is static, read from the files, not a run: a case may be skipped or failing. A rung of `example` means one passing test names the item, not a proof.

**CI.** `.github/workflows/ci.yml` is generated from `tooling/ci.source.json` and runs on pushes to `master` and on every pull request; a newer push cancels the run it supersedes. Every workflow installs pnpm with `pnpm/action-setup`, which reads the `packageManager` pin of the root `package.json` (`pnpm@11.17.0` and its sha512), and the `minimatch` and `qs` overrides live in `pnpm-workspace.yaml`, where that pnpm reads them. Each workflow declares `permissions: { contents: read }` at its top and every third-party action is pinned to a full commit SHA with its tag in a trailing comment; the one job that needs more, `sessions` in `sessions-nightly.yml`, adds `issues: write` itself. `TURBO_TOKEN` and `TURBO_TEAM` are set on the steps that run turbo (`pnpm check`, `pnpm build`, a test shard), not on the workflow. The `check` job runs `pnpm check` (whose `ledger-fresh` compares which items exist and the `unsafe` and `negativeTypes` counts, what the tree alone decides) and `node tooling/ci-shards.mjs --verify`, which fails E0013 when a test task is in no shard or in two; it saves turbo's cache (`.turbo/cache`) for the jobs after it. `test-shard` is a matrix of jobs: `tooling/ci-shards.mjs <n>` deals every workspace package with a test task to one shard, heaviest first by the task's recorded seconds on the 2-core runner (a package without a record weighs its count of test files), and runs that shard's tasks through turbo one at a time, every task even after one fails, streaming their output. Each shard then uploads the run reports its tasks wrote, every `reports/tests/*.json` outside `node_modules` in one tar with its paths, as `test-reports-<n>`. A package the script lists in `SPLIT` (`@keel/cli`) runs as several parts with vitest's `--shard=i/k`, each part in a different job, so every test file runs once; a package it lists in `WORKERS` (`@keel/cli`, two) runs its test files on at most that many vitest workers, so the builds its tests spawn do not wait on each other. It names each task as it starts, prints `file <path> <s>s` as each test file ends, ends with one line per task (result, seconds, peak memory of its processes, least free memory, its five slowest files) and prints each failed task's whole log; a cancelled step prints the task it cut and for how long. `node tooling/ci-shards.mjs --plan` prints the shards and their expected seconds; `--verify` also fails E0013 when a part of a split package is in no shard or in two, or two parts share one. `test` passes only when every shard passed. `ledger` follows the shards and `postgres`: it downloads every `test-reports-<n>` and unpacks each where its shard wrote it, then `test-reports-postgres`, std-postgres' whole run on Postgres 17, over that package's shard run, so the clauses that need a server have their evidence; it runs `keel test` in golden-1, golden-2, household, inspector, sessions, each example and each library (they write the `reports/a11y.json` the ledger reads), then `pnpm ledger --diff`, `node tooling/ledger-fresh.mjs --runs` (every rung, the WCAG items and the count per rung) and `pnpm evidence:report --check`, so every rung it judges rests on a run of the tree it checks (k.ledger-items Run evidence). `built-smokes` follows `check`, with a Postgres 17 service and `KEEL_TEST_POSTGRES_URL`: after `pnpm build` and installing Chromium (`playwright-core install --with-deps chromium`) it runs `keel test --e2e` (k.e2e) in `apps/golden-1` (a list and a todo through reloads, a SIGKILLed api restarted on its data, the removal workflow resumed after a SIGKILL inside a step on SQLite and on Postgres, two browsers' conflict and the monitor, the document policies), `apps/golden-2` (pages resumed in place with typing, caret, focus and scroll kept, `keel dev` sign-in through the identity mount, personal-data and secret canaries) and `apps/household` (sign-in, guards, the outbox offline, conflicts, the weekly run, the setup page resumed), then for each example `keel check`, `keel test`, `keel build` (a library's `keel pack --check`) and its `keel test --e2e` where it has e2e files; each project's `reports/tests/e2e.json` goes to the ledger job as the `test-reports-e2e` artifact. A failed e2e test prints its T0001 with the server's records and the paths of a screenshot and a trace under the project's `reports/e2e/`. `postgres` runs the std-db files that take `KEEL_TEST_POSTGRES_URL` against a Postgres 17 service, then builds and runs `node evals/tasks/golden-1-api/restartProof.ts` (the golden-1 `restartBuilt` proof on SQLite and on that service, without the eval's agent phase); `shell-tauri` and `shell-android` follow `check`, beside the shards, on `ubuntu-24.04` with `KEEL_ORIGIN=http://localhost:4182`: `shell-tauri` installs Tauri 2's Linux packages (WebKitGTK 4.1), WebKitWebDriver (`webkit2gtk-driver`), Rust stable and `tauri-driver` 2.1.0 (cached), runs `keel build --target tauri` in golden-1 (a debug binary; Cargo's registry and its target, kept in `.cargo-target` because each `keel build` empties `dist/<name>/`, are cached), then the shell replay, `node tooling/smoke/shell.mjs --shell tauri` under `xvfb-run`, and the same with `--session outbox`; `shell-android` sets up JDK 21 and runs `keel build --target capacitor --platform android` (Gradle `assembleDebug`, its caches kept) on the runner's Android SDK. `shell-tauri-macos` and `shell-ios` run beside them on `macos-26` under the same change filter, and only while the repository is public (`github.event.repository.private == false`), so a private repository uses no macOS minutes: `shell-tauri-macos` installs Rust stable, runs `keel build --target tauri` (Cargo's registry and `.cargo-target` cached) and `node tooling/smoke/shell-launch.mjs --shell tauri`; `shell-ios` runs `keel build --target capacitor --platform ios` (the runner's Xcode 26, an unsigned Simulator build; SwiftPM's cache kept, Xcode's derived data not, since it is under `dist/web/`, which each build empties) and `node tooling/smoke/shell-launch.mjs --shell ios --reboot`. Neither replays a session or drains an outbox: those run in `shell-tauri` on Linux only. Each shell job uploads its artifact for seven days. `build`, `budgets` and `golden-1-images` follow `test`. Every job on a push or pull request has a time limit. On a pull request that carries the `mutate` label `mutate-pr` mutates the changed packages and runs `pnpm ledger --diff` over the shards' and `postgres`' run reports; weekly `eval` runs the evals. The ordinary test suite also runs on macOS in its own workflow, `.github/workflows/test-macos.yml` (generated from `tooling/test-macos.source.json`), weekly on Mondays at 06:00 UTC and on `workflow_dispatch`, only while the repository is public: a `test-macos` matrix job on `macos-26` (`fail-fast` off, 60-minute limit, `contents: read`) runs `node tooling/ci-shards.mjs <n>` for each shard of the `test-shard` matrix, with no turbo cache from `check`; tests that take `KEEL_TEST_POSTGRES_URL` stay skipped. Mutation also has its own workflow, `.github/workflows/mutate-nightly.yml` (generated from `tooling/mutate-nightly.source.json`), at 03:00 UTC and on `workflow_dispatch`, on `master` only and in no pull-request run: a matrix job per package with a Stryker config, kernel and std (`fail-fast` off, 60-minute limit; the run's own budget is 30 minutes, `tooling/budgets.json`) restores `.git/keel-mutation` from the newest cache entry named `stryker-<pkg>-`, runs `pnpm --filter ./packages/<pkg> mutate`, saves the directory under `stryker-<pkg>-<run id>-<attempt>` even when the run was stopped at its budget, and uploads the package's `mutation.json`; a package that stops at its budget continues from its saved state the next night. `@keel/check` is too large for one budget and runs instead as `mutate-check`, a matrix of eight shards: shard `i` runs `pnpm --filter ./packages/check mutate --shard i/8`, restores and saves under `stryker-check-shard-<i>-of-8-` (falling back to the newest `stryker-check-` entry) and uploads its report as `check-shard-<i>-of-8`. A last `ledger` job (after every package and shard job, whatever their results) puts the reports where the ledger reads them, merges check's shard reports into `packages/check/reports/mutation/mutation.json` (`node tooling/mutate-shard.mjs merge <out> <dir>`: each file's results from the shard that owns it; W0015 names a shard that wrote no report, whose files keep their committed claims), runs `pnpm test` for the run reports and `keel test` in the apps and examples for their `reports/a11y.json`, then `pnpm ledger` and `pnpm ledger --diff`.

**Shell replay.** `node tooling/smoke/shell.mjs --shell tauri [--binary <path>]` checks that a recorded session replayed inside golden-1's Tauri shell gives the server state its sim replay gives. It records a one-user session group under simulation (`apps/golden-1/test/shellSession.ts`: `openGroup` at seed 11 from the stored board Home with Milk and Bread, then open Home, mark Milk done, rename it Oat milk on its edit page, add Eggs) and replays it with `replayGroup`; it stores the same board in a fresh SQLite file, serves the built `api` over it on a free port behind a recording proxy at the build's `KEEL_ORIGIN`, starts the binary through `tauri-driver`, and applies the group file's inputs in the webview over WebDriver by element id: a link is followed by clicking it, a click or a checkbox change is an element click, an `input` clears the field and types the value, and the `submit` and route change a click makes are left to that click. After each input the proxy must go quiet; then the stored `api.board` and `replayGroup`'s, each with its log times left out and its minted ids, write keys and callers numbered by first appearance, must be equal. It prints one `ok` line; E0014 is a shell that could not be started or driven (the step, the requests and the last output lines follow on stderr), E0015 one line per difference. With `--session outbox` it records `apps/golden-1/test/shellOutboxSession.ts` instead: open Home, go offline, mark Bread done, add Butter, come back online. In the shell, going offline stops the api and closes the proxy, so `KEEL_ORIGIN` refuses connections and both writes wait in the `todos.outbox` outbox; coming back online waits until the app's store files (`keel.json`, `keel.b.json`) hold them, kills the app with SIGKILL, starts the api and the proxy again over the same SQLite file and starts the app in a new WebDriver session, whose layout drains the persisted outbox. The board must then equal `replayGroup`'s and the stored outbox be empty; `--drop-store` deletes the store files before the restart, a planted failure that must end in E0015. It needs Linux (`tauri-driver` has no macOS driver; macOS and iOS get the shell drive below), `webkit2gtk-driver`, `tauri-driver` and a display (`xvfb-run -a`), and stops the binary, the driver, the proxy and the api on every path.

**Shell launch.** `node tooling/smoke/shell-launch.mjs --shell tauri|ios` is the check for the shells whose webview no WebDriver reaches (WKWebView): golden-1's Tauri binary on macOS and its Capacitor app on the iOS Simulator. It makes no input in the page, so it checks no write, no outbox and no replay; the shell drive below does. It serves the built `api` over a fresh SQLite file behind a recording proxy at the build's `KEEL_ORIGIN`; the proxy adds one cookie, `keel-smoke=<random>; Max-Age=86400`, to each answer to a request that came without it. It starts the app (the binary with `HOME` in a temporary folder; on iOS it boots the newest available iPhone simulator when none is booted, installs the app fresh and runs `xcrun simctl launch`) and waits for `GET /api/lists` and then the layout's `GET /api/board/events` from the shell's native HTTP client (a `tauri-plugin-http` or `CFNetwork` agent), which shows that the webview loaded the entry and that `net` reached the server through the native client, and for a later request carrying the cookie. Then it kills the app (SIGKILL for Tauri; `simctl terminate`, a force-stop, on iOS; at once, or `--hold <s>` after the cookie was first sent) and starts it again: every request up to the event stream must carry the cookie. `--shell ios --reboot` then shuts the simulator down, boots it and starts the app a third time under the same rule. On iOS `HTTPCookieStorage` writes to disk a moment after it takes a cookie, so `KeelHttp` flushes the session's cookie store before a response that sets a cookie resolves, and the kill waits for nothing. `--drop-data` deletes the app's data before the second launch, a planted failure that must end in E0015. One `ok` line (`ok shell-launch 3 launches, 2 killed, 1 reboots`); E0014 is an app that could not be started or made no request, E0015 a request after a relaunch without the cookie. It runs on macOS only, takes about 2 s for Tauri and 60 s for iOS with a reboot, and leaves no app, proxy, api or simulator it booted running.

**Shell drive.** `node tooling/smoke/shell-drive.mjs --shell tauri|ios [--session replay|outbox]` is the shell replay for those two shells: the sessions, the served api and proxy, the comparison and the diagnostics of `shell.mjs`, with the inputs made through the accessibility tree. For Tauri on macOS it compiles `tooling/smoke/shell-drive/ax.swift` and makes each input with the accessibility API: an element is found by its DOM id (`AXDOMIdentifier`), a link by its URL, a click is `AXPress` and typed text a field's value set. The process that runs it needs the Accessibility permission, which it reads and never asks for; GitHub's macOS runners grant it to the shell of a workflow step. For iOS it builds the UI test in `tooling/smoke/shell-drive/ShellDrive.xcodeproj` (one UI test target, no app), runs it on the simulator against the installed app's bundle id, and hands it one command at a time over a loopback port: a tap, or a field tapped, cleared and typed into. WebKit on iOS gives the accessibility tree a role and a label and no DOM id, so each id of the session is named by role and label from the starting board (`labelled`, `linkTo` in `shellReplay.mjs`). `--session outbox` waits until the shell's store holds both queued writes (the store files under the temporary `HOME`; on iOS the app's preferences file), kills the app (SIGKILL, or `simctl terminate`), brings the server back and starts the app again; the board must equal `replayGroup`'s and the stored outbox be empty, and `--drop-store` is the planted failure that must end in E0015. One `ok` line (`ok shell-drive 6 actions, 2 queued, 1 killed, 1 restarts, 4 head`). It runs on macOS only, takes about 10 s per session for Tauri and about 60 s for iOS, shows the app window or the simulator while it runs, and leaves no app, driver, proxy, api or simulator it booted running.

**Conformance rules.** Written by `conformance-writer` from the spec section before implementation · imports public API only · lives in `packages/<pkg>/conformance/` · a claim that a call does not compile is an expectation in a negative type test, `packages/<pkg>/conformance/<name>.test-d.ts` (k.unsafe: type-checked by the package's `check`, never run, no rung), with its run-time half in the named conformance file · changes only via `rfc:NNNN` PRs (hook + CI).

**Evals.** `evals/` holds agent tasks with pass criteria. Metrics: converged ledger-green rate, iterations to green, tokens to green, unsafe count. Run weekly across >= 2 models; results committed to `evals/results/`.

**Harness.** `@keel/testing` addresses elements by id. A component is called `(props, ctx)`; the handle `render` returns exposes the `ctx` it ran on (the sim ctx made for it, or the one given as `ctx`), so a test drives `ctx.clock` and `ctx.net`. `find(id).state` and `a11y()` report `active` (the option `aria-activedescendant` names), `sort` and `checked` (`'mixed'` included). `fire` takes `keydown` with `key`, `shift`, `alt` and `mod`, sent to the focused element as a key press is (E1719 when focus is elsewhere and the target cannot take it), and `change` with `value` as a pick in a `<select>`: `input` then `change` at the select. A `render`, `renderRoute` or `resumeDocument` handle made while a test runs is disposed when that test ends, passed or failed, so no element or seeded store outlives it; one made in `beforeAll` or at module scope needs `dispose()`. `keel test` prints an error outside any test as one T0001 `uncaught: <first line>` at its first app frame. A failed test's T0001 `fix` holds the failure's first line when the 89-character message cut it, and for a fast-check failure its seed and path, counterexample, shrink count and error line, each at most 512 characters. `renderRoute(id, { url, user? })` opens a page from a path and query, signed in as `user` for the page's own requests; a harness keeps one cookie jar, so a cookie a response sets goes on the next request; under `keel test` the fetch classes are Node's; `location()` returns the history's length and `scrollY`. A widget's a11y claim holds only when every WCAG-mapped rule ran: an axe "needs review" result counts as not run, and the claim stays `none`.

**Time scale.** `KEEL_TEST_TIME_SCALE=<n>` (a positive number, default 1; `tooling/test-time.ts`) multiplies every time bound a test states itself: every bound a test file passes to vitest (the argument after the name or the callback of `it`, `test`, `describe` and `suite`, and after a hook's callback, a number or an options object's `timeout`, rewritten by the `tooling/test-times.ts` transform whatever form it takes, but for one that calls `testTime` or `fixedTime` itself, which scales its own parts: `fixedTime(10_000) + testTime(20_000)` for a test that waits out a 10 s protocol timeout), and each bound a test or support file sets itself through `testTime(ms)`. The built smokes of `built-smokes` (`tooling/smoke/`) bound a server start, a build, a `keel dev` reload, a page navigation or a render, all the machine's own work, so their limits and waits go through `fixedTime` and a loaded machine does not cut them; each is the time that work takes on CI's runner with the margin the file's comment states. The property-time transform's 300 ms per run, the watchdog's 30 s grace, its 60 s collection allowance (a worker's start, a file's import, the hooks between tests) and the 5 s bound on each of its own setup-file hooks are fixed time too, each the machine's own work (CPU, rendering, a cold import): a cold file under a loaded machine takes as long at scale 0.1 as at 1, so a test's `allowed` scales (a hang is killed at `allowed × 2 + 30 s`, `allowed` scaled) and the machine's work does not. A time that is an input to the code under test (a contract's or client's `timeout`, a lease, a wait a workflow takes, a quiet window a smoke watches) goes through `fixedTime(ms)` and does not scale. A run that passes with every bound divided by N passes on a machine N times slower, so `KEEL_TEST_TIME_SCALE=0.1` finds here the bounds a slow runner would cut. `keelConfig`'s `testTimeout` and `hookTimeout` (the defaults 5 s and 10 s, or a package's own) are not scaled: they bound the machine's own work, a cold import, a compile, a render, and a run at scale 0.1 keeps them, so a hang in a default-bound test is killed at 5 s × 2 + 30 s = 40 s. A bound a test states over a build, a spawned process or a cold import goes through `fixedTime`; only a wait the test chose goes through `testTime`. A bound states the work it bounds: a test whose work outgrows the default passes its own timeout, derived from that work in the test (a time per value or per password hash, measured here, with the margin it allows). A folder whose vitest config is not `keelConfig` (a library on the library format, run by `keel test` under its own config) has no property-time transform, so each property or simulation test there passes its own timeout, 300 ms a run; structure-lint S0017 refuses one that does not. Structure-lint S0016 refuses a time written as a number in test code that goes through neither helper; a conformance file's are listed, path and text, in `tooling/hard-times-conformance.json` with the helper each needs, until the conformance-writer moves them. A scale only shrinks the bounds a test states, so the gate's `slow-shards` job (`docs/GATE.md`, Slow machine) also runs the shards at scale 1 in a Linux container limited to 2 CPUs, which finds a default bound, a tight margin or a real timer that a fast core never reaches.

**Determinism.** All kernel tests run under a seeded clock and PRNG via `ctx`. A test reading wall time fails lint. A fast-check run (`assert`, `check`, `sample`, `statistics`) names its seed, in its options, an options `const` or a top-level `configureGlobal`, else structure-lint fails it with S0015 (package files, conformance included, tooling and eval files, and every app's and example's test files), so a property draws the same input on every run and a failure replays. A format value in a fixture is `formatLiteral(Format, 'text')` from `@keel/schema`; `keel check` reads test files for it too (E1108). `keel test` runs test files in forked processes and starts each with `KEEL_TEST=1` and `UV_THREADPOOL_SIZE=1`; there `simulate`'s law check is on, replaying each passing run after the last and comparing traces (k.drive-law), and a scenario that counts its own calls opts out with `law: false`.

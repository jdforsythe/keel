# ADR-0126: `@keel/std-credentials` hashes passwords and mints expiring tokens through a capability; the scrypt cost rises from a 2^17 floor by `std` config; a sim's strings and tokens are marked and refused (RFC 0103)

**Status:** accepted (user, 2026-11-16: the accessor, the error Result, the cost setting, the token API with built-in expiry; build now, the kernel RFC for action output and `bearer` follows); superseded in part by ADR-0163 (2026-11-18): password hashing, `Hashed`, the cost config and the derivation queue are removed, and the package is `@keel/std-tokens` with the accessor `tokens(ctx)`.

**Context.** k.privacy tells an app to keep a credential as a salted `scrypt` hash written by hand: `node:crypto` `scrypt`, a `ctx.random.id` salt, `timingSafeEqual` (ADR-0123). No package has a helper. The hand-written form goes wrong in ordinary ways. Node's `scryptSync` defaults to N = 2^14, where OWASP asks for 2^17 (to be re-checked at build); N = 2^17 throws until `maxmem` is raised; the sync call blocks the event loop for 163 ms; `timingSafeEqual` throws on unequal lengths; the parameters are not stored, so they can never rise; and an unknown account answers faster than a known one. The file also holds `reveal` beside `tx`, and E1112 ends a flow at any call, so it cannot tell `scrypt` from MD5 or a random salt from a constant one. Nothing mints a token with a digest to store. `ctx.random` has `id` and `float` and no bytes method; a real `id` is `crypto.randomUUID()` and a real `float` is `Math.random()`; k.ctx does not say where a real `id` comes from. Node 22, the supported floor and the deploy image, has `scrypt` and no Argon2. `KEEL_SECRET` signs the caller cookie inside `createApp`, and no accessor gives it or any environment value to a package. A module manifest's `std` entry is the existing place for a package's setting, checked against a registered schema (E1158). The kernel's durations are milliseconds as numbers, and `ctx.clock.now()` is the one clock, which a sim moves only by `advance`. An action returns `Href | null`, and no request header reaches a guard, loader or action. Measured: one derivation at `ln` 17 takes 163 to 175 ms and 128 MiB, and each step of `ln` doubles both; eight at once take 594 MiB and every thread of the pool; a token check takes 0.6 microseconds.

**Decision.**
- D1: a stdlib package with two spec sections, std.credentials and std.tokens, and three entries. `@keel/std-credentials` exports the schemas `Hashed`, `Digested` and `CredentialsConfig` and is client-safe. `@keel/std-credentials/server` exports the accessor `credentials` and type `Hasher`, Node only. `@keel/std-credentials/tools` registers E2201 and E2202. A module that uses it lists it in `deps`. The package calls `reveal` once; k.reveal is unchanged.
- D2: `credentials(ctx).hash(secret: Secret<string>)` resolves `Result<Hashed, credentials.length | keel.busy>`. `credentials(ctx).verify(secret, stored: Hashed | undefined)` resolves `Result<{ rehash: boolean }, credentials.mismatch | credentials.malformed | keel.busy>`. A wrong secret is `err`. `stored` `undefined` costs one derivation and is `credentials.mismatch`. Each error is one constant per code, reason and limit, and nothing throws.
- D3: `scrypt` with r = 8, p = 1 and N = 2^`ln`, a 16-byte salt, a 32-byte key, stored as `$scrypt$ln=<ln>,r=8,p=1$<salt>$<key>`. `ln` is 17 by default and at the least. An app raises it with `std: { '@keel/std-credentials': { ln } }` in a module manifest, an integer 17 to 20; a ctx uses the highest any module sets; a value outside the range is E1158 at `keel check`, `keel build` and startup. `verify` reads `ln` 14 to 20, `r` 8, `p` 1 to 5, and answers `rehash: true` for a string below the ctx's cost: a lower `ln`, a salt under 16 bytes or a key under 32. Keys are compared with `timingSafeEqual`. The input is NFKC UTF-8 of 1 to 1,024 bytes. `Hashed` checks the shape only.
- D4: the package registers capability `credentials`. Real and shell draw every salt and token from `randomBytes`; `ctx.random` is not used. Sim draws them from the capability seed and marks what it makes: `$scrypt-sim$ln=<ln>,...`, derived at N = 2^4 under the ctx's `ln` as a label, `keelsim_` tokens and `$sha256-sim$` digests. A real or shell ctx refuses each.
- D5: under a real ctx the bounds follow the ctx's `ln`: 2 derivations at once at 17 and 18, 1 at 19 and 20, with 16, 8, 4 or 2 waiting in call order. A call past that resolves `keel.busy`, a 503 from an action.
- D6: E2201 reports the server entry imported outside a `*.server.ts` file. E2202 reports it in a module a deployable other than `node` serves, which covers `client`, `static` and shells.
- D7: tokens, with expiry built in.
  - `credentials(ctx).mint(options: { ttl: number | null })` resolves `Result<{ token: Secret<string>, id: string, digest: Digested, expiresAt: number | null }, credentials.ttl>`. `ttl` is required: milliseconds, an integer from 60,000 to 31,536,000,000, or `null` for a token that does not expire; any other value is `err` `credentials.ttl`.
  - The token is `keel_<16 hex id>_<64 hex secret>`, 256 random bits of secret. The digest is SHA-256 of the token's text with no key, and it carries the expiry: `$sha256$exp=<ms>$<base64>`, or `$sha256$<base64>` with none. `expiresAt` is `ctx.clock.now()` plus `ttl`; `mint` returns it for display and clean-up, and `check` reads the expiry from the digest alone.
  - `credentials(ctx).check(token, find)` reads the id from the presented `Secret`, calls `find(id)` for the row (an object with `digest: Digested`), compares in constant time, then reads `ctx.clock.now()`, and returns `ok(row)`. A matching token with `now >= expiresAt` is `err` `credentials.expired`; at exactly the expiry instant it is expired. A value that is not a token, an unknown id and a wrong secret are `credentials.mismatch`, also against an expired row, so `credentials.expired` is answered only to the real token. An unreadable digest is `credentials.malformed`.
  - Both methods are synchronous. `mint` takes no secret, so no stored digest comes from a secret the package did not make. The app reveals a minted token once to send it; E1112 reports that value in `tx`, storage, a log or a throw and is silent on a `service` argument or a returned value.
- D8: k.privacy, the E1112 explain row, the `keel-compliance` and `keel-storage` skills, the threat model and COMPLIANCE name `credentials(ctx)` in place of the hand-written form.
- D9: build now. A token made by a write leaves through a `service` call and is presented as an action's input. The kernel RFC that lets an API action return data and hands server code a `bearer` secret follows as its own RFC.

**Alternatives.**
- Free functions, or `verify` resolving `ok({ valid })`. Rejected; the accessor and the `err` are approved.
- A plain `string` out. Rejected: the fields would be `s.string()`, with no generator and no type for the methods to ask for.
- The cost as a call argument, an environment key or a `register` option. Rejected: two call sites could disagree, an environment value is not checked until start and can differ by deployable, and a factory gets the seed only.
- `r` or `p` settable, or a cost under 2^17. Rejected: `p` adds time without memory, no published set moves `r`, and the floor is the user's.
- An error when two modules set different `ln`. Rejected: the higher one is a safe answer and needs no code.
- Salt from `ctx.random.id`, or a kernel `ctx.random.bytes`. Rejected: 122 bits and a promise k.ctx does not make in the first case; `id` is the one way to mint a token and the registry already gives a source in the second.
- One form in every mode at full cost. Rejected: a seeded salt would be valid in production, and each test sign-in would cost 170 ms and 128 MiB.
- Argon2id. Rejected for now: not in Node 22 without a native dependency. The stored form has room for it.
- `digest(secret)` for any secret, or scrypt for tokens. Rejected: a password could take the fast path in the first case, and every API request would pay 170 ms in the second.
- HMAC-SHA-256 keyed with `KEEL_SECRET`. Rejected: no accessor, and rotating the cookie key would end every token.
- The digest as the lookup key, or two calls `tokenId` and `check(token, digest)`. Rejected: a search by a value derived from the secret in the first case; a second row read and an `undefined` to narrow in the second.
- The expiry as a field the app stores beside the digest. Rejected: a row schema, a transaction or a `find` that leaves it out compiles and gives a token that never expires.
- `ttl` as a std.temporal `Duration`, optional, or throwing when out of range. Rejected: a literal needs a parse and the package would gain two dependencies; an omitted key would make a reset token that never expires; a lifetime can come from a form, and an invalid input is an `err`.
- One code for an expired and a wrong token. Rejected: the user chose a distinct code, and it is answered only to the real token.
- One spec section. Rejected: 2,497 tokens against 1,500.

**Consequences.**
- Storing a password is two lines in an action and one schema field, with no `reveal`, no parameter and no salt in app code. Making a token is one call with its lifetime, one stored row and one `reveal` where it is sent; checking one is one call, and no app code compares a time.
- An app with the memory raises `ln` in one manifest line; each account moves on its next sign-in, and no setting makes a hash weaker than 2^17.
- A token given a `ttl` cannot outlive it through an app's omission: the expiry is in the one value the app must store and `check` must read. A token that does not expire exists only where the code says `ttl: null`.
- A credential or token made under `keel test` never works on a real server, and app tests do not run the production cost; the package's conformance does. A sim test moves the clock to either side of an expiry.
- At the default a process holds up to 256 MiB for derivations and answers about 11 checks a second; at `ln` 20 it holds 1 GiB and answers 0.7.
- An API token cannot be shown in the response that creates it, or read from `Authorization`, until the kernel RFC lands; a reset or invite token works end to end today.
- Expiry trusts the checking server's clock, and nothing is keyed: servers whose clocks disagree differ around an expiry, and someone who can write the database can move one. Revoking is deleting the row.
- The docs have one way to keep a credential. An app that hand-wrote the `scryptSync` form re-encodes its hashes as `$scrypt$ln=14,...` and they verify with `rehash` true.
- Still open, each with a recommendation in the RFC: the details of `ttl`, the unkeyed hash, the sim forms, the fixed token prefix, Argon2id, a rule for a `Hashed` or `Digested` field in a loader `output`, and kernel text naming the package.
- Budgets: `@keel/std-credentials` 1kb, `/server` 3kb, `/tools` 1.25kb; std.credentials is 1,290 tokens and std.tokens 1,208; `spec/00-map.md` stays under 1,200 with three trims.

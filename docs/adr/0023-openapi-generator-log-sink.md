# ADR-0023: OpenAPI generator in @keel/services; createApp log sink is the dev stream (RFC 0034)

**Status:** accepted
**Context.** The k.services clause on the OpenAPI client had no generator behind it, and the k.server log-stream clause had no stated in-process surface, so both conformance tests were `it.todo` (backlog 0059). E1501 was asserted only at the type level in router conformance. `tooling/deps.json` fixes the import order: compiler, router, check, scaffold, server, services.
**Decision.** `openapi(doc, { name })` lives at `@keel/services/openapi`. It is pure and build-time, and returns the `api.schema.ts` and `api.ts` sources or a `schema.invalid` error with paths into the doc. Constructs outside the subset become `s.json()`. Each `#/components/schemas/<Name>` becomes a file-local `const` and is not exported, so each generated file keeps one export. `createApp({ log })` is the stated sink of the dev log stream. Router conformance asserts E1501 through `compile`, and services conformance asserts E1651-E1653 through `check`.
**Alternatives.** A generator in `@keel/scaffold` cannot be imported by services tests (scaffold precedes services). Testing `keel dev` stdout needs a live Vite server. Exporting the component schemas would put several exports in one generated file (principle 3). Inlining every ref repeated each schema at every use.
**Consequences.** `keel scaffold service --openapi` must reach `openapi()` through the cli, since scaffold cannot import services. That is a follow-up. The client bundle is unchanged, because the generator sits on a subpath. Unsupported OpenAPI constructs fall back to `JsonValue` types rather than failing.

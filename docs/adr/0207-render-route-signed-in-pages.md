# ADR-0207: k.user Testing: a `renderRoute` page is signed in for its own requests, one browser per harness (RFC 0185)

**Status:** accepted (orchestrator, under the RFC defaults; for the operator to confirm).

**Context.** `renderRoute`'s `user` reaches guards, loaders and actions only. A component's own service call on the `createApp` ctx is answered in process with no identity, so a signed-in page whose components call a guarded API gets 403 under test and passes in a browser. One ctx has one service binding, so two signed-in users on one app cannot be expressed. Under happy-dom a `Response` drops `set-cookie` and a `Request` drops `cookie`, so the harness's cookie jar is empty in practice, and shell mode has no cookie store: a sign-in round trip through the identity mount cannot be tested in process.

**Decision.** `user` covers every request the page makes, carried as `x-keel-user` signed by the `keel.user` signer of the `createApp` binding on `ctx`, so no `identify` runs; a test never chooses `caller`. In router mode a contract call that names no `user` carries the harness's `user`, and a second user on one ctx is E1724. With `app` or `shell` each harness is one browser: its page's requests to its origin go through `ctx.net` (to `app.fetch` with `app` unless routed), past one cookie jar the harness owns, which sets `cookie` as each request enters `ctx.net` and applies each answer's `set-cookie` lines. With `shell` the jar is the native store. Under `keel test`, `Request`, `Response`, `Headers` and `fetch` are Node's, so those headers survive. Two harnesses over one `app` are two users, jars and callers of one server state. A `user` with `app` on a ctx that holds no binding of `app` is E1724.

**Alternatives.** A derived ctx per page in router mode (ctx-keyed registries split from the API); a harness-added caller cookie (no source: the binding holds only the `keel.user` signer); a side table for cookies beside `Request` and `Response` (the auth library builds its own `Response`); a `cookies` method to seed the jar (signing in through the page covers it); the test's own route as the store (every shell test writes it); an ambient current page during `fire` (lost after an `await`); a `headers` option (a second way to say who the page is); a `ServerApp` method that answers as a user (production surface for a test need).

**Consequences.** Signed-in pages are testable through their components; layer 7's two-member live test is two `renderRoute` calls; a sign-in round trip through the mount runs in process in document and shell mode. `keelConfig` swaps four fetch globals back to Node's. k.user, k.mount and k.return read `implemented` until six new clauses are covered. New code E1724.

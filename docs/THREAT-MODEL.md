# Threat model

This document states what Keel protects, against whom, and where each protection stops. It is written for the people who will try to break it. Each protection below is one testable statement, followed by the specification section that makes it (`keel docs <section>` prints one) and the diagnostic or run-time refusal that enforces it. Each is followed by its limits: behavior the section itself says is not covered. A limit stated here is published on purpose and is not a finding. A way around a protection that its limits do not describe is a finding; report it as `SECURITY.md` says.

Section ids are cited in parentheses, with the part of the section in question where it has one: (k.server Request flow) is the Request flow part of section k.server.

## 1. What Keel answers for

Keel is a TypeScript framework: a server on Node (`createApp` and the generated `server.mjs`), a browser runtime and router, a checker and build (`keel check`, `keel build`, `keel dev`), and a standard library of `@keel/std-*` packages. It answers for the claims below, made by that code, in an app that passes `keel check`.

Keel does not answer for these:

- **Authentication.** Keel authenticates no one. It carries the user id a function the app supplies (`identify`) answers, and never reads, writes, mints, rotates or stores a credential, session or token for it (k.user). Keel gives the seam (`identity.server.ts`, the `handle` mount); sign-in, passwords, cookie attributes, lifetime, rotation, fixation defense and revocation of a sign-in are the auth library's or platform's (k.user, k.return The app's part). A flaw inside that library belongs to its project.
- **App data.** Keel owns no app data. A storage battery keeps it: `@keel/std-db` for the framework's own state and `@keel/std-postgres` for an app's tables. Its guarantees are the battery's section (std.db, std.postgres), stated under B5 below, and stop there: encryption at rest is the volume's or the host's (std.db On disk).
- **Identity in an app that has not opted in.** Identity is opt-in: a project with no `identity.server.ts` has no identity source, and every guard, loader and action gets `user` `''` (k.user User). Such a server answers `GET /__keel/user` with 404 (k.guards Conformance), its client router sends no user read (k.guards Client), and its channel streams count by caller (std.channels-limits Config). The caller cookie is still minted on a write (k.server Server state) and grants nothing (k.user).
- **An app with no server.** A topology with no `node` deployable has no Keel origin: nothing in it answers a request, and a shell build of it sends no request to any origin but its declared `connect` origins (k.shell Without a server).

## 2. Trust boundaries

| Id | Boundary | Who is on the far side |
| --- | --- | --- |
| B1 | A browser, or any HTTP client, sending a request to a `node` deployable | An anonymous visitor, a signed-in user acting beyond their authority, a cross-site page, a script that is no browser |
| B2 | What a deployable sends a browser: documents, built files, page state | Anyone who loads a page or reads a built file |
| B3 | One deployable of an app calling or forwarding to another, and to third parties | Anyone on the network between peers; a third-party API |
| B4 | A native shell (Capacitor, Tauri) and the links other apps send it | Another app on the device, a web page that sends a link on the shell's scheme |
| B5 | The server process writing its log and its storage | Whoever reads the log or the database |
| B6 | The build machine running `keel check`, `keel build`, `keel dev`, the editor's language server, `keel review`, `keel evidence` and `keel scaffold` | The author of a checkout you open; a dependency |
| B7 | A library: third-party Keel code inside the app's gate, at check time and at run time | The library's publisher |

## 3. Assets

- **Secrets.** `s.secret` values (`Secret<T>`): credentials an app receives, a bearer token, a minted token, `KEEL_SECRET`, `KEEL_DATABASE_URL`, `KEEL_POSTGRES_URL`, `KEEL_EVIDENCE_KEY`.
- **Personal data.** Values a schema marks `.pii(class)`, and the caller hash when the caller cookie is long-lived (k.user Caller lifetime).
- **A session.** The caller cookie, and the auth library's own cookie that rides beside it.
- **A signed-in user's authority.** The `user` a request carries and what guards admit for it.
- **The integrity of the gate.** `keel check` and `keel build` refusing what breaks the claims below, and `keel review` showing every escape from them.

## 4. Protections

### B1. Requests into a `node` deployable

1. **Same-site write proof.** A POST, PUT, PATCH or DELETE runs only with `Sec-Fetch-Site` `same-origin` or `none`, an `Origin` equal to the server's or an allowed one, `x-keel: 1` together with `accept: application/json`, or neither `Sec-Fetch-Site` nor `Origin`; otherwise it is 403 `keel.denied` and nothing runs (k.server Request flow). The identity `handle` meets the same check first: a cross-site POST under `handle.path` is 403 and `fn` is not called (k.mount Server).
   Limits: a request with neither header is admitted. `x-keel: 1` with `accept: application/json` passes, and any client that is no browser can send it; the proof stops a browser's cross-site write, not a script that writes headers.
2. **Body cap.** An action body over `maxBodyBytes` (default 1 MiB) is 413 `keel.payloadTooLarge` and no action runs (k.server Request flow).
3. **Plain data at parse.** A value `parse` accepts is plain data but for the `Secret` at each `secret` node: a `Map`, a `Set`, a `Date`, a class instance, a function, a symbol key, a non-enumerable key, a getter or a cycle fails rule `type`, at a declared position, inside `s.json()` and under an undeclared key of an open object at any depth; own `__proto__`, `constructor` and `prototype` keys are rejected (k.schema Plain data). So every value in a parsed input is reached by the walks of own enumerable keys that the log scrub, sessions' redaction and `#k-state` make.
   Limits: a Proxy is judged by what its traps answer while `parse` reads it; `parse` of a schema with no `secret` node returns the value it was given, so a change to that value after `parse` returns is not judged (k.schema Plain data).
4. **Guards first.** Every guard of a route's chain runs, outermost first, before any loader; a denial on a page redirects, on an API route is 403 `keel.denied` with no `Location`, and no guard result reaches a loader or action (k.guards, k.api Requests). A guard `redirect` to a route under that guard, a redirect loop, or a page lacking a param its `redirect` route needs is E1508 (k.guards Rules, Carried params).
5. **API methods and query.** A method no entry at a path has is 405 with `allow` listing the path's methods, before any guard runs; a `query` that fails its schema is 422 after the guard and runs nothing (k.api Requests).
   Limits: any client learns which methods a path takes from the 405 `allow`, as it would by sending them.
6. **Bearer.** An API route's handlers get the `authorization: Bearer` token only as a `Secret<string>` (1 to 4,096 characters of the stated alphabet), any other value of the header as `undefined`, with no error and nothing logged; pages never get one; a response to a request carrying `authorization` is `Cache-Control: no-store` (k.api Bearer). The token is scrubbed from that request's log (k.privacy Server log).
   Limits: any client can send a bearer; checking it is the app's (`tokens(ctx).check`, std.tokens). A token of 1 or 2 characters is scrubbed only where it stands as a whole token (k.privacy Copies).
7. **Allowed origins.** A cross-origin request gets CORS headers only when its `Origin` equals an origin listed in `KEEL_ALLOW_ORIGINS` (`createApp({ allow })`) and the route is an API route; the preflight is answered before any guard, loader or action runs; pages, assets and unlisted origins get no CORS header, a preflight 405 and a write 403. `*` or an entry with a path is E1560 (k.hosting Allowed origins).
   Limits: the grant includes `access-control-allow-credentials: true`, so an allowed origin is trusted with everything an API route answers its caller. The caller cookie reaches the API only from a same-site origin; a cross-site allowed origin is logged once as W1567 (k.hosting Caller).
8. **User comes only from the identity source.** `user` is what `identify` answers, or what a verified `x-keel-user` from another deployable of the app asserts; no header, cookie, search or body value of the client sets it (k.user User). `identify` runs after the same-site check and before guards; a throw is 500 with a `diag` naming the error's `name` only, an answer that is no string of at most 256 characters is 500, and past 5,000 ms it is 503; no guard, loader or action then runs (k.user Identity source).
   Limits: `identify`, and the library it calls, are trusted completely. An event stream keeps the `user` it opened with until it closes; a live loader can ask again with `currentUser()` (k.user User).
9. **The identity mount.** `handle` takes only a path whose undecoded text is `handle.path` or begins `handle.path/`, textual and case-sensitive; no page matches at or under it or at a path holding a raw `\`, and the server answers `/%67ate` (for `/gate`) 404 without calling `handle` (k.mount-scope). A `handle.path` not of lowercase `/` segments, at or under `/assets`, or with a route under it is E1579 in `keel check` and `keel build`, and `createApp` throws it (k.user Rules). An `identityMount` call anywhere but `identity.ts`'s default export is E1593 (k.mount Rules). Keel sets no cookie on a `handle` response (k.mount Server).
   Limits: `/GATE` is matched by the page table as any other path, so a proxy that changes the case of paths must not sit in front (k.mount-scope Conformance). A form post may not end on another origin (`form-action 'self'`), so a sign-in that leaves for a provider starts from a link (k.mount Server).
10. **Return targets.** A `next` a guard redirect carries becomes a redirect only through `pageHref`, which answers only a page of the route table, root-relative (k.router Return targets). A sign-in returns only to pages its own origin answers: `identity.server.ts`, or a file it imports, importing the routes of a module served on another origin is E1592 (k.user Rules).
    Limits: E1592 follows imports of a module's `routes` only; a table built another way is not judged.
11. **The user read.** `GET /__keel/user` answers `{ user }` only with `x-keel: 1`, with `cache-control: no-store`, else 403; the client router holds the answer in memory for navigation and rendering only, never in storage, a log or a URL, and each API the page calls runs its own guards (k.guards Client).
12. **Caller cookie.** The caller cookie is `HttpOnly; SameSite=Lax; Path=/`, named `__Host-keel-caller` with `Secure` on https and `keel-caller` otherwise; it is HMAC-signed under `KEEL_SECRET` (at least 32 bytes, else E1556), and a value the server did not sign counts as none; loaders see only its base64url SHA-256 as `caller` (k.security Caller cookie, k.server Server state). A production start without `secure` or an https origin logs W1557, without a secret W1556 (k.security, k.server).
    Limits: the cookie is no credential: whoever holds it is that caller (k.user). Over plain http, or behind a proxy that sends no `x-forwarded-proto` while `secure` is unset, the cookie is `keel-caller`, and a sibling host can plant a validly signed value it got with one write of its own (fixation); https with `__Host-` closes it. Whoever holds `KEEL_SECRET`, or runs code in any one deployable, can sign a caller every deployable accepts (k.deploy Build). With `caller: { days }` the caller hash is a long-lived device identifier, classed `.pii('network')` (k.user Caller lifetime).
13. **Request isolation.** A request holds its own live store per id; overlapping actions on one factory's stores each see only their own instance, and a save after another request's save is 409 `keel.conflict` (k.server Server state). Every state-changing operation on a module store during a request throws E1256 and changes nothing, including work the request starts that runs after its response (k.leave Module stores).
    Limits: a callback registered outside a request (module load, a runner, startup) is not checked, even when a request resolves its promise (k.leave Module stores).
14. **Event streams.** A live loader's stream runs its guards first and a denial is 403; past `createApp({ maxStreams })` (default 1,000) open streams an open is 503 `keel.busy` and no loader runs; an event over 1,048,576 bytes as written is not written, and the stream ends with a `keel.unexpected` `err` (k.server Request flow).
    Limits: `maxStreams` is one pool for every live loader of the app with no per-caller share, so one client that holds it makes every other open 503 until its streams end (std.channels-limits Limits).
15. **Channel stream caps.** A channel stream counts against its user's `perCaller` (default 8) per module when it has a user, else its caller's, and only a stream with neither counts against `perAnonymous` (default 64), shared by every module of the process; a full open gets `{ kind: 'closed', reason: 'full' }` (std.channels-limits Config). A signed-in person's own opens are never taken by an anonymous flood or another user (std.channels-limits What the caps bound).
    Limits: a caller cookie is set on any write, so a client that writes holds a new caller per cookie, with `perCaller` streams each; the anonymous places are shared, so a flood makes a real visitor's anonymous open full. Keel counts no address: limiting opens per client address belongs to the proxy or platform in front of the app (std.channels-limits Limits).
16. **Policy reports.** `POST /__keel/csp` takes bodies up to 16 KiB (else 413, nothing logged) without the write proof; each report is logged as directive, blocked kind or origin and route id, never a path, query or sample; at most 100 reports in each 60 s are logged, at most 10 per source address, and the rest are counted (k.security Reports).
    Limits: the per-source count reads the last `x-forwarded-for` entry, so it binds only behind a proxy that appends that header (k.security Reports).
17. **Built files.** Production serves the client build loaded at startup from the deployable's build folder, `/assets/*` but `*.map`, each `nosniff`, `immutable` when the manifest names it hashed and `no-cache` otherwise; a symlink out of `assets/` is not served (k.deploy Assets). An unmatched request under `/assets/` is 404 (k.hosting Served by).
18. **Inspect.** `GET /__keel/inspect` is served only in dev (a `createApp` with `mode: 'dev'`, or the dev and preview servers), to a loopback or listed `Host` with its own or a listed `Origin`, an absent `Origin` for GET only; else 403 (k.inspect).
    Limits: it shows every store's state unredacted, `.pii()` values included; a dev server reachable from another machine shows them to it.
19. **Errors outside dev.** An uncaught throw in production is 500 whose body holds neither the thrown message nor a stack frame (k.server Conformance). An uncaught exception or rejection in a served process writes one E1577 record with the route id and no thrown text; production then stops listening, lets requests in flight finish for at most 10,000 ms and exits 1 (k.leave Process).

### B2. What a deployable sends a browser

1. **Escaped output and the URL policy.** Server HTML escapes text and attribute contexts separately; every URL attribute (`href`, `src`, `action`, `formaction`, `xlink:href`, `poster`, `data`, `ping`, `srcset`, `imagesrcset`, and `to`, `from`, `by` and `values` on any element) whose parsed scheme is not `http`, `https`, `mailto` or `tel` renders as `about:blank`; raw HTML has no API outside `unsafe` (k.compiler Escaping by context).
   Limits: a navigation attribute (`href`, `action`, `formaction`) takes any absolute `http(s)` URL, so a link the app writes may lead off the origin; only an `Href` (below) is held to the page's origin.
2. **Links Keel follows.** An `Href` starts with one `/` and holds no `\`, control character or `#`; `Link`, `navigate`, `Form action` and an action's `ok` take only an `Href`, rechecked when run: a `Link` renders `about:blank`, a `Form` throws E1501, an `ok` is `keel.unexpected` with nothing saved or followed and no `Location` (k.router Links, k.server Request flow).
3. **Response headers.** Every `createApp` response carries `nosniff`, `Referrer-Policy: same-origin`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, `X-Frame-Options: DENY` and a `Permissions-Policy` denying camera, microphone, payment and usb; on https also `Strict-Transport-Security` (k.security Headers).
4. **Content security policy.** Every production document carries `default-src 'none'`, a script nonce new per response, `base-uri 'none'`, `object-src 'none'`, `frame-ancestors 'none'`, `form-action 'self'`, and Trusted Types (`require-trusted-types-for 'script'`, policy `keel`); the document is `private, no-store`, so no cache replays its nonce; the one inline script is `#k-state`, of type `application/json`; other responses carry `default-src 'none'; frame-ancestors 'none'` (k.security Policy). A string assigned to an HTML sink other than through policy `keel` throws (k.security Trusted Types).
   Limits: dev sends the policy as report-only, with `'unsafe-inline'` in `style-src`. A `client` or `static` deployable's policy is `csp.txt` with `script-src 'self'` and no nonce, served by its host (k.security Other deployables).
5. **Declared origins.** Only an exact origin with a reason, declared in `topology.ts` under `img`, `media`, `font`, `connect` or `frame`, widens the policy; scripts, styles and Trusted Types take no declaration; a declaration the static read cannot take, an inexact origin or a reason out of form is E1590, a duplicate E1591 (k.origins). A `Frame` renders sandboxed (`allow-scripts allow-same-origin allow-popups allow-presentation`), with `referrerpolicy="strict-origin"`, and renders `about:blank` for a `src` of the document's origin; a `frame` origin of the app's own is E1590 and is left out of `frame-src` (k.origins Frame). E1570 and E1571 report a literal absolute URL whose origin is undeclared (k.security Rules).
   Limits: a declared `connect` origin can receive anything the document holds, and every declared origin sees the address of each browser that loads from it. E1570 and E1571 read a URL as written (a literal, a template's text before its first substitution, the left side of `+`, `new URL`, `new Request`, through `const`s and imports); one computed otherwise is not reported, and the policy blocks it in the browser with a `csp` report (k.origins Rules).
6. **Server-only code stays on the server.** On a `node` or `static` deployable no byte of a server-only file (`*.server.*`, `*.guard.*`, by its name on disk in any case and extension), nor of what only server-only files import, is in a browser asset; a browser build stubs those files, and fails with E1007 when its graph, workers and dynamic imports included, still holds one, a Node built-in or a file using `loader`, `action` or `guard` (k.boundary, k.bundle). A specifier differing in case from the file on disk is E1010 (k.bundle Names). Client code reaching a server-only file is E1004 in `keel check`; `keel build` stops on any check error (k.boundary Reach, Build gate).
   Limits: a value in a file that is not server-only ships when a browser file imports it, so a secret hard-coded in a schema, a `routes.ts` or a shared helper is public. On a `client` deployable loaders, actions and guards run in the browser and ship (k.boundary). `vite build` alone runs no check; the stubs and E1007 still hold (k.boundary Build gate).
7. **No environment value in a browser file.** No value of a variable set for a build is in a browser asset but the public origins `KEEL_PEER_<NAME>` and a shell's `KEEL_ORIGIN`, and `NODE_ENV`; a project config that sets `envPrefix` or `define` fails the build with E1007, as does an emitted file holding the value of a `KEEL_*` variable of 8 characters or more (k.bundle Environment, k.boundary Environment). `import.meta.env` holds only `MODE`, `DEV`, `PROD`, `SSR` and `BASE_URL`, and a type reference directive or a foreign `ImportMeta` declaration is E1016, so those types are Keel's and Node's alone (k.boundary Ambient types).
   Limits: a script a project plugin bundles in a pass of its own, a file copied from `public/`, and a value a project plugin writes of a variable not named `KEEL_*` are the project's (k.bundle Limits).
8. **Only reachable app modules are named in a client bundle.** A `client` bundle's service map holds only the modules its browser code reaches; a bundle holding a file of an app module the map omits fails with E1011 (k.bundle Service map).
9. **Page state.** `#k-state` holds a request store's snapshot only when an island needs it to resume; a document with no island ships `{}`; no factory store enters it and no server store restores from it (k.leave Snapshots, k.server Server state). A store in client-reachable code whose state holds a `.pii()` class its module's `clientPii` does not list is E1107, as are a state schema the check cannot read, `stores()` in client code, and `store` used other than as a call (k.leave E1107).
   Limits: `#k-state` is not a privacy sink: a `.pii()` value of a store an island needs, in a class `clientPii` lists, reaches the browser as the island renders it. A store a package creates is the package's (k.leave E1107). The snapshot holds its stores' write keys (k.store); a write key is checked only against the store a write commits to, so a key read from a page suppresses a server write only where that server store already holds the same transaction with that key (k.sync).
10. **Secrets never serialize.** A `Secret` gives `"[secret]"` to `encode`, `JSON.stringify`, `String()`, templates and `util.inspect`, has no own enumerable keys, and the marker never parses back (k.privacy Secrets). A secret in a route's `params`, `search` or `query` is E1111 (k.privacy URLs); a secret in a loader or action `output` is E1113 (k.privacy Rules); a token digest in an `output` is E2203 (std.tokens Rules).
    Limits: `reveal` returns plain data; an action may return a revealed value in a plain `output` field on purpose (k.api Output).
11. **A route table check cannot read is refused.** A route table, entry, `params` or `search` that `keel check` cannot read statically is E1111, because it cannot show the table holds no `.pii()` (k.privacy Rules). A schema binding a project file may change (an assignment, `Object.assign`, a call that receives it) is not held, and is read as unreadable (k.privacy-reads Held).
    Limits: a package's exported table or schema is the package's (k.privacy Rules). A package factory is read through at most eight package functions on one path; past that bound, or on recursion, the call is unreadable (k.privacy-reads Factories).
12. **Personal data in inputs and the 422 page.** A control bound to a `.pii()` path reports its input values to observers as `x` repeated (k.privacy Inputs). A rejected no-script submission re-renders without password-input values and without any value that may reach an `s.secret` (k.forms). A password control bound to a field that is not `s.secret` is W1114 (k.privacy-reads Password controls).
    Limits: a field the browser alone turns into a password input is not seen by the server; declare a credential field `s.secret`.
13. **Session recordings.** `record` keeps no `s.secret` value, password input or `redact` entry, writes each `.pii()` value as a generated value, and records store state, payloads and route values as their schema encodes them, so no undeclared key at any depth is recorded; it uploads only to a credential-free http(s) URL on the document's origin (E2006). `sessions.list` admits only a `user` or `caller` listed in `readers`; `to-test` writes every `s.string()` value not named by `expose` as `x` repeated (std.sessions).
    Limits: a recording is redacted once, in the browser: `sessions.ingest` takes unauthenticated posts of at most 256 KiB and redacts nothing, and the server log's scrub never covers a filed session. Anonymous ingest is one bounded buffer (5 sessions per fingerprint, 64 fingerprints, 4 MiB), so a flood replaces its contents. Error text is scrubbed of dropped values written as is, URL-encoded or JSON-escaped only, not of the log scrub's other encodings (std.sessions-redact). Session files under `.keel/sessions/` hold everything `record` kept.
14. **Outbox owner.** A queued write holds the owner its page gave; a flush posts only the entries of the owner last given on the ctx, and another owner's entries are stored `failed` and never posted (std.offline Owner). An outbox whose endpoint body holds an `s.secret` is E2651 (std.offline Rules).
    Limits: entries stay in browser storage until sent (std.offline Privacy).

### B3. Between deployables, and to third parties

1. **Forwarding.** A request for a path a peer deployable serves goes to that peer's origin with its method, path, search, body (capped at `maxBodyBytes`) and headers less `host` and hop-by-hop ones; the peer's response, a 3xx too, comes back unfollowed; an unreachable peer is 502 `keel.unreachable` naming no host (k.topology Calls and peers).
   Every request a deployable forwards, and every request a server's `service` call sends, carries `x-keel-forwarded: 1`; the deployable that matches it to a `local` route refuses it 403 `keel.denied`, whatever its remote address or `Host` (k.contract Local routes).
   Limits: a request carrying `x-keel-forwarded` is not forwarded again, and any client can send that header; it only makes the receiving deployable answer for itself and refuse it on `local` routes.
2. **Signed user assertion.** `x-keel-user` is an HMAC-SHA-256 under `KEEL_SECRET` over method, path, search, body hash, `user`, the receiving deployable's name and an expiry 60 s ahead; a receiver ignores it on a mismatch, an expiry more than 65 s ahead of its clock or a `user` over 256 characters, and runs `identify` instead (k.user Across deployables, User header).
   Limits: until it expires a captured header replays that one request to that deployable, and plain http between peers exposes it; whoever holds `KEEL_SECRET` can assert any user to every deployable.
3. **Keel headers go only to Keel origins.** `x-keel` and `x-keel-user` go only to a `contract` service target, and for a `base` service to the document's origin, a `keel-peer` origin or a URL peer; any other origin, declared or not, gets only `accept`, a bearer's `authorization` and `content-type`, with `same-origin` credentials (k.services Encoding). A `base` call naming `user` is `api.input` and sends nothing (k.services API).
4. **Service clients.** A service call follows no redirect (a 3xx is `api.status`), reads at most `maxBytes` (default 1 MiB) of a body or of one event, and never throws; a third party's body shaped like a Keel `Result` is data, decoded by `output` (k.services).

### B4. Native shells

1. **The shell's net.** A shell's `net` sends a page-origin request to `KEEL_ORIGIN`, a request to `KEEL_ORIGIN`, a `keel-peer` origin or a declared `connect` origin as given, and refuses every other origin or scheme with a `TypeError` naming no URL, at each redirect hop too; a hop to another origin drops `authorization`, and at most 20 hops are followed (k.shell Origins). A shell build with a `node` deployable needs an https `KEEL_ORIGIN` outside `localhost` (E1574) (k.shell Build). The Capacitor package leaves the global `fetch` unpatched (std.shells).
   Limits: that the native plugin refuses an unlisted origin when script the app did not ship calls it, that each native store keeps a cookie set on a manual redirect and past a relaunch, and that a return link reaches a cold-started and a running app need a device or an installed bundle and are not shown by tests (std.capacitor Limits, std.tauri Limits).
2. **Mount requests.** In a shell a navigation to the identity mount is a request through `net` with `x-keel: 1` and `redirect: 'manual'`; Keel reads only the answer's status and `location`; a `location` whose path begins `//` or `/\` once dot segments are removed is ignored, and only an `http:` or `https:` redirect to another origin opens in the external browser, which shares no cookie with the app (k.return Mount requests).
3. **Return links.** A link on the shell's scheme to a page the router matches navigates there as a web link would; one to a path the mount declares in `links` sends one GET at any time; any other path under the mount is taken only against a pending opening, one link per opening, within 600,000 ms of it, the opening kept in `ctx.storage`; any other link is ignored (k.links Return links).
   Limits: a declared path is reachable by any app or page at any time with the user's native cookies, so declaring one asserts the library's handler there is safe to receive unsolicited. While an opening is pending, another app or page can send a return link first and take it; the real return is then ignored. Another app may register the same scheme, so a return carries nothing the library has not bound to the native store (PKCE). Where another app can launch this one with no link, a sign-in the app starts on render with no act records an opening that app's link can take (k.links Limits).
4. **Openings need a person.** From the moment a link is taken, or a launch report names links or fails, until a trusted pointer, touch or key act on the page, no mount request records an opening, whoever starts it; a `click()` or `requestSubmit()` from script is no act (k.opening Link-started).
   Limits: an opening is no proof that a person started a sign-in: after any act, any in-app navigation to a `MountHref` that ends in the external browser records one, including a link in content another user wrote if the app renders such links (k.opening Limits). Link-started is per ctx, in memory: a webview reload starts a new ctx (k.return Limits).

### B5. The server's log and storage

1. **Log scrub.** In each `diag` record's message and frames and each `req` path, every `.pii()` value of the request (its decoded input, its loaders' and actions' outputs, its factories' state) is `[pii]`, and every string, number and key of a `Secret` the request or a runner's `run` makes or reveals is `[secret]` (k.privacy Server log). A value is found as given, in NFC and NFD, as hex and as base64 or base64url at any alignment (from 8 bytes; a shorter value as its own padded base64, whole), in the text and in decoded views that undo `%` escapes, `+`, JSON escapes and HTML entities, together and one family at a time, so any single or double nesting of those escapings is found (k.privacy Copies, Views, Base64). A package that clears the server's secret listener loses no secret: each text of a scope during which the slot was lost is one `[secret]` (k.privacy Server log).
   Limits, as the section states them: a copy under three or more escapings; an escape the views do not read (`\x41`, octal, `\U`, `%u`, another named entity, a numeric entity without `;`); a value holding an escape of one family under two escapings of two different families, one of which leaves that escape as is (`a"b%41` JSON-escaped, then URL-encoded); a copy part NFC and part NFD, and compatibility forms; hex of a value under 8 bytes; base64 of a value under 8 bytes inside a longer encoding; hex or base64 of a text in which the value is itself escaped; base64 with line breaks; hex of UTF-16 and any other encoding, a hash, compression or encryption; a copy cut, split or changed; a value revealed outside every scope (k.privacy Copies). Past 65,536 bytes of a scope's distinct values, or a `Secret` with more than 1,000,000 values, every text of the scope is one mark, over-marking on purpose (k.privacy Cost). A form under 3 characters is marked only as a whole token.
2. **Path marks.** Before the scrub, a `req` path segment at a secret `params` field of any route is `[secret]` and at a `.pii()` field `[pii]`; a longer path is cut there, as is a path holding `%2F` or `%5C` at a secret param, taking in the slashes beside it (k.serverlog Path).
   Limits: a path no route lines up with (a static typo, an extra leading segment, a raw `/` in an earlier param, `&` for `?`) is logged as sent (k.serverlog Path).
3. **Records cannot be forged.** Control characters, U+2028, U+2029 and `…` are written as `\u` escapes; a message or path keeps 2,048 characters and a frame or method 256, then `…+<n>`, which input cannot forge; the cut keeps a head of the scrubbed text, so it never shows part of a marked value; a record is at most 8,192 characters and 12,288 bytes plus a `req` record's route id (k.serverlog). A text over 2,000,000 characters in a scope holding a secret or `.pii()` value is one mark, unread (k.serverlog Parts).
4. **Revealed values in one file.** E1112 reports a revealed value reaching `tx`, `store`, `ctx.storage`, a console method, stdout or stderr, a file write, an `Error` or a throw, through bindings, literals, operators, members, methods and the standard conversions and encodings (k.reveal). `reveal` outside a `*.server.ts` file is E1105 (k.privacy Rules). Store state refuses a secret (E1303), a snapshot folds every log entry up to the last secret payload, and job inputs, channel messages and outbox bodies refuse one (E2503, E2602, E2651) (k.store, std.jobs, std.channels, std.offline).
   Limits: any other call, a parameter, an import, a callback and a field of `this` end the read, so a value carried through a helper is not tracked; a `return` is not a sink (k.reveal Flow). A credential parsed as `s.string()` is plain data from the start. The rules stop accidents: an author who means to store a secret can.
5. **Framework storage.** `@keel/std-db` stores exactly what `ctx.storage` receives and exposes no SQL; no value reaches a log line, diagnostic, error message or change notification; `KEEL_DATABASE_URL` is in no log line, diagnostic or generated file, and E2153 names the key and no part of its value (std.db, k.deploy Storage). Postgres connections use TLS as the URL's `sslmode` says; each commit takes a transaction-level advisory lock per key in sorted order (std.db API). App code importing the driver is E2151 (std.db Rules).
   Limits: `.pii()` data is stored as the store holds it; encryption at rest is the volume's or the host's; a removed value leaves the database once its log entry folds past `logLimit`, and Postgres keeps dead row versions until vacuum (std.db On disk). TLS is only what `sslmode` asks for.
6. **App data.** `@keel/std-postgres`'s `sql` sends each `${value}` as a numbered parameter, never as text; only a `fragment` is spliced; a `Secret` or other non-JSON parameter throws E2457; a transaction is `serializable` unless `allow` with a literal `reason` (E2459) gives that up; no error, log line or diagnostic holds a parameter or row value; a missing or unknown `KEEL_POSTGRES_URL` scheme is E2455, naming no part of it (std.postgres). Importing its server entry outside a `*.server.ts` file is E2451 (std.postgres Rules). Migrations are the module's `migrations/NNNN-<kebab>.sql` files, applied in order, each in its own transaction under an advisory lock per capability so each runs once across processes; a gap or bad name is E2453, an applied file changed or removed is E2454 (std.postgres Migrations).
   Limits: the section puts no limit on what a migration's SQL may do: it runs as written, with the connection's rights. `allow: 'lost updates'` and `'write skew'` give up the isolation they name (listed by `keel review` as R2451). TLS is only what `sslmode` asks for.
7. **Tokens.** `mint` gives a token holding 256 random bits as a `Secret` and a SHA-256 digest to store, the expiry inside it; `check` compares in constant time and refuses a token at or past its expiry; a real ctx refuses a simulated token or digest (std.tokens).
   Limits: there is no key in the digest, so someone who can write the database can plant a digest or move an expiry; revocation is deleting the row (std.tokens Forms).
8. **Bounded store logs.** A store keeps at most `logLimit` log entries (default 256) and `keyLimit` write keys, so a saved snapshot stays bounded (k.store).

### B6. The build machine

1. **The gate runs no app code but declared packages.** `keel check` on every surface and `keel build` import each `@keel/std-*` package an app module lists in `deps`, its entry and its `./tools` export, and a library only through its `./tools` export (k.module Std config, k.library-pack Package); a `@keel/std-` name of another form, or a `deps` package that does not import, is E1159 (k.module Rules). `keel check` and `keel build` also import the `./tools` entry of each shell a `client` deployable declares (k.shell Shell target).
   Limits: this runs the project's own dependencies with your privileges, the trust of `pnpm test` in that checkout; opening an untrusted checkout with the Keel language server runs them. `keel evidence` runs the project's tests and imports its `*.schema.ts` files in Node (k.evidence Command).
2. **Check reads only the project.** A relative import in project code that resolves outside the project root is E1015, because `keel check` reads only the project's files (k.boundary Following). A specifier other than relative reaching a file under `modules/` is E1013 (k.bundle Aliases). A `@keel/*` internal entry named outside `packages/`, `node_modules/` and `.keel/` is E1576 (k.security Rules).
3. **Escapes are named.** `unsafe(reason, fn)` is the one named path around a check, its reason at least 8 words (E1760) (k.unsafe). `keel review` lists each opt-in by name and each workaround by shape, with no network request and no project code run: a cast or suppression where `keel check` does not read, a computed module specifier, a computed global key, a dependency override, patch or non-registry source, an install script, a changed check, type, lint, test or CI configuration, fewer assertions, fewer `.pii(`, `s.secret(` or `guard(` calls, a file that does not parse; its baseline is read at the range's base, so a change cannot accept its own escapes (k.review, k.escapes).
   Limits: not seen are a capability reached through a value from another file or a parameter, an escape in a dependency's published code, behavior that depends on run-time data, and a test asserting the wrong thing at full strength; the baseline cannot prove a person wrote an entry (k.review Limits).
4. **Scaffold writes stay in the project.** A scaffold or `keel docs --sync` edit set is refused whole when a target is a symbolic link, an existing file with more than one hard link, or a path whose real ancestor is outside the project root (E1357); a shell's files likewise (E1585) (k.scaffold Links).
   Limits: the judgement is made once, so a link made between it and the write is followed.
5. **Server bundle files.** A bundled package file's `new URL(<a>, import.meta.url)` must name a literal path inside that file's folder, which `keel build` copies beside `server.mjs`; a path leaving the folder, a computed one, a missing file, or two packages naming one path for different bytes is E1014, and nothing is written (k.server-deps Files a bundled package reads). A module's `env` entry naming a `DeployEnv` key is E1167 (k.server-deps Rules).
   Limits: a package that reads a file above the reading file's folder (`new URL('../x.tar.gz', import.meta.url)`) cannot be served by `keel build`, even though the file is inside the package (k.server-deps).
6. **Evidence.** `keel evidence` writes a bundle holding no app value (ids, codes, paths, counts and hashes), signed with an Ed25519 key read only from `KEEL_EVIDENCE_KEY`; `--verify` checks the key id, the signature, every file's hash and schema, and that no file was added (k.evidence).
7. **Command tokens.** `keel session ingest` sends `KEEL_SESSIONS_TOKEN`, and `keel report` of an app's own route sends `KEEL_REPORT_TOKEN`, as the caller cookie of that one request (std.sessions Commands, std.report).
   Limits: `keel report` sends its token to an `http` URL too, where anyone on the path can read it.

### B7. Libraries

1. **A library is checked as the app's own code.** Every rule of `keel check`, the type pass included, runs over an installed or linked library's files as if they were `modules/<id>/`, and nothing turns a rule off there: personal data and secrets, the content security policy, accessibility, host elements and internal entries (k.library In an app, Guarantees). A library file importing outside its package folder is E1163; a library whose module id an app module or another library holds is E1166 (k.library Rules).
   Limits: a bare import in a library resolves to one of its own `dependencies`, whose code is not a library file and is not checked. A library's exported schema is read as a package's for E1111 (k.library Guarantees).
2. **Its counts are the app's.** The app recounts `unsafe` and `hostElements` over an installed library's files; a `.keel/ledger.json` missing, over 262,144 bytes, misshapen or stating other counts is E1162, and a library raising either count is E1706 under `keel ledger --diff` until the ledger is rewritten (k.library Ledger, k.library-pack Ledger file).
   Limits: the library's claimed rungs are shown as its own and counted in none of the app's; a linked library has no shipped file to compare.
3. **Listing a library adds nothing served.** Only a deployable whose `modules` names a library's id serves its routes; listing it adds no route, server code or identity (k.library In an app).
4. **What runs at check time.** No check imports a library's entry: `keel check` and `keel build` import only its `./tools` export when it declares one, so its rules, formats and config register (k.library-pack Package).
   Limits: a library's `./tools` is the publisher's code running on the build machine at check time, with the same trust as any dev dependency. At run time the library's code runs inside the app with the app's authority, under the same checks as the app's own code and their stated limits.

## 5. Out of scope for the framework

- The host: the cloud account, network, TLS termination, the proxy in front of the app and per-address rate limiting, which the sections above name as the proxy's or platform's.
- The app's own logic: what its guards admit, what its loaders return, what its actions write, which origins it declares and allows, and every `unsafe` and `reveal` it makes.
- Dependencies an app adds, and their published code, including an auth library and a library's own `dependencies`.
- Denial of service beyond the caps stated above (`maxBodyBytes`, `maxStreams`, the channel caps, the report and ingest bounds, the scrub and log cuts). Exhausting a stated cap as its limit describes is not a finding; a way past the cap is.
- Native shells on a device: what the limits of B4 say needs a device or an installed bundle is unproven.

## 6. How to report

Report a vulnerability privately as `SECURITY.md` says, never in a public issue or pull request. Name the protection above that it breaks, with its section id, the commit, and the steps or test that reproduce it.

## 7. Not stated in the spec

# Threat model (seed)

Assets: user data in stores and logs; secrets in server env; session files. Adversaries: web attackers (XSS, CSRF, injection), malicious dependencies, agents reaching for `unsafe`.

Kernel commitments:

- **Output.** Escaped by default. One URL policy covers `href`, `src`, `action`, `formaction`, `xlink:href`, `poster`, `ping` (http, https, mailto, tel only; `srcdoc` is always `about:blank`); the runtime enforces it and E1003 reports literals it would blank.
- **Secrets.** `s.secret` values (`Secret<T>`) serialize and log only as `"[secret]"`, never restore from JSON, and are read only by `reveal` in `*.server.ts`. E1105 (`packages/check/src/rules/revealInServerFile.ts`) reports `reveal` anywhere else in app code. No `Secret` reaches storage or a database. Store state refuses one (`store()` throws E1303), a snapshot folds every log entry up to the last secret payload, a plain or JSON field refuses one, and job inputs, channel messages and outbox bodies refuse one (E2503, E2602, E2651). What `reveal` returns is plain data, and nothing at run time tells it from another string. E1112 reports a revealed value reaching a log, storage, a file, store state or a throw in the same file (k.reveal), and the server writes `[secret]` in place of a request's own secret input in its log. These are not detected: a value carried through a helper's parameter, a callback or an import, std.jobs' `enqueue`, a response, and a credential the app parses as `s.string`, which is plain data from the start. The rules stop accidents. An author who means to store a secret can always do so, and the documented form is `credentials(ctx)` (std.credentials, std.tokens).
- **Server and client split.** `.server.ts` cannot reach the client. Documents load runtime JS only when a page has islands, so a static page carries no module script. Built client assets are read once at startup from the deployable's build directory and served only from that fixed set, so a request path never reaches the filesystem. Only files whose real path is inside `assets/` are read: no symlink or `..` manifest entry leads out. Every asset response is `nosniff`. Only files the manifest names with a content hash are `immutable`; others are `no-cache`.
- **Dependencies and code.** `unsafe.*` is justified and counted.
- **Stdlib loading.** `keel check` (binary, MCP `check`, and every LSP open or change), `keel build`, `keel dev` (the Vite plugin), `keel session` and the MCP `tools/list` and `session` calls import each `deps` entry named `@keel/std-[a-z0-9-]+`, and its `./tools` export when it has one, resolved as an ESM import from the manifest's folder through its own and its ancestors' `node_modules`; any other `@keel/std-` name is E1159 and is not imported, and a `deps` entry outside `@keel/std-` is never imported. This runs the project's own dependencies, the trust level of `vite dev` or `pnpm test` in that checkout, so opening an untrusted clone in an editor with the Keel LSP runs its stdlib packages. This name gate is the trust boundary: no workspace-trust prompt; a checkout you would not `pnpm test` is one you should not open with the Keel LSP.
- **Content security policy.** Every document carries a policy with a per-response nonce (two `ctx.random.id('Nonce')` values) on its module script, `default-src 'none'`, no inline script other than the `application/json` `#k-state`, and Trusted Types (`require-trusted-types-for 'script'`, policy `keel`); dev sends it as report-only. The policy has no option, so no app widens it. Other responses carry `default-src 'none'; frame-ancestors 'none'`, and every response carries `nosniff`, `Referrer-Policy`, the cross-origin opener and resource policies, `X-Frame-Options: DENY` and a `Permissions-Policy` (k.security).
- **Report endpoint.** `POST /__keel/csp` takes policy reports without the write proof, since it changes no state. Bodies over 16 KiB are 413 and not logged; past 100 reports in 60 s the rest are counted, not logged. A report is logged as directive, blocked kind or origin and route id; no path, query or sample (k.security).
- **Personal data.** `schema.pii(class)` marks personal data. It serializes where the app sends it and is redacted in session capture, input events, the server log and error text; a marked node in a route `params` or `search` is E1111. The evidence bundle holds no app value, and `keel evidence` signs it with `KEEL_EVIDENCE_KEY`, an Ed25519 key read only from the environment (k.privacy, k.evidence).
- **Mode.** Servers default to production; dev serves inspect and error text.
- **Writes.** A write needs same-site proof, else 403 `keel.denied`: `Sec-Fetch-Site` of `same-origin` or `none`, an `Origin` equal to the server's, `x-keel: 1` together with `accept: application/json`, or, on an API route, an `Origin` in the allowed list (below). A request with neither `Sec-Fetch-Site` nor `Origin` is admitted, since no browser sends a cross-site write without them; submitted values drop `__proto__`, `constructor`, `prototype`. An action body over `maxBodyBytes` (default 1 MiB) is 413 `keel.payloadTooLarge` and nothing runs.
- **Allowed origins.** `KEEL_ALLOW_ORIGINS` (`createApp({ allow })`) lists http(s) origins that may call API routes from another origin; `*` or a value with a path is E1560. A request is granted only when its `Origin` equals a listed origin's serialization exactly (scheme, host and port; a near miss, `null` or a path matches nothing) and the route is declared `api: true`. The grant is the `access-control-allow-origin` of that origin, `access-control-allow-credentials: true` and `vary: origin` on the response, the same-site proof for a write, and, for an `OPTIONS` with `access-control-request-method`, a 204 listing the route's methods and the headers `accept, content-type, x-keel`. That preflight is answered before any guard, loader or action runs. Pages, assets, the document fallback of a host and every unlisted origin get no header: a preflight is 405 and a write is 403. The grant is the reach of a same-origin page and carries the caller cookie only where the browser sends it (same-site origins); an allowed origin is trusted with everything an API route returns to a caller, so list only origins you serve. A request from an allowed origin with `Sec-Fetch-Site: cross-site` is logged once per origin as W1567 (k.hosting).
- **Inspect.** Dev and the Vite preview server only. It answers a loopback or listed host whose `Origin` is its own or listed; an absent `Origin` is admitted for GET only, so a POST needs a matching `Origin`. The document is decided before the request scope exists, so it never lists another request's stores. Inspector sections come from `read(ctx)` hooks that stdlib code registers, and the viewer shows each value as JSON; a `Secret` in a section value encodes as `"[secret]"`.
- **State in the page.** `#k-state` carries only stores created in the request scope (components), and on an island document the client-readable part of the `std` config `createApp({ std })` bound: only packages that declare `clientStd(pkg)`, and only the served deployable's modules. A `client` bundle embeds the same part. Every other package's config stays on the server; the default is server-only, since a private repo's `module.ts` is not public. Secrets still come through `ctx`, never `std`. Stores a loader or action creates through `stores` live for one request and persist through `ctx.storage` under `keel.store.<id>`; they never enter `#k-state`, and no process-shared log can be exposed.
- **Forwarding.** A request for a path a peer deployable serves is sent to that peer's configured origin with the request's path and search; a path starting `//` or `/\` is not forwarded. No redirect is followed, the body is capped at `maxBodyBytes`, hop-by-hop headers are dropped, and an unreachable peer is 502. A request that carries `x-keel-forwarded` is not forwarded again, and any client can send that header, so it only makes the receiving deployable answer for itself. `service()` calls never follow a redirect either.
- **Event streams.** A live loader's stream runs its guards first, and a denial is 403 with no redirect. The response is `no-store`, errors pass through the same public error rule as documents, its stores open and are never saved, and it ends on request abort or `close()`. The server caps open streams per app (`maxStreams`, default 1,000; past it 503 `keel.busy`, no loader runs), and `@keel/std-channels` caps them per caller (`perCaller`, default 8) and per process. The server's cap is one pool for every live loader of the app, with no per-caller share, and a caller cookie costs one write to obtain, so one client that opens streams up to the cap makes every other subscriber get 503 until its streams end.
- **Request isolation.** Every request has its own isolated store registry and its own store instances, so overlapping requests cannot read each other's half-done writes .
- **Caller identity.** The caller cookie (`HttpOnly; SameSite=Lax; Path=/`) is minted on a write that has none. It is a per-browser token. On https it is `__Host-keel-caller` with `Secure`, which no sibling subdomain can set; on http it is `keel-caller`. `createApp({ secure })` says which; unset, the request URL's scheme does, and a first `x-forwarded-proto` value of `https` upgrades it, never downgrades it. A client that spoofs the header over plain http only gets a `Secure` cookie its own browser drops. `createApp({ origin })`, which the generated entry sets from `KEEL_ORIGIN`, decides it before either when set. `secure: true` or an https `origin` is the production setting, and a production start with neither logs W1557. Its value is HMAC-signed under `createApp({ secret })` (at least 32 bytes, else E1556; a production start without one logs W1556), and a value the server did not sign counts as none. Loaders and actions see only its base64url SHA-256 as `caller`, which apps record in tx `meta` to scope undo, so a stored snapshot never holds a cookie that could be replayed. It is not authentication: anyone who holds the cookie is that caller. Residual risk (fixation): over plain http, or behind a proxy that sends no `x-forwarded-proto` while `secure` is unset, the cookie is `keel-caller`, and a sibling host can plant a validly signed value it obtained with one write of its own. The server cannot see whether a cookie was set `Secure` or by whom, so rotating such a cookie on the next write would rotate every http caller and stop nothing. This stays by design; https with `__Host-` closes it. Without a shared `secret`, callers reset per restart and per instance, which fails closed.
- **Stored logs.** A store keeps at most `logLimit` log entries (default 256), so a saved snapshot, and the work to restore it per request, stays bounded.
- **Durable storage.** `@keel/std-db` keeps each store's snapshot, std.jobs queues, std.schedules marks and std.workflows stores as written, `.pii` data included: encryption at rest is the database's or the disk's, not Keel's. The driver puts no stored value in a log line, diagnostic or error message, and `KEEL_DATABASE_URL` is never printed: E1560, E2152 and E2153 name the key and no part of its value. App code cannot import the driver (E2151), so state reaches the database only through stores and `ctx.storage` (std.db).
- **Credentials** (std.credentials, std.tokens). `credentials(ctx).hash` takes a `Secret` and gives a salted `scrypt` string that names its parameters, at N = 2^17, r = 8, p = 1 or a higher N the app's `std` config sets; a lower one is E1158. `verify` compares in constant time and says when to rehash. `mint` gives a token with 256 random bits as a `Secret` and its SHA-256 digest to store, with the expiry inside the digest; `check` finds the row by the token's id, compares in constant time, and refuses a token at or past its expiry on `ctx.clock`. `credentials.expired` is answered only to the real token. No stored digest comes from a secret the package did not mint. Real salts and tokens come from the system generator. A sim ctx's are seeded and marked, and a real ctx refuses them. An unknown account costs one derivation, so timing does not list accounts. A process runs 2 derivations at once and answers 503 past its waiting bound: a sign-in flood can deny sign-in, and rate limiting is the operator's. Not covered: a token's way out of a write and in by a header, which the kernel does not carry; a key in either hash, so someone who can write the database can plant a digest or move an expiry; revocation other than deleting the row; clocks that disagree between servers; a credential the app must present later, which needs encryption; password rules and lockout; a `Hashed` or `Digested` field an app returns from a loader.
- **Shells.** In a Capacitor or Tauri shell the caller cookie is meant to live in the shell's native cookie store and go only to the origin that set it. Whether the native HTTP client keeps and sends the cookie has not been verified on a device, and no native build has run, so treat that as unproven. The `net` driver sends the page's own-origin requests to the one `KEEL_ORIGIN` the build was given (https outside `localhost`, else E1574), and a request to another origin goes as written. Neither shell package replaces the global `fetch` (k.shell, std.shells).

Stdlib commitments:

- **Sessions** (std.sessions). `record(ctx)` is called by the app; in a browser it keeps transaction payloads, store state and input values, except a module's `redact` entries, `s.secret` fields and password inputs; the k.ctx observer masks `input` values and one-character keys on any field that has been a password field (`type` or `autocomplete`), for the rest of the ctx, before any observer sees them. Store state cannot hold a secret: `store()` throws E1303 on a state schema holding `s.secret`, and `keel check` reports it and `reveal` in a transaction function early. A revealed value is plain data; the Secrets commitment says what E1112 catches. An `el:` entry covers every event of that element, `s.secret` search values are redacted in `nav` hrefs, and error messages and `data` (but `data.at`) drop redacted values. On the server `record` is a no-op. Uploads are same-origin JSON POSTs under the k.server write proof: `record` throws E2006 on an `upload` that is not credential-free http(s) on the document's origin, and the real `put` refuses another origin and never follows a redirect; a failed upload stays in the session as `sessions.putFailed`. A recorder started late still gets the errors reported since the page's current route, which the ctx keeps in memory (the first 16) for a new observer; it scrubs them of the current values of `el:` fields and password fields and of earlier redacted payloads, and when a redacted field is gone it keeps only the error's code and `data.at`. Each kept error is uploaded once per ctx. An island page whose loader failed carries that error's code and `data.at` (nothing else) in `#k-state`. `sessions.ingest` takes unauthenticated posts of at most 256 KiB (measured as filed) and computes each fingerprint from the session alone (the first error event's code, recorded `data.at` and route id), never from a posted value. Anonymous ingest is one bounded buffer: 5 sessions per fingerprint, 64 fingerprints, 4 MiB, the oldest `last` evicted first. A flood of 4 MiB of distinct fingerprints (or 64 small sessions with distinct routes) replaces its contents, and five posts with a real bug's code, `data.at` and route replace that fingerprint's kept sessions and raise its `count`. A caller cookie is no defence, since a cookieless POST mints a new caller; the defence is the operator's rate limiting in front of the service. `sessions.list` is behind the package guard `sessions.reader`, which admits only a `caller` hash listed in a module's `readers`; `readers` and `expose` are server-only config, and only `redact` reaches browsers (`clientStd` keys). `to-test`, and through it the GitHub Action's issue bodies, writes every `s.string()` value as `x` repeated unless an `expose` entry names it, so a public repository gets only exposed values. Session files under `.keel/sessions/` hold everything `record` kept; a scaffolded project's `.gitignore` lists the folder and nothing redacts the files, so the emitted test, not the session file, is the form to share. The GitHub Action (`@keel/std-sessions/action`) runs the project's own test code under the job's privileges, and any child process of the job can reach the job's tokens, so it belongs on a repository whose ingest service only the project writes to.

Grows per package.

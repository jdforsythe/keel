# Threat model (seed)

Assets: user data in stores and logs; secrets in server env; session files. Adversaries: web attackers (XSS, CSRF, injection), malicious dependencies, agents reaching for `unsafe`.

Kernel commitments:

- **Output.** Escaped by default. One URL policy covers `href`, `src`, `action`, `formaction`, `xlink:href`, `poster`, `ping` (http, https, mailto, tel only; `srcdoc` is always `about:blank`); the runtime enforces it and E1003 reports literals it would blank (RFC 0024, red-team 0084).
- **Secrets.** `s.secret` values (`Secret<T>`) serialize and log only as `"[secret]"`, never restore from JSON, and are read only by `reveal` in `*.server.ts`. E1105 (`packages/check/src/rules/revealInServerFile.ts`) reports `reveal` anywhere else in app code (RFC 0026).
- **Server and client split.** `.server.ts` cannot reach the client. Documents load runtime JS only when a page has islands, so a static page carries no module script (RFC 0037). Built client assets are read once at startup from the deployable's build directory and served only from that fixed set, so a request path never reaches the filesystem (RFC 0048). Only files whose real path is inside `assets/` are read: no symlink or `..` manifest entry leads out. Every asset response is `nosniff`. Only files the manifest names with a content hash are `immutable`; others are `no-cache` (RFC 0057).
- **Dependencies and code.** `unsafe.*` is justified and counted.
- **Stdlib loading.** `keel check` (binary, MCP `check`, and every LSP open or change), `keel build`, `keel dev` (the Vite plugin), `keel session` and the MCP `tools/list` and `session` calls import each `deps` entry named `@keel/std-[a-z0-9-]+`, and its `./tools` export when it has one, resolved as an ESM import from the manifest's folder through its own and its ancestors' `node_modules`; any other `@keel/std-` name is E1159 and is not imported, and a `deps` entry outside `@keel/std-` is never imported (RFC 0066). This runs the project's own dependencies, the trust level of `vite dev` or `pnpm test` in that checkout, so opening an untrusted clone in an editor with the Keel LSP runs its stdlib packages. The user decided (2026-11-09, backlog 0194 closed) that this name gate is the trust boundary: no workspace-trust prompt; a checkout you would not `pnpm test` is one you should not open with the Keel LSP.
- **Mode.** Servers default to production; dev serves inspect and error text (RFC 0022).
- **Writes.** A write needs same-site proof, else 403 `keel.denied`: `Sec-Fetch-Site` of `same-origin` or `none`, an `Origin` equal to the server's, or `x-keel: 1` together with `accept: application/json`. A request with neither `Sec-Fetch-Site` nor `Origin` is admitted, since no browser sends a cross-site write without them; submitted values drop `__proto__`, `constructor`, `prototype` (RFC 0022). An action body over `maxBodyBytes` (default 1 MiB) is 413 `keel.payloadTooLarge` and nothing runs (RFC 0024).
- **Inspect.** Dev and the Vite preview server only. It answers a loopback or listed host whose `Origin` is its own or listed; an absent `Origin` is admitted for GET only, so a POST needs a matching `Origin` (RFC 0022, RFC 0024). The document is decided before the request scope exists, so it never lists another request's stores (RFC 0042). Inspector sections come from `read(ctx)` hooks that stdlib code registers, and the viewer shows each value as JSON; a `Secret` in a section value encodes as `"[secret]"` (RFC 0042).
- **State in the page.** `#k-state` carries only stores created in the request scope (components), and on an island document the client-readable part of the `std` config `createApp({ std })` bound (RFC 0069): only packages that declare `clientStd(pkg)`, and only the served deployable's modules. A `client` bundle embeds the same part. Every other package's config stays on the server; the default is server-only, since a private repo's `module.ts` is not public. Secrets still come through `ctx`, never `std`. Stores a loader or action creates through `stores` live for one request and persist through `ctx.storage` under `keel.store.<id>`; they never enter `#k-state`, and no process-shared log can be exposed (`createApp({ expose })` is gone) (RFC 0044, superseding the `expose` opt-in of RFC 0022).
- **Forwarding.** A request for a path a peer deployable serves is sent to that peer's configured origin with the request's path and search; a path starting `//` or `/\` is not forwarded. No redirect is followed, the body is capped at `maxBodyBytes`, hop-by-hop headers are dropped, and an unreachable peer is 502. A request that carries `x-keel-forwarded` is not forwarded again, and any client can send that header, so it only makes the receiving deployable answer for itself. `service()` calls never follow a redirect either.
- **Event streams.** A live loader's stream runs its guards first, and a denial is 403 with no redirect. The response is `no-store`, errors pass through the same public error rule as documents, its stores open and are never saved, and it ends on request abort or `close()`. Nothing caps the number of open streams.
- **Request isolation.** Every request has its own isolated store registry and its own store instances, so overlapping requests cannot read each other's half-done writes (RFC 0022, RFC 0044).
- **Caller identity.** The caller cookie (`HttpOnly; SameSite=Lax; Path=/`) is minted on a write that has none. It is a per-browser token. On https it is `__Host-keel-caller` with `Secure`, which no sibling subdomain can set; on http it is `keel-caller`. `createApp({ secure })` says which; unset, the request URL's scheme does, and a first `x-forwarded-proto` value of `https` upgrades it, never downgrades it (RFC 0060). A client that spoofs the header over plain http only gets a `Secure` cookie its own browser drops. `createApp({ origin })`, which the generated entry sets from `KEEL_ORIGIN`, decides it before either when set. `secure: true` or an https `origin` is the production setting, and a production start with neither logs W1557. Its value is HMAC-signed under `createApp({ secret })` (at least 32 bytes, else E1556; a production start without one logs W1556), and a value the server did not sign counts as none (RFC 0057). Loaders and actions see only its base64url SHA-256 as `caller`, which apps record in tx `meta` to scope undo, so a stored snapshot never holds a cookie that could be replayed (RFC 0054). It is not authentication: anyone who holds the cookie is that caller (RFC 0044). Residual risk (fixation): over plain http, or behind a proxy that sends no `x-forwarded-proto` while `secure` is unset, the cookie is `keel-caller`, and a sibling host can plant a validly signed value it obtained with one write of its own. The server cannot see whether a cookie was set `Secure` or by whom, so rotating such a cookie on the next write would rotate every http caller and stop nothing. This stays by design; https with `__Host-` closes it (RFC 0060). Without a shared `secret`, callers reset per restart and per instance, which fails closed (RFC 0057).
- **Stored logs.** A store keeps at most `logLimit` log entries (default 256), so a saved snapshot, and the work to restore it per request, stays bounded (RFC 0054).

Stdlib commitments:

- **Sessions** (std.sessions, RFC 0070). `record(ctx)` is called by the app; in a browser it keeps transaction payloads, store state and input values, except a module's `redact` entries, `s.secret` fields and password inputs; the k.ctx observer masks `input` values and one-character keys on any field that has been a password field (`type` or `autocomplete`), for the rest of the ctx, before any observer sees them. Store state cannot hold a secret: `store()` throws E1303 on a state schema holding `s.secret`, and `keel check` reports it and `reveal` in a transaction function early. A revealed value copied into a plain payload or state field is not detected. An `el:` entry covers every event of that element, `s.secret` search values are redacted in `nav` hrefs, and error messages and `data` (but `data.at`) drop redacted values. On the server `record` is a no-op. Uploads are same-origin JSON POSTs under the k.server write proof: `record` throws E2006 on an `upload` that is not credential-free http(s) on the document's origin, and the real `put` refuses another origin and never follows a redirect; a failed upload stays in the session as `sessions.putFailed`. A recorder started late still gets the errors reported since the page's current route, which the ctx keeps in memory (the first 16) for a new observer; it scrubs them of the current values of `el:` fields and password fields and of earlier redacted payloads, and when a redacted field is gone it keeps only the error's code and `data.at`. Each kept error is uploaded once per ctx. An island page whose loader failed carries that error's code and `data.at` (nothing else) in `#k-state`. `sessions.ingest` takes unauthenticated posts of at most 256 KiB (measured as filed) and computes each fingerprint from the session alone (the first error event's code, recorded `data.at` and route id), never from a posted value. Anonymous ingest is one bounded buffer: 5 sessions per fingerprint, 64 fingerprints, 4 MiB, the oldest `last` evicted first. A flood of 4 MiB of distinct fingerprints (or 64 small sessions with distinct routes) replaces its contents, and five posts with a real bug's code, `data.at` and route replace that fingerprint's kept sessions and raise its `count`. A caller cookie is no defence, since a cookieless POST mints a new caller; the defence is the operator's rate limiting in front of the service. `sessions.list` is behind the package guard `sessions.reader`, which admits only a `caller` hash listed in a module's `readers`; `readers` and `expose` are server-only config, and only `redact` reaches browsers (`clientStd` keys). `to-test`, and through it the GitHub Action's issue bodies, writes every `s.string()` value as `x` repeated unless an `expose` entry names it, so a public repository gets only exposed values. Session files under `.keel/sessions/` hold everything `record` kept; a scaffolded project's `.gitignore` lists the folder and nothing redacts the files, so the emitted test, not the session file, is the form to share. The GitHub Action (`@keel/std-sessions/action`) runs the project's own test code under the job's privileges, and any child process of the job can reach the job's tokens, so it belongs on a repository whose ingest service only the project writes to.

Grows per package.

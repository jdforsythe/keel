# Threat model (seed)

Assets: user data in stores and logs; secrets in server env; session files. Adversaries: web attackers (XSS, CSRF, injection), malicious dependencies, agents reaching for `unsafe`.

Kernel commitments:

- **Output.** Escaped by default. One URL policy covers `href`, `src`, `action`, `formaction`, `xlink:href`, `poster`, `ping` (http, https, mailto, tel only; `srcdoc` is always `about:blank`); the runtime enforces it and E1003 reports literals it would blank.
- **Secrets.** `s.secret` values (`Secret<T>`) serialize and log only as `"[secret]"`, never restore from JSON, and are read only by `reveal` in `*.server.ts`. E1105 (`packages/check/src/rules/revealInServerFile.ts`) reports `reveal` anywhere else in app code. No `Secret` reaches storage or a database. Store state refuses one (`store()` throws E1303), a snapshot folds every log entry up to the last secret payload, a plain or JSON field refuses one, and job inputs, channel messages and outbox bodies refuse one (E2503, E2602, E2651). What `reveal` returns is plain data, frozen deep when the secret is made (the caller's own object where `s.json()` keeps it), so it cannot change after the server reads it; nothing at run time tells it from another string. E1112 reports a revealed value reaching a log, storage, a file, store state or a throw in the same file (k.reveal), and the server writes `[secret]` in its `diag` records and its `req` path in place of each string, number and data key of each secret a request or a runner's `run` makes or reveals: its input, `bearer`, a later parse, a minted token, a record's keys (past 2,000,000 characters of their forms or 100,000 values, or for a text over 2,000,000 characters, everything after the server's own prefix is one mark). A secret in a route's `params` or `search` is E1111, and the query is never logged. A secret made at process startup, at module scope, in `createApp`'s config or in an earlier request joins the set of each scope that reveals it. Limits: a value revealed outside every scope and kept as plain text is in no scope, so a log line that holds it writes it; a secret made by an in-process request a runner starts (`service({ module })`) joins that request's set, not the runner's, so a runner that throws the revealed value logs it; and a `req` path no route lines up with is logged as it came: a raw `/` in a plain param before the secret, a static typo or homoglyph, an extra leading segment, a secret search value in a link missing its `?`. The path is marked by every route of the table, a peer's too, so a front server marks a path it forwards; a path longer than a secret route it lines up with is cut at the secret, the rest one `[secret]`, and in a table with a secret param a segment holding `%2F` or `%5C` in either case is cut the same way; a failed forward logs the error's name, never its message. These are not detected: a value carried through a helper's parameter, a callback or an import, std.jobs' `enqueue`, a response, and a credential the app parses as `s.string`, which is plain data from the start. The rules stop accidents. An author who means to store a secret can always do so; for a token the documented form is the digest `tokens(ctx).mint` gives (std.tokens).
- **Server log.** Every text a request or a thrown value puts in a log record is scrubbed, then escaped, then cut (k.serverlog): control characters, U+2028, U+2029 and `…` are written as `\u` and four hex digits, so a thrown line break cannot forge a record and no terminal escape reaches a tailing terminal; a message or path keeps 2,048 characters, a frame or method 256, then `…+<n>`, which input cannot forge. A record is at most 8,192 characters and 12,288 bytes of UTF-8 plus a `req` record's route id, which is the app's text and is not cut. The cut keeps a head of the scrubbed text, so it never shows part of a marked value, and the scrub reads at most 2,000,000 characters of any text.
- **Server and client split.** On a `node` or `static` deployable no byte of a server-only file (`*.server.*`, `*.guard.*` by the name on disk, any case and extension: loaders, actions, guards, data) is in a browser asset: every browser bundle, each worker's included, stubs those JS and TS files and fails with E1007 when one, a non-JS server-only file, a handler (known by binding) or a Node built-in (from a list Keel ships) is still in the graph, a miscased specifier is E1010, and `keel build` stops on any `keel check` error. No environment value is in a built file but the public origins `KEEL_PEER_<NAME>` and a shell's `KEEL_ORIGIN`: a project config that sets `envPrefix` or `define` fails the build, and an emitted file holding a `KEEL_*` value of 8 or more characters fails it. On a `client` deployable loaders, actions and guards run in the browser and ship. Limits: a value in a file that is not server-only ships when a browser file imports it, so a secret hard-coded in a schema, a `routes.ts` or a shared helper is public; a script a project plugin bundles in a pass of its own, a file copied from `public/`, and a value a project plugin writes of a variable not named `KEEL_*` are the project's; the build's own names (`KEEL_DEPLOYABLE`, `KEEL_SHELL`) are not scanned (k.boundary, k.bundle). Documents load runtime JS only when a page has islands, so a static page carries no module script. Built client assets are read once at startup from the deployable's build directory and served only from that fixed set, so a request path never reaches the filesystem. Only files whose real path is inside `assets/` are read: no symlink or `..` manifest entry leads out. Every asset response is `nosniff`. Only files the manifest names with a content hash are `immutable`; others are `no-cache`.
- **Dependencies and code.** `unsafe.*` is justified and counted.
- **Stdlib loading.** `keel check` (binary, MCP `check`, and every LSP open or change), `keel build`, `keel dev` (the Vite plugin), `keel session`, `keel report` and the MCP `tools/list`, `session` and `report` calls import each `deps` entry named `@keel/std-[a-z0-9-]+`, and its `./tools` export when it has one, resolved as an ESM import from the manifest's folder through its own and its ancestors' `node_modules`; any other `@keel/std-` name is E1159 and is not imported, and a `deps` entry outside `@keel/std-` is never imported. This runs the project's own dependencies, the trust level of `vite dev` or `pnpm test` in that checkout, so opening an untrusted clone in an editor with the Keel LSP runs its stdlib packages. This name gate is the trust boundary: no workspace-trust prompt; a checkout you would not `pnpm test` is one you should not open with the Keel LSP.
- **Content security policy.** Every document carries a policy with a per-response nonce (two `ctx.random.id('Nonce')` values) on its module script, `default-src 'none'`, no inline script other than the `application/json` `#k-state`, and Trusted Types (`require-trusted-types-for 'script'`, policy `keel`); dev sends it as report-only. The policy has no option, so no app widens it. Other responses carry `default-src 'none'; frame-ancestors 'none'`, and every response carries `nosniff`, `Referrer-Policy`, the cross-origin opener and resource policies, `X-Frame-Options: DENY` and a `Permissions-Policy` (k.security).
- **Report endpoint.** `POST /__keel/csp` takes policy reports without the write proof, since it changes no state. Bodies over 16 KiB are 413 and not logged; past 100 reports in 60 s the rest are counted, not logged. A report is logged as directive, blocked kind or origin and route id; no path, query or sample (k.security).
- **Personal data.** `schema.pii(class)` marks personal data. It serializes where the app sends it and is redacted in session capture, input events, the server log and error text; a marked node in a route `params` or `search` is E1111. Where a table outside `keel check` serves one anyway, a segment at a marked `params` field is `[pii]` in the `req` path by the line-up secret params use, a longer path cut there (`[secret]` where a secret param stands at the same segment). A store an island needs reaches `#k-state` with its `.pii()` values, so E1107 reports a store in client-reachable code holding a class its module's `clientPii` does not list. The evidence bundle holds no app value, and `keel evidence` signs it with `KEEL_EVIDENCE_KEY`, an Ed25519 key read only from the environment (k.privacy, k.evidence).
- **Mode.** Servers, the client root fallback (`mount`, `resume`) and the client router (`createRouter`) default to production; dev serves inspect and error text. A `keel build` client is production whatever `NODE_ENV` the build sees: the generated entries hold `mode` as a literal from Vite's command, and `keel build` runs Vite with `NODE_ENV=production`. Outside dev a `keel.unexpected` shows as `unexpected` with no data on a server page and in the router's default alert, a route's `errorElement` and a `Form`'s `error`, and the root fallback shows its code; observers and `onError` still get the full error.
- **Writes.** A write needs same-site proof, else 403 `keel.denied`: `Sec-Fetch-Site` of `same-origin` or `none`, an `Origin` equal to the server's, `x-keel: 1` together with `accept: application/json`, or, on an API route, an `Origin` in the allowed list (below). A request with neither `Sec-Fetch-Site` nor `Origin` is admitted, since no browser sends a cross-site write without them; submitted values drop `__proto__`, `constructor`, `prototype`. An action body over `maxBodyBytes` (default 1 MiB) is 413 `keel.payloadTooLarge` and nothing runs.
- **Allowed origins.** `KEEL_ALLOW_ORIGINS` (`createApp({ allow })`) lists http(s) origins that may call API routes from another origin; `*` or a value with a path is E1560. A request is granted only when its `Origin` equals a listed origin's serialization exactly (scheme, host and port; a near miss, `null` or a path matches nothing) and the route is declared `api: true`. The grant is the `access-control-allow-origin` of that origin, `access-control-allow-credentials: true` and `vary: origin` on the response, the same-site proof for a write, and, for an `OPTIONS` with `access-control-request-method`, a 204 listing the route's methods and the headers `accept, authorization, content-type, x-keel`. That preflight is answered before any guard, loader or action runs. Pages, assets, the document fallback of a host and every unlisted origin get no header: a preflight is 405 and a write is 403. The grant is the reach of a same-origin page and carries the caller cookie only where the browser sends it (same-site origins); an allowed origin is trusted with everything an API route returns to a caller, so list only origins you serve. A request from an allowed origin with `Sec-Fetch-Site: cross-site` is logged once per origin as W1567 (k.hosting).
- **Inspect.** Dev and the Vite preview server only. It answers a loopback or listed host whose `Origin` is its own or listed; an absent `Origin` is admitted for GET only, so a POST needs a matching `Origin`. The document is decided before the request scope exists, so it never lists another request's stores. Inspector sections come from `read(ctx)` hooks that stdlib code registers, and the viewer shows each value as JSON; a `Secret` in a section value encodes as `"[secret]"`.
- **State in the page.** `#k-state` carries only the request stores an island level's server render created, looked up or read (a page with no island ships none), and on an island document the client-readable part of the `std` config `createApp({ std })` bound: only packages that declare `clientStd(pkg)`, and only the served deployable's modules. A `client` bundle embeds the same part. Every other package's config stays on the server; the default is server-only, since a private repo's `module.ts` is not public. Secrets still come through `ctx`, never `std`. Stores a loader or action creates through `stores` live for one request and persist through `ctx.storage` under `keel.store.<id>`; they never enter `#k-state`, and no process-shared log can be exposed.
- **Forwarding.** A request for a path a peer deployable serves is sent to that peer's configured origin with the request's path and search; a path starting `//` or `/\` is not forwarded. No redirect is followed, the body is capped at `maxBodyBytes`, hop-by-hop headers are dropped, and an unreachable peer is 502. A request that carries `x-keel-forwarded` is not forwarded again, and any client can send that header, so it only makes the receiving deployable answer for itself. `service()` calls never follow a redirect either.
- **Event streams.** A live loader's stream runs its guards first, and a denial is 403 with no redirect. The response is `no-store`, errors pass through the same public error rule as documents, its stores open and are never saved, and it ends on request abort or `close()`. The server caps open streams per app (`maxStreams`, default 1,000; past it 503 `keel.busy`, no loader runs), and `@keel/std-channels` caps them per caller (`perCaller`, default 8), for all cookieless opens together (`perAnonymous`, default 64) and per process (`maxStreams`, default 1,000); a stream open sets no cookie. The server's cap is one pool for every live loader of the app, with no per-caller share, so one client that opens live-loader streams up to the cap makes every other subscriber get 503 until its streams end.
- **Request isolation.** Every request has its own isolated store registry and its own store instances, so overlapping requests cannot read each other's half-done writes .
- **Uncaught errors.** A served process writes one E1577 record per uncaught exception or rejection, with the route and no error text; production then stops listening, drains requests in flight for at most 10 s and exits 1 for a supervisor to restart, since its state is unknown. Work a request starts stays under the E1256 module-store check after the response; the check follows async context, not data.
- **Caller identity.** The caller cookie (`HttpOnly; SameSite=Lax; Path=/`) is minted on a write that has none. It is a per-browser token. On https it is `__Host-keel-caller` with `Secure`, which no sibling subdomain can set; on http it is `keel-caller`. `createApp({ secure })` says which; unset, the request URL's scheme does, and a first `x-forwarded-proto` value of `https` upgrades it, never downgrades it. A client that spoofs the header over plain http only gets a `Secure` cookie its own browser drops. `createApp({ origin })`, which the generated entry sets from `KEEL_ORIGIN`, decides it before either when set. `secure: true` or an https `origin` is the production setting, and a production start with neither logs W1557. Its value is HMAC-signed under `createApp({ secret })` (at least 32 bytes, else E1556; a production start without one logs W1556), and a value the server did not sign counts as none. Loaders and actions see only its base64url SHA-256 as `caller`, which apps record in tx `meta` to scope undo, so a stored snapshot never holds a cookie that could be replayed. It is not authentication: anyone who holds the cookie is that caller. Residual risk (fixation): over plain http, or behind a proxy that sends no `x-forwarded-proto` while `secure` is unset, the cookie is `keel-caller`, and a sibling host can plant a validly signed value it obtained with one write of its own. The server cannot see whether a cookie was set `Secure` or by whom, so rotating such a cookie on the next write would rotate every http caller and stop nothing. This stays by design; https with `__Host-` closes it. Without a shared `secret`, callers reset per restart and per instance, which fails closed. The cookie has no `Max-Age` unless a `node` deployable sets `caller: { days }` (1 to 400) in `topology.ts`: the cookie it mints then lasts that long from that write, never extended, and the caller hash is a long-lived device identifier, classed `.pii('network')` and recorded in the evidence bundle's `pii.json`. Either way it is not a credential.
- **Identity.** Keel authenticates no one. `user` is what the app's `identify` answers, trusted completely: the trust boundary is that function and the library, platform or proxy it calls. Keel guarantees that `user` comes only from `identify` or from an `x-keel-user` assertion another deployable of the app signed under `KEEL_SECRET` (bound to method, path, search, body and the receiving deployable; it expires 60 s after signing and a receiver ignores one expiring more than 65 s ahead of its clock; `user` at most 256 characters), never from a client value; that writes, `handle` included, pass the same-site check first; that `identify`'s errors are logged by name only; and that the only cookie it sets is the caller cookie. Cookie attributes, lifetime, rotation, fixation defence, revocation and storage of a sign-in are the library's. Limits: an event stream keeps the `user` it opened with until it closes; whoever holds `KEEL_SECRET` can assert any user to every deployable; the header is no sign-in credential and is never sent to a browser, but a captured `x-keel-user` replays that one request to that deployable until it expires, and on plain `http` between peers anyone on the path can capture it, so peers should talk over `https`; a header a proxy injects is only as good as the network that keeps clients from going around the proxy. Pages reach `handle` only by a same-origin `href` under `handle.path` (no `href` names another origin or escapes the path); a page's form posts there natively and passes the same-site check; Keel reads no answer of `fn` and sets no cookie on it. Limits: a form post may not end on another origin (`form-action 'self'`), so OAuth starts from a link; cookies are per origin, so an app with two public origins has two sign-ins. In a shell, the library's cookie is kept by the platform's native cookie store and sent by `net` to `KEEL_ORIGIN` only; Keel reads a mount answer's status and `location` only. Return links use a private-use scheme any app can claim on Android and desktop, so a return must carry nothing usable without the native store. Any app or web page can also send a link on that scheme, so the shell accepts a return link only while it has itself opened the external browser from a mount request the page started: one link per opening, within 10 minutes of it, the opening kept in `ctx.storage` across a relaunch. Requests a return link starts, and their redirects, record no opening, so an admitted link cannot admit the next. Any other return link is ignored and sends no request (k.return, k.opening). Residual risk: while an opening is pending, another app or a web page can send a return link first; it takes the opening, its GET under the mount carries the native cookies, and the real return is ignored. A library that changes state on a GET under its mount is reachable in that window only, a POST never; a flow started outside the app, or one that leaves the app again from a return link's callback, cannot return to it. An opening is not proof that a person started a sign-in: any in-app navigation to a `MountHref` that ends in the external browser records one, including a link in content another user wrote if the app renders such links. On Capacitor the launch URL can be delivered again after a webview reload; it is treated as any other link and needs a pending opening. A redirect to another origin opens in the external browser only when it is `http:` or `https:`.
- **Bearer.** An API route's handlers get the `authorization: Bearer` token as a `Secret` (`bearer`); any other value of the header is none, and pages never read it. It is scrubbed from the log and never kept by the server. It does not change `caller` or the same-site check, and an API route's response to a request that carries one is `no-store`. Any client can send one, checked or not, and its text is scrubbed from that request's own log lines wherever it appears, inside words too; a bearer of 1 or 2 characters, as written, only where it stands as a whole token. Checking it is the app's (`tokens(ctx).check`).
- **Stored logs.** A store keeps at most `logLimit` log entries (default 256), so a saved snapshot, and the work to restore it per request, stays bounded.
- **Durable storage.** `@keel/std-db` keeps each store's snapshot, std.jobs queues, std.schedules marks and std.workflows stores as written, `.pii` data included: encryption at rest is the database's or the disk's, not Keel's. The driver puts no stored value in a log line, diagnostic or error message, and `KEEL_DATABASE_URL` is never printed: E1560, E2152 and E2153 name the key and no part of its value. App code cannot import the driver (E2151), so state reaches the database only through stores and `ctx.storage` (std.db).
- **Tokens** (std.tokens). Keel hashes no password: sign-in, and the passwords behind it, are the identity source's (k.user). `mint` gives a token with 256 random bits as a `Secret` and its SHA-256 digest to store, with the expiry inside the digest; `check` finds the row by the token's id, compares in constant time, and refuses a token at or past its expiry on `ctx.clock`. `credentials.expired` is answered only to the real token. No stored digest comes from a secret the package did not mint, so a fast unsalted hash is sound. Real tokens come from the system generator. A sim ctx's are seeded and marked, and a real ctx refuses them. Not covered: a key in the digest, so someone who can write the database can plant a digest or move an expiry; revocation other than deleting the row; clocks that disagree between servers; a credential the app must present later, which needs encryption; a `Digested` field an app returns from a loader.
- **Shells.** In a Capacitor or Tauri shell the caller cookie is meant to live in the shell's native cookie store and go only to the origin that set it. Whether the native HTTP client keeps and sends the cookie has not been verified on a device, and no native build has run, so treat that as unproven. The `net` driver sends the page's own-origin requests to the one `KEEL_ORIGIN` the build was given (https outside `localhost`, else E1574), and a request to another origin goes as written. Neither shell package replaces the global `fetch` (k.shell, std.shells). A sign-in cookie a library sets lives in the same native cookie store, a file in the app's private data that Keel does not encrypt (the WebView cookie database, `Cookies.binarycookies`, `.cookies`); Keel adds no secure slot, and a library or platform that needs one brings its own native plugin.

Stdlib commitments:

- **Sessions** (std.sessions). `record(ctx)` is called by the app; in a browser it keeps transaction payloads, store state and input values, except a module's `redact` entries, `s.secret` fields and password inputs; the k.ctx observer masks `input` values and one-character keys on any field that has been a password field (`type` or `autocomplete`), for the rest of the ctx, before any observer sees them. Store state cannot hold a secret: `store()` throws E1303 on a state schema holding `s.secret`, and `keel check` reports it and `reveal` in a transaction function early. A revealed value is plain data; the Secrets commitment says what E1112 catches. An `el:` entry covers every event of that element, `s.secret` search values are redacted in `nav` hrefs, and error messages and `data` (but `data.at`) drop redacted values. On the server `record` is a no-op. Uploads are same-origin JSON POSTs under the k.server write proof: `record` throws E2006 on an `upload` that is not credential-free http(s) on the document's origin, and the real `put` refuses another origin and never follows a redirect; a failed upload stays in the session as `sessions.putFailed`. A recorder started late still gets the errors reported since the page's current route, which the ctx keeps in memory (the first 16) for a new observer; it scrubs them of the current values of `el:` fields and password fields and of earlier redacted payloads, and when a redacted field is gone it keeps only the error's code and `data.at`. Each kept error is uploaded once per ctx. An island page whose loader failed carries that error's code and `data.at` (nothing else) in `#k-state`. `sessions.ingest` takes unauthenticated posts of at most 256 KiB (measured as filed) and computes each fingerprint from the session alone (the first error event's code, recorded `data.at` and route id), never from a posted value. Anonymous ingest is one bounded buffer: 5 sessions per fingerprint, 64 fingerprints, 4 MiB, the oldest `last` evicted first. A flood of 4 MiB of distinct fingerprints (or 64 small sessions with distinct routes) replaces its contents, and five posts with a real bug's code, `data.at` and route replace that fingerprint's kept sessions and raise its `count`. A caller cookie is no defence, since a cookieless POST mints a new caller; the defence is the operator's rate limiting in front of the service. `sessions.list` is behind the package guard `sessions.reader`, which admits only a `caller` hash listed in a module's `readers`; `readers` and `expose` are server-only config, and only `redact` reaches browsers (`clientStd` keys). `to-test`, and through it the GitHub Action's issue bodies, writes every `s.string()` value as `x` repeated unless an `expose` entry names it, so a public repository gets only exposed values. Session files under `.keel/sessions/` hold everything `record` kept; a scaffolded project's `.gitignore` lists the folder and nothing redacts the files, so the emitted test, not the session file, is the form to share. The GitHub Action (`@keel/std-sessions/action`) runs the project's own test code under the job's privileges, and any child process of the job can reach the job's tokens, so it belongs on a repository whose ingest service only the project writes to. `keel session ingest` and `keel session monitor` send `KEEL_SESSIONS_TOKEN`, and `keel report` with a url that has a path or a query sends `KEEL_REPORT_TOKEN`, as the caller cookie of that one request: each is read from the environment of the command, goes only to the url the command was given (a redirect to another origin drops it, as `fetch` does), and is never written to a file or printed. `keel report` sends its token to an `http` url too, where anyone on the path can read it. `keel report` leaves the url's query out of its E1056 message.
- **Outbox** (std.offline, std.outbox-owner). Each queued write holds the `owner` its page gave `send`, the request's `user` (k.user) or `""`, and a flush sends it in `body.write`. The caller cookie is shared by every tab of a browser and does not change at sign-in, so a tab can flush a write queued by a user that a second tab has since signed out, or replaced by signing in another user. The action behind each outbox endpoint passes the write through `writeFor` with the request's `user`; a write of another owner is answered 400 `offline.owner`, nothing is saved, and the entry is `failed` and never posted again. Limits: the check runs when the action runs, so a sign-in that lands after it leaves the write committed under the owner who queued it; a write the server committed whose answer was lost, resent after the owner changed, is refused though the server holds it; an action that spreads `input.write` into `tx` without `writeFor` commits a write of any owner; and the check decides which owner a write commits under, not what reaches the server, since a refused entry's body still reaches the action. Deploy the server before the client: a client that sends no `owner` is answered 422 `keel.fields` and commits nothing.

# Threat model (seed)

Assets: user data in stores and logs; secrets in server env; session files. Adversaries: web attackers (XSS, CSRF, injection), malicious dependencies, agents reaching for `unsafe`.

Kernel commitments:

- **Output.** Escaped by default. One URL policy covers `href`, `src`, `action`, `formaction`, `xlink:href`, `poster`, `ping` (http, https, mailto, tel only; `srcdoc` is always `about:blank`); the runtime enforces it and E1003 reports literals it would blank (RFC 0024, red-team 0084).
- **Secrets.** `s.secret` values (`Secret<T>`) serialize and log only as `"[secret]"`, never restore from JSON, and are read only by `reveal` in `*.server.ts`. E1105 (`packages/check/src/rules/revealInServerFile.ts`) reports `reveal` anywhere else in app code (RFC 0026).
- **Server and client split.** `.server.ts` cannot reach the client. Documents load runtime JS only when a page has islands, so a static page carries no module script (RFC 0037). Built client assets are read once at startup from the deployable's build directory and served only from that fixed set, so a request path never reaches the filesystem (RFC 0048). Only files whose real path is inside `assets/` are read: no symlink or `..` manifest entry leads out. Every asset response is `nosniff`. Only files the manifest names with a content hash are `immutable`; others are `no-cache` (RFC 0057).
- **Dependencies and code.** Parameterized queries only (stdlib db). `unsafe.*` is justified and counted.
- **Stdlib loading.** `keel check` (binary, MCP `check`, and every LSP open or change) and `keel build` import each `deps` entry named `@keel/std-[a-z0-9-]+`, resolved as an ESM import from the manifest's folder through its own and its ancestors' `node_modules`; any other name is E1159 and is not imported (RFC 0066). This runs the project's own dependencies, the trust level of `vite dev` or `pnpm test` in that checkout, so opening an untrusted clone in an editor with the Keel LSP runs its stdlib packages. The user decided (2026-11-09, backlog 0194 closed) that this name gate is the trust boundary: no workspace-trust prompt; a checkout you would not `pnpm test` is one you should not open with the Keel LSP.
- **Mode.** Servers default to production; dev serves inspect and error text (RFC 0022).
- **Writes.** A write needs same-site proof (`Sec-Fetch-Site`, `Origin`, or `x-keel`), else 403 `keel.denied`; submitted values drop `__proto__`, `constructor`, `prototype` (RFC 0022). An action body over `maxBodyBytes` (default 1 MiB) is 413 `keel.payloadTooLarge` and nothing runs (RFC 0024).
- **Inspect.** Dev only. It answers a loopback or listed host whose `Origin` is its own or listed; an absent `Origin` is admitted for GET only, so a POST needs a matching `Origin` (RFC 0022, RFC 0024). The document is decided before the request scope exists, so it never lists another request's stores (RFC 0042). Inspector sections come from `read(ctx)` hooks that stdlib code registers, and the viewer shows each value as JSON; a `Secret` in a section value encodes as `"[secret]"` (RFC 0042).
- **State in the page.** `#k-state` carries only stores created in the request scope (components), and on an island document the client-readable part of the `std` config `createApp({ std })` bound (RFC 0069): only packages that declare `clientStd(pkg)`, and only the served deployable's modules. A `client` bundle embeds the same part. Every other package's config stays on the server; the default is server-only, since a private repo's `module.ts` is not public. Secrets still come through `ctx`, never `std`. Stores a loader or action creates through `stores` live for one request and persist through `ctx.storage` under `keel.store.<id>`; they never enter `#k-state`, and no process-shared log can be exposed (`createApp({ expose })` is gone) (RFC 0044, superseding the `expose` opt-in of RFC 0022).
- **Request isolation.** Every request has its own isolated store registry and its own store instances, so overlapping requests cannot read each other's half-done writes (RFC 0022, RFC 0044).
- **Caller identity.** The caller cookie (`HttpOnly; SameSite=Lax; Path=/`) is minted on a write that has none. It is a per-browser token. On https it is `__Host-keel-caller` with `Secure`, which no sibling subdomain can set; on http it is `keel-caller`. `createApp({ secure })` says which; unset, the request URL's scheme does, and a first `x-forwarded-proto` value of `https` upgrades it, never downgrades it (RFC 0060). A client that spoofs the header over plain http only gets a `Secure` cookie its own browser drops. `secure: true` is the production setting, and a production start without it logs W1557. Its value is HMAC-signed under `createApp({ secret })` (at least 32 bytes, else E1556; a production start without one logs W1556), and a value the server did not sign counts as none (RFC 0057). Loaders and actions see only its base64url SHA-256 as `caller`, which apps record in tx `meta` to scope undo, so a stored snapshot never holds a cookie that could be replayed (RFC 0054). It is not authentication: anyone who holds the cookie is that caller (RFC 0044). Residual risk (fixation): over plain http, or behind a proxy that sends no `x-forwarded-proto` while `secure` is unset, the cookie is `keel-caller`, and a sibling host can plant a validly signed value it obtained with one write of its own. The server cannot see whether a cookie was set `Secure` or by whom, so rotating such a cookie on the next write would rotate every http caller and stop nothing. This stays by design; https with `__Host-` closes it (RFC 0060). Without a shared `secret`, callers reset per restart and per instance, which fails closed (RFC 0057).
- **Stored logs.** A store keeps at most `logLimit` log entries (default 256), so a saved snapshot, and the work to restore it per request, stays bounded (RFC 0054).

Stdlib commitments:

- **Sessions** (std.sessions, RFC 0070). `record` is on by default in a browser and keeps transaction payloads, store state and input values, except a module's `redact` entries, `s.secret` fields and password inputs; the k.ctx observer masks `input` values and one-character keys on any field that has been a password field (`type` or `autocomplete`), for the rest of the ctx, before any observer sees them. Store state cannot hold a secret: `store()` throws E1303 on a state schema holding `s.secret`, and `keel check` reports it and `reveal` in a transaction function early. A revealed value copied into a plain payload or state field is not detected. An `el:` entry covers every event of that element, `s.secret` search values are redacted in `nav` hrefs, and error messages and `data` (but `data.at`) drop redacted values. On the server `record` is a no-op. Uploads are same-origin JSON POSTs under the k.server write proof: `record` throws E2006 on an `upload` of another origin, and a failed upload stays in the session as `sessions.putFailed`. A recorder started late still gets the errors reported since the page's current route, which the ctx keeps in memory (the first 16) for a new observer. `sessions.ingest` takes unauthenticated posts of at most 256 KiB (measured as filed) and computes each fingerprint from the session alone (the first error event's code, recorded `data.at` and route id), never from a posted value. Anonymous ingest is one bounded buffer: 5 sessions per fingerprint, 64 fingerprints, 4 MiB, the oldest `last` evicted first. A flood of 4 MiB of distinct fingerprints (or 64 small sessions with distinct routes) replaces its contents, and five posts with a real bug's code, `data.at` and route replace that fingerprint's kept sessions and raise its `count`. A caller cookie is no defence, since a cookieless POST mints a new caller; the defence is the operator's rate limiting in front of the service. `sessions.list` is behind the package guard `sessions.reader`, which admits only a `caller` hash listed in a module's `readers`; `readers` and `expose` are server-only config, and only `redact` reaches browsers (`clientStd` keys). `to-test`, and through it the GitHub Action's issue bodies, writes every `s.string()` value as `x` repeated unless an `expose` entry names it, so a public repository gets only exposed values. Session files under `.keel/sessions/` hold everything `record` kept; nothing ignores or redacts them, so the emitted test, not the session file, is the form to share. The GitHub Action (`@keel/std-sessions/action`) runs the project's own test code under the job's privileges, and any child process of the job can reach the job's tokens, so it belongs on a repository whose ingest service only the project writes to.

Grows per package.

# k.derived: Derived files
status: proposed
A derived file is one Keel computes from a project's tree: the k.compiler artifacts in `.keel/` (`a11y.json`, `deps.json`, `ids.json`, `routes.json`, `std.json`, `styles.json`), `.keel/surface.json` (k.compat) and the deploy files (k.deploy). No command judges, tests or serves from a derived file's bytes on disk. Each reader takes the derivation of the tree it runs over; the files on disk are views of it, for people, reviewers and tools.

**Derivations.** Compiled: `a11y.json`, `deps.json`, `ids.json`, `std.json` and `styles.json`, from compiling the project's sources and its libraries' files (k.compiler Artifacts). Evaluated: `routes.json` and `surface.json`, both from one evaluation of the project's contracts, route tables and store factories (k.compiler Build-time evaluation). Deploy files: from `topology.ts` and the libraries' manifests. A derivation that fails reports its codes (E1000, E1006, E1049, E1807) at `keel check` as at `keel build`, and writes no view.

**Readers.** `keel check` takes every rule's `artifacts`, E1511's API entries and the current surface of E1562, E1563 and W1564 (k.compat Base) from the derivation. `keel test` gives each test process, before its first test file, the `a11y.json` derived from the tree (k.a11y Artifacts). `keel ledger` reads each project's derived `routes.json` (k.a11y Claims). The inspect document of `keel dev` holds the derivation of the tree it serves. Other `.keel/` files are not derived and are read as their sections say: a `--base` surface, `ledger.json`, `monitored.json`. `tokens.ts` is evaluated by each run (k.a11y-static Tokens) and no view derives from it.

**Derivation cache.** An evaluated derivation is kept in `<root>/node_modules/.cache/keel/derived/` when `<root>/node_modules` exists. An entry is named by the SHA-256 of the Keel version, the project's code file paths and the evaluation's inputs: each file it loaded, and the `package.json` of each package holding one. An entry holds its key, its `inputs` (each input's path, a project file's relative to the project and another's as `<package name>/<path in the package>`, with the SHA-256 of its bytes) and the derivation; it is used only when every recorded input gets the same answer again, as k.check-cache Probes and Entries say. A cached derivation is the one a fresh evaluation gives: the cache changes the time a run takes, never its output, exit code, trailer or the files it writes. Compiled derivations are computed on every run.

**In process.** `check()` (`@keel/check`) is frozen by nature: it writes nothing; a compiled view among its files that differs from its compile is E1005, and an evaluated view is compared only with the evaluated derivation a caller passes as `derived`, else not at all.

**Refresh.** After it judges, `keel check` writes each view of each project it checked whose bytes differ from the derivation. `keel build` does so before its bundles, an applied `keel scaffold` operation after its edits in a project holding a view (k.scaffold Refresh), `keel test` before its first test file, and `keel dev` after each change it applies. `keel lsp`, and an MCP call given file texts, write no view. A write is a temporary file `<name>.<pid>.tmp` beside the view, made read-only, then renamed over it, so a reader sees one whole file; no lock is taken, and a write is skipped when one of its inputs changed during the run. No source file, nothing in `dist/` and nothing outside the project is written; in a library's own folder (k.library-pack Own folder) no view is written. A view that cannot be written is W1018 and the run goes on with the derivation. The compact trailer counts the views written, `ok check 217 files, 2 refreshed, 0 errors`, with no `refreshed` when it is 0; the json summary's `counts` hold `refreshed`, `evaluated` (evaluations run) and `cached` (evaluated derivations taken from the cache) on every run, 0 included.

**Frozen.** A command runs frozen with `--frozen`, with `CI` set to a value other than empty, `0` or `false`, or with `KEEL_FROZEN=1`, which a frozen command sets for its children and the Vite plugin reads. Frozen, no view is written, and each view present that differs from its derivation is E1005 (for `surface.json` naming the first store, contract or entry that differs), with the fix k.compiler gives; an absent view is no diagnostic.

**Version control.** `keel scaffold project` writes a `.gitignore` holding one line per compiled view and `routes.json` (`.keel/a11y.json` and so on); `surface.json` and the deploy files are committed, so a reviewer reads a change to them in the diff and the generated CI compares against the base branch's surface.

**Work.** With the cache holding a project's evaluated derivation and no input of it changed, a run evaluates nothing for that project and reads one cache entry for it. An edit to a file the evaluation did not load evaluates nothing; an edit to one it loaded runs exactly one evaluation of that project, whose new entry records exactly the files it loaded. Without `node_modules`, each run evaluates once per project with route tables. Durations are not part of the contract.

**Rules.** E1005 (k.compiler) frozen, a view that differs from its derivation; frozen or not, a file in `.keel/` that no derivation writes and no section names, never removed · W1018 a view not written: the reason (read-only file system, no permission) and the path; the run judged from the derivation. W1018 is a command code (k.check Codes): `keel check`, `keel test`, `keel build`, `keel dev` and `keel scaffold` print it, `check()` never reports it, `reportedCodes()` does not list it, and clause 8 is its fixture.

4. After the edit of clause 1, `keel check --frozen` exits 1 with one E1005, at `.keel/routes.json`, and no file in `.keel/` changes.
5. After the edit of clause 1, `keel check` with `CI=true` gives the output of clause 4, and with `CI=false` the output of clause 1.

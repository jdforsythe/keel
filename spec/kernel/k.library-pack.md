# k.library-pack: Library publishing
status: implemented

**Package.** A library (k.library) publishes, as its `package.json` `files`: `module.ts`, `src/`, `unsafe/` when it has one, `dist/` (its `tsc` build: declarations, and the `./tools` file Node imports), `.keel/ledger.json` and its `README.md`. Each `exports` key maps `keel` to the source file, then `types` and `default` to the built files; `publishConfig.exports`, where a package has one, keeps `keel` at the source path. The `@keel/*` packages its files import, and `@keel/reactive` and `@keel/runtime-dom`, which the compiler's output of its JSX imports, are `peerDependencies` and never `dependencies`, so each resolves to the app's copy. Its root `tokens.ts` is not published: an app checks the library against its own. No check imports a library's entry: `keel check`, `keel build` and every path that registers a package's rules, formats and config (E1159, k.module) import a library only through its `./tools` export, when it declares one, and read its components from source. So a library with no `./tools` needs no build for any app command; one with `./tools` ships that file as Node imports it, and a declared `./tools` that does not import is E1159 `<name> ./tools <target> does not import; build it`, `<target>` as `exports` writes it. An unmarked `@keel/std-*` package imports its entry and its `./tools`.

**Own folder.** In a folder whose `package.json` has `"keel": "library"` and a scoped name, `keel check`, `keel test` and `keel ledger` read the root `module.ts` as the manifest of the folder's one module, `src/` and `unsafe/` as that module's code, `test/` and co-located tests as its tests, and the root `tokens.ts` as its tokens. `keel check` reads the folder as an app holds the library installed: every k.library rule holds there, each diagnostic at the folder's own path, and the libraries its manifest lists are read and imported as an app's are; E1162 does not, since the folder is no app's install. `keel test` there writes no `.keel/` artifact and no `reports/a11y.json`. Its ledger file counts `unsafe` and `hostElements` over the files under `src/` and `unsafe/`, as an app counts them (k.library Ledger); its `exports` are every export of a `src/` file but tests, `Props` and `uses`, `pkg` the manifest's `id` and `file` the file's path, with rungs from its tests; its `libraries` is `{}`.

**Ledger file.** The app reads at most 262,144 UTF-8 bytes of an installed library's `.keel/ledger.json` (k.library Ledger), as `JSON.parse` does (of duplicate keys, the last wins), on `version`, `unsafe`, `hostElements` and `exports` alone, as k.ledger File gives them; other keys are not judged. E1162 (k.library), from `keel check` alone (`keel ledger` takes a failing file as none: its items are not shown, its counts recounted), has five messages, each whole within 89 units for a name of up to 38 units and counts of up to six digits: `<name> ships no .keel/ledger.json` (the name and 27 units: 65); `<name> .keel/ledger.json is over 262144 bytes` (39: 77), the file read no further; `<name> .keel/ledger.json is not a JSON object` (39: 77) for an empty file, text that is not JSON, or JSON other than an object (an array, `null`, a number, a string, a boolean); `<name> .keel/ledger.json fails its shape at <key>` (38 and the key, at most 12: 88), `<key>` the first of `version`, `unsafe`, `hostElements` and `exports` missing or holding a wrong value (an `exports` entry with a field missing or of another type is a wrong value); else `<name> ships <field> <shipped>, its files hold <counted>` (25, the field, at most 12, and both counts' digits: 87 at `hostElements` with a shipped 999999 and a counted 100000 to 999999; a longer count lengthens it), one per field that differs, `unsafe` at the entry's opening quote and `hostElements` a column after it, so `unsafe` sorts first.

**Pack.** `keel pack`, run in a library's folder, runs five steps: `kind`, `package`, `check` (`keel check`), `test` (`keel test`) and `ledger` (`keel ledger --write .keel/ledger.json`). The `ledger` step reads the run report of the `test` step, held and never written, in place of any `reports/tests/` on disk, so its rungs rest on that run. It stops at the first step that fails, reports that step's own diagnostics and then one E1164 whose message begins with the step's name, and writes no file. On success it prints one summary record whose `counts` are `{ unsafe, hostElements, exports }` of the ledger it wrote, `exports` the number of its entries, and writes `.keel/ledger.json` alone. `keel pack --check` runs the same steps and writes nothing; its `ledger` step is E1164 when `.keel/ledger.json` is missing, fails its shape as an app reads it (Ledger file), or holds an `unsafe`, `hostElements` or `exports` other than the ones `keel pack` would write; other keys are not judged. It changes nothing in the folder but the type cache under `node_modules/` (k.check-cache). A tarball is made by the package manager, whose `prepack` runs `keel pack --check`; it holds what `files` selects and what the package manager always packs (`package.json`, `README`, `LICENSE`), never a `node_modules` folder, and `keel pack` reads that list.

By one rule, a library an app could not read, check or trust as its folder is read does not pack. Each E1164, whole within 89 units for a path, key or name of up to 28 units (40 for `kind`'s name), is at `package.json` for a field, its line and a column at the start of its value, at the file for a file, and nowhere for a step:
- `kind`: no `package.json` (`kind: no package.json here, so no library`, nowhere); one that is no JSON (`kind: package.json is not JSON`, at line 1); no `"keel": "library"` (`kind: package.json has no "keel": "library"`, at `keel`, else line 1); a name that is no scoped package name (k.library Kind: `kind: name "<name>" is no scoped package name`, at `name`).
- `package`, the first in this order, at the field: no root `module.ts` (`package has no root module.ts, the library's manifest`, at `keel`); an `exports` whose `"."` entry lists no `keel` condition first (`package exports "." lists no keel condition first`), an entry holding `keel` under another condition at any depth (`package exports "<key>" nests keel under another condition`, read at the top level alone), another entry listing `keel` after another condition (`package exports "<key>" lists keel after another`; resolvers take the first matching condition, and `default` matches all, so `keel` leads or the compiler reads the built file), or a `keel` target that is no `.ts` or `.tsx` file under `src/` or `unsafe/` (`package exports "<key>" keel is no file under src/ or unsafe/`), at `exports`; no `files` (`package lists no files, so a tarball would hold everything`, at `keel`); a `files` that does not select `module.ts`, then `.keel/ledger.json`, then a file under `src/`, then `unsafe/`, sorted by path (`package files omits <path>`), or an `exports` target, entries and conditions in the order written (`package files omits <path>, exports "<key>"`), at `files`, `<path>` package-relative with no `./` (`src/Badge.tsx`, `dist/src/index.d.ts`); a `@keel/*` package the files import, or the compiler's output of a `.tsx` file imports, that `dependencies` lists (`package dependencies lists <name>; a peer resolves to the app's`, at `dependencies`) or `peerDependencies` omits (`package peerDependencies omits <name>`, at `peerDependencies`, else `keel`); a tarball holding a `.env` file, whose secrets would leave with it (`package files ships <path>, a secret's file`), or the root `tokens.ts`, the library's own check fixture where an app reads its own (`package files ships tokens.ts; an app checks the library against its own`), at `files`. A `node_modules` folder is not judged: the package manager never packs one. An entry holding `keel` both at its top level and nested under another condition is refused as nesting it (`package exports "<key>" nests keel under another condition`). A `"."` entry whose only `keel` is nested is reported by the earlier case in this order, `package exports "." lists no keel condition first`.
- `check`: `check: <n> errors; nothing packed` (`1 error`), nowhere, after the check's diagnostics.
- `test`: `test: <f> of <n> tests failed; nothing packed` (`1 test`), counted as `keel test` counts them, a test file that fails to load one failed test; or `test: the run did not pass; nothing packed` when none failed and the run still failed (an error outside any test, such as an unhandled rejection); nowhere, after the test's diagnostics.
- `ledger`: `ledger: .keel is not a folder` (at `.keel`) or `ledger: .keel/ledger.json cannot be written here` (at the file) when it cannot write; under `--check`, `ledger: .keel/ledger.json is missing; keel pack writes it` (nowhere), `ledger: .keel/ledger.json fails its shape; keel pack writes it again` and `ledger: .keel/ledger.json is stale at <field>; keel pack writes it again`, `<field>` the first of `unsafe`, `hostElements` and `exports` that differs (at the file, line 1).

**Scaffold.** `keel scaffold library <name>`, `<name>` a scoped package name `@<scope>/<base>` of lowercase letters, digits and `-`, the scope not beginning with `-` and the base `-`-joined segments, the first beginning with a letter (so its lowerCamel form is a module id), writes folder `<base>/` in the working directory, holding:
- `package.json`: `name`, `version` `0.1.0`, `"type": "module"`, `"keel": "library"`, `exports` `{ ".": { "keel": "./src/index.ts", "types": "./dist/src/index.d.ts", "default": "./dist/src/index.js" } }`, the `files` of Package, `scripts` `{ "build": "tsc -p tsconfig.build.json", "check": "keel check", "test": "keel test", "prepack": "tsc -p tsconfig.build.json && keel pack --check" }`, `peerDependencies` `@keel/compiler`, `@keel/reactive`, `@keel/runtime-dom`, `@keel/schema` and `@keel/ui`, each `^<version>`, `<version>` the running `@keel/cli`'s, and in `devDependencies` the same five, `@keel/cli` and `@keel/testing` at that range, with `@types/node`, `happy-dom`, `typescript`, `vite` and `vitest`, so the library's own folder resolves what its check, tests and build import;
- `module.ts`: `id` the base in lowerCamel (`keel-charts` gives `keelCharts`), `deps: []`, `capabilities: []`, `public: { exports: ['Example'] }`;
- `src/index.ts` re-exporting `Example`; `src/Example.tsx`, a component whose props are `{ id: string }`, with its `Props` schema (k.testing renders by it), and which renders one `Text` with id `` `${props.id}.text` ``; `test/Example.test.ts`, rendering it and finding `<id>.text`;
- `tokens.ts` as `keel scaffold project` writes it, `tsconfig.json`, `tsconfig.build.json` (`src/` built to `dist/`), `vitest.config.ts` (tests under `test/` and `src/`) and `README.md`, whose presence alone is fixed.
It writes source alone: as written the library passes `keel check` and `keel test` and holds no `.keel/ledger.json` (a committed generated file is stale at the first edit), so `keel pack --check` is E1164 naming `ledger` until `keel pack` writes it, and passes after. No `<name>` is k.cli E1052 `library: input does not fit its schema at name (required)`. An existing `<base>/` is E1351 and a `<name>` of another form E1352 (k.scaffold); either writes nothing.

**Rules.** E1164 `keel pack`: the step its message begins with failed (`kind`, `package`, `check`, `test`, `ledger`; Pack); nothing is written.

**Conformance.**
- `keel scaffold library @acme/keel-charts` writes `keel-charts/` whose `package.json` has `"keel": "library"` and whose `module.ts` has `id: 'keelCharts'`; with its dependencies installed, `keel pack` there exits 0 and writes `.keel/ledger.json` with `unsafe` 0 and `hostElements` 0, after which `keel pack --check` exits 0.
- `keel scaffold library charts` and `keel scaffold library @acme/Charts` are each one E1352 and write nothing; run twice with `@acme/charts`, the second run is one E1351 and writes nothing.
- In that scaffolded library, a test made to fail makes `keel pack` report one E1164 whose message names `test`, and no `.keel/ledger.json` is written; `<text />` in `src/Example.tsx` makes it report one E1805 and one E1164 naming `check`.
- In that scaffolded library, after `keel pack`, adding `Host` to `src/Example.tsx` makes `keel pack --check` report one E1164 naming `ledger` and leaves `.keel/ledger.json` unchanged; `keel pack` then writes `hostElements` 1.
- `keel pack` in a folder whose `package.json` has no `keel` field is one E1164 naming `kind`.

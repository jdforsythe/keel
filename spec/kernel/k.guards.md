# k.guards: Guards
status: implemented

**Guards.**
```ts
export const auth = guard({ redirect: 'app.login' }, async ({ url, caller }, ctx) => ok(null))
```
`caller` and `user` are k.server's and k.user's (on a `client` deployable: Client below); `bearer` is k.api's (`undefined` off an API route; a redirect hop's guards get none). A guard returns `Result<null, KeelError<'keel.denied'>>`. Every guard in the chain runs, outermost first, before any loader; on `err` the request redirects to `redirect`, with the matched route's same-name params and search `{ next: url }` (`url`'s own `next` if `url` is a `redirect` route; never nested). A guard's `Result` reaches no loader or action. The action or `handle` that sends the person back reads `next` with `pageHref` (k.router Return targets).

**Home.** A guard lives in a `*.guard.*` file of a module (k.boundary). A `routes.ts` binds it by value import, so a module binding another module's guard lists that module in `deps` (E1152), and that module may then neither list the binder nor link to its pages, since a link imports the binder's contract (k.contract Derived): E1153, naming the guard. A guard bound by modules that link to one another lives in a module of its own, with no pages, whose files are guards and what they import, and whose `deps` reach no module that binds them; each binding module lists it:
```
modules/access/    deps: []                     public.exports: ['signedIn']   signedIn.guard.ts
modules/members/   deps: ['access', 'shopping']  routes.ts binds signedIn; the sign-in page links to shopping.list
modules/shopping/  deps: ['access']             routes.ts binds signedIn
```
A guard's `redirect` is a route id resolved in the deployable's route table (k.routes), not an import: `signedIn` names `members.signin` with no `deps` entry. A file outside every module is no home: k.module checks no import of it, and it is server-only in every deployable (k.boundary), so a `client` deployable's build refuses it (E1007).

**Client.** A `node` deployable with an identity source answers `GET /__keel/user` carrying `x-keel: 1` with `{ user }`, `identify`'s answer (k.user), and `cache-control: no-store`; without `x-keel: 1`, 403 `keel.denied`. A `client` deployable's router, in a project with `identity.ts` beside `topology.ts` (k.mount), sends that GET to its page's origin once before its first guard runs, and again after each mount request's answer in a shell (k.return); a guard waits for the answer in flight. Its guards, loaders and actions get that `user`: `''` before any answer, and after a failure or an answer other than 200. It is what the server last said, for navigation and rendering only, never authority: the router holds it in memory, never in `ctx.storage`, a log or a URL, and each API the page calls runs its own guards. A sign-in or out the router does not take part in (an API route of the app's, another tab) shows at the next document load. A router with no `identity.ts` sends none, and `user` is `''`. Under `renderRoute` its `user` option stands for the answer, and no GET is sent. Without `user` and without `app`, a `renderRoute` router reads as a built one: it sends the GET when an identity mount (`identityMount`, k.mount) was made in the test file's module graph, its `mount` (k.mount-scope) the `path` of the first one made, and sends none when none was. Under vitest with the `keel()` plugin, as `keel test` runs it, the project's `identity.ts` beside `topology.ts` is evaluated before each test file, as the built entry imports it; so a test sees the read exactly when the built app sends it (k.requests). `keel test` adds that file to its run itself, so a project whose vitest config has no plugin sees the read too; one evaluated twice (plugin and `keel test`) is harmless, a second `identityMount` call not throwing (k.mount).

**Carried params.** For each page whose chain holds a page or layout guard with `redirect`, every field of the `redirect` route's `params` must be a field of the page's `params` whose node fits the target's: the same node, or one of the same type with the same options (an `id` of the same brand), or one holding only values the target accepts (an `enum` or `literal` each of whose values the target's node parses; a `string`, `number` or `int` whose `min` and `max` lie within the target's of the same type, or an `int` within a `number` target's, an absent bound unbounded; a `number` never fits an `int`). A missing field or one that does not fit makes `manifest` throw E1508 naming the page, the `redirect` route and the field, and `routeTable` for a chain it joins across modules, so `keel build` reports it (k.compiler Build-time evaluation) before any denial. On an API route a guard's denial is 403 `keel.denied` (k.api), and a loader or action that returns `err` of `keel.denied` is answered 403 in its own body (k.api Requests), so a `bearer` check may deny in either.

**Rules.** E1508 a guard's literal `redirect` route is under that guard, or (route table) a carried param missing or not fitting, or (runtime) a guard redirect loop.

**Conformance.**
- A guard returning `err` redirects to its `redirect` route with `next` and the matched route's same-name params (one missing: E1508); no loader or route component runs.
- A guard redirect revisiting a location, or a ninth, is E1508 (server: 500 `keel.unexpected`); no redirect nests `next`.
- A guard's `caller` is the hash `createApp` gives loaders (`''` with no signed cookie) and under `renderRoute` its `caller` option (default `''`).
- A `createApp` with `identify` answering `'u1'` answers `GET /__keel/user` with `x-keel: 1` 200 `{ "user": "u1" }` and `cache-control: no-store`, one `identify` call; without `x-keel: 1`, 403 and `identify` uncalled; with no identity source, 404.
- A client router in a project with `identity.ts` beside `topology.ts`, its net answering `/__keel/user` with `'u1'`: a guard on the first and on a second navigation gets `'u1'`, after one GET; answered 500, or the fetch rejecting, `''`; a router in a project without it sends no GET and its guard gets `''`.
- Under `renderRoute(id, { routes, shell: true, ctx })`, the origin routed to a `createApp` whose `handle` answers a mount `Form` POST 303 to a page guarded by `user !== ''` with `set-cookie: s=1`, and whose `identify` answers `'u1'` for `s=1`: a second `/__keel/user` GET carries `s=1`, and the page renders without a redirect.
- `renderRoute(id, { routes, user: 'u1' })` over a module importing `identity.ts`: its guard gets `'u1'` and no `/__keel/user` GET is sent.
- `manifest` throws E1508 naming the page, the `redirect` route and the field when a guarded page lacks a field of the `redirect` route's `params`, or carries `s.id('User')` to `s.id('Recipe')`, `s.enum(['a', 'b', 'c'])` to `s.enum(['a', 'b'])` or `s.string()` to `s.string({ max: 8 })`; it throws none for the same schema, `s.enum(['a'])` to `s.enum(['a', 'b'])`, `s.literal('a')` to `s.string()` or `s.int({ min: 1 })` to `s.int()`; `routeTable` throws E1508 for a page of one module under another module's guarded layout.
- In a test file that calls `identityMount('/auth')` before the harness opens, `renderRoute(id, { routes, ctx })` of a page with no guard and no loader, no `user`, and no route for `/__keel/user` on the sim `ctx`: `requests()` is exactly `[{ method: 'GET', url: new URL('/__keel/user', location.href).href, headers: ['accept', 'x-keel'] }]`, and after a `navigate` to a second page it is still that one entry; with `user: 'u1'` it is `[]`; in a test file that makes no identity mount, it is `[]`, and a guard on the page gets `''` in each case but `user: 'u1'`. The two halves are read on two pages opened the same way: the log on a page with no guard, the guard's `user` on a page with one.
- `keel test` over a project with `identity.ts` beside `topology.ts`, which no module file imports, whose one test asserts that `renderRoute(id, { routes })`'s `requests()` holds one entry whose `url` ends `/__keel/user`, passes; with `identity.ts` and `identity.server.ts` removed, the same test fails.

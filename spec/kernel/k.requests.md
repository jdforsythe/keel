# k.requests: Requests a page sends
status: proposed

From `@keel/testing`: the requests a harness's page sent, Keel's own among them, so a test asserts which requests an app makes without a browser.

**Log.** Each `render`, `renderRoute` and `resumeDocument` handle (k.testing) has `requests()`: `readonly SentRequest[]`, `{ method, url, headers }`, one entry per `fetch` its page's net was given from the call that made the handle until its `dispose()`, in the order the fetches were made. `method` is the `Request`'s method, `url` its absolute URL, `headers` the names of the headers it entered `ctx.net` with, lower case, sorted, each once: after the cookie jar and `x-keel-user` were set (k.mount Testing, k.user Testing), so a request that carried cookies lists `cookie`. An entry holds no header value and no body, so a failed assertion on the log prints no cookie, signature, bearer or submitted value; a Keel URL holds no marked field (E1111). A disposed handle's `requests()` is E1705.

**Whose requests.** With `app` or `shell` the page runs on a ctx of its own (k.mount Testing), and its log holds every request of that browser: each document load and submit, each redirect hop it follows, the router's `/__keel/user` read, service calls and event streams, to any origin; a request `app` itself makes on `ctx` is not the page's. Otherwise the page runs on `ctx`, and its log holds every `fetch` of `ctx.net` while the handle is open, the test's own and another open harness's on that `ctx` among them: one ctx cannot tell its pages apart (k.user E1724).

**Unanswered.** A fetch is logged when it is made, before the net answers. A request the schedule drops or answers 503 (k.sim), one made offline, and one no `ctx.net` route matches are logged as any other. A request no route matches is answered as the sim net answers it, a 404, and fails no test by itself: a test that wants each request routed asserts the log.

**Rules.** None of its own: E1705 (k.testing).

**Conformance.**
- `renderRoute(id, { routes, ctx })` of a page whose loader fetches `GET https://api.example.com/a?x=1` with header `accept: application/json`, then `POST https://api.example.com/b` with headers `x-b: hidden-value` and `content-type: text/plain` and body `secret-body`, on a sim `ctx` whose net routes only `https://api.example.com/a*`: the page renders, and `requests()` is exactly `[{ method: 'GET', url: 'https://api.example.com/a?x=1', headers: ['accept'] }, { method: 'POST', url: 'https://api.example.com/b', headers: ['content-type', 'x-b'] }]`; `JSON.stringify(requests())` holds neither `hidden-value` nor `secret-body`.
- A `ctx.net.fetch` of `https://x.example.com/t` that the test itself makes on `ctx` while a `render` handle on that `ctx` is open is the one entry of that handle's `requests()`; one made before the `render` call is in no entry; after `dispose()`, `requests()` rejects E1705.
- On a sim ctx whose schedule `net` is `[{ delay: 0, fault: 'drop' }]`, a page's one fetch of `https://api.example.com/a` rejects and is the one entry of `requests()`; on a ctx with no route, the same fetch resolves 404, is the one entry, and the test passes.
- `renderRoute(id, { routes, app, ctx })` of a page whose loader fetches `https://peer.example.com/x` through its own ctx, with a `Form` its action answers `ok(href)`: after the page is ready `requests()` is one entry, `GET` of the page's URL with headers `['accept', 'sec-fetch-site']`; after a valid submit it is three, that GET, a `POST` to the form's action whose headers hold `content-type`, then a `GET` of `href`; each of the last two lists `cookie` exactly when an earlier answer of `app` set a cookie that is still in the jar; no entry's `url` is `https://peer.example.com/x`.

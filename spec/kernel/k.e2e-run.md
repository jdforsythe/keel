# k.e2e-run: End-to-end runner
status: implemented
What `keel test --e2e` (k.e2e) guarantees about the browser it launches, what that browser and the served processes can reach, the folders a run makes and what an unexpected error prints.

**Browser.** `playwright-core` is an optional peer dependency of `@keel/testing`, pinned to one version as `z3-solver` is (k.prove). The engine is `--engine`, default `chromium`. Before any file runs, a missing `playwright-core` is one E1734 `playwright-core is not installed` (fix adds it to `devDependencies`), and a missing browser of the engine one E1734 `the <engine> browser is not installed: run playwright-core install <engine>`; either fails the run, and no e2e test is reported skipped. One browser process is started per test file on its first `open`, headless, and closed when the file ends. It starts with a new, empty profile folder inside the run folder (Teardown), never the developer's own browser profile, with no extension. Chromium runs with its sandbox on, and the runner never turns it off to get through. Before the first file it launches Chromium once to see whether the sandbox starts. Where it cannot (Linux refusing unprivileged user namespaces: a non-root container, a hardened runner), the run fails before any file with one E1734 `chromium cannot start its sandbox here`, whose fix text names what a user can do as written, safest first: on the host, `sysctl kernel.apparmor_restrict_unprivileged_userns=0` (Ubuntu 23.10 and later) or `sysctl kernel.unprivileged_userns_clone=1` (Debian); in a container, a seccomp profile that allows `clone` with `CLONE_NEWUSER`, or `docker run --security-opt seccomp=unconfined`, which lifts every syscall filter from the container; last, `--no-sandbox`, an unsandboxed browser with W1734 on every run. `keel test --e2e --no-sandbox` is the one way to run without it, a flag with no environment value or config key, and it prints W1734 `chromium sandbox off: --no-sandbox` on every run. On Linux as root, where Chromium refuses its sandbox, the run does so without the flag and prints W1734 `chromium sandbox off: running as root` on every run. `KEEL_E2E_SANDBOX=unavailable` in the run's environment makes the check fail as a refused user namespace does, without launching, for a test of that path; no value of it turns the sandbox off.

**Build input.** For each unserved `client` deployable, `keel test --e2e` builds with `KEEL_PEER_<NAME>` set to `http://<name>.peer.keel.test` per `node` deployable (k.hosting Peers); it sets no other input `keel build` reads, and a `KEEL_PEER_<NAME>` of the environment is replaced for that build.

**Time.** A `within` time a wait takes is a time the test chose: it is multiplied by `KEEL_TEST_TIME_SCALE` (a positive number, default 1; docs/TESTING.md Time scale). A `fixed` time is an input to the app (a lease, a workflow's step) and is added unscaled. The defaults bound the machine's own work and are fixed time too: 10 s per wait, 20 s for a deployable to answer, and 60 s for an e2e test that declares no timeout.

**Ledger.** An e2e file is a test file the ledger reads (k.ledger-items Run evidence): a passing e2e test gives `example` evidence to each item it references, as any test does, and adds no rung and no item kind. `keel test --e2e` writes its run report to `reports/tests/e2e.json` and changes no other file there; `keel test` writes `run.json` and leaves `e2e.json`.

**Reach.** Every server the run starts listens on `127.0.0.1` alone: each deployable of a `serve` (`HOST=127.0.0.1`, k.deploy), its static host, its proxy, each `answer` and `keel dev` under `dev: true` (k.topology). A page may reach the origins of its `serve`'s deployables, each `<name>.peer.keel.test` name, and each origin `origins` maps (k.e2e Answered origins). A mapped origin's or a peer name's request goes through the `serve`'s proxy to its server. The run refuses every other request of a page, a loopback one among them, at the `serve`'s proxy, which every request of the run's browser goes through, before it reaches any server, and the page's request fails as a network error; the browser's own request handling, CORS preflights among it, is left as it is. Each refused request is a problem `{ kind: 'offsite', text: '<method> <origin><path>' }` (k.e2e-page Problems). `https` to a mapped origin ends at the proxy with a certificate made for that `serve` with its mapped host names alone, on a key each test file's process makes when it first needs one, and trusted by that process's browser alone. No certificate or key is shipped in a package.

**Environment.** A process a `serve` starts gets these names from the run's environment when they are set, and no other: `PATH`, `LANG`, `LC_ALL`, `TZ` and, on Windows, `SystemRoot`. `HOME`, `TMPDIR`, `TMP` and `TEMP` are set to folders inside its data folder. Then come the names k.e2e serve lists, then `env`. The browser process gets the same names and no `env`. So a cloud or API token in the developer's shell reaches no app code under test unless the test passes it in `env`. A served process's own outbound requests are not refused: a test points them at an `answer` through `env`.

**Teardown.** `keel test --e2e` makes one run folder `keel-e2e-<random>` in the OS temporary folder, holding a `.keel-e2e` file with its process id and start time. It sets `TMPDIR`, `TMP` and `TEMP` to that folder for the vitest it starts, so every data folder, host folder, profile, trace and temporary file of the run is inside it. When the run ends, passed or failed, or on SIGINT or SIGTERM, every process the run started is stopped and the folder is removed. On SIGINT or SIGTERM the run prints one line `stopped: removed <n> processes and the run folder` and exits 130. At its start a run removes each `keel-e2e-*` folder of the OS temporary folder whose `.keel-e2e` names a process that is not running and that is more than 1 hour old: what a SIGKILLed run left. A folder without that file is never touched.

**Failure output** (docs/OUTPUT.md). A failed e2e test is one T0001 at the test's line, its message the error's code and one line: `E1735 until shop.cart.count: text was "0", not "2", after 10.0s`. Below it, at most 10 lines `server: <record>`, the compact form of each record its `serve`'s deployables wrote from the start of the failing verb, then `screenshot: <path>` per open tab and `trace: <path>` per context. A context records a trace (DOM snapshots, network, console) from its `open`; on a failed test each is written under `reports/e2e/`, named `<file>-<line>-<n>`: `<file>` the test file's name less its `.ts` (`checkout.e2e`), `<line>` the T0001's line, `<n>` counting the tabs for `.png` and the contexts for `.zip` from 1; a passing test writes nothing there.

**Walls.** There is no verb for a drag, the clipboard or an element inside an `<iframe>`. A drag is tested through its keyboard path, which a drag must have (WCAG 2.5.7, k.a11y), with `press`. A copy control is tested by the text it holds, and a paste by typing with `fire` `input`. A framed app is tested with its own `serve`. An id that is shown only inside a frame is E1705 `<id> is inside a frame: serve that app`.

**Output.** A Keel diagnostic prints as docs/OUTPUT.md says, `fix:` holding only its fix hunk. Any other error thrown inside a verb or `serve` (a Node system error, a driver's error) is the failing test's T0001. Its message is `uncaught: <code> <first line>`, as k.test-run prints an error outside a test, clipped to one line, and its stack's app frames follow. It is never printed under `fix:`.

**Rules.** E1734 the browser is missing, or Chromium cannot start its sandbox · W1734 the Chromium sandbox is off (as root on Linux, or `--no-sandbox`).

**Conformance.**
- A run under a non-root user on Linux or macOS launches Chromium with its sandbox on and prints no W1734; the same run as root on Linux prints one W1734 `chromium sandbox off: running as root` and passes.
- The browser of a run starts with a profile folder inside the run folder that holds no file before its first `open`, and no file outside the run folder is written by it.
- A page's request to `https://example.org/x`, an origin the run does not serve or map, reaches no server, fails in the page as a network error, and leaves `{ kind: 'offsite', text: 'GET https://example.org/x' }` among `problems()`.
- Each deployable a `serve` starts listens on `127.0.0.1` alone: a connection to its port on the machine's other addresses is refused.
- With `AWS_SECRET_ACCESS_KEY=k` in the run's environment, a served deployable's route that answers `process.env.AWS_SECRET_ACCESS_KEY ?? 'none'` answers `none`, and `k` when the test passes it in `env`.
- After a passing run, a failing run and a run stopped by SIGINT, no `keel-e2e-*` folder of that run is left in the OS temporary folder, and the SIGINT run printed one `stopped:` line.
- A `keel-e2e-*` folder whose `.keel-e2e` names a process that is not running and that is 2 hours old is gone after the next run starts; one that is 10 minutes old, or names a running process, or has no `.keel-e2e`, is left.
- A `serve` that fails with `EEXIST` from the file system makes the test's T0001 message begin `uncaught: EEXIST`, with no `fix:` line.
- `keel test --e2e` with `KEEL_E2E_SANDBOX=unavailable`, as a non-root user, prints one E1734 `chromium cannot start its sandbox here` whose fix text holds `kernel.apparmor_restrict_unprivileged_userns`, `kernel.unprivileged_userns_clone`, `CLONE_NEWUSER` and `--no-sandbox`, runs no test, reports none skipped and exits 1.
- The same run with `--no-sandbox` prints one W1734 `chromium sandbox off: --no-sandbox` and runs its tests, and a second such run prints it again.
- `KEEL_E2E_SANDBOX=on` or any value but `unavailable` changes nothing: a run where the sandbox starts prints no E1734 and no W1734.
- In that E1734's fix text `kernel.apparmor_restrict_unprivileged_userns` comes before `CLONE_NEWUSER`, `CLONE_NEWUSER` before `--security-opt seccomp=unconfined`, and `--security-opt seccomp=unconfined` before `--no-sandbox`.

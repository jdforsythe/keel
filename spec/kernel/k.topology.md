# k.topology: Deployables
status: conformance-covered

**Declaration.** `topology.ts` default-exports `topology({ <name>: { modules, adapter, host?, storage?, shells?, origins? } })` (`@keel/server`), read statically; `storage`: k.deploy, `shells`: k.shell, `origins`: k.origins. Adapters: `node` (serves the resume entry), `static` (prerendered HTML), `client` (loaders, actions in the browser; entry `mount(App, el)`, real `ctx`). Each module, app or stdlib, is in one deployable; its routes, actions, live loaders and runners run there and no other file names a deployable, so moving one edits `topology.ts` alone.

**Route table.** The generated entries merge each module's `routes` into `createApp({ routes })`: an app module's `modules/<id>/routes.ts`, a stdlib module's package `./routes` export (none: no routes).

**Runners.** A module's background work is the `runners` export of `modules/<id>/runners.server.ts`: `Runner`s `{ run(ctx, signal): Promise<void> }`. `createApp({ runners: { [moduleId]: Runner[] } })` calls each `run` of the served deployable's modules once after startup with the app's `ctx`. A `run` that rejects before `signal` aborts is a `keel.unexpected` `diag` and runs again 1,000 ms later on `ctx.clock`. `app.close()` aborts each runner's `signal` and open event stream and resolves when every `run` has settled.

**Calls and peers.** A module calls another's routes through `service({ module })` (k.services), encoded alike in every topology: a split adds latency and `api.network`/`api.timeout` outcomes, never another value. `createApp({ peers: { [deployable]: URL | ServerApp } })` names the other `node` deployables: URLs in production, apps in process. A `service({ module })` request is answered in process when its module is here or in an in-process peer, else by its URL. A request for a path a peer serves (by `routes.json` in `artifacts`) is forwarded to the peer's origin: method, path, search, headers but `host` and hop-by-hop ones, body (`maxBodyBytes`); its response, a 3xx too, is returned less the same headers and `content-encoding` (unreachable: 502 `keel.unreachable` and a `diag` `peer unreachable: <name>`, the error's `name` only); one carrying `x-keel-forwarded` is not forwarded (a loop guard only: any client may send it). Every `node` deployable takes the app's one `KEEL_SECRET` (k.deploy), so code running in any one of them can sign a caller, or assert a `user` (k.user), that every other accepts.

**Build.** `keel build`, `server.mjs`, `DeployEnv`, `assets` and deploy files: k.deploy.

**Local topology.** `keel dev` serves every deployable in one process on one origin: Vite serves `client` and `static` entries with HMR; each `node` deployable runs its dev `createApp` (real `ctx`, storage in `.keel-dev/`) and runners, the others its in-process peers, and serves its paths; its documents resume its own islands. In dev, or with no `assets` in development/test, a document scripts `/@keel/entry.ts?d=<deployable>`, the resume entry of the islands of `createApp({ deployable })`'s modules (none given: every `node` module's).

**Rules.** E1552 `topology.ts` not statically readable (a spread, computed key or key twice in a deployable too), a name not `[a-z][a-z0-9-]*`, a module unknown or in two deployables. A project root is the root or any folder without a `modules` segment that holds a `.keel/` artifact or a `topology.ts` with a default export, readable or not; an unreadable one is E1552 at its path and the folder's files are checked as that project's · E1553 a `static` route with params or actions · E1559 one path in two deployables (names both; `keel check` and `keel build`) · E1558 a live loader, or a `loader` or `action` naming `stores`, in a `*.server.ts` of a module a `client` or `static` deployable serves (at the call in `keel check` and `keel build`; `createApp` throws it; fix: none), and there a `loader` or `action` call those commands cannot read: options not an object literal, or with a spread or computed key; a loader `fn` neither inline nor a function or `const` at the top of the file · E1511 (k.api) · E1560 (k.deploy).

**Conformance.**
- Fixture modules `a` (its loader calls `service({ module: 'b' })`) and `b` (a runner), served in one process as `{ one: [a, b] }` and as `{ x: [a], y: [b] }` under sim ctxs of one seed: a generated request script through `one` and through `x` gets equal statuses, bodies and final store states.
- `x` answers a path of `b` with `y`'s status, headers and body, or 502 `keel.unreachable` with `y` down; one carrying `x-keel-forwarded` is not forwarded.
- With `a` and `b` in one deployable a `service({ module: 'b' })` call makes no `ctx.net.fetch`; with `y` at `http://y.test` it makes one, to that URL.
- `createApp({ runners })` runs each runner of the served deployable once, none of another; `close()` aborts their signals and resolves once each `run` settles; a rejected `run` runs again 1,000 ms later on the sim clock.
- Two routes with path `/p` in modules of different deployables are one E1559 in `keel check` and in `keel build`.
- With `origin` `https://a.example`, a POST with that `Origin` to another host passes the same-site check, and the caller cookie is `__Host-keel-caller`.
- `keel dev` answers a `client` page and a path of each `node` deployable from one process on one origin.
- In a module a `client` deployable serves, a `loader` naming `stores`, an `action` naming `stores` and a loader whose `fn` is `async function*` are each one E1558 in `keel check` and `keel build`, and `createApp` for that deployable throws E1558; in a `node` deployable's module none is.
- In a `client` module's `*.server.ts`, `loader({ output }, feed)` with `const feed = async function* …`, `r.loader({ output, stores })` through `import * as r`, and `loader({ ...base, output }, fn)` are each one E1558 in `keel check` and `keel build`; `loader({ output }, load)` with `load` an `async function` of the file is none.

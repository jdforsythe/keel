# k.check-cache: Type cache
status: implemented
The type pass of `keel check` (k.check Pipeline, step 1) keeps its results across processes, so a `keel check` after a `keel build` or another `keel check` over the same inputs runs no TypeScript program. A result taken from the cache is the result a fresh process computes: the cache changes the time a run takes, never its output, its exit code or its trailer. The same holds for each `check()` call in a long-lived process (an editor session, `keel mcp`): nothing an earlier call parsed, loaded or registered changes a later call's answer.

**Where.** `keel check` and the check `keel build` runs keep entries in `<root>/node_modules/.cache/keel/`, where `<root>` is the project root, when `<root>/node_modules` exists; without it there is no cache and nothing is created. `check()` keeps entries in the folder its `typeCache` option names, and none without it. Deleting the folder is always safe and is the one way to clear it; there is no flag.

**Key.** An entry is named by the SHA-256 of: the entry format version; the `@keel/check` version and the SHA-256 of the bytes of each of its own code files; the TypeScript version and the SHA-256 of the bytes of its `package.json` and `lib/typescript.js`, so a patched TypeScript of one version is another key; the compiler options the pass uses; the absolute project root and whether the file system is case sensitive; the path and text of each checked code file; and, per file, the codes already reported that the pass drops.

**Probes.** An entry records every question the pass asks the file system, with its answer: each file read (path, SHA-256 of its bytes, or absent), each file or folder existence test (path, yes or no), each real-path lookup (path, target) and each folder listing (path, SHA-256 of its sorted entry names). Module resolution, `package.json` reads and the paths it found absent are among them. An entry is used only when every recorded question, asked again, gets the same answer; one different answer is a miss. Modification times are never read, so a file rewritten within one clock tick, restored with an old time (`cp -p`, `tar`, a CI cache) or reached through a link is judged by its bytes. The in-process memo of `check()` is held to the same probes.

**In one process.** A parsed file, and the previous program a pass starts from, is reused only by a pass whose compiler options are identical to the pass that parsed it: parsed files are kept by compiler options, path and text together. Options differ, for one, when `@keel/runtime-dom/jsx-runtime` starts or stops resolving from the root (`jsxImportSource`). A `@keel/std-*` package's formats (E1108) apply to a module only while the project's app manifests list the package in `deps` at the time of the call. Its rules run on every call, except when the package was first imported in the process by `importDeps` (`@keel/compiler/std/importDeps`, which the `keel` commands call with the project's files before they check) for an earlier call's `deps` and the app manifests at this call do not list it. A rule the caller registered itself, by importing its package before any `importDeps` call did or by calling `defineRule`, runs on every call whatever `deps` lists, as it does in a fresh process whose caller registered it.

**Entries.** An entry holds its own key, its probes, the pass's diagnostics as `keel check` reports them (messages and fixes, which may quote source lines) and the date receivers it found: paths, hashes and diagnostics, no other file text. It is written to a temporary file `<name>.<pid>.tmp` in the folder and renamed into place, so a reader sees a whole entry or none; of two processes writing one entry, the last rename stands. An entry that cannot be read, does not parse, lacks the entry shape, or holds a key other than the one it was looked up by (a copied or renamed file) is a miss, and the run writes a fresh one; a failed write is ignored. An entry is written only when its JSON is at most 16 MiB; above that the result is returned and nothing is stored. A folder keeps at most 4 entries, so at most 64 MiB: each write removes the least recently written beyond them and every `*.tmp` file in the folder other than its own (a writer whose file was removed loses its write, which is a miss later). An entry is trusted as the `node_modules` around it is: a process that can write there can already change what the project runs.

**Conformance.**
- In a project whose `package.json` is `{"name":"p","private":true,"type":"module"}`, with `node_modules/foo/package.json` `{"name":"foo","types":"index.d.ts"}`, `node_modules/foo/index.d.ts` `export declare const n: number` and `modules/a/a.ts` `import { n } from 'foo'`, an empty line and `export const a: number = n`, a first `keel check` reports no diagnostic; after it, each of these changes makes the next `keel check --format=json` print the same bytes to stdout, and exit with the same code, as a run with `node_modules/.cache/keel` deleted, and report one E1751 at `modules/a/a.ts` line 3: `index.d.ts` rewritten to `export declare const n: string` with its modification time set back to the one it had; `node_modules/foo/other.d.ts` holding `export declare const n: string` and `package.json`'s `types` changed to `other.d.ts`.
- In that project with `modules/a/a.ts` importing `n` from `'foo/sub'` and `node_modules/foo/sub.d.ts` holding `export declare const n: number`, after one `keel check`, adding `node_modules/foo/sub.ts` holding `export const n: string = 's'` makes the next `keel check` report one E1751 at `modules/a/a.ts` line 3, and deleting `node_modules/foo/sub.d.ts` instead makes its stdout the same bytes as a run with `node_modules/.cache/keel` deleted.
- In that project with `node_modules/foo` a symbolic link to a folder `../foo` beside the project holding the same two files, after one `keel check`, rewriting `../foo/index.d.ts` to `export declare const n: string` with its old modification time makes the next `keel check` report one E1751 at `modules/a/a.ts` line 3.
- For 4 generated sequences (seed 1337) of 1 to 3 edits to that project, each one of: rewriting `modules/a/a.ts` with `number` or `string` as the type of `a`; rewriting `node_modules/foo/index.d.ts` with `number` or `string` as the type of `n`, its modification time set back to the old one; adding or deleting `node_modules/foo/other.d.ts`; setting `package.json`'s `types` to `index.d.ts` or `other.d.ts`: after each edit, `keel check --format=json` with `node_modules/.cache/keel` as the previous run left it prints the same stdout bytes and exits with the same code as the run that follows it with the folder deleted.
- In that project, after one `keel check`, replacing each file in `node_modules/.cache/keel` with its first 40 bytes, or with `{}`, leaves the next `keel check --format=json` printing the same stdout bytes and exit code as a run with the folder deleted, and after it every file in the folder parses as JSON.
- `check()` called twice in one process with the same files and `{ root }`, with `node_modules/foo/index.d.ts` rewritten between the calls to `export declare const n: string` with its old modification time, reports no E1751 on the first call and one on the second.
- After 5 `check()` calls with one empty `typeCache` folder into which a file `t.json.999999.tmp` was placed first, each call over a different text of `modules/a/a.ts`, the folder holds 4 entry files and no `t.json.999999.tmp`.
- `keel check` in that project with `node_modules` removed leaves no `node_modules` folder.
- In that project, with an empty `node_modules/.cache/keel`, `keel check` with `modules/a/a.ts` declaring `a: number`, then with it declaring `a: string` (`n` still `number`), leaves two entry files; with the two files' contents swapped, `keel check` of each of the two trees prints the same stdout bytes and exits with the same code as a run with the folder deleted.
- In one process, `check()` with `{ root, typeCache }` of a project whose `modules/a/a.tsx` is `export const a = <span foo={1} />` and whose `node_modules` holds no `@keel/runtime-dom`; then `node_modules/@keel/runtime-dom/package.json` `{"name":"@keel/runtime-dom","exports":{"./jsx-runtime":{"types":"./jsx-runtime.d.ts"}}}` and `node_modules/@keel/runtime-dom/jsx-runtime.d.ts` `export namespace JSX { interface IntrinsicElements { span: { bar?: 1 } } }` are written; a second `check()` in that process, and a following `keel check` with the folder the second call left, each report the diagnostics a fresh `keel check` with `node_modules/.cache/keel` deleted reports, none of them a message starting `TS2875` or `TS7026`.
- In one process, after `@keel/std-temporal` has been imported, `check()` over a module whose `module.ts` lists `@keel/std-temporal` in `deps` and whose file holds `formatLiteral(Instant, '2026-02-28T00:00:00.000Z')` reports no E1108; with that module's `deps` then empty, a second `check()` over the same files reports one E1108 at the call, as a fresh `keel check` of that tree does, which exits 1.
- In one process whose caller has imported `@keel/std-db/tools`, with `root` a folder whose `node_modules/@keel/std-db` links to the package, `check(files, { root, types: false })` over `modules/orders/module.ts` holding `import { module } from '@keel/compiler'` and `export default module({ id: 'orders', deps: [], capabilities: [], public: { exports: [] } })` and `modules/orders/x.ts` holding `import * as db from '@keel/std-db'` and `export const y = db` reports one E2151 at `modules/orders/x.ts` line 1; after `importDeps(root, files)` and `check(files, { root, types: false })` with that manifest's `deps` set to `['@keel/std-db']`, a `check()` with `deps` set back to `[]` again reports one E2151 at `modules/orders/x.ts` line 1.
- In one process that has not imported `@keel/std-db` or `@keel/std-db/tools`, with `root` and the two files of the previous case but `deps` set to `['@keel/std-db']`, `importDeps(root, files)` then `check(files, { root, types: false })` reports one E2151 at `modules/orders/x.ts` line 1; with `deps` then set to `[]`, `importDeps(root, files)` then `check(files, { root, types: false })` reports no E2151, as a fresh `keel check` of that tree reports none.

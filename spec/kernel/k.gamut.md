# k.gamut: Color gamut forms
status: proposed

Keel ships a color only in forms it computes and judges, each inside the gamut of the screen that shows it, so check judges exactly the colors a screen or a printer shows. Luminance, and when a color is inside sRGB or display-p3: k.values Contrast. Combinations: k.themes.

**Forms.** A color inside sRGB has one form, as written. One outside sRGB has two: its sRGB form `rgb(<r> <g> <b>)`, mapped into sRGB by CSS Color 4's gamut mapping (the OKLCH chroma search with JND 0.02 and epsilon 0.0001), each channel encoded by CSS Color 4's sRGB transfer function, times 255 and rounded to an integer; and its P3 form, the color as written when it is a `color(display-p3 ...)`, else `color(display-p3 <u> <u> <u>)` after the same mapping into display-p3 (no mapping when inside it), each channel encoded by the same function, rounded to 4 decimals and written as the shortest `<n>` of that value (`1`, `0.5055`). An `<alpha>` keeps its ` / <a>` as written in both. A color inside sRGB is its own P3 form.

**CSS.** A declaration of the compiled CSS writes each color in its sRGB form. Each block of k.schemes CSS that writes a color outside sRGB, but in the `print` layer, is followed at once by a block of the same selector in the same layer, under its conditions with `screen` and `(color-gamut: p3)` (`screen` once), declaring those properties again with each color in its P3 form. So a screen that matches `(color-gamut: p3)` shows P3 forms, any other screen sRGB forms, and printing sRGB forms only. Keel's declarations in the built CSS hold no other color value: each is kept as compiled, in its form and numbers, under no at-rule Keel did not write. A browser build that sets no `cssMinify` and no `minify: false` minifies CSS with esbuild, which keeps each custom property's value as written whatever the `cssTarget`. Every browser at Vite's default build target reads `color()`, so none matching `(color-gamut: p3)` lacks it. One that lacks it keeps a P3 declaration, since a custom property holds any value, and a property reading it through `var()` is then invalid at computed-value time: inherited or initial, not the sRGB form. So a browser build whose `build.cssTarget` names a browser older than `color()` (Chrome or Edge before 111, Firefox before 113, Opera before 97, Samsung Internet before 22, Safari before 15) gets each P3 block inside `@supports (color: color(display-p3 0 0 0))`, and such a browser shows sRGB forms.

**Output check.** Each browser build (`keel build`, or `vite build` alone) reads its output as written once everything is (a `client` build's folder after every plugin's last hook; a `node` or `static` deployable's whole `dist/<name>/`, server bundle and documents included): each `.css`, `.js`, `.mjs`, `.cjs`, `.html` and `.svg` file, in path order, against the CSS that build compiled (P3 blocks guarded as above). In a `.css` file, each `--k-*` declaration sits in a rule of the selector, `@layer` names, `@media` conditions and every other at-rule (`@supports`, `@container`, `@scope`, `@starting-style`, one the reader does not know: none flattened) of a compiled block declaring it; a color one (a `--k-color-*` or `--k-overlay-*` property, or another `--k-*` one whose value there or in the compiled CSS holds a hex color or a color function) holds a value that block declares, numbers compared as numbers (`.5` is `0.5`), spaces beside `,`, `/` and parentheses ignored, all else as written, so a harmless respelling (`#000000` as `#000`) is refused too; each P3 block follows at once its sRGB block; and each compiled color declaration is found so. The compiled CSS declares no color only when the tokens hold none: then there is nothing to find. Keel's CSS ships in `.css` files: a color declaration in any other file is refused, and Keel writes none there (each document links its stylesheets, k.head Server). A declaration of a property not starting `--k-` is not read. The first difference, in file and declaration order with a missing one last, fails the build with E1819, one line, no position, `see` k.gamut, no `dist/<name>/` written: `<property> is <found> in the built CSS, expected <value>`, `<property> is missing from the built CSS, expected <value>`, `<property> is <found> under @<name> in the built CSS, expected none`, `<property> is <found> in the built CSS where Keel declares none`, `<property> is <found> in <file>; Keel's CSS ships in .css files` or `<property>'s P3 block does not follow its sRGB block in the built CSS`, each value cut to an equal share ending `...` to keep the message within 89 units. `keel build` prints the record alone, not Vite's printout of the throw. Fix (`keel explain E1819`): unset the `build.cssMinify` (Lightning CSS rewrites colors and adds `@supports`), `css.transformer` or PostCSS plugin that rewrote it, or the plugin that moved Keel's CSS out of its file. `keel dev` serves the same compiled CSS through Vite's dev pipeline, which injects stylesheets from JavaScript, and runs no output check.

**Judging.** E1804, at check and at render, and `base.focus` judge each pair in each form, sRGB forms together and P3 forms together, in each combination, printing ones in sRGB forms only. The lower ratio stands, sRGB's on a tie, and E1804's message names its form when a color it judges is outside sRGB (k.a11y-static Message). An `<alpha>` over a backdrop is composited within each form: `a × c + (1 - a) × b` on each encoded channel, sRGB or display-p3, of the two colors' forms, times 255 rounded to an integer. `contrast(fg, bg)` (`@keel/ui/css`) gives the lower ratio. So `color(display-p3 0 0.52 0.5)` on `#000000` ships `rgb(0 133 127)`, 4.66:1, and itself, 4.56:1, and passes 4.5:1; `oklch(70% 0.48 290)` on it ships `rgb(160 131 255)`, 7.19:1, and `color(display-p3 0.6085 0.5055 1)`, 7.12:1; `color(display-p3 0 0.66 0 / 0.95)` over `#FFFFFF` composites to `rgb(13 171 17)` and to display-p3 channels 13, 173 and 13 of 255, 3.07:1 and 3.09:1 under `#FFFFFF` text.

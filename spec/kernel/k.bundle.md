# k.bundle: Browser bundles
status: implemented

Which bundles, file names and handler uses k.boundary's stubs, Assertion and Reach cover, and how a build keeps every environment value out of a browser asset.

**Bundles.** Each bundle a browser build emits is a browser build for k.boundary, with the stubs and the Assertion: the entry's, each Web Worker's and shared worker's (`new Worker(new URL(<literal>, import.meta.url))`, `new SharedWorker(…)`, an import with `?worker` or `?sharedworker`) and any other chunk Vite bundles in a pass of its own. A worker's chain runs through the file that names it: `<entry> -> <page> -> <worker> -> … -> <file>`.
- Reach (E1004 and E1571) follows `new URL(<literal>, import.meta.url)` and `?worker`, `?sharedworker` and `?url` specifiers as it follows a literal `import()`; a worker file a client entry reaches is a client entry.

**Names.** A file is server-only by its name on disk, matched case-insensitively, whatever its extension: `notes.Server.ts`, `keys.server.json`, `copy.server.txt`, `logo.guard.svg`.
- A server-only file named `.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, `.cjs`, `.mts` or `.cts` gets a stub. Any other (data, styles, text, an image) gets none: in a browser build's graph, with or without a query, it fails the build with E1007 reason `server-only file`; named from client-reachable code it is E1004.
- A specifier whose path differs in case from the file's name on disk is E1010, in `keel check` and in every build, on any file system.

**Handlers.** `loader`, `action` and `guard` are the exports of `@keel/router`, known by binding, not by spelling: through a named import (with `as` or not), a namespace import's member (`R.loader`, `R['loader']`), a dynamic `import()`'s, a re-export through any module (`export { loader } from`, `export *`), and any specifier of the package, a subpath too.
- A file uses one when it calls it or reads it as a value (passes, assigns, destructures or re-exports it); a namespace object of the package read other than by a literal member uses all three. A type-only use is none.
- E1551, E1009 and E1007's reason `handler` use this one definition.

**Node built-ins.** The Assertion's Node built-ins are every `node:` specifier and every bare name a supported Node version (22 and later) lists, from a list Keel ships, not the running Node's; so `node:sqlite` fails a browser build on every supported version, which maps no built-in.

**Environment.** No value of a variable set for a build is in a browser asset, whatever the project's Vite config says (`envPrefix` as a string or an array, `define`, a plugin), but k.boundary's public origins and `NODE_ENV`.
- A project config that sets `envPrefix` or `define` fails each browser build before bundling with E1007 reason `environment config`, chain `vite.config.<ext>`. A value a browser reads comes through `clientStd` (k.leave).
- After bundling, an emitted browser file holding the value of a `KEEL_*` variable of 8 characters or more, the public origins excepted, fails the build with E1007 reason `environment value`.

**Types.** `@keel/compiler/client` declares what a browser build promises: `import.meta.env` as `{ BASE_URL: string; MODE: string; DEV, PROD, SSR: boolean }` (k.boundary Environment), any other key a type error, and the default import of `*?worker` and `*?sharedworker` (a `Worker` or `SharedWorker` constructor) and of `*?url` (a `string`). `keel check` loads it when it resolves from the project root, and the scaffold's `tsconfig.json` lists it in `types` beside `node`; app code writes no reference. A `/// <reference types>` in project code adds that package's ambient types (`vite/client` adds Vite's), the app's, not Keel's promise; under it any other `import.meta.env` key is still a type error.

**Service map.** A `client` deployable's entry binds `service({ contract })` targets (k.hosting Peers) for its service map, when the topology has a `node` deployable; with none it maps nothing and every call goes to the document's origin. The map holds the client's own modules, each module of a `node` or `static` deployable that the scan reaches, and each placed module with no folder `modules/<id>/` (a stdlib module). No other app module's name is in the browser build.
- The scan starts at every file under `modules/<id>/` of each of the client's modules and follows each relative specifier (starting `./` or `../`) of a static `import` (a bare `import '<s>'` too), an `export … from` and an `import('<literal>')`; not a type-only `import` or `export`, a specifier in a comment, a computed `import()`, or any other specifier. A specifier resolves to the file it names, else that name plus `.ts`, `.tsx`, `.js`, `.jsx`, `.mts` or `.mjs`, else `index.<ext>` in that folder, in that order; one naming no file is not followed. The scan never reads a server-only file (k.boundary), so what only such a file imports is not reached. A module is reached when a file the scan reads lies under `modules/<id>/`, whatever that file is.
- E1011: after bundling, a `client` deployable's build in `keel build` fails, exits 1 and writes nothing for it, when its graph holds a file under `modules/<id>/`, `<id>` listed by a `node` or `static` deployable and not in the map, that is neither server-only by name nor a stub. One line, no position, no fix: `E1011 <id> is not in the client's service map: imported by <file>`, the file first by absolute path among such files, `<file>` the project-relative path of the first file the bundler records importing it. `keel check`, `keel dev` and every other build report no E1011.

**Aliases.** A file under the project's `modules/` is imported by a relative specifier. `keel check` resolves every other specifier of an `import`, `import type`, `export … from` or `import('<literal>')` in a code file of the project outside `node_modules/`, its `?query` stripped, as its type check does: bundler resolution, a package's `exports` and `imports`, `node_modules` up from the file, symlinks followed to the real path, no `tsconfig.json` read. One that resolves to a file under `modules/` is E1013 at its opening quote: `E1013 '<specifier>' reaches modules/<id>/<path> by an alias; import it as '<relative>'`, `<relative>` the path from the importing file's folder to that file as named on disk, starting `./` or `../`, the query appended. The fix replaces the specifier with `<relative>`. By form:
- a package `imports` entry (`#notes/lib.ts`), a package reached through a workspace link or a `node_modules` symlink, or the project's own name through its `exports`, landing under `modules/`: E1013.
- a `tsconfig.json` `paths` or `baseUrl` alias (`@/notes/lib.ts`), a root-absolute `/modules/notes/lib.ts`, a Vite `resolve.alias`: no file resolves, so one E1751 whose message starts `TS2307`, and no E1013.
- a specifier resolving outside `modules/` (`@keel/ui`, `#lib/x.ts` to `./lib/x.ts`): nothing.
A build reports no E1013; an alias reaching a module the map omits is E1011 there.

**Limits.** A script a project plugin bundles in a pass of its own, or a file copied from `public/`, is not walked; it is the project's. So is a project plugin that writes the value of a variable not named `KEEL_*`.

**Rules.** E1011 a client bundle holds a file of an app module of a `node` or `static` deployable that its service map omits (Service map) · E1013 a specifier other than relative reaching a file under `modules/`, in `keel check` (fix: the relative specifier; Aliases) · E1010 a specifier naming a file in a case other than its name on disk (fix: the name on disk) · E1007 reasons `environment config` and `environment value`, beside k.boundary's.

**Conformance.**
- In a `node` fixture whose `lib/notes.server.ts` holds a canary and `lib/w.ts` imports it: a page starting `new Worker(new URL('../../lib/w.ts', import.meta.url), { type: 'module' })`, and one importing `../../lib/w.ts?worker`, ship no canary under `dist/<name>/`; `keel check` reports E1004 at `lib/w.ts` naming the chain; a worker importing `notes.server.ts?raw` fails `vite build` with one E1007 whose chain runs through the worker.
- `keys.server.json` and `copy.server.txt?raw` imported by a page fail `vite build` with one E1007 `server-only file` each, and are E1004 in `keel check`; a file on disk `Notes.SERVER.ts` is stubbed.
- An import `./notes.Server.ts` of `notes.server.ts` is one E1010 in `keel check`, and on a case-insensitive file system `vite build` ships no canary.
- In a plain file, `R.loader(...)` through `import * as R from '@keel/router'`, `loader` re-exported through `lib/r.ts`, `const L = loader`, and `R.guard(...)`: each one E1551 (E1009 for the guard) in `keel check` and one E1007 `handler` in `vite build`.
- A project `vite.config` with `envPrefix: ['KEEL_']`, with `envPrefix: 'KEEL_'`, or with a `define`: `vite build` fails with E1007 `environment config` and writes nothing; a project plugin writing `KEEL_TEST_VALUE`'s value into a page fails it with E1007 `environment value`.
- A page importing `node:sqlite` fails `vite build` with E1007 `node built-in`, with or without `sqlite` in the running Node's built-in list; the server build maps it.
- With no type reference, a page reading `import.meta.env.MODE` and `DEV` and importing `./w.ts?worker` and `./a.svg?url` checks clean; `import.meta.env.VITE_X` is one E1751, also with `/// <reference types="vite/client" />`.
- A fixture with topology `api` (`node`, module `notes`) and `web` (`client`, module `app`, its page `modules/app/Page.tsx`), `notes` holding `notes.contract.ts`, `lib.ts` (`export const lib = 'x'`), `T.ts` (`export type T = string`), both public, and a loader in `ping.server.ts`, and a symlink `node_modules/linked-notes` to `modules/notes`: a page importing `linked-notes/lib.ts`, with no other import of `notes` in `app`, makes `keel build` exit 1 printing exactly one E1011 line, `E1011 notes is not in the client's service map: imported by modules/app/Page.tsx`.
- In that fixture, `keel build` exits 0 with no E1011 when the page imports nothing of `notes`, when it imports `../notes/notes.contract.ts` and calls `service({ contract: notes })`, when beside `linked-notes/lib.ts` it imports `./client.ts` which imports `../notes/lib.ts`; it prints no E1011 when the page's one import of `notes` is `../notes/ping.server.ts`.
- In that fixture, a page holding `linked-notes/lib.ts` and also `import type { T } from '../notes/T.ts'`, or `// import { lib } from '../notes/lib.ts'`, makes `keel build` print one E1011 for `notes`; with the topology `site` (`static`, module `notes`) and `web`, no `node` deployable, `linked-notes/lib.ts` prints none.
- `keel check` of that fixture with `"imports": { "#notes/*": "./modules/notes/*" }` in its `package.json`, the page importing `{ lib }` from `#notes/lib.ts`: one E1013 at the specifier's opening quote, `E1013 '#notes/lib.ts' reaches modules/notes/lib.ts by an alias; import it as '../notes/lib.ts'`; after its fix the line reads `import { lib } from '../notes/lib.ts'` and `keel check` reports no E1013.
- In that project, one E1013 each, its fix `'../notes/T.ts'` or `'../notes/lib.ts'`, for `import type { T } from '#notes/T.ts'`, `export { lib } from '#notes/lib.ts'`, `import('#notes/lib.ts')`, and `linked-notes/lib.ts` through a symlink `node_modules/linked-notes` to `modules/notes`; with `"#app/*": "./modules/app/*"` added, `#app/Page.tsx` imported from `modules/app/sub/Deep.tsx` is one E1013 whose fix is `'../Page.tsx'`.
- In that project, with `tsconfig.json` `paths: { "@/*": ["./modules/*"] }`, an import of `@/notes/lib.ts` is one E1751 whose message starts `TS2307` and no E1013, as is one of `/modules/notes/lib.ts`; with `"#lib/*": "./lib/*"` and a file `lib/x.ts`, an import of `#lib/x.ts` is neither; `keel build` of the project with `#notes/lib.ts` prints no E1013.

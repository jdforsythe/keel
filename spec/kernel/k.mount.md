# k.mount: Pages into the identity mount
status: conformance-covered

How a page on any deployable sends the browser to the identity source's `handle` (k.user), Keel touching no credential.

**Declaration.** `identity.ts` beside `topology.ts` default-exports `identityMount(path, { links }?)` (`@keel/router`): `{ path, href, links }`, `path` a literal of lowercase `/` segments. `identity.server.ts` then gives `handle: { path: <its default import>.path, fn }`. `identity.ts` imports nothing server-only, so a page on any deployable imports it. A second `identityMount` call in one module graph does not throw. A test names the mount its `renderRoute` harness takes (`mount`, k.testing); no call made elsewhere gives one.
- `href(subpath?, search?)` returns a `MountHref`, an `Href` (k.router): `path`, `subpath`, then `?` and the `search` string map's keys sorted, keys and values encoded by `encodeURIComponent`; no `?` for an empty map. `subpath` is `''` or `/`-led segments of `[A-Za-z0-9._~-]`, none `.` or `..`; else (`//`, `..`, `?`, `#`, `%`, `\`, a scheme) it throws E1582. So it is root-relative under `path`, never absolute or protocol-relative.
- `links` (default `[]`; `['/magic-link/verify']`): subpaths a shell takes from a link at any time with no opening (k.return), each a literal of `subpath`'s form, not `''`, none repeated: an exact path under `path`, no search. Declaring one asserts the library's handler there is safe to receive unsolicited, from any app or page, with the user's cookies, as on the web.

**Navigation.** `Link to`, `navigate` and an action's `ok(href)` take it as any `Href`. A router handles client-side only a path its table matches as a page and k.mount-scope allows; a link click, `navigate` or `ok(href)` to another path is a document navigation (`location.assign`; `replace`: `location.replace`). An initial load or history pop of an unmatched path renders the 404. Without a router (a server-rendered page) links and an action's 303 are the browser's.

**Form.** A `<Form>` whose `action` no enclosing router matches, or with no router, submits natively; `method` must be `'POST'` when `action` is a `MountHref` (a type error otherwise). On `submit` it validates its `form` handle: errors show (k.forms) and the submit is prevented; else `pending()` is `true` and the browser posts `application/x-www-form-urlencoded` the form's named controls and the submitter's, Keel adding none. A chosen file throws E1583 and nothing is sent. `pending()` is `false` again on a `pageshow` from the back-forward cache. A queued submit (k.defaults) runs this at replay: sent once if valid, never if not.
- `.pii()` and `s.secret` fields go in the body as typed, to the page's own origin only; Keel logs no body. A URL lands in history and access logs, so none goes in `search`.
- The app's `handle.fn` answers a form post with a 303 to a page `Href` carrying its library's `set-cookie`; a rejection redirects to the form's page with a search key that route's schema declares (`?error=credentials`), which the page reads. Keel reads neither. The submitted email or password never goes back into a URL.

**Server.** A native POST under `handle.path` meets the same-site check first (k.server): same-origin passes; cross-site is 403 `keel.denied`, `fn` not called. Keel sets no cookie on a `handle` response. `form-action 'self'` (k.security) admits the post and a same-origin 303; browsers that apply it to redirects block a form post redirected to another origin, so leaving for a provider starts from a `Link` (a GET), whose redirect no directive governs.

**Origins.** `href` resolves against the page's origin, which must mount `handle`: every `node` deployable does (k.user), a `client` one through its `servedBy`. Cookies are per origin: a sign-in is unseen by a deployable the browser reaches on another origin, so an app serves one public origin and forwards to peers (k.topology).

**Testing.** `renderRoute` and `resumeDocument` handles have `documents()`: the document navigations the page started, in order, `{ method, url, body }` (`body` the urlencoded text, `null` for a GET); none is made and the page stays, but one to `app` under `renderRoute` with `app` (k.testing).
- A `renderRoute` harness with `app` or `shell` is one browser. With `app` its page runs on a ctx of its own (`ctx`'s clock and random, its own storage); with `shell`, on the shell ctx (k.return Testing). Each request the page sends to its origin (load, submit, mount request, service call, event stream) goes through `ctx.net`, to `app.fetch` with `app` unless the test routed that origin.
- Its cookie jar holds that origin's cookies: each such request enters `ctx.net` with `cookie` set to the jar's pairs, and each `set-cookie` line of its answer (a followed redirect's or a `redirect: 'manual'` 3xx's too) is applied: `name=value` kept, removed by `Max-Age` ≤ 0 or a past `Expires` on `ctx.clock`, other attributes ignored. So `app` mints each harness's caller and a sign-in through `handle` holds; with `shell` the jar is the native store (k.return).
- Under `keel test` the DOM is happy-dom's but `Request`, `Response`, `Headers`, `fetch` and abort classes are Node's, so `cookie` and `set-cookie` pass in process.

**Rules.** E1580 `identity.ts` whose default export is not `identityMount('<literal>')` of lowercase `/` segments, optionally with `{ links: [...] }`, or with no `identity.server.ts` giving `handle: { path: <its default import>.path }` (a literal there too) · E1581 a module file importing `identity.ts` where a `static` deployable, or a `client` one without `servedBy`, serves the module: no origin of it mounts `handle` · E1589 with `identity.ts`, a `static` deployable, or a `client` one without `servedBy` (shells or not), its key in `topology.ts`: no origin of it answers the router's `/__keel/user` read (k.guards Client); none when a module file it serves is E1581 · E1582 a `subpath` `href` refuses (`keel check` for a literal; the call throws) · E1583 a native submit with a file chosen · E1584 a `links` entry not a string literal, `''`, not of `subpath`'s form, or repeated (`keel check`; the call throws). Fix: none, but E1589's below.

**Messages.** E1580: `identity.ts's default export is not identityMount('<literal>') of lowercase / segments` (86 units) or `identity.server.ts gives no handle: { path: <identity.ts default import>.path }` (79). E1589: `<name> (static) serves no router, so with identity.ts its pages never learn the reader` (`site`: 84) or `<name> (client) has no servedBy: no origin of it mounts the identity handle` (`web`: 72). What to do instead is `keel explain`'s. E1589's fix, for a `client` deployable when `topology.ts` has exactly one `node` deployable, adds `servedBy: '<its name>'` to the entry; otherwise none.

**Conformance.**
- With `path` `/api/auth`, `href('/sign-in/email', { b: '2', a: 'x y' })` is `/api/auth/sign-in/email?a=x%20y&b=2` and `href()` is `/api/auth`; `'//x.example'`, `'/../x'`, `'/a/..'`, `'/a?b'`, `'/a#b'`, `'/a%2f'` and `'https://x'` each throw E1582.
- In a router, a `Link` click, `navigate` and an action's `ok` to it each record one GET in `documents()` and keep the page; a contract's `href` link navigates client-side.
- A `Form` POST to it with invalid input shows the errors and records nothing; valid, one POST whose body is exactly the named fields, no `_method`, with `pending()` `true`.
- One page module under `renderRoute` and served by `createApp` then `resumeDocument` records equal `documents()` for equal input.
- A submit queued before resume is sent once when valid, never when invalid.
- A same-origin urlencoded POST under `handle.path` reaches `fn`, a cross-site one is 403 without it; no response sets a cookie `fn` did not.
- E1580, E1581 and E1582 each have a triggering fixture and a clean one; a chosen file is E1583, nothing recorded.
- With `identity.ts` and `identity.server.ts`, no module file importing `identity.ts`: `{ web: client }`, `{ web: client, shells }` and `{ site: static, api: node }` each give one E1589 at that deployable's key in `keel check` and `keel build`; `{ web: client, servedBy: 'api', api: node }` with or without `shells`, `{ api: node }` and the same topologies without `identity.ts` give none; a file of `web` importing `identity.ts` gives one E1581 and no E1589.
- `identityMount('/api/auth', { links: ['/verify'] })` is clean, its `links` `['/verify']`; entries `''`, `'verify'`, `'/a?b'`, `'/../x'`, a second `'/verify'` and a variable each give one E1584 under `keel check`, and the call throws E1584 for each literal.
- With `app` and no `user`, a mount `Form` POST answered 303 with `set-cookie: s=1; HttpOnly`: the followed GET and each later request of that page carry `s=1`, a second harness's none; after an answer with `s=; Max-Age=0`, none does.
- Under `keel test`, `new Response(null, { headers: { 'set-cookie': 'a=1' } }).headers.getSetCookie()` is `['a=1']` and `new Request(url, { headers: { cookie: 'a=1' } })` keeps its `cookie`.

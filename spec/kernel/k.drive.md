# k.drive: Driving a simulation
status: implemented

How `simulate` (k.sim) moves a run's clock: when no work of the run is pending, to its next moment, so a scenario that awaits work waiting on the clock is answered and two runs of one `SimRun` give one trace. An *empty replay* is `simulate(scenario, { replay })` of a `SimRun` of seed 1 whose schedule is `{ net: [], storage: [], offline: [], plans: {} }`.

**Driving.** `simulate` (k.sim) runs each scenario inside the run's async context (Node `AsyncLocalStorage` and an `async_hooks` hook, in `@keel/testing`; `@keel/ctx` imports no Node module and a sim ctx outside `simulate` is never driven). Work of the run is *pending*:
- each async resource other than a promise created in that context, from its creation until Node destroys it: a timer or immediate after its callback, a file, DNS or thread-pool request (a password hash) after it answers, a socket, server, interval or port once closed;
- held work, until it settles;
- a harness `fire`, `settle`, `navigate` or render in progress, but not while it waits only on an unanswered `ctx.net` route.

The harness's and the drive's own macrotask turns are made outside the run's context and are not work; the drive moves the clock inside the run's context, so waiters, offline-edge callbacks and `observe` callbacks it runs make work of the run. Work that waits only on the sim clock or on the net's online state is promises alone and is never pending: it is *parked*, as is the request, job or route around it. A *moment* is the earlier of `ctx.clock.next()` and the next edge (`at` or `at + ms`, later than the clock) of a window in the run's `schedule.offline`. On each of its turns, while the scenario is pending and no work is pending, the drive advances the clock to the next moment if it is at most `horizon` ms past the run's start (or, while a `run(ms)` waits, at most its `t + ms`). Real work's speed decides nothing. A harness call moves no clock itself. Every `ctx.clock.after` waiter is driven alike: a net step's or plan step's `delay`, a job's `delayMs`, backoff, lease and `timeoutMs` (std.jobs), a runner's poll, a schedule's next time, a stream's heartbeat, a 5,000 ms bound (std.channels, std.live). A scenario awaiting work that waits on the clock gets its answer at the first moment it can, with no `run()` call; code after an `await` that needs no clock runs at that `await`'s time; after `run(ms)` the run's state at `t + ms` is readable, work parked across it included. The scenario's own `ctx.clock.advance(ms)` moves the clock too. `horizon: 0` leaves every later moment to the scenario's `advance`.

**Seams.** A run reaches real work only through these, each covered: `ctx.net` (a sim route, `app.fetch` behind a harness's `app` among them, runs as app code); `ctx.storage` (sim: microtasks only); `ctx.clock` and `ctx.random` (no real work); a registered capability's sim implementation (its own resources, and `hold` for what answers through something made outside the run); the server's handling of a request and an identity source's work (app code, its hash a thread-pool request); a harness's `routes: () => import()` load, held by the harness with the route id as label. App code reaches nothing else: E1601, E1603 and E1759 (k.ctx, k.host) report the ambient effects.

**Law.** The drive draws no random and reads no real time. Two runs of one `SimRun` and one scenario take the same moments in the same order and report the same observer events (k.ctx) in the same order at the same `ctx.clock.now()`, ending with equal store snapshots. *The same moments* are the `ctx.clock.now()` at each completion the scenario sees (a waiter, a save, a net call); *store snapshots* are the final values of the storage keys the scenario wrote; observer events include the `net` events of the schedule's offline windows. The run's *trace* is the list of moments taken and observer events of the run's ctx and its replicas, each with its `ctx.clock.now()`. The run's trace ends with the final value of each storage key the run wrote, by key in code-unit order, then the snapshot of each live store (`stores()`), by id, its log entries without their `at`. Entries are `{ kind: 'moment', at }`, `{ kind: 'event', at, event }`, `{ kind: 'storage', key, value }`, `value` the stored string as stored, and `{ kind: 'store', id, value }`, `value` the store's snapshot with each log entry's `at` left out (a per-store counter no restore resets). What the law rests on: within the run's context every non-promise resource is pending; work that answers through something made outside the run changes nothing only if it is held with `hold`. Three things escape the tracker and can change a trace: a resource made before the run or outside its context (a worker started at import, a module-level timer, channel or `AsyncResource`), unless the work answering through it is held; an `import()` in app code other than a harness's `routes` loader, which the test runner answers over its own channel; state kept outside the run's stores from one run to the next. `keel check` reports none of them. The law check reports a difference only when `law` is on or on the replays of a failing run, and only when it reaches the trace.

**Law check.** With `law: true` each run is run a second time with its `SimRun` and the two traces are compared; a failing run's shrunk `SimRun`, unless it failed with E1727 or E1728, is always replayed twice before it is reported. `law` is off by default. Two traces that differ, final values included, fail with E1729 (k.testing) `two replays of the run differ at trace entry <n>`, the two entries as JSON on the next two lines, in place of E1704.

**Stalls.** A scenario pending with no `run` call of it pending, when no work is pending and no moment is within its bound, fails the run on that turn with E1727 (k.testing), `the scenario waits past the horizon: next deadline <n> ms` when `ctx.clock.next()` is `n`, else `the scenario waits and nothing in the run is due`. A `ctx.clock.after` or an online wait made inside held work fails it at once with E1728 `held work waits on the sim clock: <label>`. `simulate` has a real-time *budget*: `simulate(scenario, { budget })` in ms, else the enclosing vitest test's timeout less a tenth of it (at least 50 ms), counted from the instant the runner starts the test (before its hooks), else 300,000 ms from the `simulate` call. When the budget is spent, the run in progress fails with E1728 `the budget ran out with work in flight: <labels>`, each pending piece's label (held work's label, else the resource's Node type: `Timeout`, `PBKDF2REQUEST`, `TCPWRAP`) oldest first, separated by `, `, or `none`; it is not shrunk or replayed. No piece of work has a bound of its own: endless short work is no stall, and the budget, the author's own bound, ends it. The budget reads real time only to fail a run: it never moves the clock or changes a trace. A scenario that resolves with work of the run still pending fails with E1728 `work outlived the scenario: <label>`, the first pending in creation order; it closes what it opened first (`app.close()`, `clearInterval`, a socket's `close`). A scenario that rejects is reported with its own error.

**Conformance.**
- In an empty replay, a scenario that awaits `ctx.clock.after(500)` and calls no `run` resolves, with `ctx.clock.now()` 500 after the await.
- In an empty replay, a scenario that starts a `ctx.clock.after(1000)` waiter, then awaits `ctx.clock.after(100)` and after it `ctx.clock.after(200)`: after the second await `ctx.clock.now()` is 300 and the 1,000 ms waiter has not resolved.
- In an empty replay, with waiters at 100, 200 and 300 ms each recording `ctx.clock.now()` as it resolves: after `await run(250)` the record is `[100, 200]` and the clock 250; after a following `await run(0)`, the same; after a following `await run()`, `[100, 200, 300]` and the clock 300.
- In an empty replay with `horizon: 0`, a scenario with waiters at 50 and 200 ms that calls `ctx.clock.advance(100)` then `await run()`: the clock is 100, the 50 ms waiter has resolved and the 200 ms one has not.
- A capability registered with a `sim` factory whose `work()` returns `hold('probe', () => p)`, `p` resolving when a `MessagePort` made before `simulate` delivers a message the test posts after 50 macrotask turns: in an empty replay, a scenario that starts a `ctx.clock.after(10)` waiter and awaits `work()` sees `ctx.clock.now()` 0 when `work()` answers and the 10 ms waiter not resolved.
- In an empty replay, with a `ctx.clock.after(100)` waiter pending, `fire` on a `render` handle on the run's ctx whose handler runs a transaction and waits on no clock resolves with `ctx.clock.now()` 0.
- In an empty replay, a scenario that awaits a promise nothing resolves, with no clock waiter, rejects `simulate` with E1704 whose first line holds `E1727 the scenario waits and nothing in the run is due`.
- In an empty replay with `horizon: 1000`, a scenario that awaits `ctx.clock.after(5000)` rejects `simulate` with E1704 whose first line holds `E1727 the scenario waits past the horizon: next deadline 5000 ms`, the clock at 0.
- A capability registered with a `sim` factory whose `work()` returns `hold('probe', () => new Promise(() => {}))`: in an empty replay, a scenario that awaits `work()` under `budget: 300` rejects `simulate`, no sooner than 300 ms of real time after the call, with E1704 whose first line holds `E1728 the budget ran out with work in flight: probe`.
- A scenario that starts ten waiters `ctx.clock.after(Math.floor(ctx.random.float() * 1000))`, each recording its index and `ctx.clock.now()` as it resolves, then awaits `run()`: under `simulate` with `{ runs: 20, seed: 7 }` each run's record lists all ten ordered by time, ties by index, and `replay` of the `SimRun` that run received records an equal list.
- In an empty replay, for each `d` of 0, 12 and 50, a scenario that starts `ctx.clock.after(10)` and a `setTimeout(d)` of `node:timers`, each recording its name and `ctx.clock.now()` as it resolves, then awaits `run()`: the record is `real` at 0, then `timer` at 10.
- In an empty replay, a scenario that starts a `ctx.clock.after(5)` waiter recording whether a `node:crypto` `pbkdf2` of 100,000 iterations started before it has answered, then awaits the hash and `run()`: the waiter records `true` at clock 5.
- A capability registered with a `sim` factory whose `work()` returns `hold('probe', () => ctx.clock.after(10))`: in an empty replay, a scenario that awaits `work()` rejects `simulate` with E1704 whose first line holds `E1728 held work waits on the sim clock: probe`.
- In an empty replay, a scenario that starts work writing `'running'` to a storage key, awaiting `ctx.clock.after(1000)`, then writing `'done'`: after `await run(500)` the key reads `'running'` and the clock is 500; after a following `await run(600)`, `'done'`.
- In an empty replay, with a `ctx.clock.after(10)` waiter pending, `renderRoute` given `app` and `routes` as `() => import(path)` resolves with `ctx.clock.now()` 0 and the waiter not resolved.
- Under `simulate` with `{ runs: 1, seed: 1, law: true }`, a scenario that awaits `ctx.clock.after(10 * k)`, `k` the count of its calls so far counting this one, rejects `simulate` with E1729 whose first line holds `two replays of the run differ at trace entry 0`.
- Under `simulate` with `{ runs: 1, seed: 1 }`, a scenario that awaits `ctx.clock.after(10 * k)`, `k` as above, then throws rejects `simulate` with E1729, not E1704; one that awaits `ctx.clock.after(10)` then throws rejects with E1704.
- In an empty replay under `budget: 300`, a scenario that runs a loop of `node:timers` `setTimeout(1)` calls, each started when the previous answers, for 600 ms of real time, then awaits `run()`, rejects `simulate` with E1704 whose first line holds `E1728 the budget ran out with work in flight: Timeout`; the same loop for 100 ms resolves.
- In an empty replay under `budget: 300`, a scenario that awaits one `node:timers` `setTimeout(400)` rejects `simulate` with E1704 whose first line holds `E1728 the budget ran out with work in flight: Timeout`; one that awaits `setTimeout(100)` resolves.
- Under `simulate` with `{ runs: 1, seed: 1, law: true }`, a scenario that sets storage key `n` to `String(k)`, `k` the count of its calls so far counting this one, and makes no other effect, rejects `simulate` with E1729 whose first line holds `two replays of the run differ at trace entry 0` and whose next two lines are `{"kind":"storage","key":"n","value":"1"}` and `{"kind":"storage","key":"n","value":"2"}`.
- In an empty replay, a scenario that starts a `node:timers` `setTimeout(50)` and resolves without awaiting it rejects `simulate` with E1704 whose first line holds `E1728 work outlived the scenario: Timeout`; one that starts a `setInterval` and calls `clearInterval` on it before resolving resolves.
- A capability registered with a `sim` factory whose `work()` returns `hold('probe', () => new Promise(() => {}))`: in an empty replay, a scenario that calls `work()` without awaiting it and resolves rejects `simulate` with E1704 whose first line holds `E1728 work outlived the scenario: probe`.
- Under `simulate` with `replay` of a `SimRun` of seed 1 whose schedule's `offline` is `[{ at: 100, ms: 50 }]`, an `observe` callback that, on the `net` event at 100, starts a `node:timers` `setTimeout(20)` recording `ctx.clock.now()` as it answers: it records 100, and after `run()` the clock is 150.
- In a vitest test declaring a 2,000 ms timeout, an empty replay with no `budget` whose scenario awaits `work()` of a capability whose `work()` returns `hold('probe', () => new Promise(() => {}))` rejects `simulate` with E1704 whose first line holds `E1728 the budget ran out with work in flight: probe`, between 1,800 and 2,000 ms of real time after the test started.

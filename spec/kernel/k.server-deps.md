# k.server-deps: Server dependencies
status: proposed

A package that keeps app data (k.data), or any other server dependency, states what it needs from the build and the deploy files as an app module does. The kernel names no such package.

**Environment.** A module manifest (k.module), a library's root `module.ts` included (k.library), may hold `env`: an array of string literals, the environment variables its server code reads. A `node` deployable needs the `env` names of each module its `modules` list and of each library those modules' manifests list, transitively. `deploy/compose.yaml` passes each name a deployable needs from the environment, required (`NAME: ${NAME:?}`), once per service, after the k.deploy keys and sorted, and no generated file holds a value. The names are read by server code only: no browser build holds one (k.bundle Environment).

**Files a bundled package reads.** When `server.mjs` bundles a file under a `node_modules` folder that holds `new URL('<f>', import.meta.url)` with `<f>` a string literal `./<file>` or `<file>`, `<file>` holding no `/`, `keel build` copies `<file>` from that file's folder into `dist/<name>/`, beside `server.mjs`, where the bundle reads it.

**Registration through a library.** A file registers a capability (k.data Dev) when it imports `@keel/ctx` and names `register`, or when it imports from a library (k.library) a name whose defining file in that library, followed through its re-exports, imports `@keel/ctx` and names `register`. Editing either kind of file under `keel dev` loads the server graph again whole, as k.data Dev states. In a library file, a `register` call whose name is a parameter of the exported function holding it is no E1607 (k.data); instead each app call of that export whose argument for the parameter is not a string literal `<id>.<name>`, `<id>` the calling file's module, is one E1607 at the argument.

**Rules.** E1167 an `env` entry that is not a string literal matching `[A-Z][A-Z0-9_]*`, or that is a key `DeployEnv` parses (`PORT`, `KEEL_SECRET`, `KEEL_ORIGIN`, `KEEL_DATABASE_URL`, `KEEL_ALLOW_ORIGINS`) or begins with `KEEL_PEER_`, at the entry · E1014 `keel build`: a `<file>` that a bundled package file names (Files a bundled package reads) is missing from that file's folder (message names the package file and `<file>`); the build fails and writes no `dist/<name>/`.

**Conformance.**
- In a project with `node` deployables `x` (modules `['a']`) and `y` (modules `['b']`), where `modules/a/module.ts` lists `'@acme/store'` in `deps` and `node_modules/@acme/store/module.ts` holds `env: ['ACME_STORE_URL']`, `deploy/compose.yaml` passes `ACME_STORE_URL: ${ACME_STORE_URL:?}` to `x` and holds no `ACME_STORE_URL` for `y`.
- In that project, `env: ['NOTES_URL']` in `modules/b/module.ts` makes `deploy/compose.yaml` pass `NOTES_URL: ${NOTES_URL:?}` to `y` only; `env: ['notes_url']`, `env: ['KEEL_SECRET']` and `env: ['KEEL_PEER_X']` there are each one E1167 at the entry.
- In a `node` fixture whose server code imports `node_modules/blob/index.js`, which holds `new URL('./blob.bin', import.meta.url)` and `new URL('other.bin', import.meta.url)` beside files `blob.bin` and `other.bin`, `keel build` writes `dist/<name>/blob.bin` and `dist/<name>/other.bin` equal to them; with `other.bin` deleted, `keel build` fails with one E1014 naming `node_modules/blob/index.js` and `other.bin`.
- Under `keel dev`, with `node_modules/@acme/store` a library of `id: 'store'` whose `src/index.ts` re-exports `store` from `./store.ts`, which imports `register` from `@keel/ctx` and calls `register('store.main', ...)` inside `store`, and `modules/a/data.server.ts` importing `store` from `'@acme/store'` and calling it, editing `modules/a/data.server.ts` makes the next request run the edited code, with no E1602.
- In that project, with `store(name)` calling `register(name, ...)`, `store('a.main')` in `modules/a/data.server.ts` is no E1607 and `store('main')` there is one E1607 at the argument; the library file reports none.

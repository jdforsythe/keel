# k.server-deps: Server dependencies
status: implemented

A package that keeps app data (k.data), or any other server dependency, states what it needs from the build and the deploy files as an app module does. The kernel names no such package.

**Environment.** A module manifest (k.module), a library's root `module.ts` included (k.library), may hold `env`: an array of string literals, the environment variables its server code reads. A `node` deployable needs the `env` names of each module its `modules` list and of each library those modules' manifests list, transitively. `deploy/compose.yaml` (its layout: k.deploy Deploy files) passes each name a deployable needs from the environment, required (`NAME: ${NAME:?}`), once in the deployable's service, after the k.deploy keys and sorted, and no generated file holds a value. The names are read by server code only: no browser build holds one (k.bundle Environment).

**Files a bundled package reads.** A bundled package file is a file a `node` deployable's `server.mjs` bundles that lies under a `node_modules` folder or is a library's (k.library), wherever the library's real folder is: installed, linked through a workspace, or inside the project. A library's file is named at `node_modules/<name>/<f>`. Its `new URL(<a>, import.meta.url)` calls are read; a `new URL` with any other base is not. The bundle resolves `<a>` against `server.mjs`, so:
- `<a>` a string literal, or a template literal without an expression, naming a path inside that file's folder (`./x.bin`, `x.bin`, `wasm/x.bin`): `keel build` copies the file or folder at that path into `dist/<name>/` at the same path, beside `server.mjs`.
- `<a>` naming an absolute URL (it begins `<scheme>:`) or that folder itself (`.`, `./`): left alone.
- `<a>` naming a path that leaves that folder (`../x.bin`, `/x.bin`), even inside the package, or `<a>` of any other form: E1014, since `dist/<name>/` could not hold the file where the bundle reads it.
- Two bundled package files naming one path for files of different bytes, in one package or in two (two libraries each shipping `data.bin`): E1014; with equal bytes the path is copied once. A file is never renamed or moved, and the bundle is not rewritten.

A stated limit: a package whose own layout reads a file above the reading file's folder (`new URL('../x.tar.gz', import.meta.url)`) cannot be served by `keel build`, even though the file is inside the package. All bundled files become `server.mjs`, so the bundle resolves that path against `server.mjs`, above `dist/<name>/`.

**Registration through a library.** A file registers a capability (k.data Dev) when it imports `@keel/ctx` and names `register`, or when it imports or re-exports from a library (k.library) a name whose defining file in that library, followed through its re-exports, imports `@keel/ctx` and names `register` (a namespace import: any such name). Editing either kind of file under `keel dev` loads the server graph again whole, as k.data Dev states, before the file has registered too: after an edit that adds such an import to a file that held none, module state other server files hold starts again at the next request.

In a library file, a `register` call whose name is a parameter of the exported function holding it (the innermost enclosing function with a parameter, plain or defaulted, of that name) is no E1607 (k.data); the name is judged where that export is called. Check traces every binding that may hold such an export: an import of it under any name; a namespace of a module that holds one (`import * as`, `import x = require`, an imported `export * as`); its declaration; a `const` alias or plain-keyed `const` destructuring of any of these; and a directly awaited literal `import()` of such a module. It crosses files through re-exports of any form and reads at most 8 files, the calling and the defining file counted. Every occurrence of such a binding is exactly one of three things:
- a further binding the trace continues through: a `const` declaration (not an exported one), a plain destructuring key, `export { x }`, `export default x`, a static member of a namespace;
- a call, whose argument for the parameter is judged as k.data judges a `register` name in the calling file: not a string literal `<id>.<name>`, `<id>` the calling module's id and `<name>` one lowerCamel segment, is one E1607 at the argument, and at the call when it has none (message `<export> of "<name>": name it '<id>.<lowerCamel>'`, or `<export> of a name that is not a string literal: ...`; a spread is no string literal); a name two such calls, or a call and a `register`, give in two files is one E1607 at the later file's;
- one E1607 at the occurrence, message `<export> used as a value: the name it registers cannot be read here`: any other position (an optional call, `new`, `.call`, a computed, defaulted or rest key among them). A binding reached through more than 8 files is this at each occurrence, message `<export> comes through more than 8 files: the name it registers cannot be read here`.

A name in a type position (`typeof x`, an annotation) carries no value and is no occurrence; a parameter of the same name hides the binding in its function. An `import(x)` with a computed specifier is an occurrence when a file it can reach holds such an export: for a relative template, the project files under its folder with its ending; for any other, always. `<export>` is an import's local, an alias's original, a member's or destructured key, a namespace's local, or `import()`. Any other non-literal library `register` name is E1607 in the library file. Code held in a string (`eval`, `new Function`) is out of scope.

**Rules.** A clipped E1167 `<name>` (28 units), E1607 `<name>` (30), `<f>` (40), `<other>` (36), `<export>` or `<id>` (20) ends in `...`, by k.check Diagnostics' clip at that width, and every message is within 89. E1167 an `env` entry that is not a string literal matching `[A-Z][A-Z0-9_]*`, or that is a key `DeployEnv` parses (`PORT`, `KEEL_SECRET`, `KEEL_ORIGIN`, `KEEL_DATABASE_URL`, `KEEL_ALLOW_ORIGINS`) or begins with `KEEL_PEER_`, at the entry: its line and the column of its first character, a string literal's opening quote (an `env` that is no array literal: at its value); messages `env entry is not a string literal` (an entry or an `env` that is no string literal), `env name "<name>" does not match [A-Z][A-Z0-9_]*`, and `env name "<name>" is a key DeployEnv reads` (a `DeployEnv` key, or a name in the pattern beginning with `KEEL_PEER_`); no fix · E1014 `keel build`: a bundled package file's `new URL(<a>, import.meta.url)` whose `<a>` is of no form Files a bundled package reads copies or leaves alone, names a missing path, or names a path another bundled package file names for a file of other bytes; located at the package file (a library's at `node_modules/<name>/<f>`, any other by its path from its last `node_modules/` folder); messages `reads <f>, which is missing`, `reads <f>, outside its own folder`, `reads <f>, as <other> reads another file`, `reads new URL(x, import.meta.url) with x no string literal`, `<f>` the first argument as written, a leading `./` kept, `<other>` the other package file as located; the build fails and writes no `dist/<name>/`.

**Conformance.**
- In a project with `node` deployables `x` (modules `['a']`) and `y` (modules `['b']`), where `modules/a/module.ts` lists `'@acme/store'` in `deps` and `node_modules/@acme/store/module.ts` holds `env: ['ACME_STORE_URL']`, `deploy/compose.yaml` passes `ACME_STORE_URL: ${ACME_STORE_URL:?}` to `x` and holds no `ACME_STORE_URL` for `y`.
- In that project, `env: ['NOTES_URL']` in `modules/b/module.ts` makes `deploy/compose.yaml` pass `NOTES_URL: ${NOTES_URL:?}` to `y` only; `env: ['notes_url']`, `env: ['KEEL_SECRET']` and `env: ['KEEL_PEER_X']` there are each one E1167 at the entry.
- In a `node` fixture whose server code imports `node_modules/blob/index.js`, which holds `new URL('./blob.bin', import.meta.url)` and `new URL('other.bin', import.meta.url)` beside files `blob.bin` and `other.bin`, `keel build` writes `dist/<name>/blob.bin` and `dist/<name>/other.bin` equal to them; with `other.bin` deleted, `keel build` fails with one E1014 naming `node_modules/blob/index.js` and `other.bin`.
- Under `keel dev`, with `node_modules/@acme/store` a library of `id: 'store'` whose `src/index.ts` re-exports `store` from `./store.ts`, which imports `register` from `@keel/ctx` and calls `register('store.main', ...)` inside `store`, and `modules/a/data.server.ts` importing `store` from `'@acme/store'` and calling it, editing `modules/a/data.server.ts` makes the next request run the edited code, with no E1602.
- In that project, with `store(name)` calling `register(name, ...)`, `store('a.main')` in `modules/a/data.server.ts` is no E1607 and `store('main')` there is one E1607 at the argument; the library file reports none.
- In that `node` fixture, `node_modules/blob/lib/deep.js` holding `new URL('deep.bin', import.meta.url)` makes `keel build` write `dist/<name>/deep.bin` from `lib/`, and `new URL('./wasm/x.bin', import.meta.url)` in `index.js` writes `dist/<name>/wasm/x.bin`; `new URL('https://example.com/x', import.meta.url)` and `new URL('.', import.meta.url)` copy nothing and fail nothing; `new URL('../up.bin', import.meta.url)`, `new URL(name, import.meta.url)` and ``new URL(`./${name}.bin`, import.meta.url)`` each make `keel build` fail with one E1014 naming `node_modules/blob/index.js`, and no `dist/<name>/`.
- Under `keel dev`, with `modules/a/data.server.ts` importing nothing from `'@acme/store'` and `modules/a/count.server.ts` counting the requests its loader answers, after requests answered 1 and 2, an edit that makes `data.server.ts` import `store` from `'@acme/store'` and call it makes the next request answer 1.
- In the fifth bullet's project, `store()` with no argument in `modules/a/data.server.ts` is one E1607 at the call; `store('a.main')` in both `modules/a/data.server.ts` and `modules/a/other.server.ts` is one E1607, in `other.server.ts`; `register(name, ...)` in the library with `name` a `const` of `store.ts` is one E1607 in the library file.
- In a `node` fixture whose `modules/a` lists `@acme/store`, a library linked through a workspace (its real folder outside the project) whose `src/store.ts` holds `new URL('./store.bin', import.meta.url)`, `keel build` writes `dist/<name>/store.bin`; with `store.bin` deleted it fails with one E1014 naming `node_modules/@acme/store/src/store.ts`; two libraries each shipping a `data.bin` of other bytes fail it with one E1014.
- In the fifth bullet's project, `const db = store` then `db('a.main')` is no E1607 and `db('main')` one at the argument; `run(store)`, `{ make: store }`, `store.call(undefined, 'a.main')`, `store.bind(undefined)` and `export const db = store` are each one E1607 at the use.

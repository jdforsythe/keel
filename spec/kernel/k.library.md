# k.library: Libraries
status: proposed

**Kind.** A library is a package of Keel code an app checks and compiles as its own. Its `package.json` has `"keel": "library"` and a scoped name; its root `module.ts` is a k.module manifest (`id` prefixes its route ids, store ids, transaction names and error codes; `deps` names the libraries it uses; `public.exports` is its surface); its files are those under `src/` and `unsafe/` of its package folder. An `exports` entry with no `keel` condition (k.library-pack) is read at its other target.

**In an app.** An app module lists a library in `deps` by package name; a `deps` entry beginning with `@` names a package, any other a module id. The app's libraries are those its manifests list, transitively, each found as Node resolves the name from the listing manifest's folder, a link followed to its real path. `check()` reads its `package.json`, `module.ts` and `.keel/ledger.json` from the files given, under `node_modules/<name>/`. For them:
- The compiler resolves imports with the `keel` condition on every surface and transforms a library's files as the app's, at `modules/<id>/<f>` (JSX, element ids, style props against the app's `tokens.ts`); the `.keel/` artifacts and E1005 derive from them. A linked library resolves its imports from its real folder, where the kernel packages must resolve to the app's.
- `keel check` runs every rule but E1106 (k.formats Who declares) over them, the type pass included, against the app's `tokens.ts`, kernel packages and `topology.ts`. Where a section reads app code or `modules/<id>/` (k.check App code), it reads a library's file `<f>` as `modules/<id>/<f>`, its `unsafe/` files with their lifted ranges. A diagnostic in one is the app's, at `node_modules/<name>/<f>`, with no `fix`. A bare import there resolves from the library's folder, to one of its `dependencies`, and is no E1163.
- The k.module rules hold for a library: E1151 (an app file imports only its entries and its `public.exports`), E1152, E1155, E1156; a library in `deps` is used by being listed (no E1165) and may be a `std` key (E1158).
- k.module (Std config), k.topology and k.contract read a library's entry, `./tools`, `./module`, `./routes`, `./contract` and `std` config as a stdlib package's (k.parity By kind). `keel check` and `keel build` import only its `./tools` (k.library-pack); its rule codes are held to E1753. Only a deployable whose `modules` names its `id` serves its routes: listing it adds no route, server code or identity.

**Guarantees.** Installing a library weakens no check of the app's: personal data and secrets (E1111 reads its exported schemas as a package's), the content security policy, accessibility, host elements and code, internal entries (E1576) and detached scopes (E1207, k.parity).

**Ids.** Each `@keel/ui` base element (`Host` among them) and `@keel/ui/aria` `Part` a library file renders, as JSX or a call, takes an `id` check reads as built from its component's `id` prop (`<id>.<part>`, k.component IDs): `<p>.id`, `<p>` a top-level function's first parameter; a name bound to one or destructured as `id`; a template literal with one; a conditional of two; a call whose callee check reads (a function of a library's files, a closure, or a member of an object read back to a literal or a call) and whose every returned expression is one, parameters standing for the arguments, closure names read where bound (a function met again while its read is open, or past eight calls, the call at the element the first, is not read); or such an `id` in an object literal, spread or not, with no unreadable spread after it. Anything else is E1161. An element of a route component file (one the library's `manifest(` of `@keel/router` binds as a `component`, a relative default import, its stem in no `public.exports` or `exports` target) may instead take a literal `id` `<id>.<rest>` (no spread after it), `<id>` the manifest `id`, `<rest>` not empty.

**Ledger.** A published library carries `.keel/ledger.json`, written by its own `keel ledger --write`. The app's `keel ledger` counts `unsafe` and `hostElements` over each library's files as over its own; a library file the project's own read holds (a workspace's `packages/<pkg>/`) is counted once, as the project's. A library is installed when its real path lies in a `node_modules` folder, else linked. Per entry of an installed library's ledger `exports` (libraries by name, entries in file order), `keel ledger` emits `{ kind: 'ledger', item: '<name>/<file>#<export>', rung, evidence: 'library <version>' }` after the project's records, `<version>` its `package.json` `version`; `--scope` keeps one whose item starts with it. None of it is the app's: the summary `counts`, the written `exports` and `rungs`, and `--diff` leave it out; a file E1162 fails adds none. The written `libraries` has an entry per library, installed or linked, by name: its `version` and the app's `unsafe` and `hostElements` counts over its files.

**Rules.** E1161 an element in a library file whose `id` Ids does not accept (fix: none) · E1162 an installed library's `.keel/ledger.json` missing, misshapen, or stating an `unsafe` or `hostElements` other than the app's count over its files, at each `deps` entry naming it, from `keel check` alone (messages: k.library-pack Ledger file; fix: none) · E1163 a library file's relative import, re-export or literal `import()` resolving outside its package folder, at the specifier, or a library manifest `deps` entry not beginning with `@`, at the entry (fix: none; no E1153 edge, no E1165) · E1166 a library whose `id` a project module or another of the app's libraries holds, at each `deps` entry naming it (message `module id <id> is held by <a> and <b>`, an app module before a library, libraries by name; fix: none). A diagnostic at an entry lies on it, from its opening quote to its closing one. A `deps` entry naming no `"keel": "library"` package is E1159.

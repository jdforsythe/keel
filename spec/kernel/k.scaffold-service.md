# k.scaffold-service: Service scaffold
status: conformance-covered
`keel scaffold service <module>` writes a client of an API no app module serves (k.services). It is a generator (k.scaffold): one edit set, applied atomically, `--dry-run` as for any operation.
```sh
keel scaffold service orders --openapi openapi.json --name gitHub
keel scaffold service geo --base https://geo.example.com --reason 'place lookup'
```

**Input.** `keel scaffold service <module>` takes `--openapi <file>` or `--base <url>`, one of them, and `--name <name>` with either. Input `{ id, name?, base?, schema?, service?, reason? }`: `base` alone, or `schema` and `service` together (the two sources of k.openapi, whose `base` literal is the URL); anything else is E1052.
- `name` names the declaration: `<Name>Api` in `<Name>Api.schema.ts`, `<Name>` being `name` with its first letter upper-cased. It is lowerCamel, as a module id is (else E1352, nothing written, in either form); without it, `name` is the module id. The client is `api` in `api.server.ts` whatever the name, so a module holds one scaffolded service: a second is E1351. An empty `--name ''` is a name outside the rule: E1352.
- `--openapi`: both files as k.openapi generates them for `name`, read-only.
- `--base`: an absolute `http` or `https` URL with no query, fragment or credentials (else E1052). `<Name>Api.schema.ts` exports `<Name>Api = endpoints({})` and `api.server.ts` exports `api = service({ base: '<url>', schema: <Name>Api })`; both are the author's to edit.

**Edits.** Both forms add `@keel/services` to `dependencies` at the version of `@keel/server` when it is absent. Where the module's deployable is `client`, `api.server.ts` ships (k.boundary), so the operation declares the URL's origin as well: `origins.connect` of that deployable in `topology.ts` gains `'<origin>': '<reason>'` (k.origins), `reason` from `--reason <text>`, and without one it is E1358. An origin that deployable already declares needs no `reason`, and `topology.ts` is not changed. A `reason` with nothing to declare (the module's deployable is not `client`, or the origin is declared) is E1052. An origin or reason k.origins refuses, or a 17th `connect` origin, is E1353 naming E1590.

**Rules.** E1358 `service` in a module of a `client` deployable whose origin that deployable does not declare under `connect`, with no `reason`; names the deployable and the origin (no fix: pass `--reason`, or `codemod place` the module on a `node` deployable). A failing input schema reports k.cli E1052.

**Conformance.**
- Each project below holds module `orders`. In a `--adapter node` project, `service { id: 'orders', base: 'https://api.example.com' }` creates exactly `modules/orders/OrdersApi.schema.ts` (one export, `OrdersApi = endpoints({})`) and `modules/orders/api.server.ts` (one export, `api = service({ base: 'https://api.example.com', schema: OrdersApi })`), neither with a generated first line; it changes `package.json` alone, which gains `@keel/services` at the version of `@keel/server`; `keel check` and `keel test` are clean.
- In the default project that input with `reason: 'order list'` also changes `topology.ts`: `web` has `origins: { connect: { 'https://api.example.com': 'order list' } }` and its other properties as before, and `keel check` is clean; with `base: 'https://api.example.com/v2'` the key is still `https://api.example.com`.
- In the default project, with no `reason`, that input and the `{ id, schema, service }` form are each E1358 naming `web` and `https://api.example.com`, nothing written; with `connect` already declaring that origin, each applies without a `reason` and leaves `topology.ts` byte-identical, and with one is E1052.
- E1052, nothing written: a `reason` in the `node` project; `base` with `schema` and `service`; none of the three; a `base` of `ftp://a.example`, `/v1`, `https://a.example/?q=1` or `https://u:p@a.example`.
- In the default project, each is E1353 naming E1590, nothing written: `base: 'http://api.example.com'` with a `reason`; a `reason` of 201 characters; an origin that would be the 17th under `connect`. In the `node` project `base: 'http://internal:8080'` applies.
- In the `node` project, `service { id: 'orders', name: 'gitHub', base: 'https://api.github.com' }` creates exactly `modules/orders/GitHubApi.schema.ts` (one export, `GitHubApi = endpoints({})`) and `modules/orders/api.server.ts` (one export, `api = service({ base: 'https://api.github.com', schema: GitHubApi })`), changes `package.json` alone, and leaves `keel check` and `keel test` clean; with `name: 'orders'` the edit set equals that of no `name`.
- In the `node` project holding as `openapi.json` an OpenAPI 3 document k.openapi accepts, `keel scaffold service orders --openapi openapi.json --name gitHub` creates exactly `modules/orders/GitHubApi.schema.ts` (one export, `GitHubApi`) and `modules/orders/api.server.ts` (one export, `api`, importing `./GitHubApi.schema.ts`), each with the generated first line, and leaves `keel check` clean; with `--name GitHub` it is E1352, nothing written.
- In the `node` project, `service { id: 'orders', base: 'https://api.github.com', name }` with a `name` of `GitHub`, `git_hub`, `git-hub`, `1x` or `''` is E1352, nothing written. With `name: 'gitHub'` it is E1351 naming `modules/orders/api.server.ts` where that file exists, and E1351 naming `modules/orders/GitHubApi.schema.ts` where only that one does; nothing written.

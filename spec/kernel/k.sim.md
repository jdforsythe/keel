# k.sim: Schedules and simulation
status: implemented

Under sim (k.ctx) every capability is deterministic by seed. A schedule fixes what the seed leaves alone: how long each request takes, which requests and storage calls fail, and when the network is offline. `simulate` runs one scenario under many generated schedules, as `properties` (k.testing) runs one property under many inputs.

**Clock.** The sim clock starts at 0 and moves only through `advance(ms)`, which resolves each waiter whose deadline it crosses in deadline order (ties: registration order), with `now()` at that deadline for code that runs synchronously as the waiter resolves. `next()` returns the earliest pending deadline, else `null`.

**Schedule** (`@keel/ctx`, a schema; JSON):
```ts
type Schedule = { net: NetStep[]; storage: ('ok' | 'fail')[]; offline: { at: number; ms: number }[]; plans: { [capability: string]: JsonValue[] } }
type NetStep = { delay: number; fault: 'none' | 'drop' | 'lost' | 'unavailable' }   // delay: integer 0 to 60000
```
`createCtx({ mode: 'sim', seed, schedule })` applies it:
- **net.** The n-th `fetch` of the ctx (from 0) takes `net[n]`, or `{ delay: 0, fault: 'none' }` past the end. It waits `delay` ms on the sim clock, then: `none` runs the route and resolves its response; `drop` rejects with a `TypeError` and runs nothing; `lost` runs the route, then rejects with a `TypeError`; `unavailable` resolves a 503 and runs nothing. Each step is taken when the fetch is made, so responses can arrive out of order.
- **storage.** The n-th `get` or `set` takes `storage[n]`; `fail` rejects with an `Error`, and a failed `set` stores nothing.
- **offline.** Each window sets the net offline (k.sync) when the clock reaches `at` and online again at `at + ms`.
- **plans.** `register(name, { real, shell, sim, plan? })`: `plan` is the schema of one step of that capability's plan. Its sim factory gets `{ seed, plan, hold }`, `plan` being `plans[name]` parsed by it (default `[]`), and consumes it in call order as its own documentation says. `hold(work, label)` returns `work` and marks it held until it settles: real I/O whose progress no microtask or clock of the ctx shows (std-postgres's PGlite calls). A replica's held work is its parent's; outside `simulate` nothing reads it.

A ctx without `schedule` behaves as with an empty one. `schedule` on a real or shell ctx, or one that fails `Schedule`, throws E1604.

**Replicas.** `replica(ctx)` (`@keel/ctx`) of a sim ctx is a sim ctx standing for another process on the same storage, as two replicas of a `node` deployable are. It shares `ctx`'s clock, random, net, schedule and capability implementations (a capability accessor returns one object for both). Its `ctx.storage` is another storage object on the same data: commits through either serialize as one storage's (k.persist), they take steps of one schedule, and each sees the other's through `watch` (k.persist Watch). Its observers are its own: an event reported on one, a `save` of a `createApp` on it among them, reaches only that one's observers, but `net`, reported to both. `replica` of a real or shell ctx throws E1604. A test of two replicas serves one `createApp` on `ctx` and one on `replica(ctx)`, and renders each page with `app` (k.testing) against the one it reaches.

**simulate** (`@keel/testing`).
```ts
await simulate(async ({ ctx, run }) => {
  const t = await renderRoute('todos.list', { routes, params: { listId: 'l1' }, ctx })
  await t.fire('todos.addTodo', { type: 'click' })
  await run()
  expect(t.state(serverBoard).todos).toHaveLength(3)
}, { runs: 100, seed: 7 })
```
`simulate(scenario, { runs = 100, seed?, horizon = 600000, replay? })`. Each run draws a `SimRun` `{ seed, schedule }` from fast-check, the schedule generated from `Schedule` and each registered `plan` schema, creates that sim ctx, and awaits `scenario({ ctx, seed, schedule, run })`. `run(ms?)` waits while the drive (below) moves the clock: `run()` resolves once the run is idle, no `ctx.net` route of it is unanswered, and no moment is within the horizon, so no window edge within the horizon is left ahead of the clock; `run(ms)`, `ms` an integer 0 to 600000, takes each moment at or before `t + ms` (`t` the clock when called; the horizon does not bound it), then advances the clock to `t + ms` if it is earlier, and resolves once the run is idle with no `ctx.net` route unanswered. `run(0)` moves no clock. Another `ms` rejects with `schema.invalid`, failing the run. Each run starts from the snapshots the live stores (`stores()`) held before `simulate`, restored after it. A scenario that throws or rejects fails the run. The seed is `seed`, else `KEEL_SEED`, else 1337; success resolves `{ seed, runs }`.

**Driving.** While a run's scenario is pending, `simulate` drives the run's clock, which its replicas share. The run is *idle* when no held work is pending, two macrotask turns in a row, each after the microtask queue drains, change no store log and no DOM, and no harness `fire`, `settle`, `navigate` or render is in progress but one waiting only on an unanswered `ctx.net` route. A *moment* is the earlier of `ctx.clock.next()` and the next edge (`at` or `at + ms`, later than the clock) of a window in the run's `schedule.offline`. When the run is idle, the drive advances the clock to the next moment if it is at most `horizon` ms past the run's start (or, while a `run(ms)` waits, at most its `t + ms`), and waits for idle again. A harness call moves no clock itself. Every `ctx.clock.after` waiter is driven alike: a net step's or plan step's `delay`, a job's `delayMs`, backoff, lease and `timeoutMs` (std.jobs), a runner's poll, a schedule's next time, a stream's heartbeat, a 5,000 ms bound (std.channels, std.live). The clock moves only when nothing in the run can move without it, so a scenario that awaits work waiting on the clock gets its answer at the first moment it can, with no `run()` call, and code after an `await` that needs no clock runs at the time that `await` answered. The scenario's own `ctx.clock.advance(ms)` moves the clock too. `horizon: 0` leaves every later moment to the scenario's `advance`.

**Law.** The drive draws no random and reads no real time. Two runs of one `SimRun` and one scenario whose effects go through the run's ctx, its real I/O held, take the same moments in the same order and report the same observer events (k.ctx) in the same order at the same `ctx.clock.now()`, ending with equal store snapshots. *The same moments* are the `ctx.clock.now()` at each completion the scenario sees (a waiter, a save, a net call); *store snapshots* are the final values of the storage keys the scenario wrote; observer events include the `net` events of the schedule's offline windows. Work the run cannot see (a file read, an `import()` no harness call is loading, a timer) is outside the law.

**Stalls.** A scenario pending with no `run` call of it pending, in a run idle with no `ctx.net` route unanswered and no moment within its bound through 1,000 more macrotask turns, fails the run with E1727 (k.testing), `the scenario waits past the horizon: next deadline <n> ms` when `ctx.clock.next()` is `n`, else `the scenario waits and nothing in the run is due`. Held work pending, or an unanswered `ctx.net` route with no moment within the bound, through 200,000 macrotask turns with no store log or DOM change fails it with E1728 `work in flight never answered: <label>`, `<label>` the held work's, else `a ctx.net request`. The bounds count turns, not time.

**Failure.** A failing run is shrunk (fewer steps, shorter delays, fewer faults and windows) and reported as E1704 (k.testing) with the seed, the run, and the shrunk `SimRun` as JSON on the next line. `simulate(scenario, { replay: simRun })` runs that one `SimRun` once, and two runs of one `SimRun` take the same steps in the same order.

**Conformance.**
- `clock.next()` is the earliest pending `after` deadline, and `null` once `advance` has passed every one or each waiter aborted.
- With `net` `[{ delay: 50, fault: 'none' }, { delay: 10, fault: 'none' }]`, two fetches made at time 0 resolve the second at 10 and the first at 50, and a route that records calls sees the second first.
- `drop` and `unavailable` never run the route; `lost` runs it once and the fetch rejects with a `TypeError`; `unavailable` resolves status 503.
- A `ctx.net` route that awaits a promise the scenario resolves after `run()` starts, or a `ctx.clock.after` of the run: `run()` resolves once the route has answered, never before.
- A `fail` storage step rejects that call and a failed `set` leaves the key's earlier value.
- An `offline` window `{ at: 100, ms: 50 }` makes `ctx.net.online()` false from clock time 100 to 150, and an observer gets the two `net` events.
- A registered capability with a `plan` schema receives `plans[name]` in its sim factory; a plan step that fails its schema, or `schedule` on a real ctx, throws E1604.
- A ctx with an empty schedule gives the same results and observer events as one without.
- A scenario that fails only when a response is `lost` fails `simulate` with E1704 whose shrunk `SimRun` holds exactly one `lost` step and no other fault; `replay` of it fails the same way.
- Two `simulate` runs with one seed pass the same `SimRun`s to the scenario in the same order.
- A module store written by one run holds its pre-`simulate` state when the next run starts and after `simulate` resolves.
- `replay` of a `SimRun` whose `offline` is `[{ at: 100, ms: 50 }]`, its scenario advancing the clock to 120 with no `after` waiter pending: after `run()`, `ctx.net.online()` is true and `clock.now()` is 150; with `horizon: 130` it is still false.
- With `b = replica(a)` of a sim ctx `a`: a value `set` through `a.storage` is what `b.storage.get` returns; `b.clock.now()` equals `a.clock.now()` after `advance(100)` on `a`'s clock; a capability accessor returns the same object for `a` and `b`; `replica` of a real ctx throws E1604.
- With `createApp` A on sim ctx `a` and B on `b = replica(a)`, an action on either app that saves store `s` reports one `save` event to an observer of that app's ctx and none to an observer of the other's, and so for each of repeated saves; overlapping actions on A and B that save `s` from one read leave one saved and the other 409 `keel.conflict`.
- Under `simulate` with `replay` of a `SimRun` of seed 1 and an empty schedule, a scenario that awaits `ctx.clock.after(500)` and calls no `run` resolves, with `ctx.clock.now()` 500 after the await.
- Under `simulate` with `replay` of a `SimRun` of seed 1 and an empty schedule, a scenario that starts a `ctx.clock.after(1000)` waiter, then awaits `ctx.clock.after(100)` and after it `ctx.clock.after(200)`: after the second await `ctx.clock.now()` is 300 and the 1,000 ms waiter has not resolved.
- Under `simulate` with `replay` of a `SimRun` of seed 1 and an empty schedule, with waiters at 100, 200 and 300 ms each recording `ctx.clock.now()` as it resolves: after `await run(250)` the record is `[100, 200]` and the clock 250; after a following `await run(0)`, the same; after a following `await run()`, `[100, 200, 300]` and the clock 300.
- Under `simulate` with `replay` of a `SimRun` of seed 1 and an empty schedule and `horizon: 0`, a scenario with waiters at 50 and 200 ms that calls `ctx.clock.advance(100)` then `await run()`: the clock is 100, the 50 ms waiter has resolved and the 200 ms one has not.
- A capability registered with a `sim` factory whose `work()` returns `hold(p, 'probe')`, `p` resolving after 50 `MessageChannel` macrotask turns: under `simulate` with `replay` of a `SimRun` of seed 1 and an empty schedule, a scenario that starts a `ctx.clock.after(10)` waiter and awaits `work()` sees `ctx.clock.now()` 0 when `work()` answers and the 10 ms waiter not resolved.
- Under `simulate` with `replay` of a `SimRun` of seed 1 and an empty schedule, with a `ctx.clock.after(100)` waiter pending, `fire` on a `render` handle on the run's ctx whose handler runs a transaction and waits on no clock resolves with `ctx.clock.now()` 0.
- Under `simulate` with `replay` of a `SimRun` of seed 1 and an empty schedule, a scenario that awaits a promise nothing resolves, with no clock waiter, rejects `simulate` with E1704 whose first line holds `E1727 the scenario waits and nothing in the run is due`.
- Under `simulate` with `replay` of a `SimRun` of seed 1 and an empty schedule and `horizon: 1000`, a scenario that awaits `ctx.clock.after(5000)` rejects `simulate` with E1704 whose first line holds `E1727 the scenario waits past the horizon: next deadline 5000 ms`, the clock at 0.
- A capability registered with a `sim` factory whose `work()` returns `hold(new Promise(() => {}), 'probe')`: under `simulate` with `replay` of a `SimRun` of seed 1 and an empty schedule, a scenario that awaits `work()` rejects `simulate` with E1704 whose first line holds `E1728 work in flight never answered: probe`.
- A scenario that starts ten waiters `ctx.clock.after(Math.floor(ctx.random.float() * 1000))`, each recording its index and `ctx.clock.now()` as it resolves, then awaits `run()`: under `simulate` with `{ runs: 20, seed: 7 }` each run's record lists all ten ordered by time, ties by index, and `replay` of the `SimRun` that run received records an equal list.

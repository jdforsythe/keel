# k.boundary: The server boundary
status: conformance-covered

Which code reaches a browser, decided by the deployable that lists the code's module (k.topology); with no `topology.ts` (tests, `renderRoute`), as on `node`.

**Server-only.** A server-only file is a file named `*.server.*` or `*.guard.*`, in the app or a package, unless its module is one only `client` deployables list (a file under `modules/<id>/` is module `<id>`'s, a stdlib package's file its module's; a file outside every module is server-only). In a module a `node` or `static` deployable lists, loaders and actions (E1551) and guards (E1009) live in server-only files and run only on the server or at build; no byte of a server-only file, nor of what only server-only files import, is in an asset served to a browser. In a module only `client` deployables list nothing is server-only: its `*.server.*` and `*.guard.*` files hold the loaders, actions and guards the browser runs (k.router), are browser files (k.host) and ship like any other.

**Browser builds.** Every browser build the Vite plugin runs (a `node` deployable's client build, a `client` deployable's, a shell's, the project's own) resolves an import of a server-only JS or TS file, without a query, to a stub: the file's export names (`export *` followed), each a function that throws an Error with code E1008 `<name> of <file> runs only on the server` when called, and no import but the router's. The file's code, imports and top-level statements are never evaluated in a browser. `manifest` accepts a stub wherever a loader, action or guard goes and skips its checks, which ran when the build evaluated `routes.ts` in Node (k.compiler), so the client router keeps typed params and search, `Link`, `navigate`, `Form` and `matchHref`; a page takes links from its contract (k.contract), which imports no server file. `node:sqlite` is mapped in the server build only.

**Assertion.** After bundling, a browser build fails with E1007, writes nothing for its deployable and exits 1 when its graph from any entry, dynamic imports and emitted files included, holds a server-only file (any query), a Node built-in (k.bundle), or a file calling `loader`, `action` or `guard` from `@keel/router`, unless the build is a `client` deployable's and the file's module one it lists. Message: `server code in browser build: <reason>: <entry> -> <a> -> <file>`, each step a project-relative path or package specifier. It holds when an import gets around the stubs.

**Environment.** No environment value is in a file `keel build` writes, but the origins `KEEL_PEER_<NAME>` (k.hosting) and, in a shell build, `KEEL_ORIGIN` (k.shell). A browser build's `import.meta.env` holds only `MODE`, `DEV`, `PROD`, `SSR` and `BASE_URL`, exposing no variable by prefix (`VITE_*` too); `process.env.<x>` is never replaced by a value but `NODE_ENV` (k.deploy). Config a browser reads comes through `clientStd` (k.leave).

**Ambient types.** `import.meta` is typed by TypeScript's lib, `@types/node` and k.bundle's Types alone. E1016 is a `/// <reference …/>` directive (`types`, `path`, `lib` or `no-default-lib`) in a project code file (E1576's files, k.security), tests included: `type reference in project code; import.meta.env and import types are Keel's` (75 units), at the directive, fix: delete its line. E1016, no fix, is also a declaration of the global `ImportMeta` or `ImportMetaEnv` in any other file the type pass loads (a project `declare global`, or Vite's, through `import 'vite/client'` or `import type {} from 'vite/client'`): once per declaring file, at its first such declaration when it is a project file, else at the first import, by path then position, of a project file through which the pass loads it: `<file> declares import.meta types; they are Keel's and Node's only`, `<file>` the project-relative path or package specifier of the declaring file, cut from its front to fit 89 units (60 without it): whole leading segments are dropped behind `.../` (`.../c/env.d.ts`), and a last segment still too long keeps its end behind `...`.

**Reach.** Client-reachable code (E1004, E1571 and E1107), with a `topology.ts`: a file under `modules/<id>/`, not server-only, of a `node` or `static` module (one such a deployable lists); a file of a `client` module, for imports of another module's server-only files; and a project file outside `node_modules/` a client entry reaches by value imports, re-exports and `import()` (Following), not through a server-only file. Client entries: each route `component` of a `node` or `static` module and every file of a `client` one. No `topology.ts`: every file but server-only ones. A `routes.ts` may import server-only files by value; a specifier with a query names its file; package imports are not followed (E1007 covers them). An E1004 found through a chain ends `(<entry> -> … -> <file>)`.

**Following.** Reach, and k.origins' file importing another, follow a specifier to the project file k.bundle Aliases resolves it to (relative, the project's own name, a workspace link or a `node_modules` symlink whose real path is a project file), its query stripped; one resolving under `node_modules/` or outside the project is a package's, not followed (E1007 holds at build), but for a listed library's `exports` entry, followed to the file it gives among the project's files (k.library In an app). An `import()` of a template literal whose text before its first substitution starts `./` or `../` reaches each project file its pattern matches, each substitution read as `*` within one path segment, as Vite expands it; any other non-literal `import()` (W1608) reaches nothing, and E1007 holds at build. E1015 is a relative specifier in a non-test project code file that resolves to a file outside the project root, at its opening quote as E1013: `keel check` reads only the project's files, so no rule follows it; shared code is a package. Message `'<specifier>' resolves outside the project; check reads only its files`, the specifier cut from its front to fit 89 units (59 without it); no fix.

**E1004's message.** At the import, in the importing file. When a client entry reaches that file: `client code reaches server-only (<chain>)`, the shortest chain of files from the entry to the server-only file the import names (a package specifier when it names no project file), joined by ` -> `. When that passes 89 units, the files between the first and the last become one `...`, then the first loses leading segments, then the last (k.check Diagnostics). The middle is then not reported: the position names the importer, the ends name the entry and the server-only file, and the fix is at the importer. With no such chain (a file of a `node` module, or no `topology.ts`): `client code imports server-only <file>`. Examples: `client code reaches server-only (modules/a/Page.tsx -> lib/fmt.ts -> lib/keys.server.ts)` (88 units); a fourth file between them gives `client code reaches server-only (modules/a/Page.tsx -> ... -> lib/notes.server.ts)` (82).

**Build gate.** `keel build` runs `keel check` first; an error ends it with exit 1 and nothing written, a warning does not. `vite build` alone runs no check; the stubs and E1007 still hold.

**Limits.** A value in a file that is not server-only ships when a browser file imports it: a secret hard-coded in a schema, a `routes.ts` or a shared helper is public. A `routes.ts` a page imports runs in the browser; only its server-only imports are stubbed. Bundles, names and config: k.bundle.

**Rules.** E1007 server code in a browser build (names the chain) · E1008 a stub of a server-only export called · E1009 `guard` from `@keel/router` used (k.bundle) outside a `*.guard.*` or `*.server.*` file (fix: none) · E1016 a type reference, or an `import.meta` declaration not Keel's, Node's or TypeScript's (Ambient types; fix deletes a reference) · E1015 a relative specifier resolving outside the project (Following; fix: none).

**Conformance.**
- In a `node` fixture, canaries in a `*.server.ts` loader, an action, a `*.guard.ts` guard, a module two imports past the loader and a `*.server.ts` top-level statement are in no file under `dist/<name>/assets/`; the resumed page's `Link` and `Form` carry a contract's `href` with typed params, and a post runs the action.
- A `client` deployable it hosts ships its own `*.server.ts` loader and none of those canaries; a `static` fixture's browser build ships none of its own.
- A page importing `./x.server.ts?raw` or `?url`, a plain file calling `loader`, or one importing `node:path` fails `vite build` with one E1007 naming the chain; `keel build` stops at `keel check`.
- Each export of a stubbed file is a function throwing E1008 that names it; `manifest` takes stubs.
- No environment value set for a build (`KEEL_SECRET`, `VITE_*`, others but those origins) is in a file under `dist/`.
- A route component reaching `lib/keys.server.ts` through `lib/fmt.ts` is one E1004 at `lib/fmt.ts` naming the chain, and a literal-origin `ctx.net.fetch` in `lib/fmt.ts` is E1571; none for a type-only import, a schema both sides import, a `routes.ts` value import, or a file only server-only files import.
- In a `client` module `process.env.X` in `load.server.ts` is E1759; in a `node` module's `a.guard.ts` it is not; `guard(...)` in `modules/a/auth.ts` is E1009.
- For generated import graphs, E1004 is reported exactly when a route component reaches a server-only file by value imports through no server-only file or `routes.ts`.
- `/// <reference types="vite/client" />`, `/// <reference path="./g.d.ts" />` and `/// <reference lib="dom" />`, each as the first line of `modules/a/Page.tsx`, and the first as the first line of `modules/a/a.test.ts`, are each one E1016 at line 1, col 1, whose fix deletes that line; `/// <reference lib="es2023.intl" />` in a file under `packages/` is none.
- `import 'vite/client'` as the only import of `modules/a/Page.tsx` is one E1016 at that import whose message starts `vite/` and contains `declares import.meta types`; a file `modules/a/env.d.ts` holding `export {}` and `declare global { interface ImportMetaEnv { VITE_X: string } }` is one E1016 at `interface`; a project with neither, whose test file imports `vitest` and `@keel/testing`, reports no E1016.
- `import { x } from '../../../shared/x.ts'` in `modules/a/Page.tsx`, resolving to a file outside the project root, is one E1015 at the specifier's opening quote with no fix; the same import in `modules/a/a.test.ts`, and `import { y } from '../b/y.ts'` resolving inside the project, are none.
- In a `node` fixture whose `package.json` is `{"name":"p","type":"module","exports":{"./*":"./*"}}`, a route component importing `p/lib/fmt.ts`, where `lib/fmt.ts` imports `./keys.server.ts`, is one E1004 at that import in `lib/fmt.ts`; a route component calling `` import(`../../lib/p/${n}.ts`) ``, where `lib/p/x.ts` imports `../keys.server.ts`, is one E1004 at that import in `lib/p/x.ts`; with `import(name)` in its place, `name` a parameter, no E1004 is reported in `lib/p/x.ts`.

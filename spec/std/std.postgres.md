# std.postgres: Postgres app data
status: implemented
**Extension points.** Capability registry (k.ctx, k.data): `database(name, ...)` registers a capability per call; `follow` is the std.channels follow seam. Check rule registry: `/tools` (E2451, E2452, E2458, E2459, E2460, W2456). A module using it lists it in `deps`, the database's name in `capabilities`.

**API.** `@keel/std-postgres` is client-safe; `/server`, `/testing` Node only.
```ts
import { database } from '@keel/std-postgres/server'   // modules/kitchen/kitchenDb.server.ts
export const kitchenDb = database('kitchen.db')            // tables: modules/kitchen/migrations/*.sql
import { NoRows, fragment, sql } from '@keel/std-postgres'
const r = await kitchenDb(ctx).query(sql(Recipe)`select ... where id = ${id}`)   // in a loader's fn: Result<Recipe[], E>
```
- `sql(schema)` tags a template into a `Query<T>` `{ text, params }`. Each `${value}` is a parameter, never text, numbered `$1`, ... in template order; a `fragment` value is spliced, its own parameters numbered in place; nothing else is spliced. A parameter is a JSON value: a string, finite number, boolean, `null`, an array of these (a Postgres array) or a plain object (as JSON); anything else, a `Secret` too, throws E2457 naming its `$N`.
- `query(q)`: every row, parsed by `q`'s schema. `one(q)`: the one row; none is `keel.notFound`, more than one throws. `run(q)`: the count of rows changed; `q` is `sql(NoRows)`, which refuses any row. `transaction(fn, { allow?, reason? })`: `fn(tx)`, `tx` with `query`, `one` and `run`, in one `serializable` transaction: committed ones act in some serial order: no lost update, no write skew. `ok` commits, `err` or a throw rolls back. A serialization failure or deadlock runs `fn` again, at most 3 runs, then is `keel.conflict`, nothing committed; what `fn` does outside `tx` must be safe to repeat.
- `changed`, `follow`: std.postgres-changes.
- `allow`, with `reason` a non-empty string literal (E2459), gives some up: `'write skew'` runs at `repeatable read` (one snapshot; writing a row since changed fails), `'lost updates'` at `read committed` (a value read and written back can overwrite another write). Another value, or no `reason`, throws. A lone `query`, `one` or `run` is its own `serializable` transaction, rerun as `fn` is; a write using another call's read goes in one `transaction` with it.
- Errors: a row failing its schema is `postgres.result`, data `{ row, issues }` (its index; paths, rules); a unique, foreign key, check or not-null violation is `postgres.constraint`, data `{ kind }`, `kind` `unique`, `foreign`, `check` or `notNull`, and `constraintOf(e, names)` (`/server`) the member of the app's list `names` naming the constraint broken (a not-null violation's column) or `undefined`: a name is never data; a refused or lost connection is `keel.unreachable`; a serialization failure or deadlock past its third run is `keel.conflict`. A database error of a class a caller can act on is `postgres.database` (`DatabaseError` of `@keel/std-postgres`, so `DatabaseError.in(e)` finds it), data `{ sqlstate }` and nothing of the error's text; any other is the defect E2461 (std.postgres-errors). No error, log line or diagnostic holds a parameter or row value.
- Values arrive as JSON: `bool` as a boolean; `int2`, `int4`, `int8`, `float4`, `float8` as numbers (an `int8` past 2^53 - 1 as its text); `json` and `jsonb` parsed; arrays as arrays; every other type as Postgres's text form (`date` `2026-11-21`). An instant is an `int8` of `ctx.clock.now()` milliseconds.

**Migrations.** `database(name, { migrations? })`. A database's migrations are the files `modules/<moduleId>/migrations/*.sql` of the app folder (k.data Files), read synchronously at its first call (`query`, `one`, `run`, `transaction`); no folder is none. `migrations`, given, maps `./migrations/NNNN-<kebab>.sql` to its text and is read instead. Names are `NNNN-<kebab>.sql` from 0001 without a gap; another name or a gap throws E2453, when `database` runs for a given map, at the first call for files. The first call of a database on a ctx applies its pending migrations in order, each in its own transaction with its row in `keel_migrations (capability, id, name, digest)`, under an advisory lock per capability: once across processes. A `keel_migrations` row of the capability whose file is gone or whose SHA-256 differs from its `digest` is E2454. A failed pass keeps nothing: a refused or lost connection, opening the store or in it, is that call's `keel.unreachable`; any other failure (a migration's SQL, E2453, E2454) rejects that call; the next call, on any ctx, runs it again.

**Modes.** `KEEL_POSTGRES_URL` picks the store, read at the first query: `postgres:` or `postgresql:` uses `pg`, a pool of at most 10 per URL per process and one listening connection per URL, its `application_name` `keel-listen-<pid>`, opened at the first `follow` outside the pool and closed when the last follow stops (a lost one is `lost` to every follow on it, and the next `follow` opens it again), TLS per `sslmode`, idle ones letting the process exit; `pglite:<folder>` uses PGlite on disk, one process, delivering to its follows. Missing, it is `pglite:<KEEL_DEV_DIR>/postgres` when `KEEL_DEV_DIR` is set (`keel dev`, k.data Files); else, or another scheme, E2455, naming no part of the value. Under sim each database is PGlite in memory, migrated, one per sim ctx and capability, `setseed` from the capability seed; after `await ready()` (`/testing`, in the app's vitest `setupFiles`) sim queries settle without a timer. The plan (k.sim) is `{ delay, fault }[]`, `delay` integer 0 to 60,000 sim ms, `fault` `none`, `unavailable` (`keel.unreachable`, runs nothing) or `conflict` (a serialization failure, committing nothing); each run of a lone statement or of `fn` takes one step, statements on `tx` none; past its end, `none`. Under sim, delivery of a change happens when the committing step settles, in step order, with no timer. Under sim the engine's boot and each call into PGlite (a statement, `begin`, `commit`, `rollback`, a migration) are held (k.drive) from the call until PGlite answers, labelled `<capability> boot` and `<capability> query`; a plan step's `delay`, the wait for the database to be free and `fn`'s own awaits are not: each waits on held or parked work. Sim runs each transaction whole in step order, which `serializable` allows; what `allow` permits never happens under sim. PGlite has no statement timer: a `statement_timeout` left in force there is refused (std.postgres-errors).

**Rules.** E2451 `@keel/std-postgres/server` imported (static or `import()`) outside a `*.server.ts` file, tests and type-only imports aside · E2452 that import in a module a deployable other than `node` serves · E2453, E2454, E2455 above · W2456 `now()`, `current_timestamp`, `clock_timestamp()`, `random()` or `gen_random_uuid()` in a template's text or a migration, not replayed under sim (pass `ctx.clock.now()` or `ctx.random.id(brand)`) · E2457 a parameter that is not a JSON value; E2453 to E2455 and E2457 throw · E2461 a database error no error above takes, a defect (std.postgres-errors) · E2458 a `database` name that is not a literal `<moduleId>.<name>` of its module (E1607) · E2459 `allow` in a `.transaction(` options object without a `reason` that is a non-empty string literal · E2460 a bad `changed` (std.postgres-changes). R2451 (k.escapes) each `allow`.

**Conformance.**
- `` sql(S)`select ${"x'; drop table t"}` `` has `text` `select $1` and `params` `["x'; drop table t"]`; `` sql(S)`a ${1} ${fragment`b ${2}`} ${3}` `` has `text` `a $1 b $2 $3`.
- `query` parses every row with the schema; a row failing it is `postgres.result`, holding no value; `one` of no row is `keel.notFound`; `run` of a statement returning a row is `postgres.result`.
- An insert breaking unique index `t_name_key` is `postgres.constraint` with data `{ kind: 'unique' }`, `constraintOf(e, ['x', 't_name_key'])` is `'t_name_key'`, and `constraintOf` of `e` given `['x']`, or of `{ ...e }`, is `undefined`; a `Secret` or `undefined` parameter throws E2457.
- Under sim, a plan `conflict`, `conflict`, `none` makes a `transaction` run `fn` three times and commit once; `conflict` three times is `keel.conflict`, nothing committed; `fn`'s `err` commits nothing.
- Two processes on one `postgres:` URL apply each pending migration once; a changed applied file is E2454; `0001`, `0003` is E2453.
- Under sim, two ctxs of one seed give equal answers to the same calls; one ctx sees none of another's rows; a plan step `unavailable` is `keel.unreachable` and writes nothing.
- On PGlite and on Postgres 17 in CI, `int8`, `jsonb`, `date` and `text[]` columns arrive as the API says.
- E2451, E2452, E2458 and W2456 each fire on a fixture, not on its clean twin; a missing `KEEL_POSTGRES_URL` is E2455.
- With no `migrations`, in a working directory holding `modules/notes/migrations/0001-notes.sql`, `database('notes.db')`'s first sim `query` reads the table it makes; with `KEEL_APP_DIR` naming another folder, that folder's file is read; a lone `0002-x.sql` rejects the first call with E2453; no folder makes no table and no error.
- With `KEEL_POSTGRES_URL` a `postgres:` URL whose port refuses connections, the first `query` is `err` `keel.unreachable`, and an API loader returning it answers 502.
- On a `pglite:` folder, a migration referencing a table that does not exist rejects the first `query` with its error; once another database on that folder makes the table, the next `query` on the same ctx applies the migration and answers.
- With `KEEL_POSTGRES_URL` unset and `KEEL_DEV_DIR` a folder `d`, a `query` answers from PGlite in `d/postgres`, which exists after it.
- Under sim, on PGlite and on Postgres 17, `` sql(S)`show transaction_isolation` `` answers `serializable` in a `transaction` and alone, `repeatable read` with `allow: 'write skew'`, `read committed` with `allow: 'lost updates'`.
- On Postgres 17, each pair waiting until both have read: two `transaction`s writing a counter's value read + 1 are each `ok` or `keel.conflict`, a `fn` runs twice, and the counter equals the `ok` count; two that each take their own doctor off call when two are on call leave one on call, or none with `allow: 'write skew'`.
- Under sim, a plan `conflict`, `none` runs a lone `run` twice, changing its row once; `conflict` three times is `keel.conflict`, nothing changed.
- `allow: 'phantoms'`, or no `reason`, throws; E2459 fires on `{ allow: 'write skew' }` and on a variable `reason`, not on `reason: 'audit rows only'`.
- Under sim, two callers started together on one ctx, each a lone `one` of a counter then a lone `run` of the value read + 1 held 10 sim ms by the plan, end it at 1; each in a `transaction`, at 2.
- Under `simulate` with `replay` of a `SimRun` of seed 1 whose plan for the database is `[{ delay: 500, fault: 'none' }]`, a scenario that awaits a lone `query` and calls no `run` gets its answer with `ctx.clock.now()` 500; with that plan empty, a `transaction` whose `fn` runs a `tx` statement, awaits `ctx.clock.after(100)` and runs another commits both, answering with `ctx.clock.now()` 100.
- In an empty replay (k.drive), a first `query` on a database no earlier run used, started beside a `ctx.clock.after(1)` waiter, answers with `ctx.clock.now()` 0 and the waiter not resolved.
- In an empty replay (k.drive), a scenario that runs two `insert` statements through `query`, each committing, then awaits `ctx.clock.after(10)`, resolves `simulate` with `ctx.clock.now()` 10, less than 5,000 ms of real time after the first `insert` answers.
- On Postgres 17 and on a `pglite:` folder, `run` of `insert into t (v) values ('xyz')`, `t.v` a `varchar(2)` column, is `err` `postgres.database` with data `{ sqlstate: '22001' }` and `query` of `select 'a'::int` with `{ sqlstate: '22P02' }`; on Postgres 17, inside a `transaction` after `set local statement_timeout = 1`, `select pg_sleep(1)` is `err` `postgres.database` `{ sqlstate: '57014' }`; on a `pglite:` folder that `set local` is the E2461 defect with `data.sqlstate` `0A000`; `select raise_it()`, a function doing `raise exception 'x'`, is `{ sqlstate: 'P0001' }`; no `data` holds more keys than `sqlstate`.
- `query` of `select * from no_such_table` rejects with a value `isDefect(v, 'E2461')` accepts whose `data` is `{ sqlstate: '42P01' }`.

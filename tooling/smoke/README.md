# Browser smoke

`node tooling/smoke/smoke.mjs <png>` loads http://localhost:4180 (or SMOKE_URL)/ (run `pnpm --filter golden-1 build && pnpm --filter golden-1 exec vite preview --port 4173` first) in headless Chromium and prints text, element ids, and console errors. `interact.mjs` adds a list and follows its link. Needs `pnpm exec playwright install chromium` once.

`inspector.mjs [png]`: serve golden-1 with `keel dev --port 4180` from `apps/golden-1` (the dev entry reports live graph and stores to the `/__keel/inspect` that `keel dev` serves; or set SMOKE_TARGET); build and serve `apps/inspector` with `vite preview --port 4182` (SMOKE_INSPECTOR). It adds a list in golden-1, opens the inspector at `?url=<target>`, and prints the graph, stores, and ids views.

`persist.mjs [png]`: golden-1 data lives behind the api. Run `pnpm dev > dev.log` from `apps/golden-1` (`keel dev` serves the web app and both api modules on one origin) and set `SMOKE_URL` to the address it serves (default http://localhost:4182/), `SMOKE_API_LOG=dev.log`. It creates a list, reloads, opens it, adds a todo, reloads, toggles, undoes, reloads, then prints the POST `req` lines of the log and a trailer. To smoke the built entry instead, run `pnpm --filter ./apps/golden-1 build`, then `KEEL_SECRET=<32+ bytes> PORT=<port> pnpm --filter ./apps/golden-1 api > api.log` and point `SMOKE_URL` at that port.

# Shell replay

`shell.mjs --shell tauri [--session replay|outbox] [--drop-store] [--binary <path>]`: a recorded session replayed inside golden-1's Tauri shell gives the server state its sim replay gives. On Linux, after `KEEL_ORIGIN=http://localhost:4182 CARGO_TARGET_DIR=.cargo-target pnpm exec keel build --target tauri` in `apps/golden-1`, with `webkit2gtk-driver` from apt and `cargo install tauri-driver --locked`, run `xvfb-run -a node tooling/smoke/shell.mjs --shell tauri` from the repository root. It records a one-user session group under simulation (`apps/golden-1/test/shellSession.ts`) and replays it with `replayGroup`, writes the group to `.keel/sessions/golden-1-shell.group.json` in a temporary folder, serves the built `api` on a free port over a SQLite file holding the group's starting board, with a recording proxy at `KEEL_ORIGIN`, and drives the binary through `tauri-driver` (WebDriver over HTTP, `webdriver.mjs`): each input of the group file becomes a click, a followed link or a cleared and typed field by element id (`actionsOf` in `shellReplay.mjs`). Then the stored `api.board` and `replayGroup`'s, `normalized` (log times left out; minted ids, write keys and callers numbered by first appearance), must be equal. One `ok` line on success; E0014 when the shell cannot be started or driven, E0015 with one line per difference (`boardDiff`). The binary defaults to `.cargo-target/debug/golden-1`, else `apps/golden-1/dist/web/tauri/target/debug/golden-1`; `TAURI_DRIVER` names the driver when it is not on `PATH` or in `~/.cargo/bin`. `--session outbox` records `apps/golden-1/test/shellOutboxSession.ts` instead (open Home, go offline, mark Bread done, add Butter, come back online): going offline stops the api and closes the proxy, so `KEEL_ORIGIN` refuses connections, and the two writes wait in the `todos.outbox` outbox; coming back online waits until the app's store files (`keel.json`, `keel.b.json`) hold them, kills the app with SIGKILL, starts the api and the proxy again and starts the app in a new WebDriver session, where the outbox drains. The board must then equal `replayGroup`'s and the stored outbox be empty. `--drop-store` deletes the store files before that start, a planted failure the comparison reports as E0015. macOS has no WebDriver for its webview, so the replay runs on Linux only.

# Built crash proofs

`restart.mjs` and `workflow.mjs` build a copy of golden-1 in a temporary folder, serve its `api` on a SQLite file there and SIGKILL it. `restart.mjs` writes a list, two todos, a toggle and an edit, then restarts on the same file: the stored board row is byte-equal, GET answers the same board and the next write's log entry is one higher. `workflow.mjs` plants a two-second wait in the removal workflow's `restore` step, removes and undoes a list, kills the server inside the step and restarts it: the instance ends `kept`, the step ran twice and `api.removal.restored` is logged once. Both are SQLite only, take about 15 and 20 seconds, and run in the `built-smokes` job of pull-request CI.

# Served page resume

`resume.mjs [runs]` builds a copy of golden-2 whose `web` deployable is a `node` server holding the `recipes` module (its `topology.ts` rewritten in the copy), serves golden-2's real `api` deployable on a web storage file and `web` on free ports, each naming the other as its peer, seeds two recipes through `POST /api/recipes` and loads five pages in headless Chromium `runs` times: from `web` the recipe index (the `recipes.shell` layout around an `If` and a `For` of recipe rows), a recipe's show page (the `recipes.show` island), the new-recipe page and the catalog, and from `api` the sign-in page. Each page's scripts are held until the test has typed into an input and set its caret (new-recipe: the title; sign-in: the email) or scrolled the page down 200 px (index, show, catalog; the viewport is 1000 by 500, and Chrome scrolls a page with a focused input back to the top after load whatever its scripts do). After resume it checks on each page that every served island is still marked, that no element was removed after the parser finished and none was added under an island root, that every served element is still in the document (on the index, each recipe row is the very element the server sent), that the focused input, its value and its caret, or the scroll position, are kept, and that no console warning or error was logged; then one interaction: the index's first recipe link opens that recipe, the show page's Toggle favorite shows the new state and the api stores it, clearing the title and leaving it shows the title's error, the catalog's filters disclosure opens, and a bad email shows the email's error. It runs three times in the `built-smokes` CI job.

# Dev sign-in

`dev-signin.mjs` starts `keel dev --port <free port>` with `AUTH_FIXTURE=dev` (as golden-2's `dev` script does) in a copy of golden-2 in a temporary folder, so its `.keel-dev/` state is not shared with a dev server running in the app, and checks over HTTP, with no browser: `/` and `/catalog` answer the shell that loads `/@keel/entry.ts`, the `api` deployable serves `/account/signin`, and `GET /api/me` answers 403 without a session. A form-encoded sign-up and sign-in post to the identity mount (`/api/auth/sign-up/email`, `/api/auth/sign-in/email`) must each answer 303 to `/account/signin`, the sign-in with a `better-auth.session_token` cookie and a wrong password without one; with the cookie, the sign-in page names the account and `GET /api/me` answers its email. Last, the browser's module request for each `*.server.ts` file that `modules/accounts/routes.ts` imports, and for `authOf.server.ts` (which imports `node:sqlite`), must answer the stub (`serverOnly(...)`) with no `node:` import. The child runs in its own process group, which every path kills, including the 90 s time limit. It takes about two seconds and runs in the `built-smokes` CI job.

# Built apps in a browser

The browser and built-server proofs of the apps and examples are end-to-end tests in the projects they test (`test/*.e2e.ts`, k.e2e), run by `keel test --e2e` in each: golden-1 (persistence, restart, the removal workflow on SQLite and Postgres, monitor, the document policies), golden-2 (resume in place, `keel dev` sign-in, the personal-data canaries), household and the examples. CI's `built-smokes` job runs them. Three scripts stay here: the shell smokes below, `monitor.mjs` and `inspector.mjs`.

`monitor.mjs` serves a built golden-1 and drives two browsers through an offline conflict, then waits for the production tally of `sessions.tally`, a storage key that no store holds, and reads it with `keel session monitor`; `golden-1/test/monitor.e2e.ts` checks the browsers' part. Shared helpers: `built.mjs`.

# Shell replay

`shell.mjs --shell tauri [--session replay|outbox] [--drop-store] [--binary <path>]`: a recorded session replayed inside golden-1's Tauri shell gives the server state its sim replay gives. On Linux, after `KEEL_ORIGIN=http://localhost:4182 CARGO_TARGET_DIR=.cargo-target pnpm exec keel build --target tauri` in `apps/golden-1`, with `webkit2gtk-driver` from apt and `cargo install tauri-driver --locked`, run `xvfb-run -a node tooling/smoke/shell.mjs --shell tauri` from the repository root. It records a one-user session group under simulation (`apps/golden-1/test/shellSession.ts`) and replays it with `replayGroup`, writes the group to `.keel/sessions/golden-1-shell.group.json` in a temporary folder, serves the built `api` on a free port over a SQLite file holding the group's starting board, with a recording proxy at `KEEL_ORIGIN`, and drives the binary through `tauri-driver` (WebDriver over HTTP, `webdriver.mjs`): each input of the group file becomes a click, a followed link or a cleared and typed field by element id (`actionsOf` in `shellReplay.mjs`). Then the stored `api.board` and `replayGroup`'s, `normalized` (log times left out; minted ids, write keys and callers numbered by first appearance), must be equal. One `ok` line on success; E0014 when the shell cannot be started or driven, E0015 with one line per difference (`boardDiff`). The binary defaults to `.cargo-target/debug/golden-1`, else `apps/golden-1/dist/web/tauri/target/debug/golden-1`; `TAURI_DRIVER` names the driver when it is not on `PATH` or in `~/.cargo/bin`. `--session outbox` records `apps/golden-1/test/shellOutboxSession.ts` instead (open Home, go offline, mark Bread done, add Butter, come back online): going offline stops the api and closes the proxy, so `KEEL_ORIGIN` refuses connections, and the two writes wait in the `todos.outbox` outbox; coming back online waits until the app's store files (`keel.json`, `keel.b.json`) hold them, kills the app with SIGKILL, starts the api and the proxy again and starts the app in a new WebDriver session, where the outbox drains. The board must then equal `replayGroup`'s and the stored outbox be empty. `--drop-store` deletes the store files before that start, a planted failure the comparison reports as E0015. macOS has no WebDriver for its webview, so this script runs on Linux only; `shell-drive.mjs` replays the same sessions on macOS and iOS.

# Shell launch

`shell-launch.mjs --shell tauri [--binary <path>]` and `shell-launch.mjs --shell ios [--app <path>] [--device <udid or name>] [--reboot]`, each with `[--hold <s>] [--drop-data]`: the launch and cookie check for golden-1's shells on macOS, where the webview (WKWebView) has no WebDriver. It makes no input in the page, so it checks no write, outbox or replay; `shell-drive.mjs` does. On macOS, after `KEEL_ORIGIN=http://localhost:4182 CARGO_TARGET_DIR=.cargo-target pnpm exec keel build --target tauri` or `KEEL_ORIGIN=http://localhost:4182 pnpm exec keel build --target capacitor --platform ios` in `apps/golden-1`, run it from the repository root. It serves the built `api` on a free port over a fresh SQLite file, with a recording proxy at `KEEL_ORIGIN` that adds the cookie `keel-smoke=<random>; Max-Age=86400` to each answer to a request without it. `--shell tauri` starts the binary with `HOME` in a temporary folder, so its store and cookie files stay there (WebKit's own cache under `~/Library/Caches/golden-1` does not follow `HOME`). `--shell ios` uses `--device`, else the booted iPhone simulator, else boots the first iPhone of the newest iOS runtime; it installs the app fresh and starts it with `xcrun simctl launch`; the Simulator shares the host's network, so `localhost` needs no forwarding. Each launch must make `GET /api/lists` and then `GET /api/board/events` through the native client (agent `tauri-plugin-http/…` or `… CFNetwork/…`), and the first launch a later request carrying the cookie. The app is then killed (SIGKILL; on iOS `simctl terminate`; `--hold` seconds after the cookie was first sent, 0 by default) and started again, and every request up to the event stream must carry the cookie. `--reboot` (iOS) follows with a simulator shutdown, a boot and a third launch under the same rule. On iOS the cookie is on disk before the page hears of the response that set it (`KeelHttp` flushes the session's cookie store), so the force-stop waits for nothing. `--drop-data` removes the app's data before the second launch (the temporary `HOME`, or an uninstall and install), a planted failure reported as E0015. One `ok` line on success; E0014 when the app cannot be started or makes no request, E0015 per request that came without the cookie after a relaunch, with the proxy's requests on stderr. Each run starts the app two times (three with `--reboot`), one at a time, with no retry. On every path it stops the app, the proxy and the api, uninstalls the app and shuts down a simulator it booted. About 2 s for Tauri, 60 s for iOS with `--reboot`; the `shell-tauri-macos` and `shell-ios` CI jobs run it while the repository is public.

# Shell drive

`shell-drive.mjs --shell tauri [--binary <path>]` and `shell-drive.mjs --shell ios [--app <path>] [--device <udid or name>]`, each with `[--session replay|outbox] [--drop-store]`: the shell replay for golden-1's shells on macOS, where the webview (WKWebView) has no WebDriver. It records the same sessions as `shell.mjs`, serves the same way (the built `api` over a SQLite file holding the group's starting board, a recording proxy at `KEEL_ORIGIN`), makes each input of the group file in the page through the accessibility tree, and compares the same way: the stored `api.board` and `replayGroup`'s, `normalized`, must be equal, and after `--session outbox` the shell's stored outbox must be empty. Run it from the repository root on macOS, after the build `shell-launch.mjs` needs.

`--shell tauri` compiles `shell-drive/ax.swift` with `swiftc` into a temporary folder and starts the binary with `HOME` there. `ax <pid> <command>` makes one input through the accessibility API (`AXUIElement`): it finds an element by its DOM id, which WebKit gives as `AXDOMIdentifier`, and a link by the path of its `AXURL`; a click is `AXPress`, typed text is the field's `AXValue` set (the page hears an `input` event), and the route is the page's `AXURL`. The process that runs the script needs the Accessibility permission (System Settings, Privacy & Security, Accessibility, for the terminal); `ax <pid> trusted` reads it and never asks, and without it the script ends in E0014. GitHub's macOS runner images grant it to `/bin/bash`, which runs a workflow step.

`--shell ios` uses `--device`, else the booted iPhone simulator, else boots the first iPhone of the newest iOS runtime, installs the app fresh, builds the UI test `shell-drive/ShellDrive.xcodeproj` with `xcodebuild build-for-testing` into a temporary folder and runs it with `test-without-building`. The project holds one UI test target and no app: the test starts the installed app by its bundle id (`XCUIApplication(bundleIdentifier:)`), so nothing is added to the generated Capacitor project. The test asks the script for one command at a time (`POST /next` on a loopback port, given as `TEST_RUNNER_KEEL_DRIVE_URL`) and answers each: `launch`, `click` (a tap; a checkbox is tapped on its box) and `type` (the field tapped at its end, its content deleted, the value typed, the keyboard put away with Done). WebKit on iOS gives the accessibility tree an element's role and label and not its DOM id, so the script names each id by role and label under the `main` landmark (`labelled` and `linkTo` in `shellReplay.mjs`): `todos.toggle.t1` is the checkbox labelled `Done: Milk`, the link to `/lists/l1` the link labelled `Home`. The names and titles are the starting board's, so a session renames a todo only after its last input on that todo's old label.

`--session outbox`: going offline stops the api and closes the proxy. Coming back online waits until the shell's store holds the queued writes, every write of the sim replay the server has not stored: `keel.json` and `keel.b.json` under `HOME`, or on iOS the `keel` entry of `Library/Preferences/dev.keel.golden1.plist` in the app's data container, which the simulator writes up to about 15 s after the app's write resolves. Then it kills the app (SIGKILL; on iOS `simctl terminate`), starts the api and the proxy again and starts the app, where the outbox drains. `--drop-store` deletes the store before that start (the store files; on iOS an uninstall and install), a planted failure the comparison reports as E0015. One `ok` line on success (`ok shell-drive 6 actions, 2 queued, 1 killed, 1 restarts, 4 head`); E0014 when the shell cannot be started or driven, E0015 with one line per difference. The app window, or the simulator, is on screen while it runs: one app at a time, with no retry. On every path it stops the app, the driver, the proxy and the api, uninstalls the app and shuts down a simulator it booted. About 10 s and 12 s for Tauri, 55 s and 60 s for iOS; the `shell-tauri-macos` and `shell-ios` CI jobs run both sessions while the repository is public.

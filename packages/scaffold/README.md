# @keel/scaffold

**Spec:** k.scaffold, k.scaffold-service · **Status:** conformance-covered · **verified:** (none)

## Contract

- **Public API:** `scaffold(op, input, files)` -> `Result<Edit, ScaffoldError>`; pure, so it is also the dry run. `files: ReadonlyMap<path, content>`; `Edit = { files, created, changed, removed }` (sorted paths). `Op`: `project {name, adapter?, workspace?}` · `module {id}` · `route {id, path, file?, api?, method?, 'no-loader'?}` (`no-loader`: no loader file, a binding of `component` alone) · `component {id: "mod/Name", ctx?}` · `store {id: "mod.name"}` · `transaction {id: "mod.store.name"}` (store must exist) · `service {id: "mod", name?, base?, schema?, service?, reason?}` (`name`, lowerCamel else E1352, defaults to the module id and names the declaration `<Name>Api` in `<Name>Api.schema.ts`; the client stays `api` in `api.server.ts`, so a module holds one scaffolded service and a second is E1351 naming `api.server.ts`; `base` alone writes an empty `<Name>Api.schema.ts` and its client `api.server.ts`; `schema` and `service` together place the `@keel/services/openapi` sources there, which the cli converts from `--openapi`; in a module on a `client` deployable the URL's origin joins that deployable's `origins.connect` with `reason`, E1358 without one) · `library {name, version?, exists?}` (k.library-pack Scaffold: `<base>/` of `@<scope>/<base>` holding `package.json`, `module.ts`, `src/index.ts`, `src/Example.tsx`, `test/Example.test.ts`, `tokens.ts`, both tsconfigs, `vitest.config.ts` and `README.md`; the `@keel/*` entries at `^<version>`, the running cli's; a name of another form E1352, `<base>/` in the tree or `exists` E1351) · `shell {shell: tauri|capacitor, id, name?, to?}` (the `client` deployable `to`, default the one there is, gains `shells: { <shell>: { id, name } }`, `name` defaulting to the title-cased `package.json` `name`; `package.json` gains `@keel/std-<shell>` at `@keel/server`'s version text and the shell's app packages at the versions the std package declares, carried in the generated `SHELL_PACKAGES.ts`; two files change and nothing refreshes; E1353 naming E1573 for an `id` that is not reverse-DNS, E1359 with no one `client` deployable, E1351 when it declares that shell) · `rename {kind: component|store|route|schema|module, from, to}` · `move {name, to}` · `place {module, to, adapter?}` · `add-field {schema, field, type, default?}`. `deployFiles(topology, { ci, version?, pkg?, policy?, identity?, shells? })` -> path -> text: `deploy/<name>/Dockerfile` per `node` deployable, `deploy/compose.yaml` when there is one, the shell files of each `client` deployable's `shells` (its target's `files(app)` under `deploy/<name>/<shell>/`), `.github/workflows/ci.yml` when `ci` (k.deploy Deploy files, k.shell Files). `deployDrift(files, always?, policy?, shells?)` -> `{ path, want, have }[]`: the generated deploy files of a tree that differ from `deployFiles` of its `topology.ts` (version and package name from its `package.json`); `keel check` reports them (E1005), `keel build` and `tooling/generate.mjs` write them. `tauri.conf.json` is checked and written only with `policy`, which gives a `client` document's content security policy for a deployable's declared origins (k.origins). `shells` is `DeployShells`, the shell targets registered through `shellTarget` (`@keel/cli`); `scaffold(op, input, files, shells?)` takes it too. The three functions stay pure: they read no target themselves. Types `DeployShells`, `ShellApp` and `ShellJob` are exported.
- **Agent files (`@keel/scaffold/agents`):** `agentFiles(files, skills)` -> `Result<{ path, want, have }[], ScaffoldError>`: the agent files of a tree that differ from what `keel docs --sync` writes, sorted by path: `AGENTS.md` with the Keel block (`AGENTS_START` to `AGENTS_END`: the reading path, the commands, the rules, each skill's `.claude/skills/<name>/SKILL.md`) replaced in place or appended after the user's text, `CLAUDE.md` holding `@AGENTS.md` only when absent, and each skill's copy. A CRLF `AGENTS.md` gets the block in CRLF. Markers other than one start line before one end line are E1355. `AgentSkill = { name, description, text }`.
- **Invariants:** pure; never mutates `files`; byte-identical output for equal input. All or nothing: a refusal is `KeelError<'scaffold.rejected', diag>`: E1351 duplicate, E1352 naming, E1353 would break check, E1354 required field without default, E1005 generated location or a change to a file whose first line is a generated marker (`// _generated`, `// Generated`, `# _generated`; a relocation with equal bytes is allowed), E1052 bad input or target, E1051 unknown op. E1353 proxy: new TS2307 (unresolved relative import), E1151, E1152, E1153, E1165 (a `deps` entry no non-test file uses; `move` removes the entries it leaves unused). Codemods are AST-aware (oxc, magic-string): data keys never change (shorthand expands to `key: new`); strings change only as whole segments of an id shape (dotted id, element id). `project`, `module`, `rename module` and `place` write `turbo.json` (module set changes only), the CI workflow and the deploy files; deploy files are kept in a tree with `turbo.json` or a `deploy/` file, the CI workflow in a tree that has one. `place` inserts modules and new deployables in sorted position and removes a deployable it empties, so placing a module back restores a sorted `topology.ts` byte for byte; a new deployable needs `adapter` (E1052), an existing one keeps its own (a different `adapter` is E1052), a module in no deployable is E1052, a deployable name that is not lowerCamel E1352.
- **Dependencies:** `@keel/schema`, `oxc-parser`, `magic-string`.
- **Rungs:** conformance; properties: rename round trip per kind, bare string prefixes survive, determinism, edit set = tree difference, check proxy, import-path helpers, deploy files independent of topology order, drift names exactly a changed file, `place` sequences undone in reverse restore the tree.

## Emitted shape

Code is biome-clean for the repo config, and every generated tree passes the real `keel check` and `keel test` (conformance runs the binary). `vite.config.ts` sets `test.environment: "happy-dom"`. A module gets `module.ts` (no `public.routes`), `<id>.contract.ts` (`export const <id> = contract("<id>", {})`) and `routes.ts` (`export const routes = manifest(<id>, {})`). A route `<mod>.<leaf>` adds an entry to the contract (`path`, `params` for `:name`) and its binding to `routes.ts` (`component` and `loader`), and writes `load<Leaf>.server.ts` exporting `load<Leaf>` over `loader(<mod>, "<id>", ...)`; `route {api: true}` (`--api`, with `method`, default `GET`, else E1052; the id is `<mod>.<name>`, one segment) writes an API entry (`method`, `path`, `output`), a binding `{ loader }` (a write `{ action }`, the handler `<verb><Leaf>.server.ts` over `action(<mod>, "<id>", ...)`), no page component, and a test that requests the path of `createApp` over a sim ctx (the module must sit on a `node` deployable, E1511), and refuses a path `file` (a bare `file` name sits in the module folder); `id`/`*Id` params are `s.id("<Entity>")`. A component takes `(_props)`, and `(_props, _ctx: Ctx)` with `ctx`. `rename route` follows the contract key, the binding key, handler ids and files, and `href` calls; `rename module` also moves `<id>.contract.ts` and renames its export. Importing a contract needs `deps` only, so `move` and the check proxy never ask for it in `public.exports`. `project` writes no `index.html` (Keel writes every document), and its deployable has `styles: ['@keel/ui/fonts']`; `place` gives a deployable it creates the same `styles`. `project {workspace: true}` targets an app inside the monorepo: `vitest.config.ts`, `workspace:*` deps, only check/test/build scripts, no turbo/CI; tests go under `test/`. `rename module` moves the folder and rewrites ids, topology and manifests. `topology.ts` holds one deployable per line, module lists sorted.

Generated deploy files (each starts with a `_generated` line; read-only): a `node` deployable's Dockerfile is `FROM node:22-slim@sha256:5ec23b7c622b00547753bc6ffd78085dd868a68aeb41c8e0a1418f033e13d96d`, copies `dist/<name>/` only, prepares `/data` for user `node`, declares port 8080 and, per `storage`: `'file'` (default) prepares and declares volume `/data` for user `node` and runs `server.mjs` with `--experimental-webstorage --localstorage-file=/data/storage`; `'sqlite'` keeps the volume and drops the flags; `'postgres'` has no volume. `compose.yaml` holds one service per `node` deployable on host ports from 8080 and a volume per one with a volume, `KEEL_PEER_<NAME>: http://<name>:8080` for each peer, and `KEEL_ORIGIN`/`KEEL_SECRET` from the environment (`${KEEL_SECRET:?}`); `KEEL_DATABASE_URL` is required from the environment for `'postgres'` and passed through when set for `'sqlite'`, never written. Each `env` name a deployable's modules and the libraries they list name (k.server-deps Environment, a library's manifest read at `node_modules/<name>/module.ts` of the tree) follows the deploy keys, sorted, required from the environment (`NAME: ${NAME:?}`), never written. Shell files come from the registered targets: a declared shell's files are its target's `files(app)` under `deploy/<name>/<shell>/`, removed when no deployable declares it (other files there stay), and `tauri.conf.json` only with a `policy`. `Cargo.lock` is never generated or removed. The CI workflow has a `keel-paths` job that marks each deployable whose modules or shared files (`package.json`, `pnpm-lock.yaml`, `topology.ts`, `tokens.ts`, `vite.config.ts`) a pull request changes, and a job per deployable (a host's also runs on the modules of the `client` deployables it hosts) with SHA-pinned actions: install, `keel check --base` the base branch's `.keel/surface.json` (without `--base` when it has none), `keel test`, `keel build`, then `docker build` (never pushed) for `node` or an uploaded `dist/<name>` for `client` and `static`. A `client` deployable's shells add jobs from the target's `ci(app)`, each named `<name>-<job>`, on the deployable's paths with `KEEL_ORIGIN` from the repository variable: checkout, pnpm, Node 22, the job's own steps, install, `keel build --target <shell>` with its platform and environment, then an upload of its artifact. A `manual` job adds `&& github.event_name == 'workflow_dispatch'` to its `if` and `workflow_dispatch: {}` to the triggers.

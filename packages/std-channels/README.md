# @keel/std-channels

**Spec:** std.channels · **Status:** conformance-covered · **verified:** (none)

Named channels between users over a server event stream: a member re-reads after each save of a server store and each committed change of followed app data, and members exchange schema-typed messages.

## Contract

- **Public API:** stdlib module `channels` (`module.ts` at the package root; capabilities `clock`, `net`, `observe`).
  - `channel(name, { path, params, message? })` in a `*.schema.ts` file whose name is the export, so a contract may import it. `params` is parsed from the stream URL's search and picks an instance; `message` is what members publish (absent: nothing can be published). It holds `events`, the `ChannelEvent` schema of its `message`, and `body`, `s.object({ message })` (undefined without `message`), made once, which its contract entries name. It throws E2602 (an Error with `code`) when `message` holds an `s.secret`.
  - The serving contract writes the channel's entries out, as every entry is (k.contract Static reading): at the stream id `{ method: 'GET', path, query: Params, events: true, output: ch.events }`, at the publish id `{ method: 'POST', path, query: Params, body: ch.body, output: s.object({}) }`, `Params` the schema the channel's `params` names, so `keel check` reads it for E1111. A channel without `message` has no publish entry.
  - `subscribe(ctx, origin, channel, params, on)`, inside a scope, returns `{ status, close }`. `status()` reads a signal: `connecting`, `open` (once `reset` arrived), `offline`, `denied`. `publish(ctx, origin, channel, params, message)` resolves `Result<null, ApiError>`. Both go through `@keel/services` on the channel's path.
  - Types `Channel`, `ChannelEntries`, `ChannelEvent`, `ChannelStatus`, `Subscription`.
  - `./server` (node): `channelRoute(contract, channel, { id, publish?, stores?, follows?, member })` in a `*.server.ts` file returns `{ loader, action }` (`{ loader }` without `message`), which the serving module's `manifest` binds by entry: `{ [id]: { loader: r.loader }, [publish]: { action: r.action } }`. `stores` and `follows` are optional, a route having either, both or neither; `follows` lists data capability accessors (k.data) whose object has `follow(channel, key, on)`, such as a std-postgres `database`, and an entry without one is a type error. `publish` is required exactly when the channel has `message`: a type error otherwise, and a `publish` on a channel without `message` throws E1510. Its handlers are declared through `contract`, the serving module's, as `loader` and `action` are; an entry at `id` or `publish` whose `method`, `path`, `events`, `query`, `body` or `output` is not the channel's (by identity; `output` taking `{}`) is a type error where the types differ and throws E1515 naming those members. `ChannelsConfig` is the `std['@keel/std-channels']` schema `{ perCaller?, perAnonymous?, maxStreams? }`, registered under the package name. Types `ChannelRoute`, `Member`.
  - `./tools` (node): E2601 (`channelRoute` outside a `*.server.ts` app file) and E2602 (a `channel` whose `message`, inline or a `const` of the same file, holds `s.secret`). Neither has a fix.
- **Invariants:**
  - Every open goes through the k.server live loader: the caller comes from the caller cookie, which an event-stream GET never sets, and `user` from the identity source (k.user). `member` gets `{ caller, user, params, stores }`: at open the opener's, at a publish the publisher's, after a save the opener's. `member` runs first: false, or a throw, makes `closed` `denied` the only event, so a non-member learns nothing about the caps. Past the serving module's `maxStreams` for the process (default 1,000), or, for a caller with a cookie, its `perCaller` streams (default 8), or, for a cookieless open (caller `""`, which a cookie that does not verify also yields), `perAnonymous` streams of all cookieless opens together (default 64), the only event is `closed` `full`; cookieless opens are never held to `perCaller`. Each bound counts only the streams open on the serving module's own channel routes, so two serving modules never use up each other's. A stream's place is freed once when it ends, however it ends. A route whose `member` refuses `""` holds no cookieless stream.
  - An open stream gets `reset`, then `saved` `{ store, head }` for each `save` the server ctx reports of a store its `stores` instance holds, in report order. Before each one its stores are restored from `ctx.storage` `keel.store.<id>` and `member` runs again; false, or a failed read or restore, ends the stream with `closed` `denied`, and later saves still reach the other streams.
  - A route with `stores` on a storage with `watch` (k.persist Watch: std.db's `postgres`, a sim ctx) is watching before `reset`, with the 5,000 ms bound and the drop on `lost` that `follows` has; a process holds one watch for those streams. A `committed` report makes each stream's route read the named key and deliver `saved` with the stored head, so a save by any process on the same data reaches every replica's streams. A stream's `saved` heads of a store strictly rise (a head not above the last delivered is dropped), and none is promised in between. A `message` reaches only the member streams open in the process that serves its publish, and is never resent: a stream closed, reopening or open on another replica misses it. What every replica's members must see is a save of a store in `stores` or a `changed` the route `follows`; a `message` is for what may reach only some members, such as a typing mark, a cursor or a ping. A `message` served after a save of a store in `stores` in the same process reaches each stream after that save's `saved` or `reset`. On a storage with no `watch` (`'file'`, `'sqlite'`) a save is seen live only by its own process.
  - Before each delivery (`saved`, `changed`, `message`) the stream asks the live loader's `currentUser()` (k.user); an answer less than 1,000 ms old on `ctx.clock` stands for that stream, so a burst costs one `identify` per stream per second. An answer other than the stream's `user`, or a `currentUser()` that fails, gives `closed` `denied` in place of the event. Each stream checks in its own order, apart from the others. With no identity source (or a verified `x-keel-user`) the route sees `currentUser.fixed` at open and takes a delivery path with no check on it: no `identify`, no clock read, no timer.
  - At open, before `reset`, the stream follows each `follows` entry at the canonical JSON (keys sorted) of the channel's encoded params. Each committed change the capability reports is `{ kind: 'changed' }`, after `member` runs again (false: `closed` `denied`); `changed` and `saved` arrive in the order the process got them. A followed change reaches the member streams of every process whose capability shares the database; `saved` and `message` stay in the serving process. An entry not listening within 5,000 ms on `ctx.clock`, a refused follow or a `lost` report ends the stream with no `closed` event, a drop the client reopens after; the stream stops its follows when it ends.
  - A publish is an action: the k.server same-site proof, `maxBodyBytes` and 422 `keel.fields` apply. `member` false is 403 `keel.denied`; else every open stream of the same channel and params in this process gets `message` and the answer is `ok({})` (`publish` on the client resolves `ok(null)`). A stream whose re-check after a save is pending gets the message once that re-check allows it, and none when it ends the stream. Params that fail the channel's schema are the entries' failing `query`: the server answers 422 `keel.fields` to an open or a publish and `member` does not run. A channel without `message` has no publish entry. A message is never stored or logged.
  - Events carry only `kind`, `store`, `head`, `message` and `reason`: no caller, cookie or store state. `changed` names nothing: neither the capability, the params nor a row.
  - A stream holds at most 256 unread events; past that it ends and the client reopens with `reset`.
  - `subscribe` starts its stream after the current tick, so a page or layout may call it while rendering inside an effect: the first `status()` is the signal's initial value (`connecting`, or `offline`), and nothing is written during the render.
  - The client reopens 1 s after a stream ends, doubling to 30 s on `ctx.clock`; a `reset` starts the doubling over. While `ctx.net.online()` is false it sends nothing and aborts an open stream, and it reconnects at once on `{ kind: 'net', online: true }`. After `closed` `denied` it stops. Disposing its scope, or `close()`, aborts the request and `on` gets no later event.
  - Every effect goes through `ctx`: `clock.after`, `net.fetch` (through `@keel/services`), `net.online`, `observe`, `storage.get`.
- **Dependencies:** `@keel/check` and `oxc-parser` (tools only), `@keel/compiler` (`module`, `stdConfig`), `@keel/ctx`, `@keel/reactive`, `@keel/router`, `@keel/schema`, `@keel/server`, `@keel/services`, `@keel/store`.
- **Rungs:** conformance (examples and properties, seed 1337) for reset and saved, changed of followed data and its drop, member at open and after saves and changes, publish scope and proof, no identity in events, `perCaller`, `perAnonymous`, bounds per serving module, subscribe backoff and dispose, and E2601 and E2602; properties for the event schema round trip, the stream caps over any opens and closes on two modules, params instance keys, the inbox bound, the backoff sequence with resets, canonical follow keys, and E2602 under any nesting.

## Extension points

Uses the **module manifest** (k.module: stdlib module `channels` and `std` config `{ perCaller, perAnonymous, maxStreams }`) and the **check rule registry** (k.check: E2601 and E2602 from `./tools`).

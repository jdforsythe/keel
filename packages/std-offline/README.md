# @keel/std-offline

**Spec:** std.offline, std.outbox, std.outbox-owner · **Status:** conformance-covered (std.outbox-owner: implemented) · **verified:** (none)

An outbox of writes made offline: each keeps its key and base, goes out in order on reconnect, and waits for the user when refused.

## Contract

- **Public API:**
  - `outbox(id, api, { module, limit = 100, maxBytes = 262144 })`, over the k.services `endpoints` map of module `module`'s routes, returns `Outbox<D>`: the reads and log of the client store `id` (`get`, `select`, `head`, `log`, `snapshot`, `restore`, …) with state `{ entries: OutboxEntry[] }`, changed only by `<id>.add`, `<id>.settle` and `<id>.resolve`. Inside a scope the store is created at once and the outbox stops flushing when that scope is disposed; at module level (no scope) it is created on first use and lives as long as the module, as a module-level `store` does. Each ctx that uses it reaches only the entries it added or loaded: its owner change, flush, retry, `resolve` and storage writes touch no other ctx's entries, while the store shows them all and holds one entry per key: `send` draws again a write key another ctx's entry has (two ctxs of one seed), and the load leaves out a stored entry with such a key, which that ctx's writes keep in its storage. It throws E2652 (an Error with `code`) for an `events: true` endpoint, whose answer is a stream, and E2651 when an endpoint body holds an `s.secret`.
  - `Write` (schema and type) `{ key: s.id('Write'), base: s.int({ min: 0 }), owner: s.string() }`: the `write` field of each endpoint body an outbox sends to.
  - `writeFor(write, owner)` returns `ok({ key, base })` when `write.owner` is `owner`; else `err({ code: 'offline.signin', message: 'signin', data: {} })` when `owner` is `""` (the request has no user), and `err({ code: 'offline.owner', message: 'owner', data: {} })` when it is another user. The action behind an outbox endpoint passes its write through it with the request's `user` (k.user: the id its pages give `send` and `drain`, `""` for no one), returns the err, which the server answers 400 with no store saved, and passes the value on: `const w = writeFor(input.write, user); if (!w.ok) return err(w.error); tx(t, payload, { meta, ...w.value })`.
  - `send(ctx, outbox, endpoint, input, { base, owner })`, `input` typed by the endpoint without `body.write`, `owner` the signed-in user's id or `""`, resolves `OutboxResult<O>`: `{ state: 'sent', value }`, `{ state: 'queued' }`, `{ state: 'conflict', head }` or `{ state: 'failed', error }` (an `ApiError`, `offline.full`, `offline.storage` when a write to `ctx.storage` rejected or did not settle within 10 s, or `offline.owner`).
  - `drain(ctx, outbox, { owner })`, inside a scope (E1203 outside one), loads the stored outbox, makes `owner` the ctx's owner, flushes, and flushes again on each `{ kind: 'net', online: true }` until the scope is disposed, which also drops the retry pending on that ctx and keeps the post in flight from arming one; the next `send`, `resolve` or `drain` flushes again.
  - `resolve(ctx, outbox, key, 'mine' | 'theirs')` resolves `false`, changing nothing, for a key with no such entry among those the ctx added or loaded. `'mine'` queues a `conflict` entry again, last, with `base` set to its `head`, flushes, and resolves that entry's `OutboxResult` as `send` does (`queued` when offline or the flush stops first; typed `false | OutboxResult<O>`, `O` the union of the api's outputs); `'theirs'` removes a `conflict` or `failed` entry and resolves `true` (`boolean`), also when its storage write rejects. A `Resolution`-typed argument resolves the union of both.
  - Schemas and types `OutboxEntry` (`{ key, endpoint, owner, input, base, at, state, head?, error? }`), `Resolution`; types `Outbox`, `OutboxResult`, `SendInput`.
  - `./tools` (node): rule E2651, an `outbox` whose endpoints map (inline, a `const` of the same file, or one imported from a project file) has an endpoint body holding `s.secret`. No fix.
- **Invariants:**
  - `send`, `drain` and `resolve` first load the outbox stored in `ctx.storage` `keel.outbox.<id>`, once per ctx, so a write made before `drain` keeps the stored entries. The load reads entry by entry and adds, in order, each stored entry the store lacks, a `sending` one as `queued`, while the entries stay within `limit` and `maxBytes`; the rest, and any value that is not an `OutboxEntry`, are not loaded, and the next write of the outbox drops them. A stored entry that holds an `origin`, or no string `owner`, loads `failed` with `offline.owner`, owner `""` and no `origin`, and the outbox is written back once.
  - Each entry holds the `owner` its `send` was given. `send` and `drain` make their `owner` the ctx's owner: every entry of another owner that is not `failed` becomes `failed` with `offline.owner` (`{ code, message: <outbox id>, data: {} }`), and the outbox is written to `ctx.storage` only when one did. The owner `""` (no one signed in) fails nothing: other owners' entries stay `queued`, their bodies in `ctx.storage`, until `send` or `drain` names their owner again; only another named owner fails them. A flush posts only `queued` entries of the ctx's owner; on a ctx no owner was given (a `'mine'` `resolve` alone) it posts nothing. An entry is posted only while, once its `sending` write settles, it is still `sending` and its owner is the ctx's; one whose owner stops being the ctx's before it is posted or while it is in flight, and is not answered 2xx, is `failed` with `offline.owner`, and its call resolves that `failed`; when the ctx's owner became `""` it stays `queued` instead and its call resolves `queued`. A `send` whose owner stops being the ctx's while its owner change is written adds nothing and resolves `failed` with `offline.owner`. A `failed` entry is never posted; `'theirs'` removes it.
  - `send` adds an entry with `body.write` `{ key: ctx.random.id('Write'), base, owner }` and `at` from `ctx.clock`, writes `{ entries }` as JSON to `ctx.storage` `keel.outbox.<id>`, and flushes when online. An outbox holding `limit` entries, or whose encoded entries would pass `maxBytes`, refuses with `offline.full` and adds nothing. When the write to `ctx.storage` of `send` or of a `'mine'` `resolve` rejects, the entry is `failed` with `offline.storage` (in memory), the outbox is written once more, nothing is posted, and the call resolves that `failed`. A flush already running does not post the entry until that write settles. An `offline.storage` error's message is the outbox id, never the text the storage threw, so a `Form` can show it.
  - One flush per outbox, one request in flight, entries in the order added, each through `service({ module, schema: api })` with its original key, read as `service({ module })` reads answers: a 2xx `{ ok: true, value }` gives `value` decoded by `output`, an error status the err's `error` decoded by `errors[status]`, and an endpoint that declares no 400 or 409 has it read as JSON. On a ctx no `createApp` bound it posts to `http://<module>.keel.invalid` plus the path, and in a page to the document's origin. 2xx removes the entry. `api.network` (a 502 `keel.unreachable` among them) and `api.timeout` keep it `queued` and stop the flush until the next `send`, a reconnect while draining, or a retry 1 s later doubling to 60 s on `ctx.clock` while online. A 409 `keel.conflict` err naming `data.transaction` leaves it `conflict` with `data.head`, whether or not the endpoint declares a 409; another 409 is sent once more, then `failed`. An error whose `code` is `offline.owner`, whatever its status, is `failed` with `offline.owner` (message the outbox id), and that entry is never posted again. An error whose `code` is `offline.signin`, whatever its status, is a pause: the entry stays `queued`, nothing more is posted on that ctx, a reconnect included, and the waiting calls resolve `queued`, until `send` or `drain` gives an owner there again; each entry is then posted once with its key. Any other status is `failed` with its `ApiError`. The flush moves on after `conflict` and `failed`.
  - An entry naming no endpoint of the outbox's api (an own key of the map) is `failed` with `api.input`. A write to `ctx.storage` that rejects while flushing fails the entry in hand with `offline.storage` (in memory), writes the outbox once more and releases the flush, so later sends flush; when it is the write recording the server's answer (`sent`, `conflict` or `failed`), the answer stands instead and the call resolves it. Any other throw in a flush releases it, leaves the entries as they are, resolves the calls waiting on it `queued`, and is rethrown.
  - A `ctx.storage.set` that throws counts as rejected, as does every write to `ctx.storage` not settled 10 s after it began, on `ctx.clock`; its timer is cancelled when it settles, a later settlement changes nothing in memory, and one that lands later is followed by one more write of the outbox as memory then holds it. When the second write is rejected too, storage keeps its last written state, which a later `drain` loads as any other.
  - The owner check runs when the action runs: a sign-in as another user in another tab before then refuses the write and a sign-out pauses it, one after it leaves the write committed under the owner who queued it. A write the server committed whose answer was lost, resent after the owner changed, is refused, so its entry is `failed` though the server holds the write. An action that spreads `input.write` into `tx` without `writeFor` commits a write of any owner, and a refused entry's body still reaches the action: the check decides which owner a write commits under, not what reaches the server.
  - Deploy the server before the client. A client that sends no `owner` fails the server's `Write` (422 `keel.fields`), so its entry is `failed` and nothing commits; a server that predates `owner` ignores it and checks nothing.
  - A resent entry keeps its key, so a write the server already committed commits nothing again while the store keeps that key: its last `keyLimit` keyed writes.
  - Every effect goes through `ctx` (`clock`, `net`, `random`, `storage`) and `observe`, so one seed and one script of sends and connectivity changes give byte-equal outbox and server logs.
- **Dependencies:** `@keel/check` and `oxc-parser` (tools only), `@keel/ctx`, `@keel/reactive`, `@keel/schema`, `@keel/services`, `@keel/store`.
- **Rungs:** conformance (examples and properties, seed 1337) for sending online through the module's service, queueing offline, flush order, lost responses, 409s, resolve and its answer, a rejected storage write, a full outbox, backoff, a drain's scope ending its retry, owners, the owner check, ctxs kept apart, E2651, E2652 and determinism; properties for scripts of sends, connectivity changes and lost responses that apply every entry once, in order, and for stored mixes of owners, `origin`s and missing owners, of which a drain posts exactly its owner's entries, for a server that refuses a random subset by owner, each refused entry failing alone, for a signed-out server (one post, a pause across reconnects, then each entry once, in order, when the owner returns), and for owners on two ctxs over one outbox, neither of which posts, fails, resolves or stores the other's entries.

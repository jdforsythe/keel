# @keel/std-sessions

**Spec:** std.sessions, std.multi · **Status:** implemented · **verified:** (none)

## Contract

- **Public API:** stdlib module `sessions` (`module.ts` at the package root; capabilities `clock`, `observe`, `session`, `storage`). Subpaths `./record`, `./replay`, `./minimize`, `./session`, `./Session`, `./redact`, `./tools`, `./commandJob`, `./routes`, `./action`, `./group`; bin `keel-session-action`; the root (the browser budget) re-exports `record`, `replay`, `redact`, `session` and the schemas, not `minimize`, `redactSession` or the node subpaths.
  - `record(ctx, { limit = 500, upload? })` returns `{ events(), errors(), stop() }`, one per ctx until its `stop()`; a `record` after `stop()` starts a fresh recorder. The recorder runs in a detached reactive scope (k.reactive), so it outlives the component that called `record`. The base is the ctx's route when it starts, else its first `nav`. `tx` comes from each store's `log()`; `nav`, `fire`, `net`, `resource` and `error` come from `observe` (k.ctx); a `net` event (`{ online }`, a connectivity change) is an input, and a `save` event is the server's, so the recorder drops it. Past `limit` the buffer drops through its oldest `nav` and rebases there; with none buffered it rebases to now and keeps the appended input. With `upload`, the first error puts the session through `session(ctx)`. Uploads are same-origin, because the k.server write proof refuses a cross-site POST: the app that records mounts `./routes` in its own `node` deployable and passes `new URL('/sessions', location.origin)`; an `upload` that is not http(s), carries a user name or password, or is not on the document's origin (`self.origin`, else `location.origin`; an opaque `"null"` origin has none) throws E2006 at the `record` call. The real `put` checks the same and sends with `redirect: "error"`. A recorder gets the errors the ctx reported since its current `nav` (k.ctx keeps the first 16), at their report time; a `nav` clears them. Before it observes, it treats the current value of each `el:` element and every password field, the redacted `tx:` payloads in store logs and the current route as already matched, so a kept error is scrubbed of them; when an `el:` element is not in the document, a kept error's message becomes its code and its `data` strings (but `data.at`) are masked. A kept error a recorder on the same ctx took is not taken again, so it is uploaded once. The recorder's scope has its own `onError`: a throw inside it lands in `errors()`. Without `document` it is a no-op. It registers inspect section `sessions.live`.
  - Redaction: each module's `redact` entries (`<subject>:<target>#<path>`, subjects `tx`, `store`, `route`, `el`, `error`) become their schema's generated value, seeded by the session seed and path. `el:` and `error:` values become `x` repeated. An `el:` entry masks every input value and one-character key of its element, and so does an element once reported masked (a password). `s.secret` fields always go, and `nav` hrefs are rebuilt from the redacted params and search. Every value an entry matched is masked again in later error messages and data, except `data.at`, which only an `error:` entry masks; other free text in errors is out of scope. `redact(schema, value, { paths, seed, salt, strings?, found? })` is the pure function. Path grammar: segments split on `.`; a bare `*` matches any one segment (an array index, a record key or an object field); `\.`, `\*` and `\\` are a literal `.`, `*` and `\` (so `store:a.b#headers.x\.trace` addresses the key `x.trace`). A recorder remembers the newest 256 distinct matched values to scrub from later errors.
  - `seed` is absent for a real or shell ctx (unseeded random), and `deterministic` is then false: a replay runs under seed 0 and may draw other ids.
  - Overflow with no `nav` buffered rebases to the oldest input but the first, at the state it saw; else to now, keeping the appended input or error, so an upload always names its error.
  - Bounds: past `limit` events or 192 KiB of session JSON the buffer cuts by the overflow rule until it fits; an event alone over 192 KiB leaves the session empty, rebased to now. `errors()` keeps the first and last 32. A failed upload (a non-2xx answer, or a put that rejects or throws: `data.status` 0) is recorded as a `sessions.putFailed` error, never an unhandled rejection. The real `put` sends `keepalive` only up to 64 KiB.
  - `./routes` (node, E2005): `sessions.ingest` (`POST /sessions`: a `Session` up to 256 KiB, else 413 `keel.payloadTooLarge`; invalid input 422 `keel.fields`) and `sessions.list` (`GET /sessions/list`, search `failing`, `since`) behind guard `sessions.reader` (caller hash in config `readers`, else 403 `keel.denied`, a JSON body; both routes are API routes). Store `sessions.archive` (`archiveStores`, persisted through `ctx.storage`, no log): per fingerprint `count`, `first`, `last` (the ingest clock) and the newest 5 sessions in arrival order, each as `{ bytes, session }` (its encoded JSON length, measured once); at most 64 fingerprints and 4 MiB, the oldest `last` evicted (ties: the smaller key), never the one this write filed. Sizes come from the tracked `bytes`, so a write is linear in the number of sessions. The ingest recomputes `error` and `fingerprint` from the session's events, never keeps a posted value, and applies the 256 KiB bound to the session as filed; `sessions.list` returns the sessions without byte counts. `apps/sessions` runs it.
  - `minimize(session, { routes, maxRuns = 200 })` (subpath `./minimize`, not in the root): replay (not reproduced: `err` `sessions.notReproduced`), the shortest reproducing prefix of the inputs (`fire`, `nav`, `net`) by binary search, then ddmin (complements of n chunks, n from 2 doubling; at n = input count these are the single removals in index order) until no single removal reproduces (`minimal: true`) or `maxRuns` (`minimal: false`). Each candidate set is replayed once; the output keeps the base and merges the kept inputs with the observations of their final replay. Deterministic: two runs are equal.
  - `redactSession(session, { routes, expose })` writes every recorded string outside `expose`, and every error message, as `x` repeated (what `to-test` emits, D3).
  - `replay(session, { routes, redact? })` returns `{ observed, state, error, reproduced, unapplied }` under `createCtx({ mode: 'sim', seed })`, applying `fire`, `nav` (through `navigate`) and `net` (through the sim net's `setOnline`, which records the `net` event again, so it shows in `observed`). It seeds every live store: one the base `state` lacks starts at its snapshot `initial`, so a replay never reads what an earlier run left and `minimize` stays deterministic. `redact` (also on `minimize`) is the recording's entries, bound on the replay ctx so the replay recorder masks what the live one did; `keel session` passes the serving modules' `redact` literals.
  - Fingerprint: 12 hex of sha256 over the first `error` event's `code`, `data.at` as recorded (after redaction) and its `route` (the route id it fired under); with no error event, the base route id. The recorder, `replay`, `minimize` and `sessions.ingest` compute it from the session alone.
  - `session(ctx)`: `put(url, session)` (real POST, shell drop, sim kept in `taken()`) and `id()` from the capability's own ctx.
  - `Session` (`sessions.Session`), `SessionEvent`, `SessionsConfig` (`{ redact?, expose?, readers? }`; only `redact` reaches browsers).
  - `./tools` (node): check rules E2001 (`redact` or `expose` entry with an unknown subject, another module's target, or a path absent from its schema; fix removes it) and E2005 (a non-`node` deployable serves `@keel/std-sessions/routes`), the `session` record formatter, and the `session` command (`stdCommand`): `keel session capture [url]` (inspect section `sessions.live` to `.keel/sessions/<fingerprint>-<id>.json`; null writes nothing), `ingest <url> [--failing] [--since t]` (`GET <url>/sessions/list`, caller cookie from `KEEL_SESSIONS_TOKEN`, each session to `.keel/sessions/`; E1056 on failure), `replay <f>`, `minimize <f> [--max-runs n]` (rewrites `<f>`), `to-test <f>` (writes `modules/<m>/test/session-<fingerprint>.test.ts`, redacted by the route module's `expose`, after a replay of the redacted session reproduces). E2002 (schema), E2003 (input N from 0, or the base: no `topology.ts` deployable serves the route) and E2004 (fingerprint differs; nothing written) are diags at `<f>:1:1`. E2005 follows `export ... from`, `export *`, `import()`, `require()`, `import x = require()` and imports through other project files by relative specifier; it does not follow a non-relative alias such as `@app/ops`.
  - `./group` (node, std.multi): `openGroup({ user, serve, users, seed, origin, at?, server? })` resolves to a group: `serve(ctx)` runs over a sim ctx of `seed` whose storage starts with `server` (each value set under `keel.store.<id>`, JSON text), and each user runs in its own worker thread (happy-dom, its own modules, loaded with tsx) on a sim ctx whose seed mixes `seed` and its index. A user renders the `user` module's `base` at `at` under `record(ctx, { limit: Infinity })` and reaches `origin` through its sim net with its own cookie jar; response bodies stream back chunk by chunk. The group gives `user(i)` (`fire`, `navigate`, `find`, `state`, each a promise), `setOnline(i, b)`, `advance(ms)` (every clock, the server's included), `settle()` (repeats until a round of user settles sees no request, response or chunk) and `stop()` (settles, ends the workers and returns the `SessionGroup`, its `server` the stored values when the group opened). `replayGroup(group, { user, serve })` restores the server storage, opens each user at its session's base under its session's `seed`, applies every user's inputs in order of `at`, then user index, then event index (advancing every clock to each `at` and settling after each), and returns `{ users: ReplayResult[], server, reproduced }`: `server` holds each store the server stored under `keel.store.<id>`, parsed as a snapshot with its log. `SessionGroup` (`sessions.SessionGroup`) is the group schema; `groupDiags(text, file)` gives E2007 (not JSON, or fails `SessionGroup`, at its first issue) or E2008 (one per user session without a `seed`), each at `<file>:1:1`. A `user` URL a dev server serves (`http://localhost:3000/<path>`, `/@fs/<path>`) loads the file it names.
  - Job contract (D1): replay, minimize and to-test write `.keel/sessions/job-<pid>-<n>.test.ts` (it imports each serving module's `routes.ts` and calls `commandJob` from `./commandJob` with the session inline), run `keel test <job> --format=json` in process on the project (its vitest config, environment and `KEEL_TEST=1`), read `JobResult` from `<job>.result.json`, and remove both. The project's vitest `include` must match `.keel/sessions/*.test.ts` (the default does); with no result the test run's diagnostics come back and the summary fails.
- **Dependencies:** `@keel/check`, `@keel/cli` (tools only), `@keel/compiler`, `@keel/ctx`, `@keel/reactive`, `@keel/router`, `@keel/schema`, `@keel/store`, `@keel/testing`, `oxc-parser` (tools only), `happy-dom` and `tsx` (`./group` workers).
- **Rungs:** conformance (examples and properties, seed 1337) for determinism, redaction, overflow, replay, `net` events, the capability, the server no-op, E2001, E2005 and E2006, and for groups (determinism, replay, isolation, order); properties for `sha256`, `redact`, `redactSession`, per-user seeds and E2007/E2008.

## Action

`packages/std-sessions/action/action.yml` is a composite GitHub Action for the nightly loop. The calling job checks out the repo without persisted credentials and grants `issues: write` and `contents: read`; the Action never pushes. Pin it to the Keel tag of the `@keel/std-sessions` version your lockfile holds, since it runs the installed `keel-session-action` bin, not code from the ref:

```yaml
permissions:
  issues: write
  contents: read
concurrency:
  group: sessions-nightly
  cancel-in-progress: false
jobs:
  sessions:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@11d5960a326750d5838078e36cf38b85af677262 # v4.4.0
        with:
          persist-credentials: false
      - uses: jdforsythe/keel/packages/std-sessions/action@<tag>
        with:
          url: ${{ vars.KEEL_SESSIONS_URL }}
          token: ${{ secrets.KEEL_SESSIONS_TOKEN }}
          working-directory: apps/shop
```

- **Inputs.** `url` and `token` are required. `token` is a reader's caller cookie value, exported as `KEEL_SESSIONS_TOKEN` to the ingest alone. `working-directory` (default `.`) is the project holding `topology.ts`; `keel` (default `pnpm exec keel`) is the command that runs the `keel` binary there; `github-token` defaults to the job's token.
- **Steps.** It sets up pnpm and node (actions pinned by commit SHA; `node-version-file: package.json`, so `engines.node`), runs `pnpm install --frozen-lockfile` in `working-directory`, and runs `pnpm exec keel-session-action` there. The bin is `dist/src/actionBin.js`, so the package must be built: a published install is; this repo's `sessions-nightly` workflow builds it first.
- **Trust.** The Action replays sessions through the project's own test code under the job's privileges, and a child process of the job can read the job's tokens however the env is scrubbed. It belongs on a repository whose ingest service only the project writes to.
- **Loop.** `runAction(io)` (`./action`, `src/runAction.ts`; `io` is `{ args, tty, env, now, fetch, run, read }`) runs `keel session ingest <url> --failing --since=<now - 26h>`. It replays each fingerprint's files from the ingest newest first until one reproduces. A reproduced fingerprint gets `minimize` and `to-test`, then the open issue labeled `keel-session` for that fingerprint is updated, or one titled `session <fingerprint>: <code> at <route>` is created, at most 20 a run (the rest count as `deferred`). The lookup key is the hidden first line of the issue body, `<!-- keel-session:<fingerprint> -->`, which holds the fingerprint and nothing else; an issue filed without it is found by a title that starts `session <fingerprint>:`, and gains the line when updated. Only the first line of the body counts, so text further down never matches. The lookup lists the label's open issues (up to 50 pages of 100, else E1056), then its closed issues newest first, up to 5 pages of 100; a closed issue beyond them is treated as absent. A renamed issue is still found; an issue without the label is not. A fingerprint with no open issue and one closed as not planned is skipped (the summary counts it as `skipped`); one whose issues are all closed as completed gets a new issue, since the bug is back. The body is the compact `session` record and the emitted test, each fenced; no other session value goes in. When no file reproduces (each replay E2004), the open issue gets one comment starting with the marker line `<!-- keel-session: not reproduced -->`, unless its newest comment already carries it.
- **Safety.** Only files named `.keel/sessions/<fingerprint>-<n>.json` reach `keel`, and `read` refuses paths outside the project. A route id or error code outside `[A-Za-z0-9_.-]` skips the fingerprint with E2002. Every printed field and issue title loses ANSI escapes and control characters, and child stderr lines print prefixed `keel: `, so no line starts a workflow command. `keel` children never get `GITHUB_TOKEN`, and only the ingest gets `KEEL_SESSIONS_TOKEN`; GitHub `Link` pages outside `GITHUB_API_URL` are not followed.
- **Output.** `--format=compact|json|pretty`, `--quiet` and `--limit N` as docs/OUTPUT.md defines them. Records: relayed `diag`s (with `fix`), and a `session` and a `session.issue` for each fingerprint whose issue changed; the `summary` counts the rest. It exits 1 when the ingest fails, a GitHub call fails or the issue list passes 50 pages (E1056), a step fails with anything but E2004, or the env lacks the url, `GITHUB_REPOSITORY` or `GITHUB_TOKEN` (E1052).

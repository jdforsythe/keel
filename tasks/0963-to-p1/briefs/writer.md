# What an RFC writer is told

Work ONLY in your lane's worktree. Do not push, do not merge, do not touch any other worktree. Do not write implementation code and do not write or edit anything under `packages/*/conformance/**`. Do not run test suites (other lanes use the machine); `pnpm spec <id>`, `node tooling/docs-check.mjs`, `node tooling/voice-lint.mjs`, `node tooling/structure-lint.mjs`, `node tooling/docs-freshness.mjs`, `node tooling/docs-pack.mjs --check`, `node tooling/format-check.mjs`, `node tooling/budgets.mjs` are fine (run `pnpm install --offline` first if the worktree has no node_modules).

Read first, in the lane: `CLAUDE.md`, `docs/PRINCIPLES.md`, `docs/GLOSSARY.md`, `tasks/0963-to-p1/briefs/README.md`. Fetch spec sections with `pnpm spec <area>` and `pnpm spec <id>`; do not read `spec/` or `docs/rfc/` wholesale. Find a backlog line with `grep -n '^- \[.\] <id>' tasks/BACKLOG.md`.

Design the smallest addition consistent with the principles: one way to do a thing; no glossary renames; checked at `keel check` where a wrong value can be caught; identity, server and user concepts cost nothing for an app that has not opted in; no bare `Date`, `Math.random`, `fetch`. Decide what the work needs yourself and say what you decided; raise a question only if it changes the product's vision.

Deliver the RFC and ADR numbers assigned to you (use no others), following exactly the shape and commit pattern of a recent one: `docs/rfc/0204-unused-deps.md`, `docs/adr/0226-unused-deps.md`, and how its spec text landed in `spec/` (`git show --stat 935078b3`):
1. `docs/rfc/NNNN-<title>.md` with sections Problem, Proposal, Alternatives, Spec diff, Conformance diff, Migration, Token impact. Status accepted (the orchestrator accepts it on standing authority, to be confirmed by the operator; list in a short "For the operator" section the calls you made that they may want to reverse). No migration notes are needed for unreleased changes.
2. `docs/adr/NNNN-<title>.md`.
3. The spec text applied to `spec/` so `pnpm spec <id>` prints the new clauses, with the status the precedent used for accepted-and-not-yet-built text. A new diagnostic takes an unused code in the right range (check how codes are allocated and registered; taken recently: E1108, E1165, E2407).
4. Any map or budget file the tooling requires (the spec map is at 1,429 of its 1,430-token budget: re-base it if you add to it, and say so in the commit message). Do not hand-edit `tooling/ledger/ledger.json`.
Write each Conformance bullet so a test header can quote it whole, word for word, and so nothing in it is ambiguous: state exact inputs and exact outcomes; do not leave a behaviour to a reader's guess (earlier writers left open: a length counted before or after normalizing, where "at the entry" falls, how a mount appears in a table). Do not change an existing bullet's wording unless the behaviour changes: existing conformance headers quote them whole. Docs and spec text describe what exists as designed, with no history ("used to", "since rfc"). Person-facing text follows the voice rules of `docs/BRAND.md`. Kernel packages never import std packages (`tooling/deps.json` order), tests included: place conformance that needs a std package in that std package.

Commit in the lane, messages prefixed `rfc:NNNN`, each ending with the session's attribution trailers.

Report, under 350 words: commits; the spec topic ids and clause numbers a conformance writer must cover (it sees only the spec text, never the implementation); the conformance file names you propose and which package's `conformance/` folder; the files a builder will own (packages, apps and examples to rewrite); the design in five lines; alternatives rejected in two lines; calls you made for the operator; which lint commands you ran with their last `ok`/`fail` line.

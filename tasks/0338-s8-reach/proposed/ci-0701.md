## Diagnosis

The whole suite (45 test tasks plus their builds) does not fit one 2-core hosted runner: in parallel it starves tests past their wall-clock bounds, in series it runs for most of an hour until the runner is lost, and the quiet wrapper prints nothing until the end. The `check` failures were real and are fixed; the `ledger` job could never pass on a fresh checkout, because the a11y claims read `apps/golden-2/reports/a11y.json`, which only `keel test` writes and which is gitignored (on a checkout of HEAD, `ledger --diff` reports 68 lowered `a11y:recipes.catalog#…` rungs; with the report written it passes).

## Design

- `check` (30 min): `pnpm check`; `keel test` in golden-2 (11 s locally) so the a11y report exists; `pnpm ledger --diff` (9 s locally, passes on the current tree and on HEAD with the report); `node tooling/ci-shards.mjs --verify`; saves turbo's cache (`TURBO_CACHE_DIR=.turbo/cache`, keyed on sha, run and attempt), which holds every build `turbo check` ran. The separate `ledger` job is gone: it ran on a fresh checkout without the report.
- `test-shard` (matrix of 6, `fail-fast: false`, 35 min each): restores the turbo cache so `^build` is a cache hit, then `node tooling/ci-shards.mjs <n>`. The script takes the test tasks from `turbo run test --dry=json`, so no package list is kept by hand, and deals them largest first (by count of test files) to the shard with the fewest files: six shards of 254 to 258 files. It runs turbo with `--concurrency=1` (the repository's rule for four cores or fewer) and `--output-logs=new-only`, so each task's log prints as it finishes. Its first line names the shard's packages and the runner's cores and memory.
- `--verify` (in `check`, 4 s): fails E0013 when the matrix is not 1 to n, or when a test task falls in no shard or in two, checked by turbo dry runs of each shard's filters against the full task list. It runs before any shard starts. The shard count comes from the matrix length in `tooling/ci.source.json`, so the script and the matrix cannot disagree.
- `test` (5 min, no checkout): passes only when every shard passed; `build` and `mutate-pr` still need `test`, so the job names downstream and any branch protection on `test` stay valid. It is skipped on scheduled runs.
- `build` 20 min, `budgets` 20 min, `golden-1-images` 30 min, all restoring the turbo cache; `postgres` unchanged (15 min); `mutate-pr` 120 min. `mutate-pr` and nightly `mutate` also run `keel test` in golden-2 before their `ledger --diff`, for the same reason. Scheduled `mutate` and `eval` keep the default limit.
- No test timeout raised, no skip, no retry. The repository's convention for heavy suites is a per-package `testTimeout` with a comment in its vitest config (`packages/cli`, `apps/inspector` 20 s); no vitest config was touched here.

## Watch on the first run

- The shard header line: cores and memory (expect 2 and about 7.8 GB). If the runner has 4 cores, the shards still run one task at a time, and could take two.
- Each shard's duration. File count is a rough weight: shard 2 holds `@keel/cli` (type-checking tests with a 30 s timeout) and shard 1 holds `@keel/server`. If one shard runs much longer than the others, add shards or a weight per package; the deal is in one function.
- Whether `^build` tasks print as cache hits in the shards. A miss means the hash differs between `check` and the shards; the run still passes, only slower.
- Whether a runner is still lost in a shard: if so, the streamed log now shows the last task that started, and memory is the first suspect.
- `pnpm install --frozen-lockfile` against the `pnpm-lock.yaml` other agents changed (`@vitest/coverage-v8`): it fails `check` before anything else when the lockfile and the package.json files disagree.
- Billing: 6 shards plus `check` for each push; superseded runs are still cancelled.

## First sharded run (44241768314): shard 2 cut at 16 minutes

Evidence from the shard 2 log: `@keel/ctx`, `@keel/std-geo`, `@keel/std-tauri` passed by 05:18:56; `@keel/cli:test` then ran alone (turbo `--concurrency=1`) for 15.5 minutes with no output, because turbo on GitHub groups a task's output until it ends. At 05:34:29.95 turbo printed `Shutting down Turborepo tasks...`, at 05:34:30.10 `Force killed Turborepo tasks: @keel/cli#test`; the cli group is empty, and the std-headless, std-live and std-schedules groups were never run. Summary `Tasks: 22 successful, 26 total` (the four not counted are those four). Then `##[error]The operation was canceled.` and the step conclusion `cancelled` (job `failure`). `ci-shards.mjs` printed nothing: it was signalled too.

What it is not: no test failed (turbo prints a failing task's log and `ERR_PNPM_RECURSIVE_RUN_FIRST_FAIL`; none here); no `Killed`, 137, `SIGKILL` or heap message; not the job limit (35 minutes, and that prints "exceeded the maximum execution time"); not concurrency (no newer run of the ref exists: 44241768314 is the latest); not fail-fast (`false`, and every other shard passed); neither ci-shards nor turbo has a bound near 16 minutes. Shards 3 (`ok ci-shard 3/6 8 packages (945.2s)`, `@keel/check` 444 s, `@keel/scaffold` 266 s) and 6 (`ok ci-shard 6/6 8 packages (936.9s)`, `@keel/std-sessions` 671 s) ran as long and ended with exit 0, so length alone does not lose a runner. The signature (step cancelled from the runner side, no stated cause, no output) matches the five earlier "runner lost" runs above.

Local reproduction, the suspect task as the 2-core runner runs it (one vitest worker): `vitest run --maxWorkers=1` in `packages/cli`, under `/usr/bin/time -l`, the process tree's RSS sampled every 5 s: `ok 969 tests, 0 failed, 0 skipped (357.5s)`, largest single process 654 MB, tree peak 1.4 GB. Memory on that evidence is far below 7.7 GB, so out-of-memory in `@keel/cli` is not shown; on the runner it took more than 935 s (2.6x the laptop at least). The log cannot name what ended the runner; the fix makes the next one name what was running and on how much memory, and shortens the shard that holds cli.

Fix (`tooling/ci-shards.mjs`): packages are dealt by recorded seconds on the 2-core runner (`SECONDS`, from this run's vitest trailers; `@keel/cli` 960 as a lower bound), a package without a record weighs one second per test file. Each package runs as its own turbo call with `--log-order=stream`, every task even after one fails. A `run <pkg> test` line names each task as it starts; a task past five minutes prints `still <pkg> test <s>s, peak <GB>, least free <GB>` every five minutes; the shard ends with one line per task (`ok|fail <pkg> test <s>s[, exit N], peak, least free`) and then each failed task's name and whole log; SIGINT or SIGTERM prints the finished tasks and `cut <pkg> test after <s>s by <signal>` with memory before exiting. `--plan` prints the deal; `--verify` also fails E0013 when `SECONDS` names a package with no test task. `docs/TESTING.md` CI paragraph updated. No test skipped, no retry, no limit raised.

New deal (`node tooling/ci-shards.mjs --plan`): 1 `@keel/cli` alone (expected 16+ min); 2 `@keel/std-sessions` (about 11 min); 3 to 6 about 520 s each (9 min). Smoke-tested locally: a passing and a failing (no such package) task give the closing lines and the failed log; SIGINT mid-task gives the `cut` line and exit 130.

Watch on the next run: shard 1's `still @keel/cli` lines (memory and how far it got) and whether it ends `ok`; its seconds, to replace the 960 lower bound. If cli alone is still lost near 16 minutes with memory low, the runner is the limit: split cli's vitest run in two (`vitest --shard`) or give it a larger runner; if memory stays low and it is still cut, the cause is outside the tests and the `still` lines bound when it happened.

## Second sharded run (44248254667): shard 1 (`@keel/cli` alone) lost, no log at all

Evidence: `check` (11.5 min), `postgres` and shards 2 to 6 (6 to 9 min each) passed. Every shard restored the `check` job's turbo cache: 928 `build` cache hits, no build miss, so the shards rebuild nothing. Shard 1 ran `node tooling/ci-shards.mjs 1` from 06:13:05; the job hit its 35-minute limit (annotation "The job has exceeded the maximum execution time of 35m0s") and was marked cancelled at 06:52:48, 40 minutes after it started. The step has no conclusion, the post steps never ran, and GitHub holds no log for the job (`gh run view --job` "log not found"; the jobs API and the run's log archive return BlobNotFound / omit it). A runner that stays healthy through a timeout signals the step, runs the post steps and uploads the log, and the `cut` line would have printed; none of that happened, so the runner itself stopped answering some time before the limit. The heartbeat lines, the last test file and the memory figures are therefore not available.

Local measurement, `vitest run --maxWorkers=1` in `packages/cli` with its own `TMPDIR`, sampled every 5 s (machine shared with an eval run): 972 tests pass in 575 s wall, 451 s summed per file; process tree at most 1.5 GB and 19 processes; temporary files at most 34 MB. Slowest files: `E1562-base-output-removed` 34 s, `compat-0092` 30 s, `E1562-base-route-change` 27 s, `evidence-tamper` 27 s, `dev-port-0091` 26 s, `build-target-e1574` 22 s. No file waits unbounded (the watchdog kills a phase past twice its timeout plus 30 s), and the build-target tests use fake `cargo`, `java` and `npx`, so no native toolchain runs on the runner.

Cause, as far as the evidence goes: `@keel/cli` whole does not finish in 35 minutes on the 2-core runner, and twice the runner holding it was lost (at 16 minutes in 44241768314, before 35 here). Locally it shows no memory, disk or process growth that would explain a lost runner; that the runner loses itself while cli runs, and why, is unproven. Ruled out: a cold build cache (all hits), a hung test (watchdog bound), the worker pool (vitest uses one worker on 2 cores).

Fix:
- `tooling/ci-shards.mjs`: `SPLIT = { "@keel/cli": 4 }`. A split package runs as parts with vitest's `--shard=i/4` (turbo passes `-- --shard=i/4` to `vitest run`), each part in a different `test-shard` job; the deal places the heaviest units first, a part never in a shard that already holds a part of its package. `--verify` fails E0013 when a part is in no shard or two, two parts share a shard, a split count is outside 2 to n, or SPLIT names a package with no test task (checked with a 7-part split and an unknown package: all three diagnostics). `SECONDS["@keel/cli"]` is 2,100 (the cut). The per-task closing line adds the task's five slowest files.
- `tooling/vitest-config.ts`: with `KEEL_FILE_TIMES=1` (set only by ci-shards, passed through turbo with `--env-mode=loose`) a reporter prints `file <path> <s>s` as each test file ends, so a lost runner's log (when one is uploaded) names the last file that finished, and each file's runner time is recorded. Without the variable nothing changes; the Keel reporter is untouched.
- `docs/TESTING.md` CI paragraph. `tooling/ci.source.json` and `ci.yml` unchanged: six shards, 35 minutes, no limit raised.

Projection: vitest's hash split of cli's 152 files gives the parts 32, 27, 21 and 20 percent of the local per-file time. With cli at 2,100 s on the runner, the largest part is about 680 s; the plan puts 810 s nominal in every shard, so the longest job is about 16 to 17 minutes with setup. If cli is twice as slow as that bound, the largest shard is still near 25 minutes.

Smoke: the script's exact turbo command for part 4/4 of cli: 38 of 152 files, `ok 214 tests, 0 failed`, 38 `file` lines; the slowest-file parse reads them.

Watch on the next run: each `@keel/cli i/4` closing line (seconds, peak memory, slowest files): sum them to replace the 2,100 bound; whether any shard holding a cli part is lost again, and if so the last `file` line before the loss and the `still` memory figures; if a part is lost with memory flat, the file after the last printed one is the suspect.

## Third run (44257427602): cli split in four, Linux failures visible; reproduced in Docker

Reproduction: `node:22` container (v22.22.3), `--cpus 2 --memory 7700m`, repo copied in, `pnpm install --frozen-lockfile`, cli's builds through turbo, `lsof` installed as on the runner, vitest with `--maxWorkers=1`. All three failures and the memory climb reproduce; all pass on macOS.

- `@keel/cli 4/4`, memory: `conformance/evidence-no-key.test.ts` (the file after `ledger-rung-promotion-cli` that never prints a `file` line; vitest's sha1 deal of the 152 files gives it to 4/4). Its `sources()` calls `readTree(dir)` (`conformance/evidence-fixture.ts:278`) on the materialized project, and `readTree` uses `statSync`, which follows the `node_modules/@keel/*`, `vite`, `vitest`, `typescript` links into the repo and through pnpm's `node_modules/.pnpm` link graph, keeping every file as a Buffer; it filters `node_modules/` only after reading. On macOS the walk throws ENAMETOOLONG within 0.2 s (path 1,017 characters, PATH_MAX 1,024, after 5,323 files), the `catch` returns an empty Map, and the test passes with `before` and `after` both empty (the "tree unchanged" check is vacuous there). On Linux (PATH_MAX 4,096) the same walk read 3 GB in 3 s with the longest path at 378 characters; run alone, the vitest fork grew 2.1, 3.9, 5.5 GB at 3, 6, 9 s; in the 4/4 part it grew to 7.2 GB and the fork died ("Worker forks emitted error"). This is a conformance defect (not edited): `readTree` should not follow links (`lstatSync`, or skip `node_modules` while walking). With that one file excluded (measurement only), 4/4 passed: `ok 211 tests`, peak process 358 MB, all processes 901 MB.
- `dev-port-0091` (3 cases) and `topology-keel-dev-one-origin`: two causes. (1) Code: Vite's default host `localhost` was bound with Node's verbatim lookup, `::1` on Linux, while a client's `localhost` lookup uses address-configuration filtering and gets only 127.0.0.1 on a machine without a non-loopback IPv6 address (the runner, containers): `::1` 200, `localhost` and 127.0.0.1 ECONNREFUSED. Fix: `keel dev` sets `dns.setDefaultResultOrder("ipv4first")` before Vite, so it binds 127.0.0.1 on every OS (banner prints `http://127.0.0.1:<p>/` where the verbatim lookup differs). (2) Conformance: `served()` (`dev-port-0091.test.ts:166`, `topology-keel-dev-one-origin.test.ts:172`) bounds its wait by 4,000 back-to-back refused connects with no timer: 782 ms on macOS (two addresses each), 327 ms on Linux, while `keel dev` listens about 550 ms after spawn in the container. With a 10 ms pause per refused attempt in a container-only copy, both files pass with the fix and fail without it (47 s each, address unreachable). The wait bound needs an RFC change (time-based or longer bound).
- `mutation-io-fs` viteRun "killed by a signal": the fake vite was a shell script reached through `npx`; on Linux the shell between turns SIGKILL into exit 137 with "Killed". The test now installs a fake `vite` package whose bin kills itself, run by Node directly (no shell), as a real installed Vite is: status null, code 1, on both systems.

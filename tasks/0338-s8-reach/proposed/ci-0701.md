## Diagnosis

The whole suite (45 test tasks plus their builds) does not fit one 2-core hosted runner: in parallel it starves tests past their wall-clock bounds, in series it runs for most of an hour until the runner is lost, and the quiet wrapper prints nothing until the end. The `check` failures were real and are fixed; the `ledger` job could never pass on a fresh checkout, because the a11y claims read `apps/golden-2/reports/a11y.json`, which only `keel test` writes and which is gitignored (on a checkout of HEAD, `ledger --diff` reports 68 lowered `a11y:recipes.catalog#…` rungs; with the report written it passes).

## Design

- `check` (30 min): `pnpm check`; `keel test` in golden-2 (11 s locally) so the a11y report exists; `pnpm ledger --diff` (9 s locally, passes on the current tree and on HEAD with the report); `node tooling/ci-shards.mjs --verify`; saves turbo's cache (`TURBO_CACHE_DIR=.turbo/cache`, keyed on sha, run and attempt), which holds every build `turbo check` ran. The separate `ledger` job is gone: it ran on a fresh checkout without the report.
- `test-shard` (matrix of 6, `fail-fast: false`, 35 min each): restores the turbo cache so `^build` is a cache hit, then `node tooling/ci-shards.mjs <n>`. The script takes the test tasks from `turbo run test --dry=json`, so no package list is kept by hand, and deals them largest first (by count of test files) to the shard with the fewest files: six shards of 254 to 258 files. It runs turbo with `--concurrency=1` (the repository's rule for four cores or fewer) and `--output-logs=new-only`, so each task's log prints as it finishes. Its first line names the shard's packages and the runner's cores and memory.
- `--verify` (in `check`, 4 s): fails E0013 when the matrix is not 1 to n, or when a test task falls in no shard or in two, checked by turbo dry runs of each shard's filters against the full task list. It runs before any shard starts. The shard count comes from the matrix length in `tooling/ci.source.json`, so the script and the matrix cannot disagree.
- `test` (5 min, no checkout): passes only when every shard passed; `build` and `mutate-pr` still need `test`, so the job names downstream and any branch protection on `test` stay valid. It is skipped on scheduled runs.
- `build` 20 min, `budgets` 20 min, `golden-1-images` 30 min, all restoring the turbo cache; `postgres` unchanged (15 min); `mutate-pr` 120 min. `mutate-pr` and nightly `mutate` also run `keel test` in golden-2 before their `ledger --diff`, for the same reason. Scheduled `mutate` and `eval` keep the default limit.
- No test timeout raised, no skip, no retry. The repository's convention for heavy suites is a per-package `testTimeout` with a comment in its vitest config (`packages/cli`, `apps/inspector` 20 s); no vitest config was touched here.

## Watch on the first run

- The shard header line: cores and memory (expect 2 and about 7.8 GB). If the runner has 4 cores, the shards still run one task at a time, and could take two.
- Each shard's duration. File count is a rough weight: shard 2 holds `@keel/cli` (type-checking tests with a 30 s timeout) and shard 1 holds `@keel/server`. If one shard runs much longer than the others, add shards or a weight per package; the deal is in one function.
- Whether `^build` tasks print as cache hits in the shards. A miss means the hash differs between `check` and the shards; the run still passes, only slower.
- Whether a runner is still lost in a shard: if so, the streamed log now shows the last task that started, and memory is the first suspect.
- `pnpm install --frozen-lockfile` against the `pnpm-lock.yaml` other agents changed (`@vitest/coverage-v8`): it fails `check` before anything else when the lockfile and the package.json files disagree.
- Billing: 6 shards plus `check` for each push; superseded runs are still cancelled.

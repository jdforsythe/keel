## Framework faults

8. (Fixed, rfc:0189.) A built shell with no `identity.ts` took no link from outside. `examples/links-in` is a `client` deployable with `shells.tauri` (`id: 'dev.keel.linksin'`) and two pages, and no identity mount. `test/linksIn.test.ts` runs `renderRoute('places.home', { routes, shell: { id } })`, then `t.returnLink('dev.keel.linksin:/places/oslo')` and `t.launch([...])`: each lands on `places.place`, and `keel test` passes (3 tests). The build disagrees. `packages/compiler/src/vite.ts` passes the shell to `entryCode` as `shellOf(exists("identity.ts") ? all[d.name]?.shells : undefined)`, so without `identity.ts` the shell entry never calls `shellMount`, the only code that calls `@tauri-apps/plugin-deep-link` `getCurrent` and `onOpenUrl` (`packages/std-tauri/src/shellMount.ts`; Capacitor the same). The generated `tauri.conf.json` still registers the scheme and `lib.rs` the deep-link plugin, so the OS opens the app on the link and the page stays where it was. Expected, from `pnpm spec k.links`: "A link from outside reaches a page as a web link does", and of a return link whose path is "A page the router matches: a client-side navigation there, at any time". `pnpm spec k.shell` (Shell ctx) says only "With `identity.ts` the entry calls the package's `shellMount(...)` ... then delivers return links (k.links)", so the two sections disagree and I did not change the entry: the fix is an always-on link intake in the shell entry (a `shellMount` with no mount, or a links-only call over `mountRequests` with `mounts: []`), a k.shell sentence, and a conformance clause owed in k.shell: "a shell build of a project with no `identity.ts` delivers a page link to the router". The test harness hides it because `renderRoute(..., { shell })` delivers links whatever the project holds.

10. A `service({ base })` call from the browser sends `x-keel: 1`, so every call to another organisation's API is preflighted. `examples/client-only-api` is one `client` deployable that reads `https://api.github.com/repos/nodejs/node/releases` through `githubApi = service({ base: "https://api.github.com", schema: GitHubApi })`, with `origins.connect` declaring the origin. In `tooling/smoke/examples.mjs` Chromium reaches a local https stand-in for `api.github.com`; the stand-in saw an `OPTIONS` with `access-control-request-headers: x-keel` before each `GET`, and the `GET` carried `x-keel: 1`. The stand-in allows the header, so the step passes; an API whose preflight lists only the headers it knows refuses the call, and the page can only show its alert. `pnpm spec k.services` (Encoding): "Every request sends `accept: application/json` and `x-keel: 1`"; the header is k.server's same-site proof for writes to a Keel server, and a `base` service names no Keel server. It falls short of `pnpm spec k.origins` (Purpose): "A deployable names, with a reason, each other origin its documents load from": the declaration should be all a client needs to read a public API. Cause: `packages/services/src/internal/buildRequest.ts:56` sets `x-keel` on every request. The spec sentence says so, so this needs an RFC: a `base` service sends no `x-keel` (and no `accept` beyond what the endpoint needs), with a k.services conformance clause owed: "a `base` service's request carries no `x-keel` header; a `contract` service's does". Since `ctx.net.fetch` is E1651 in app code, the service is the only way to call the API, so there is no workaround in app code.
12. `keel scaffold route` leaves `keel check` failing. In a fresh `keel scaffold project site` (scratch copy, outside the repository), `keel build` then `keel check` is `ok check 5 files, 0 errors`; after `keel scaffold route app.home --path /` and `keel scaffold route app.releases --path /releases`, `keel check` is `E1005 .keel/surface.json:1:1 .keel/surface.json is stale, modules/app/app.contract.ts changed; run keel build`, and `keel build` clears it. In the workspace project the same two scaffolds, then page edits, gave E1005 for `a11y.json`, `deps.json`, `ids.json` and `styles.json` too. `pnpm spec k.scaffold` (Guarantee): "If `keel check` was clean before an operation, it is clean after." Cause: `packages/cli/src/internal/scaffoldCommand.ts` writes the edit set and does not regenerate `.keel/` (the guarantee's own check leaves E1005 out). The fix is the scaffold regenerating the artifacts the edit set changes, more than a few lines; conformance clause owed in k.scaffold: "after `keel build`, each generator leaves `keel check` with no E1005".

## Docs or skill gaps

1. `Host` is missing from the skills. `.claude/skills/keel-client/SKILL.md` names no `Host`, `hostCode` or E1824; I found the element only through `keel docs k.host-element` and `keel docs k.host-code`. Expected: a short `Host` paragraph in keel-client, beside widgets and tables.
2. `hostCode`'s state type is undocumented. `k.host-code` says `mount` "returns the code's own state `S`" and shows `HostCode<I, E>` with two parameters. Following it, `hostCode<Infer<typeof Bars>, never>({ mount(node, value) { ...; return svg } })` in `examples/host-component/modules/app/barChart.ts` fails `keel check` with `E1751 ... TS2322 Type '(node: HTMLElement, value: ...) => SVGSVGElement' is not assignable to type '(node, value, out: HostOut<never>) => undefined'`. A third type argument, `hostCode<Infer<typeof Bars>, never, SVGSVGElement>`, fixes it. The section also leaves open whether `I` is the schema or its value (it is the value; `typeof Bars` gives a TS2345).
3. The keel-server skill says of `*.server.ts` files that "Browser builds stub those files". In a client-only app (`examples/static-client`, `adapter: "client"`) the `loadHome.server.ts` loader runs in the browser, as `keel docs k.router` (Execution) says. The skill misled me until the Chromium run showed the loader's text.

11. The keel skill sent me to `ctx.net` for HTTP. `.claude/skills/keel/SKILL.md` said "No ... `fetch` ... (E1601): use ... `ctx.net`", and `pnpm spec k.origins` (Conformance) gives `ctx.net.fetch(new Request('https://c.example/e'))` as the call a `connect` origin allows. My `modules/app/fetchReleases.ts` with `ctx.net.fetch(...)` failed `keel check`: `E1651 modules/app/fetchReleases.ts:10:35 ctx.net.fetch in app code; declare an endpoint in a service and call it`. `pnpm spec k.services` (Rules): "E1651 `ctx.net.fetch` in app code (no fix; declare an endpoint)". I rewrote it as `GitHubApi.schema.ts` (`endpoints`) and `githubApi.ts` (`service({ base })`), and added `@keel/services` to `package.json`. The skill line now names the service and E1651.
13. The keel-deploy skill did not say a `client` build writes `csp.txt` or that the static host sends it. Its Build paragraph listed `csp.txt` for a `static` deployable only, and "Host the client on a static host" spoke only of `KEEL_PEER_API`, which a client with no `node` deployable has no use for. `pnpm spec k.security` (Other deployables): "`keel build` writes their policy to `dist/<name>/csp.txt`". `pnpm spec k.hosting` (Artifact) also lists `index.html`, `assets/` and `keel-mark.svg` for a `client` and leaves `csp.txt` out. The skill now says both; the k.hosting Artifact sentence still omits `csp.txt`.
14. The keel-client skill said "All copy comes from a message set, never a literal" (E2406). `pnpm spec std.copy`: "In a module whose `deps` list `@keel/std-messages`, text a person reads comes from a message set". A marketing page with literal copy and no `@keel/std-messages` passes `keel check`; the skill read as if it would not. The skill now scopes the rule.

## Rough edges

4. `keel scaffold service app --openapi openapi.json` in `examples/openapi-import` writes files importing `@keel/services` and leaves `package.json` without it. `keel check` then prints `E1751 modules/app/AppApi.schema.ts:3:27 TS2307 Cannot find module '@keel/services'` twice with no fix. Expected: the scaffold adds the dependency, or `keel check` reports E1572 naming the package.
5. `keel scaffold project <name> --workspace` writes a `package.json` whose `check` script is `tsc --noEmit && biome check modules test`, without `keel check`, and with no `@keel/cli` in `devDependencies`; `apps/inspector` has both. I added both by hand in each example.
6. `keel scaffold service <module>` names the client after the module (`AppApi`, `api`), not after the service; `openapi(doc, { name })` takes a name, the command offers no flag for it. Closed by `--name` (RFC 0210, backlog 1013).
7. After the first `keel build`, a source change that `biome check --write` makes (an import reorder in `loadHome.server.ts`) turns `keel check` into `E1005 .keel/surface.json:1:1 generated .keel/surface.json does not match its sources; run keel build`. Expected: an import order change leaves the surface unchanged, or the message says which source moved.
9. A `node` peer that calls no other still needs every other peer's URL. In `examples/compose-peers`, `api` serves `/api/hello` and calls nothing; `PORT=8391 KEEL_SECRET=... node dist/api/server.mjs` exits with `E1560 KEEL_PEER_WEB fails DeployEnv (required); set it where the image runs`. `pnpm spec k.deploy` says so ("`KEEL_PEER_<NAME>` ... required per other `node` deployable"), and the reason is forwarding: a request for a path a peer serves goes to that peer (k.topology Calls and peers). So two peers started by hand each need the other's port before either starts; `tooling/smoke/examples.mjs` picks both ports first. The docs did not mislead me; the README says it.
15. A test cannot show that a client-only app sends no `/__keel/user` request. `test/clientOnly.test.ts` in `examples/client-only-api` routes every URL through `ctx.net` (GitHub, then `*` recording the rest) and asserts the only request is GitHub's, on first render, navigation and a second render. That holds whatever the app holds: `pnpm spec k.guards` (Client): "Under `renderRoute` its `user` option stands for the answer, and no GET is sent", so a project with `identity.ts` passes the same assertion. Only the built app in Chromium shows it; the `client-only-api` smoke step records every path the static server is asked for and finds no `/__keel/*`.
16. Getting from nothing to `examples/client-only-api` took 4 commands and 11 file edits. `keel scaffold project <name>` gives the shape in one step: one `client` deployable, no `node`, no `identity.ts`, and its `check`, `test` and `build` pass (scratch copy with the repository's packages linked). Then `keel scaffold route` twice and a `keel build` (finding 12). The edits: `origins.connect` in `topology.ts`; `@keel/services` in `package.json`; three new files for the API (`Releases.schema.ts`, `GitHubApi.schema.ts`, `githubApi.ts`), written by hand because `keel scaffold service` takes only `--openapi`; two pages and a masthead; `routes.ts`; two scaffolded `*.server.ts` loaders deleted; the test. The topology edit is the one line that makes a client call another origin; `pnpm spec k.scaffold` (Generators) has no option for it, which is fine.
17. Getting a page out of `keel scaffold project native-tauri --workspace` took one more scaffold and four edits. The project has module `app` with an empty contract and an empty route table; `keel scaffold route app.home --path /` adds `HomePage.tsx` (`<Box />`), `loadHome.server.ts` (`ok({})`) and a route test that asserts only the route id. A one-page app with no data has no use for the loader: I deleted it, dropped `loader` from `routes.ts`, wrote the heading and note in `HomePage.tsx`, added `Masthead.tsx` as `examples/static-client` has it, and replaced the test. Expected: `route` with no `--loader` flag or a page-only form for a `client` deployable (finding 16 names the same loader).
18. Adding the shell was all by hand and the versions came from `apps/golden-1/package.json`. `keel scaffold project` gives `adapter: "client"`; `shells: { tauri: { id, name } }` in `topology.ts`, `@keel/std-tauri` and `@tauri-apps/cli` `2.12.4` (or, for Capacitor, `@keel/std-capacitor`, `@capacitor/app` `8.1.2`, `@capacitor/core` `8.6.0`, `@capacitor/preferences` `8.0.1`, and `@capacitor/android`, `@capacitor/cli`, `@capacitor/ios` `8.6.2`) are mine to write, then `pnpm install`. `keel check` does say which plugin is missing (E1572 with the `package.json` line to add, tried by removing `@capacitor/app`); it does not name the std package or the CLI and platform packages the native build needs, which only the build's failure shows. `pnpm spec k.scaffold` (Generators) has no shell option.
19. `keel build --target tauri` in `examples/native-tauri` fails without `KEEL_ORIGIN`: `E1574 KEEL_ORIGIN must be an https: origin (http: on localhost only)`; `--target capacitor --platform ios` says the same. The app is one `client` deployable with no server and no `/__keel/*` request (the smoke step records none), so the origin it asks for is one nothing in the app calls. The builds pass with `KEEL_ORIGIN=http://localhost:4182`, the value CI's shell jobs set. Expected: no origin required when the project has no `node` deployable, `identity.ts` or `connect` origin. `pnpm spec k.shell` states the requirement for a shell build without a condition.

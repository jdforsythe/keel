# P1 and P2 plan

Backlog 0962. This plan turns `tasks/p1/INPUT.md` into workstreams, gates and an order. Every point in INPUT.md lands in a workstream; the table in "Where INPUT.md lands" checks that. The freeze review is its own document (`tasks/0963-to-p1/freeze-review.md`, backlog 0034) and this plan only cites it.

Phases:
- **P1, ready to be seen.** Everything a stranger meets is built, fixed, reviewed by outside auditors and checked by an eval, on the current repository. Nothing is announced. No app is deployed until the weakness gate (W2) is green.
- **P2, launch.** The fresh repository replaces this one, the packages go to npm as a 0.x preview, the site goes live, outsiders arrive, and the preview becomes 1.0 once the freeze has held.

## Goals and exit criteria

### P1 goals
1. The kernel sections are frozen for the 0.x preview and every open weakness is fixed.
2. Outside reviewers have audited accessibility and security, and their findings are closed.
3. An agent and a person can each learn Keel from the public material alone.
4. The site, built in Keel, shows what Keel does with evidence behind every claim.
5. The repository and packages are ready to publish in one step.

### P1 exit criteria
Each is a command, a file or a report someone can check.
- [ ] Every kernel section in `spec/` has status `frozen`, as the freeze review lists (`grep -L "status: frozen"` over the kernel sections prints nothing).
- [ ] Zero open weakness lines: the triage list `tasks/p1/weaknesses.md` (W2.1) has every line checked, and `tasks/BACKLOG.md` holds no unchecked line it names.
- [ ] golden-3 exists in `apps/golden-3`, built by an agent run of its eval after W5's agent docs and skills exist, reading what a public user's agent reads, and the eval converges (`evals/results/*-golden-3-claude-*.json`, converged true).
- [ ] The external accessibility audit report on golden-3 and the site lists no open WCAG 2.2 AA failure; S6 is CLOSED in `tasks/STAGES.md`.
- [ ] The external pen test report lists no open critical, high or medium finding; each low finding is fixed or published as a residual in `docs/THREAT-MODEL.md`.
- [ ] Every package's mutation score is at or above its threshold with each survivor killed or justified (backlog 0749), and `tooling/ledger/evidence.json` and `tasks/COVERAGE.md` are generated by CI from a clean checkout (backlog 0877, 0892).
- [ ] `pnpm eval --task public-docs` converges with Claude and with Codex, each reading only the docs shipped in the installed packages.
- [ ] A person who has not read the repo explains Keel's parts from the diagrams alone, and writes the result into `tasks/p1/newcomer-review.md` (ROADMAP P1).
- [ ] The walkthrough app builds, every layer's tests pass, and each chapter has run once as an agent eval.
- [ ] The site builds with Keel, passes `keel test` with zero axe violations, serves its CSP, meets its budgets and is deployed to a staging address.
- [ ] Every number on the site is read from `tooling/ledger/evidence.json` at build time, and a check fails when copy states a number by hand.
- [ ] The docs sweep and reset (backlog 0229) is done: a check finds no RFC, ADR or backlog number in tracked docs, READMEs, spec text or code comments, and the new ADR set is verified against the code.
- [ ] Release hygiene is green: `LICENSE` states all rights reserved and the root package is `UNLICENSED` (0941), packages private until launch (0943), `.gitignore`, `SECURITY.md` and `CONTRIBUTING.md` in place (0944), and the home-path and quotation check passes (0946).
- [ ] `changeset version` and `pnpm publish --dry-run` with provenance succeed for every `@keel/*` package in CI.

### P2 goals
1. Keel is public: one fresh repository, published 0.x packages, a live site.
2. Outsiders can use, report and propose through a written process.
3. The 0.x preview becomes 1.0 once the frozen kernel holds under outside use.

### P2 exit criteria
- [ ] The fresh public repository exists and the old one is private; the fresh tree passes `pnpm check`, `pnpm test` and `pnpm build` in CI on its first commit.
- [ ] Every `@keel/*` package is on npm at the 0.x preview version with provenance, and a CI job on a clean runner runs the scaffold from npm and `keel check` on the result.
- [ ] The site is live at its domain, served by Keel, with its CSP, and its staging audit findings stay closed on the live build.
- [ ] `SECURITY.md` names a reporting address that a person answers; the RFC process for outsiders is in `docs/RFC.md` with numbering restarted.
- [ ] A person outside the project builds an app from the public docs and files what they hit; each report has a backlog line.
- [ ] The licence is chosen by the operator and committed in the fresh repository, and every `@keel/*` package carries a `license` field that matches it.
- [ ] The move from 0.x to 1.0 holds: four weeks pass on the preview with no kernel semantic change (no `major` or `minor` changeset on a kernel package that alters behaviour a spec section states) and no frozen section reopened (no kernel spec section leaves `status: frozen` in the git log of that period); 1.0.0 is published and the site says so.

## Workstreams

Tiers follow `docs/WORKFLOW.md` Delegation: haiku for mechanical work, sonnet for routine scripts and tests, opus for design and judgment. "Concurrent" names the steps that can run at the same time; the rest run in order. The machine is shared: at most two test-running lanes at once, and one mutation run at a time.

### W1 Freeze
Outcome: the kernel sections are `frozen` at the start of P1. A section may be reopened before 1.0 through an RFC; the intent is not to need it, and the 0.x preview tries the freeze out.
1. Read `tasks/0963-to-p1/freeze-review.md` and decide each open item (opus, orchestrator).
2. Close the items the review marks as blocking: k.topology clauses (0349), the k.shell section, missing conformance (each its own lane; sonnet conformance-writer, then sonnet build).
3. Flip each kernel section to `frozen` in one commit with the review cited in the message (haiku).
- Concurrent: steps 2 and 3 follow step 1 section by section.
- Gate: every kernel section `frozen`.
- Needs a person: the operator decides the freeze (WORKFLOW "Humans").

### W2 Weakness clearance
Outcome: no open weakness in the backlog before anything is published or deployed (INPUT, gates carried into P1).
1. Triage every unchecked backlog line (297 on 2026-11-19) into one of three lists in `tasks/p1/weaknesses.md`: a weakness (fixed in P1), work for the docs sweep (W12), or a feature idea (moved to `tasks/FUTURE.md` with a reason). A weakness is any line tagged high, medium, red-team or security, any a11y or privacy gap, any missing conformance, and any low line where a user's data, a user's access or a false claim is at stake (opus).
2. Group the weaknesses by package into lanes of one context window each (opus, orchestrator).
3. Fix lanes, disjoint packages in parallel, kernel changes through an RFC under the RFC defaults (sonnet; opus for a kernel change).
4. A red-team pass over the batch diff and the principles; its findings go back into step 3 (opus, `red-team` subagent).
5. Re-run step 1 on lines filed since; the gate needs the list empty, not shrinking.
- Concurrent: step 3 runs up to two test-running lanes and any number of reading or writing lanes.
- Gate: every line in `tasks/p1/weaknesses.md` checked, and the red-team pass files no new high or medium line.
- Needs a person: the operator confirms the triage list once (decision O1).

### W3 Evidence and coverage
Outcome: the evidence is as high as the code allows and is generated, never typed.
1. Per-package survey of ledger rungs, survivors and coverage, ranked by security weight (backlog 0749 opening; sonnet).
2. Gates on the evidence data: refuse a dirty tree (0877); fail when a committed ledger or evidence file differs from what the tree produces (0892) (sonnet).
3. Mutation runs package by package, when the machine is quiet, and tests that kill survivors (sonnet; one run at a time).
4. Lift ledger items up the rungs where a proof or an exhaustive run is feasible (opus picks the targets, sonnet writes the tests).
5. Coverage published: `pnpm coverage` in CI writes the per-package table the site reads (sonnet).
- Concurrent: steps 1 and 2 at once; step 4 alongside step 3 on other packages.
- Gate: every package at or above threshold with survivors justified; evidence and coverage produced by CI from a clean checkout.
- Needs a person: none beyond the standing word on mutation runs.

### W4 External reviews
Outcome: an outside accessibility audit and an outside pen test, both passed (S6 exit, ROADMAP P1).
1. Scope documents: what is tested (golden-3, the site, the scaffold output), the threat model, test accounts, the evidence bundle, the a11y target (`docs/A11Y-TARGET.md`) (opus).
2. Readiness pack: staging deploys of golden-3 and the site, seeded data, `docs/THREAT-MODEL.md` brought current (0944), `SECURITY.md` draft (sonnet).
3. Vendor shortlist with cost and lead time for each review (opus drafts; the operator picks).
4. The reviews run. The orchestrator answers the reviewers' questions from the repo.
5. Findings become backlog lines and run through W2's fix lanes; reviewers retest.
- Concurrent: steps 1 and 3 start at once; the reviews themselves wait for W2 and W5, whose last step builds golden-3 (testers should not find what the backlog already lists).
- Gate: both reports closed as in the P1 exit criteria; S6 CLOSED.
- Needs a person: the operator chooses vendors and pays; the reviewers are outside people.

3. Agent entry files emitted by the scaffold: `AGENTS.md` for Codex and other agents, `CLAUDE.md` that points at it, both pointing at `node_modules` paths and `keel docs` (sonnet).
4. Skills by kind of work: client (components, forms, widgets, text), server (API, storage, writes, realtime), testing and correctness, deploy and shells, compliance. Reconcile each with the spec (backlog 0222) and package them for Claude skills and for Codex (opus designs the split, sonnet writes each skill in parallel).
5. The MCP server (`packages/cli/src/mcp.ts`) documented as the third reading path, inside its 1750-token tools-list budget (sonnet).

8. Fix what the golden-3 run finds in the kernel or std (lanes by package; sonnet; a kernel fix on a frozen section is a reopen and goes through an RFC).
- Concurrent: step 4 skills in parallel lanes; steps 2 and 3 in parallel once step 1 is decided; step 7 waits for steps 2 to 6 and for the golden-3 eval lane in 0963.

## Steal list

All from memory, not checked against the live sites on 2026-11-19; W11 step 1 verifies each. Each item names the site, the thing, and what Keel takes.

1. **Rust compiler error index** (`rustc --explain E0308`, the online index): every error code has a page with a failing example and the fix. Keel takes it as the diagnostics index generated from `@keel/check/explain`, one page per code with the fix diff.
2. **Rust doc-tests** (rustdoc runs code blocks in docs as tests): Keel compiles and type-checks every code block in its docs in CI (W6 step 6).
3. **docs.rs** (docs for each crate version, built from the source): Keel ships docs with each package version and the site shows the same source per version.
4. **The Rust Book and "Why Rust" on rust-lang.org**: a long-form book beside a short "why" page built on three claims. Keel's why page leads with three claims, each linked to evidence.
5. **react.dev reference pages**: one layout for every API (signature, parameters, returns, caveats, usage, troubleshooting) and a hard split between Learn and Reference. Keel's generated reference uses one fixed layout per export.
6. **react.dev pitfall and deep-dive blocks**: marked asides that hold the mistakes people make. Keel puts each diagnostic a reader is likely to hit beside the step that causes it.
7. **Svelte tutorial** (svelte.dev): an editor and live preview side by side, steps grouped in parts, a "solve" button that shows the answer. Keel's walkthrough shows each layer's diff and a check command in the same place.
8. **Svelte and others' `llms.txt`** files: a plain-text index of the docs for agents. Keel can publish one on the site, generated from the same source the packages ship.
9. **Tokio tutorial** (mini-redis built step by step) and **Ember's Super Rentals**: one app grown chapter by chapter. The model for the walkthrough app.
10. **Next.js Learn course**: chapters with progress and a finished, deployed app at the end. Keel takes the progress list and the "check your work" step.
11. **Django docs**: docs split into tutorials, topic guides, how-to guides and reference, the four kinds Diátaxis names. Keel's docs follow the same four kinds (W6 step 5).
12. **Go Tour and pkg.go.dev**: runnable steps, and reference docs per module version with the source a click away. Keel links each reference page to the source at the released tag.
13. **TypeScript playground**: compiler output beside the input with shareable links. Recorded in FUTURE for Keel (compiler output, `.keel/` artifacts and diagnostics beside the source); not built in P1 (decision O8).
14. **Vite "Why Vite"**: states the problem with existing tools before the answer, then the answer, with no adjectives. Keel's why page takes that order.
15. **Elm's home page and compiler messages**: leads with a class of error the language removes and shows the compiler message as the hero. Keel's home page shows a diagnostic with its fix diff as the first image.
16. **htmx essays** (htmx.org/essays): a section of design essays that argue ideas, apart from the docs. Keel's "Ideas" section (W9 step 6).
17. **Stripe API reference**: three columns with the request and the response beside the prose, a copy button on every sample. Keel's reference puts the schema, an example value and the generated type beside each other.
18. **Tailwind CSS docs**: search on one keystroke, and pages that show the code and the result together. Keel's search is built at build time and opens on one keystroke.
19. **Bun home page**: benchmark charts with the method linked. Keel's evidence numbers each link to the job or file that produced them.
20. **Astro docs** (Starlight) and **Laravel docs**: a version switch at the top of every page. Keel's site takes the version switch (W8 step 5).
21. **Playwright trace viewer screenshots**: a recorded run shown as a timeline of actions, DOM and network. A model for showing a replayed Keel session.
22. **Rust RFCs repository**: a template, a public comment period and a final decision. A model for the outsider RFC process in P2.

Where Keel does better than these: every number on the site comes from the ledger at build time; every claim names its rung; every diagnostic page is generated from the checker that prints it; and docs for agents and people come from one source, shipped with the version installed.

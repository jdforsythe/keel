## Ranked list (most costly first)

Scope: one Claude golden-3 run (3 iterations, not green) and one Codex Recipe box run (green in 1). Nothing below is fixed here.

1. **The kit ships two type entries that do not exist.** `@keel/compiler` exports `./client` as `./dist/src/client.d.d.ts` and `@keel/runtime-dom` exports `./jsx-runtime` as `./dist/jsx-runtime.d.d.ts` (the source has `./src/client.d.ts`; the doubled `.d.d.ts` comes from the publish rewrite, and neither file is in the tarball: `tar tzf keel-compiler-0.0.0.tgz` lists no `client.d.ts`; runtime-dom ships `jsx-runtime.d.ts` at the package root only). Effect: `TS2688 Cannot find type definition file for '@keel/compiler/client'` and `TS2875` on every JSX tag, `If` and `Form` children typed as bare `Node`, E1751 x3. This alone kept golden-3 from green across 3 iterations and $3.43. Fix: correct the export rewrite and ship the files; a pack lint that every `exports` target exists in the tarball. Why `eval:public prove` stayed green with it: its check runs on a project that uses neither; add a JSX `If` + `Form` page to the prove project.
2. **E1751 hides the root cause and points the wrong way.** `keel explain E1751`: "TS type error with no Keel rule code; correct the types as the TS message says". The agent did exactly that (iteration 1: `{() => (...)}` wrappers on `Form`/`If` children), which turned 3 E1751 into E1403 ("elements from a function, call or binding; write the JSX inline"), and it spent about 10 tool calls on it. Codex hit the same E1751 then E1403 pair. Fix (diagnostic wording): when TS2688/TS2875 is present, report one Keel code for it first ("the kit's types did not resolve: reinstall; this is not an app error"), and have E1751's text say "if the message is about `children` of `If`, `Form` or `For`: write the children inline, never a function".
3. **A kit defect looks the same as an app defect to the agent, and the loop gives it no way out.** Iterations 2 and 3 each stopped ("blocked: the installed kit has no file for ...") and left the tree as it was, which is the honest behavior, but the harness sends the same `pnpm check` output again and pays for two more runs (about 60% of the 890s were not iteration 1). Fix (harness): end the run as `kit-defect` when the same check failure comes back with no diff to the tree; (skill sentence in `keel`): "If `pnpm check` reports TS2688 or TS2875, run `keel doctor` / stop and say the kit is broken; do not edit `node_modules`." (needs the doctor command or a check code).
4. **The harness never tells the agent why `pass()` is false.** Iteration feedback is `pnpm check` and `pnpm test` output only. `converged=false` for golden-3 also because of `no properties( for signUpTx` (three times in the log), which the agent never saw. The agent wrote `properties(fresh().signUp, ...)`; the checker needs the name `signUpTx` inside the call. Fix: send `pass()`'s reason in the feedback; and word TASK.md line 48/56 as the checked shape (`properties(<name>Tx ...)`), or make the checker accept the store field.
5. **`keel docs std.*` fails until the package is a dependency.** Claude edited `package.json` and ran `pnpm install` for `@keel/std-text` and `@keel/std-sessions` only to read their docs (about 6 calls), Codex got `E1065 std.i18n is in @keel/std-i18n, w...` and had to reorder. Fix (skill sentence, `keel`): "a std module's docs open only after it is in `package.json`; add the std packages the task names first, then read `keel docs std.<name>`." Or: E1065's text should end with the exact `pnpm add` line.
6. **Docs are read from `node_modules` `.d.ts` files, not from the docs.** Claude: ~25 of 82 calls were `cat node_modules/@keel/*/dist/...d.ts` or `grep` there (`For`, `Form`, `FormProps`, `schema` types, `testing` types); Codex the same (`If.d.ts`, `For.d.ts`, `Form.d.ts`, `Signal.d.ts`, `StyleProps.d.ts`). Fix: one line per component in `keel-client` with the props (`Form`: `children?: () => ...` written inline; `For each key`; `If when fallback`), since the reader goes to the type file when the skill is silent.
7. **`keel scaffold module sessions` accepted a stdlib id.** The agent scaffolded a module with the id of `@keel/std-sessions`, then removed it by hand with `rm -rf` and rewrote `topology.ts`. Fix (diagnostic): refuse ids that a std module uses, with a code and the sentence "`sessions` is a std module; name the module for what it does". Also the starter's `app` module had to be deleted by hand: the scaffold's first step in the `keel` skill should say so.
8. **Probe and audit are flaky or leave no evidence (harness).** (a) The agent's probe answer named its own empty auto-memory path once in four; `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` in the harness's agent environment stops that. (b) The V0009 finding cuts the command at 120 characters and the transcript is deleted on failure: keep `transcript-N.jsonl` and print the matching root. (c) `/tmp` is shared: an agent used `/tmp/kd`, another lane's folder of Keel doc dumps; give each run a private `TMPDIR`. (d) `eval:h2h` rewrites tracked `pnpm-lock.yaml` and removes the built app and transcript at the end.
9. **A run gives no sign of life for 10 to 15 minutes.** `pnpm eval` prints nothing until an iteration ends; a stopped run loses its transcript (attempt B). Fix: write each tool call to the log as `stream-json` arrives, and keep the transcript when a run is killed.
10. **Codex wrote its own server start and not-found scripts** (`scripts/start.mjs`, `scripts/notFound.server.mjs`, a localized not-found shell for unmatched paths), and ran `keel codemod place ... --adapter node` with one nonzero exit first. To check against the docs: whether a documented, supported way to render a not-found page and to start the built server exists; if it does, `keel-deploy` does not surface it (Codex read `keel-deploy` first and still went to `node_modules/@keel/server/dist/src/node/start.js`). Fix: a `keel-deploy` sentence naming the supported start and not-found paths.

## Conformance notes (for the implementation lanes)

Not covered (no Conformance sentence): `maxStreams`, `close()` on the handle, 404 for unparsed params, the name and id prefixes, the heartbeat.

- k.sync (seven files in `packages/store/conformance/`, two in `packages/ctx/conformance/`, one in `packages/server/conformance/`, committed red). Readings where the spec is silent: `tx` with a held `key` is asserted only as `ok`; two stores saved by one action give two `save` events compared without order; a `key` freed by `undo` or by folding out of the kept log commits again; `setOnline` with the current value is not tested; `key` length outside 1 to 64 and a negative or fractional `base` are not tested; an offline stream's `read()` may reject in any way. The server file observes the same ctx object passed to `createApp` (a spread of the sim ctx with map storage) and relies on `save` observers firing synchronously after both stores are stored.
- std.live (eight files) and std.offline (ten files), each with `fixtures.ts`, committed red; the tests were not type-checked by their writer. Readings: the outbox reads `data.transaction` and `data.head` from a k.server err body on a 409, and the fixture endpoints declare `errors: { 409: s.json() }`; `outbox(...)` returns the client store (`o.log()`, `o.get('entries')`), persisted under `keel.outbox.<id>` as `{ entries }`; a `failed` result's `error` has a `code` (`offline.full`); flush on net online is exercised after `drain`, the timer retry after `send` alone; std.live's stale-read clause is tested as "committed reads rise in start order". std.live's sim server is hand-built from `ctx.net.route`, so `two-callers` does not exercise std.channels' server. Not covered (no Conformance sentence): std.live `denied`, a failed read retried at the next event, the status between a drop and a reopen.
- D17 (orchestrator) an outbox entry answered with a 502 `keel.unreachable` follows k.services with no rule of its own: through a `module` service it is `api.network` and stays `queued`; through a `base` service it is `api.status` and is `failed`. - D18 (orchestrator) the outbox needs the conflict's head, so an `outbox` api endpoint declares its 409 error; the offline lane implements what the fixtures do and reports whether `outbox` should refuse an endpoint without it (a check rule or a throw is a spec change, not taken in this batch).
- std.multi (six files and `group-fixtures.ts` in `packages/std-sessions/conformance/`) and std.conflicts (eight files and `fixtures.ts`), committed red. `@keel/std-conflicts` gained devDependencies on reactive, router, ui and ctx for its fixtures.

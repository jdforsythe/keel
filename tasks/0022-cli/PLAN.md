## Decisions
- D1: One `Input` type (union of all fields, all optional); each operation's `input` is an `s.object` over its subset. Binary flags go through `input.decodeStrings` (coercion + validation), MCP arguments through `input.parse`; every schema issue is E1052 (`issueDiags`). Extra checks, also E1052: unknown flag, single-dash flag, flag given twice, missing value, extra positional, `--limit` < 1.
- D2: Positionals are named input fields (`check paths[]`, `spec id`, `explain code`, `inspect what`, `render target`, `scaffold|codemod op args[]`); a positional field is not also a flag (`explain --code X` is E1052: one way).
- D3: Exit code: 2 if any E1051/E1052, else 1 if any E diag (before `--code` filtering), else 0. `--code` filters display only; the summary counts all.
- D4: No timing in the summary (`{ kind, ok, name, counts }`): byte-identical output for equal input. Trailer `ok check 2 files, 0 errors, 0 warnings`.
- D5: Render: groups in first-appearance order (diags by code, others by kind), summary last. Compact/pretty cap diags at 5 per code, `--limit N` overrides, `--verbose` uncaps; other kinds capped only by `--limit`; json capped only by `--limit` (no "more" line). More line: `... +K more CODE (keel <cmd> --code CODE)` (k.check wording).
- D6: The cli's own record kinds (`spec.section`, `spec.cite`, `explain.text`) are registered through the same registry at startup; they are not kernel kinds. `spec`/`explain` output is therefore never a `diag`, so it never fails the exit code.
- D7: Diag key order `kind, code, path, line, col, message, see, fix` (compiler and `@keel/check` order, not OUTPUT.md's example order) so `keel check --format=json` is byte-identical to the compiler's diagnostic (k.check Conformance). `test/passthrough.test.ts` asserts it.
- D8: (superseded in part by 6fc287c: I1055 is now in k.cli Rules) I1055 "<cmd> not available: needs <pkg>" for commands whose package has not landed, and for `spec` when the project has no `spec/*.md`. **Not in the spec** (k.cli Rules name E1051-E1054 only; `session` -> E1051 is the only reserved-command rule, and the Commands table forbids E1051 here). Needs an RFC adding I1055 to k.cli Rules, or a different answer.
- D9: (superseded by 6fc287c: cli is now last in deps order; see D19-D24) `@keel/testing` (`renderRoute`) and `@keel/scaffold` (`scaffold`, `plan`) are exported now, but both are later than cli in `tooling/deps.json` (S0003: a package may import only earlier packages), so cli does not import them: `keel test` in-process returns the empty-run summary; the binary spawns `npx --no-install vitest run [paths]` with `KEEL_TEST=1`. `render` reports I1055. Wiring `render`/`scaffold` needs a deps-order change (RFC) or a plugin seam.
- D10: `keel ledger` ports tooling/ledger.mjs pure over `io.files` (`src/internal/buildLedger.ts`, `scrubCode.ts`): exported functions in `packages/*/src/*.ts`, rung from referencing test/conformance files, `evidence` = first referencing file. `--diff` reads `.keel/ledger.json` or `tooling/ledger/ledger.json` from `io.files` and reports E1706 (k.testing) per lowered rung. Spec-clause items (`k.router#3`) and the unsafe-count regression (tooling L0001) are not ported.
- D11: `a11y` records are flattened nodes with `depth` (schemas are not recursive). `req`: `{ method, path, route?, status, ms }`.
- D12: MCP: hand-rolled newline-delimited JSON-RPC (`@modelcontextprotocol/sdk` is not installed). Tools carry `inputSchema` (JSON Schema of the operation input via `toJsonSchema`) and `outputSchema`; results carry `content[0].text` (compact unless `format` given) and `structuredContent.records`. Unknown tool -> E1051 result, `isError: true`.
- D13: LSP: hand-rolled Content-Length framing; full sync; diagnostics from the same `runCheck` with open documents overlaid on project files. Code actions: see D23.
- D14: `run(['mcp'|'lsp'], { stdin })` serves the whole stdin and returns the replies; the binary streams through the same `StdioServer`. `mcp --help` is E1052 (no flag outside the schemas; satisfies "not E1051").
- D15: Type `StdioServer`, not `Session`: "session" is a glossary term.
- D16: `check(files, {})` is called without `root`: the in-process `cwd` may be fictional; the binary's process cwd equals `io.cwd`.
- D17: `bin` is `./dist/src/bin.js`: the committed build tsconfig (eed24ae) has `rootDir: "."`, so `dist/bin.js` would not exist.
- D18: `@keel/check` `explain` answers unknown codes with text ("not a known code"), so `keel explain <unknown>` exits 0 with that text; the E1052 branch only fires if explain throws or returns empty.
- D19: (apply/scope superseded by D27) Effects. `execute` returns `{ records, writes }` (`internal/Outcome.ts`); `runEngine` keeps writes only when the exit code is 0; `run` drops them (pure); the binary applies them (`applyWrites`: existing files keep their mode, read-only ones are unlocked for the write; `readonly` writes end at 0444); `mcp(provide, apply)` applies them for successful tool calls.
- D20: scaffold/codemod: generators (project, module, route, component, store) under `scaffold`, codemods (rename, move, add-field) under `codemod`; the other command's op is E1052 with a hint; spec-named `transaction`/`service` (not in `@keel/scaffold`) are I1055; no op is an empty run (the commands-accepted conformance runs `scaffold` bare). argv -> scaffold input in `scaffoldInput.ts` (first positional is the id/name; `--path`, `--file`, `--adapter`, `--to`, `--kind`, `--default` as JSON else string). `rename` without `--kind` tries component then schema (PascalCase) or store then route. Refusals flow through as their diagnostic (E135x, E1005, E1052) plus the E1353 `cause` as a second diagnostic. Records are `scaffold.edit` `{ action, path, diff? }` (a cli kind, not `req`: `req` is the dev-server request record and does not fit an edit); `--dry-run` uses `plan` and carries unified diffs (`unifiedDiff.ts`, LCS, 3 context lines).
- D21: (collector superseded by D25) test: `startVitest('test', paths, { root: io.cwd, watch: false, reporters: [collector], env: { KEEL_TEST: '1' } })` with vitest's stdout/stderr discarded; process `exitCode` and `KEEL_TEST` restored. The collector (`collectResults.ts`) reads the same task tree as tooling's KeelReporter and yields the same T0001 records, but returns them instead of printing (KeelReporter writes to process.stdout and lives in the private `@keel/tooling`). Runs only when `io.files` has a test file or vitest config, so in-memory projects never start vitest. Failed tests fail through the summary (`exitCode`: summary `ok: false` -> 1), since T0001 is not an E code.
- D22: build: `compile` over app sources (no tests, no `*.config.*`, not `.keel/`); diagnostics flow through; with no error, `.keel/{a11y,deps,ids,styles}.json` as `{ data, hash }` canonical JSON, read-only. `routes.json` is left to the Vite plugin (it evaluates `routes.ts`). The binary then runs `npx --no-install vite build` when `vite.config.ts` exists (output captured; tail on stderr on failure, exit 1). `dev`: the binary hands the terminal to `vite` when the config exists; else (and always in-process) I1055.
- D23: LSP code actions: `textDocument/codeAction` returns one `quickfix` per stored diagnostic in range with a `fix`; `diffEdits` turns each hunk into a TextEdit replacing its old lines with its context+added lines, per `+++ b/<path>` file (root-relative -> `file://` URI). Property: applying `diffEdits(unifiedDiff(p, a, b))` to `a` gives `b`.
- D24: ledger: items are exported functions (port) plus every spec Conformance bullet (`<id>#<n>`, 1-based) whose evidence is the conformance files with a `// Spec:` header naming the section and quoting the clause. Evidence is static (`evidenceOf`: fast-check file -> `property` with its largest literal `numRuns`, else 100, and literal seed; else `example`; assumed passing); rungs from `@keel/testing` `ledger`, `--diff` through `ledgerDiff` (E1706). Record `evidence` is a one-line description of the strongest piece. Committed ledger read is still the tooling format (exports only).
- D25: Test results: the pure part of tooling's KeelReporter (task-tree walk, app-frame extraction from parsed `stacks` or `stack` text, compact diff, messages) moved into `@keel/testing` as `testResults(files, errors, cwd) -> TestReport`; `tooling/vitest-reporter.ts` imports it by relative path (tooling is private and `@keel/testing` devDepends on it, so a package dependency would be a cycle) and keeps only timing and printing; `keel test` uses it too. Cause of the old `1:1`: errors reaching `onFinished` carry `stack` text, not parsed `stacks`, and the cli collector read only `stacks`. Frame regex now requires a path start (`/` or `X:\`), so `node:internal/...` no longer parses as a drive path. Failed tests now carry the compact diff as `fix`.
- D26: One throw never silences a server: `mcpHandle` and `lspHandle` catch per message (request -> -32603 with its id; LSP notification -> `window/logMessage` type 1); `serveStream` also catches per chunk. `decodeURIComponent` goes through `safeDecode` (rootUri, document URIs).
- D27: The engine owns file scope and effects: `Operation.scope` (`none | query | tree`), `Io.load(scope)` (used when `Io.files` is absent, via `withFiles`), `Io.apply(writes)` called by `perform` for a successful run (exit 0). `perform` is shared by `runEngine` and MCP `tools/call`; LSP loads `query`. The binary builds one host `Io` and calls `run` for every command, `mcp`/`lsp` included: `Io.stdin` may be a stream with `Io.emit` (served incrementally by `serveStream`, LSP `exit` ends it). `serve.ts`, the bin's scope lists, and `mcp`'s `apply` parameter are gone.
- D28: `applyWrites` resolves every path against the cwd first and rejects the whole set (throws, nothing written) if any resolves outside it (absolute, `..`, or the cwd itself). A throw, not a diagnostic: `@keel/scaffold` never produces such paths, so it is an invariant breach (k.errors: boundary for the unexpected).
- D29: JSON-RPC classification in `readRpc`: unparsable -32700; batch, non-object, missing `jsonrpc: "2.0"`, no string `method` (responses included), or a bad id type -32600 (with the id when readable); notifications get no reply. The LSP framer yields `{ body } | { error }`: a header block without Content-Length is skipped and answered with a -32700 error frame.
- D30: `keel check` parses the project root `topology.ts` with `parseTopology` (now exported from `@keel/compiler`) and passes `{ topology, root: cwd }` to `check`; `root: cwd` lets the TS step resolve `@keel/*` from the project, not the process cwd. The topology is read from the whole project, not the `[paths]` subset. `test/golden.test.ts` runs the engine over apps/golden-1 (files via node:fs) and expects zero diagnostics.

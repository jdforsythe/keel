## Decisions
- D1: the Action calls the `keel` binary through the project's package manager (`pnpm exec keel session ...`) so it runs app code under `keel test` as the commands do; issue traffic goes through the GitHub REST API with `GITHUB_TOKEN` and an injected `fetch`, no third-party action dependency.
- D2: the live S1-exit run is the user's: it needs a reachable ingest URL and the repo secrets.
- D3: wiring. k.cli reserves only the `session` std command (`stdCommand` throws E1053 for another name), so the Action is a bin, `keel-session-action` (`src/actionBin.ts`), over `runAction(io)` (subpath `./action`, `src/action/index.ts`). action.yml runs `pnpm exec keel-session-action` in `working-directory`; `runAction` spawns `KEEL_COMMAND` (input `keel`, default `pnpm exec keel`) per `keel session` op. This repo passes `node ../../packages/cli/src/bin.ts`, since no app depends on `@keel/cli` and its bin points at `dist`.
- D4: exit 1 when the ingest fails, a GitHub call fails (E1056), or the env lacks url/repo/token (E1052); a session that does not replay, minimize or emit leaves 0. A silent GitHub failure would stop issues with a green nightly.
- D5: secrets. `keel` children never get `GITHUB_TOKEN`; only the ingest gets `KEEL_SESSIONS_TOKEN`; a `Link: rel="next"` outside `GITHUB_API_URL` is not followed. Output record kind `session.issue` (docs/OUTPUT.md).
- D6: node from `node-version-file: package.json` (`engines.node`); the workflow skips itself while `vars.KEEL_SESSIONS_URL` is empty.

## Decisions
- D1: the Action calls the `keel` binary through the project's package manager (`pnpm exec keel session ...`) so it runs app code under `keel test` as the commands do; issue traffic goes through the GitHub REST API with `GITHUB_TOKEN` and an injected `fetch`, no third-party action dependency.
- D2: the live S1-exit run is the user's: it needs a reachable ingest URL and the repo secrets.
- D3: wiring. k.cli reserves only the `session` std command (`stdCommand` throws E1053 for another name), so the Action is a bin, `keel-session-action` (`src/actionBin.ts`), over `runAction(io)` (subpath `./action`, `src/action/index.ts`). action.yml runs `pnpm exec keel-session-action` in `working-directory`; `runAction` spawns `KEEL_COMMAND` (input `keel`, default `pnpm exec keel`) per `keel session` op. This repo passes `node ../../packages/cli/src/bin.ts`, since no app depends on `@keel/cli` and its bin points at `dist`.
- D4: exit 1 when the ingest fails, a GitHub call fails (E1056), or the env lacks url/repo/token (E1052); a session that does not replay, minimize or emit leaves 0. A silent GitHub failure would stop issues with a green nightly.
- D5: secrets. `keel` children never get `GITHUB_TOKEN`; only the ingest gets `KEEL_SESSIONS_TOKEN`; a `Link: rel="next"` outside `GITHUB_API_URL` is not followed. Output record kind `session.issue` (docs/OUTPUT.md).
- D6: node from `node-version-file: package.json` (`engines.node`); the workflow skips itself while `vars.KEEL_SESSIONS_URL` is empty.
- D7 (review + red-team 0242-0250): the bin is `./dist/src/actionBin.js` as @keel/cli's is, so it runs from a published install; action.yml runs the installed bin. This repo's workflow builds `@keel/std-sessions` before the Action (pnpm skips a bin whose target is missing and the Action's second install links it) and passes `keel: node ../../packages/cli/src/bin.ts`; the exception is documented in the source's `$comment`, which the generator does not emit. README pins `jdforsythe/keel/packages/std-sessions/action@<tag>` and states that the ref must match the lockfile's std-sessions version.
- D8: SHA pins resolved with `git ls-remote`: checkout 11d5960 (v4.4.0), setup-node 49933ea (v4.4.0), pnpm/action-setup b906aff (v4.3.0, what `v4` points at). The generator emits `owner/repo@<sha> # vX.Y.Z` unquoted. `pnpm install --frozen-lockfile` runs in `working-directory`; `--ignore-scripts` not added (not asked; esbuild/vite installs).
- D9: per fingerprint, files replay newest first until one reproduces; a step failing with only E2004 is an outcome, any other code fails the run (exit 1). Not reproduced: comment with marker `<!-- keel-session: not reproduced -->`, skipped when the newest comment (the `rel="last"` page) carries it.
- D10: one sanitiser `clean` (ANSI, C0/C1 controls incl. newlines, length cap) on every printed field and the title; route id and code must match `^[A-Za-z0-9_.-]{1,128}$` (E2002, skipped, exit unchanged); relayed child diags must have an `[EWIS]NNNN` code; child stderr is printed per line as `keel: <clean line>`. Files passed to `keel` must match `.keel/sessions/<fp>-<n>.json` with the record's fingerprint; `read` refuses paths outside the cwd.
- D11: `MAX_ISSUES_PER_RUN` 20 creates (updates and comments uncapped); the rest are a `deferred` count in the `summary`, no new code. Issue list past 50 pages is E1056. Workflow: `concurrency: sessions-nightly` (no cancel), `timeout-minutes: 30`, a `gate` step reading the secret through step env (job `if` cannot read `secrets`), `persist-credentials: false`.
- D12: output flags `--format`, `--quiet`, `--limit` parsed by the bin (unknown flag E1052); rendering is local (`actionText`), since k.cli's formatter registry has no exported renderer; `... +N more <what> (keel-session-action --limit <n>)`; relayed diags keep `fix`; a fingerprint with no issue change prints nothing (summary counts only). 0248 stays open; the README documents the title prefix as the lookup key.
